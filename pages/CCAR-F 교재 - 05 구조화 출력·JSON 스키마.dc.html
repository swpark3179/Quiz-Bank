구조화 출력과 JSON 스키마

Tool Use 강제 · 스키마 description · 검증+리트라이 · 멀티패스 리뷰

원문 · koding.kr — 제6장  |  출제 도메인: 도메인 4 (20%)

⓪ 시험 개요① 환경② 모델③ API④ 프롬프트⑤ 구조화 출력⑥ Tool Use⑦ MCP⑧ 이후 장⑨ 자가진단

실무에서는 Claude의 출력을 프로그램이 다룰 수 있는 형식으로 받아야 한다. 자유 텍스트가 '손 편지'라면 구조화 출력은 '빈칸을 채우는 신청서'다. 도메인 4의 후반부는 어떻게 안정적인 JSON을 얻는가, 검증·리트라이를 어떻게 설계하는가, 그리고 중요 출력의 품질을 어떻게 끌어올리는가를 묻는다.

습득 포인트
  • 구조화 출력의 3가지 접근과 신뢰성 차이 — Tool Use 기반이 가장 견고
  • JSON 스키마 작성과 description = 필드 단위 지시
  • 검증 + 리트라이 루프(에러 피드백 · 상한 · HITL 에스컬레이션)
  • 자주 나는 실패 패턴과 대처, 멀티패스 리뷰(draft→review→refine)와 Best of N의 구분
01

세 가지 접근

Prompt · XML · Tool Use
접근예신뢰성구현 난이도
프롬프트 지시"JSON으로 출력해 주세요"중쉬움
XML 태그<result>…</result>로 감싸게 함중~높음쉬움
Tool Use 기반JSON 스키마로 툴을 정의하고 tool_choice로 호출을 강제높음중

툴 호출 기능을 'JSON 출력 강제 장치'로 전용하는 방식이다. Claude는 스키마에 맞춘 input을 담은 tool_use 블록을 반환하고, API가 파싱까지 끝내 돌려주므로 앱 쪽 파싱 에러도 줄어든다.

tools = [{ "name": "record_user_info", "description": "사용자 정보를 구조화해 기록한다", "input_schema": { "type": "object", "properties": { "name": {"type": "string", "description": "성명"}, "age": {"type": "integer", "description": "만 나이"}, "email": {"type": "string", "format": "email"}, }, "required": ["name", "age", "email"], }, }] response = client.messages.create( model=MODEL, max_tokens=1024, temperature=0, tools=tools, tool_choice={"type": "tool", "name": "record_user_info"}, # 이 툴을 반드시 호출 messages=[{"role": "user", "content": "저는 김민준, 35세, minjun@example.com입니다."}], ) data = next(b.input for b in response.content if b.type == "tool_use")
교재 최신 정보 노트

교재 집필 이후 Anthropic은 네이티브 구조화 출력(Structured Outputs)도 제공한다 — 스키마로 토큰 생성을 제약해 스키마 준수 JSON을 보장하는 방식(응답 형식 지정, strict 툴). 교재는 "주어진 선택지 안에서는 Tool Use + tool_choice 강제가 정답"이라는 시험 논리를 유지하되, 실무에서는 네이티브 기능도 함께 검토하라고 보완한다.

02

JSON 스키마 작성법

Schema as a data contract
요소쓰임
typestring · integer · number · boolean · object · array
enum허용 값을 고정 (예: ["pending", "approved", "rejected"])
minimum / maximum숫자 범위
items · minItems · maxItems배열 요소의 타입과 개수
중첩 object주소 등 하위 구조 — 각자 required를 가질 수 있다
required필수 필드 목록
additionalProperties: false정의되지 않은 필드 금지
formatemail · date-time 등 문자열 형식 힌트

description은 주석이 아니라 프롬프트다

BAD
"price": {"type": "number"}

단위는? 통화는? 세금 포함인가?

GOOD
"price": { "type": "number", "description": "판매가 · 부가세 포함 · 원(KRW)", "minimum": 0 }

단위·형식·언어·허용 범위를 구체적으로.

03

검증 + 리트라이 루프

Validate → feed back → retry
  1. Pydantic 모델로 스키마를 정의하고 model_json_schema()로 툴의 input_schema를 자동 생성
  2. temperature=0 + tool_choice 강제로 호출
  3. tool_use.input을 Pydantic으로 검증
  4. ValidationError가 나면 에러 내용을 다음 시도의 프롬프트에 담아 재시도 — 맹목적 재시도는 무의미
  5. 최대 시도 횟수를 둔다 (무한 루프 방지)
  6. 그래도 실패하면 스키마·description·프롬프트를 재검토하고, 시스템이 감당할 수 없는 건은 사람(HITL)에게 에스컬레이션
for attempt in range(MAX_ATTEMPTS): suffix = f"\n\n이전 출력의 검증 오류: {last_error}\n수정해서 다시 출력하세요." if last_error else "" resp = call_claude(text + suffix) # tool_choice로 record_user 강제 try: return UserInfo(**tool_input(resp)) # Pydantic 검증 except ValidationError as e: last_error = str(e) # 에러를 다음 시도에 피드백 escalate_to_human(text, last_error) # 상한 초과 → HITL
오해리트라이를 충분히 하면 언젠가는 성공한다.
사실스키마·프롬프트에 원인이 있으면 몇 번을 해도 실패한다. 실패율이 높으면 설계(스키마·description)를 고친다. 상한을 100회로 늘리거나 모델만 바꾸는 것은 근본 대책이 아니다.
04

스트리밍 × 구조화 출력시험 범위 밖

Display while streaming, parse after

스트리밍 중의 불완전한 JSON을 청크마다 파싱하지 않는다 — 거의 항상 실패하고 CPU만 낭비한다. 스트림은 화면 표시용으로만 쓰고, 구조화 데이터는 완료 후 최종 메시지의 tool_use 블록에서 꺼낸다.

06

멀티패스 리뷰

draft → review → refine

계약서 초안·중요 리포트처럼 출력 자체의 품질을 극대화해야 할 때는 한 번에 완벽을 노리지 않고 공정을 나눈다 — '초고 → 빨간 펜 → 정서'.

PASS 1
draft · 초안 생성
→
PASS 2
review · 다른 역할로 비평
예: "계약서를 검토하는 법무 담당"
→
PASS 3
refine · 지적을 반영해 정서

핵심은 생성 역할과 비평 역할의 분리다. 같은 모델이라도 역할·프롬프트를 바꾸면 '내가 쓴 것이 옳다'는 편향을 피하고 누락·모호한 조항·리스크를 잡아낸다.

관점1회 생성멀티패스
품질표준높음 (비평으로 누락 보정)
비용 · 지연낮음 (1회)높음 (최소 3회, 패스 수에 비례)
적합대량 · 경량 출력계약서 · 중요 리포트 등 중요 출력에만
멀티패스 리뷰

1개 안을 비평·수정하며 반복 개선한다 — 한 장의 초고에 빨간 펜.

Best of N

여러 안을 독립 생성한 뒤 그중 최선을 고른다 — 여러 장을 써 보고 하나 채택.

자가 점검 퀴즈

점수 0 / 8
Q1접근 선택
다음 중 Anthropic API에서 스키마를 지키는 JSON을 가장 안정적으로 얻는 방법은?
정답 (C)

Tool Use 기반 접근이 스키마 준수와 구조 보장 면에서 가장 신뢰성이 높고, API가 파싱까지 마쳐 돌려준다. 프롬프트 지시·XML은 신뢰성이 '중' 수준이고, 스트림 청크 파싱은 거의 항상 실패한다.

Q2tool_choice
extract_invoice 툴을 반드시 호출하게 하려는 지정으로 옳은 것은?
정답 (A)

특정 툴 강제는 {"type": "tool", "name": …} 형식이다. auto는 Claude가 판단(기본값), any는 어떤 툴이든 하나는 반드시 호출이다.

Q3리트라이
Claude의 출력이 Pydantic 검증에서 가끔 실패한다. 재시도 설계로 가장 효과적인 것은?
정답 (D)

무엇이 틀렸는지 알려 줘야 자기 수정이 가능하다. 상한이 없으면 무한 루프·비용 폭증 위험이 있다.

Q4신뢰성
에러 피드백 리트라이를 3회 해도 특정 유형의 문서에서 계속 스키마 위반이 난다. 다음 대응으로 가장 적절한 것은?
정답 (B)

반복 실패는 설계 쪽 문제일 가능성이 높다. '시스템이 감당할 수 없는 범위를 넘으면 사람에게 넘긴다'가 신뢰성 설계 원칙이다(도메인 5와 연결).

Q5enum
priority 필드의 enum ["low", "medium", "high"]가 가끔 '높음'처럼 한국어로 출력된다. 가장 효과적인 대책은?
정답 (C)

Claude는 description의 지시를 필드 단위로 존중한다. enum 번역 문제는 description으로 억제하는 것이 정석이다.

Q6멀티패스
투자 계약서 초안의 품질을 최대한 높이고 싶다. 비용은 2차 고려 사항이다. 가장 적절한 접근은?
정답 (A)

중요 출력은 생성과 비평을 별도 공정·역할로 나눠 반복하는 것이 품질을 가장 체계적으로 끌어올린다. 길이·다양성 조절은 품질 개선 수단이 아니다.

Q7Best of N
'Best of N'을 올바르게 설명한 것은?
정답 (D)

A는 멀티패스 리뷰의 설명이다. 둘 다 품질을 높이지만, 멀티패스는 '1개 안의 반복 개선', Best of N은 '복수 안의 독립 생성 후 선택'이다.

Q8스키마 설계
주문 스키마의 createdAt: {"type": "string"} 필드를 개선하는 가장 좋은 방법은?
정답 (B)

스키마는 데이터 계약이다. 형식·예시·필수 여부의 모호함을 남기지 않으면 Claude의 출력 품질과 검증이 함께 좋아진다.
