4.1 명시적 기준4.2 퓨샷4.3 구조화 출력4.4 검증·재시도4.5 배치 처리4.6 다중 리뷰

structured outputs를 켜면 JSON이 깨지는 문제는 사라지지만, 숫자가 맞지 않거나 값이 엉뚱한 칸에 들어가는 문제는 남는다. 이 서브도메인은 그 두 번째 종류의 오류를 앱이 검증하고, 구체적인 오류 내용을 되먹여 재시도하고, 재시도로는 고칠 수 없는 경우를 가려내는 설계를 다룬다. 재시도는 형식과 해석의 실수를 고칠 수 있지만, 원문에 없는 정보를 만들어 내지는 못한다.

습득 포인트
  • 스키마 문법 오류(제약 디코딩이 제거)와 의미 검증 오류(앱이 잡아야 함)를 구분한다
  • 재시도 요청에 원문 · 실패한 추출 결과 · 구체적인 검증 오류를 함께 넣어 자기 교정을 유도한다
  • 재시도가 통하는 경우(형식 불일치·구조 오류)와 통하지 않는 경우(정보 부재·제공되지 않은 외부 문서)를 판별한다
  • calculated_total과 stated_total을 따로 받고 conflict_detected로 원문 모순을 표시하는 자기 점검 필드를 설계한다
  • detected_pattern 필드로 개발자가 기각한 지적을 패턴별로 집계해 프롬프트를 개선한다
01

오류의 세 층

Syntax · semantics · absence

예시로 인테리어 시공 견적서에서 항목별 금액, 공급가액, 부가세, 총액, 착공일·완공일을 뽑는 파이프라인을 생각한다. 여기서 나는 오류는 세 층으로 나뉘고, 층마다 막는 주체와 처방이 다르다.

층예막는 주체재시도 효과
스키마(문법)닫히지 않은 괄호, 금액이 "1,200,000" 문자열, 필수 키 누락strict: true / output_config.format의 제약 디코딩문서는 스키마 위반에 대해서는 재시도가 필요 없다고 설명한다
의미항목 합 ≠ 공급가액, 착공일이 완공일보다 늦음, 부가세를 공급가액 칸에 기록앱의 검증 코드무엇이 틀렸는지 구체적으로 알려 주면 대개 고쳐진다
정보 부재완공일이 원문에 없음, "세부 내역은 별첨 참조"인데 별첨이 입력에 없음없음 — 원문에 답이 없다효과 없음. 오히려 지어낼 위험이 커진다

제약 디코딩에도 예외는 있다. stop_reason이 "max_tokens"면 출력이 잘렸을 수 있고, Sonnet 5.5 프롬프트 가이드는 이런 응답을 JSON이 유효해 보여도 실패로 보고 재시도하라고 권한다. 이것은 max_tokens를 늘리면 해결되는 구조적 실패다.

02

검증할 거리를 스키마에 심기

Self-check fields

의미 검증을 쉽게 하려면 모델이 "적힌 값"과 "직접 계산한 값"을 따로 쓰게 한다. 둘이 다르면 추출 실수인지, 견적서 작성자의 계산 실수(원문 자체의 모순)인지 가를 단서가 생긴다.

"line_items": [{"name": "string", "amount": "integer"}], "stated_subtotal": "integer", # 견적서에 적힌 공급가액 "calculated_subtotal": "integer", # line_items를 직접 더한 값 "conflict_detected": "boolean", # 원문 숫자끼리 서로 맞지 않으면 true "conflict_note": ["string", "null"], "start_date": ["string", "null"], "end_date": ["string", "null"]

앱은 모델이 쓴 calculated_subtotal도 그대로 믿지 않고 다시 계산한다. 모델의 계산값은 검증의 대상이지 정답이 아니다.

def validate(q): errs = [] s = sum(item["amount"] for item in q["line_items"]) if s != q["calculated_subtotal"]: errs.append(f"calculated_subtotal은 {q['calculated_subtotal']}인데 " f"line_items 합은 {s}다. 항목 금액을 원문에서 다시 확인하라.") if s != q["stated_subtotal"] and not q["conflict_detected"]: errs.append("원문 공급가액과 항목 합이 다른데 conflict_detected가 false다.") if q["start_date"] and q["end_date"] and q["start_date"] > q["end_date"]: errs.append("start_date가 end_date보다 늦다. 두 날짜가 뒤바뀌었는지 확인하라.") return errs
03

재시도 요청에 담을 것

Retry with error feedback
1 · 추출
원문 → 구조화 결과
→
2 · 검증
앱 코드가 오류 목록 생성
→
3 · 재요청
원문 + 직전 결과 + 구체적 오류
→
4 · 상한
N회 실패 시 사람 검토 큐

재요청에는 세 가지가 함께 들어가야 한다. 원문(다시 대조할 근거), 실패한 추출 결과(무엇을 고칠지), 구체적인 오류(어느 필드가 어떤 관계를 어겼는지). "다시 해 줘"만 보내면 같은 실수가 반복되기 쉽다. 추출을 도구 호출로 받았다면 직전 tool_use에 is_error: true인 tool_result로 오류를 돌려주는 방식이 자연스럽다. 문서는 도구 입력이 잘못됐을 때 Claude가 교정하며 2~3회 다시 시도한다고 설명한다.

messages = [ {"role": "user", "content": f"<document>{quote_text}</document>\n이 견적서를 record_quote로 기록하라."}, {"role": "assistant", "content": first.content}, # 실패한 tool_use 포함 {"role": "user", "content": [{ "type": "tool_result", "tool_use_id": tool_use.id, "is_error": True, "content": "검증 실패:\n" + "\n".join(errs) + "\n원문에서 해당 필드만 다시 확인해 record_quote를 다시 호출하라. " "원문에 없는 값은 null로 둔다."}]} ]
시험 가이드 표현 vs 현재 문서

시험 가이드는 "검증 오류를 붙여 재시도"를 직접 구현할 패턴으로 설명한다. 현재 문서에서 스키마 수준의 재시도는 플랫폼이 상당 부분 맡는다. API의 structured outputs는 스키마 위반 자체를 막고, Agent SDK에서 outputFormat/output_format을 쓰면 내부 StructuredOutput 도구가 스키마 불일치를 is_error로 돌려받아 다시 호출하며, 끝내 실패하면 결과 subtype이 error_max_structured_output_retries가 된다. 직접 짜는 재시도 루프는 스키마 밖의 의미 검증에 집중하면 된다.

04

재시도가 소용없는 경우 가려내기

Is the answer in the input?
재시도로 고쳐지는 것
  • 날짜를 2026.3.5처럼 써서 YYYY-MM-DD 규칙에 어긋남
  • 천 원 단위 표기를 원 단위로 바꾸지 않음
  • 공급가액과 부가세를 서로 뒤바꿔 기록
  • 항목 합계를 잘못 더함
  • max_tokens에 걸려 잘린 출력 (한도를 늘려 재요청)
재시도로 안 고쳐지는 것
  • 완공일이 견적서 어디에도 없음
  • "상세 공정은 별첨 공정표 참조"인데 공정표가 입력에 없음
  • 스캔 상태가 나빠 금액 칸이 판독 불가
  • 작성자가 원문에서 합계를 잘못 씀 (고칠 것은 추출이 아니라 원문)

오른쪽 경우에 "end_date는 필수다, 다시 채워라"를 반복하면 모델은 그럴듯한 날짜를 지어낼 압박만 받는다. 대신 값을 null로 두고 사유를 남긴다. 예를 들어 missing_reason을 not_in_document · in_referenced_attachment · illegible 중 하나로 받는다. 그 뒤 처방은 사유에 따라 갈린다. 별첨을 확보해 다시 돌리거나, 사람 검토로 보내거나, 원문 모순이면 conflict_detected로 표시해 넘긴다. 공식 문서도 환각을 줄이는 첫 방법으로 모르면 모른다고 말할 수 있게 허용하라고 권한다.

재시도 전에 던질 질문
  • 정답이 입력 안에 있는가? 없으면 재시도가 아니라 입력을 보강하거나 사람에게 넘긴다
  • 오류 메시지가 필드와 관계를 짚는가? "틀렸다"가 아니라 "A는 x인데 B의 합은 y"
  • 재시도 상한이 있는가? 같은 오류가 반복되면 프롬프트·스키마 결함을 의심한다
05

피드백 루프: 기각 패턴에서 배우기

detected_pattern

추출만이 아니라 코드 리뷰 봇에도 같은 원리가 적용된다. 각 지적에 detected_pattern(어떤 코드 구조를 보고 지적했는지)을 붙여 두면, 개발자가 지적을 기각할 때 그 이유를 패턴 단위로 모을 수 있다. 패턴 이름이 없으면 기각 로그는 "봇이 시끄럽다"는 인상만 남긴다.

{"file": "api/orders.py", "line": 142, "severity": "medium", "detected_pattern": "broad-except", "issue": "except Exception이 결제 게이트웨이 타임아웃까지 삼킨다", "suggestion": "TimeoutError를 분리해 재시도 경로로 보낸다"}
한 달 집계 예시 (가상의 수치)
detected_pattern게시기각조치
broad-except12078로그 후 다시 raise하는 경우는 제외하도록 기준을 구체화
missing-null-check959유지
magic-number6455기준을 다시 쓸 때까지 일시 중지 (4.1과 연결)

생성과 평가를 나눠 돌리는 구조는 Anthropic이 evaluator-optimizer 워크플로로 설명하는 패턴과 같다. 한 호출이 결과를 만들고 다른 호출이 명확한 기준으로 평가해 피드백을 돌려준다. Managed Agents의 outcome 기능도 별도 컨텍스트의 grader가 루브릭으로 산출물을 채점해 에이전트에게 되돌리며, 루브릭은 "데이터가 좋아 보인다"가 아니라 채점 가능한 명시적 기준으로 쓰라고 권한다.

시험 함정 · 흔한 오해

오해structured outputs를 켰으니 검증 코드는 필요 없다.
사실제약 디코딩이 없애는 것은 문법·타입 오류다. 합계 불일치, 필드 뒤바뀜, 날짜 역전 같은 의미 오류는 앱이 잡아야 한다.
오해검증에 실패하면 같은 요청을 그대로 다시 보내면 된다.
사실원문 · 실패한 결과 · 구체적 오류를 함께 줘야 모델이 무엇을 고칠지 안다. 같은 입력은 같은 실수를 부르기 쉽다.
오해필수 정보가 비어 있으면 채워질 때까지 재시도한다.
사실원문에 없는 정보는 재시도로 생기지 않는다. null + 사유로 남기고 입력 보강이나 사람 검토로 넘긴다.
오해모델이 calculated_total을 써 주니 앱에서 다시 계산할 필요는 없다.
사실모델의 계산값도 검증 대상이다. 앱이 독립적으로 계산해 대조한다.
