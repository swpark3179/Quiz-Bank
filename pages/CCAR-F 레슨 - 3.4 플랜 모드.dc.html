Claude Code에 같은 요청을 해도, 먼저 코드를 조사하고 방향을 승인받은 뒤 고치게 할 수도 있고 바로 고치게 할 수도 있다. 시험은 작업 설명을 주고 "어느 쪽이 맞는가"를 묻는다. 판단 근거는 작업의 크기 자체보다 아직 정해지지 않은 결정이 있는가다. 플랜 모드는 "어떻게 바꿀지 정하는 단계"와 "실제로 바꾸는 단계"를 갈라 놓는 장치이므로, 정할 것이 남아 있는 작업에 쓰고 정할 것이 없는 작업에는 쓰지 않는다.

습득 포인트
  • 플랜 모드가 허용하는 것(읽기·탐색·계획 작성)과 승인 전까지 막는 것(소스 편집)
  • 플랜 모드가 맞는 신호: 대규모·다파일 변경, 유효한 접근이 여럿, 아키텍처 결정이 걸린 작업
  • 직접 실행이 맞는 신호: 범위와 완료 조건이 이미 분명한 작은 변경
  • Explore 서브에이전트로 장황한 탐색 출력을 메인 대화 밖에 두고 요약만 받기
  • 조사·설계는 플랜 모드로, 승인된 계획의 구현은 직접 실행으로 이어 붙이기
01

플랜 모드가 바꾸는 것

A permission mode, not a separate agent

플랜 모드는 별도 기능이 아니라 permission mode(권한 모드) 가운데 하나다. 권한 모드는 Claude가 묻지 않고 할 수 있는 행동의 범위를 정한다. 플랜 모드에서 Claude는 파일을 읽고, 탐색용 셸 명령을 돌리고, 계획을 작성하지만 소스 파일은 편집하지 않는다. 편집은 사용자가 계획을 승인할 때까지 막혀 있다(bypassPermissions를 쓸 수 있게 시작한 대화형 터미널 세션만 예외).

들어가는 방법설명
Shift+Tab세션 중 모드 순환. 상태 표시줄에 ⏸ plan mode on이 보이면 플랜 모드
/plan [설명]프롬프트 앞에 붙여 바로 플랜 모드로 시작 (예: /plan 결제 재시도 정책 정리)
claude --permission-mode plan세션을 처음부터 플랜 모드로 시작
permissions.defaultMode: "plan"프로젝트 .claude/settings.json에 두면 그 프로젝트 터미널 세션의 기본값

계획 단계에서 셸 명령이 어떻게 처리되는지는 세션 조건에 따라 다르다. auto mode를 쓸 수 있고 useAutoModeDuringPlan(기본 켜짐)이면 classifier(분류 모델)가 명령을 검토하고, 그렇지 않으면 내장 읽기 전용 명령 집합 밖의 명령은 승인을 요청한다. 파일 읽기는 어느 모드에서든 묻지 않고 실행되므로, 플랜 모드의 특징은 "읽기가 자유롭다"가 아니라 "편집이 승인 뒤로 미뤄진다"는 점이다.

1 · 조사
읽기·검색·탐색 명령
→
2 · 계획 제시
ExitPlanMode로 승인 요청
→
3 · 검토
Ctrl+G 편집 / 계속 계획
→
4 · 승인
편집 가능한 모드로 전환

계획이 준비되면 선택지가 나온다: Yes, and use auto mode(auto mode를 쓸 수 없는 세션에서는 Yes, auto-accept edits), Yes, manually approve edits(편집마다 검토), No, keep planning(계획 수정 지시). 승인하면 플랜 모드를 빠져나가 고른 모드로 바뀌고 편집이 시작된다. 승인 없이 나가려면 Shift+Tab을 다시 누른다. Ctrl+G로 계획을 텍스트 에디터에서 직접 고칠 수도 있다.

도구 이름으로 보면

Claude Code 도구 목록에는 플랜 모드로 들어가는 EnterPlanMode와 계획을 제시하고 승인을 요청하는 ExitPlanMode가 있다. 도구 표에서 ExitPlanMode는 "Permission required: Yes"로 분류돼 있다. 즉 Claude가 스스로 계획을 끝냈다고 판단해도 편집으로 넘어가는 문은 사용자가 연다.

02

작업 신호로 고르기

Open decisions vs settled scope

비용 관리 문서는 복잡한 작업에서 플랜 모드를 먼저 쓰라고 권한다. Claude가 코드베이스를 살펴보고 접근을 제안한 뒤 승인받으므로, 처음 방향이 틀렸을 때 생기는 값비싼 재작업을 막는다는 이유다. 반대로 서브에이전트 문서는 "빠르고 범위가 정해진 변경"은 메인 대화에서 바로 처리하는 경우로 든다. 아래는 이 가이드가 만든 예시로 정리한 판단표다.

작업 설명선택판단 신호
사내 로깅 래퍼를 OpenTelemetry SDK로 교체 — import하는 파일이 60여 개플랜 모드다파일 변경, 영향 범위를 먼저 세어 봐야 함
주문 서비스의 실패 재시도를 "메시지 큐 재처리"로 할지 "동기 재시도 + 백오프"로 할지 정해야 함플랜 모드유효한 접근이 둘 이상, 인프라 요구가 다름
모놀리스의 알림 기능을 별도 서비스로 분리플랜 모드아키텍처 결정, 경계·데이터 소유권 설계
스택 트레이스가 parseCoupon()의 빈 문자열 처리 누락을 정확히 가리킴직접 실행원인·위치·완료 조건이 이미 분명
회원가입 폼에 생년월일이 미래 날짜면 거부하는 검사 한 줄 추가직접 실행한 함수, 한 조건, 결정할 것 없음
시험 판단 축
  • 열린 결정이 있는가 — 접근이 여럿이거나 설계 선택이 남아 있으면 플랜 모드
  • 영향 범위를 지금 다 알고 있는가 — 모르면 먼저 조사해야 하므로 플랜 모드
  • 틀렸을 때 되돌리는 비용 — 수십 파일을 잘못된 방향으로 고친 뒤 되돌리는 비용이 크면 플랜 모드
  • 완료 조건을 지금 말할 수 있는가 — "이 테스트가 통과하면 끝"처럼 분명하면 직접 실행

"파일 수가 많다"는 강한 신호지만 그것만으로 결정하지는 않는다. 수십 파일이라도 같은 이름 바꾸기를 기계적으로 반복하는 일이면 결정할 것이 없다. 이런 대규모 기계적 변경에는 작업을 5~30개 단위로 쪼개 계획을 보여 준 뒤 단위별 worktree에서 실행하고 PR을 여는 /batch 같은 도구도 있다.

03

계획이 오버헤드가 되는 경우

When to just do it

범위가 분명한 작은 수정에 플랜 모드를 쓰면 계획 작성과 승인 대기라는 단계만 늘어난다. 이때 품질을 올리는 것은 계획이 아니라 구체적인 프롬프트다. best practices 문서는 파일을 지목하고, 증상을 설명하고, "고쳐졌다"가 어떤 상태인지 처음에 말해 두면 교정 한 바퀴를 아낄 수 있다고 설명한다.

BAD · 작은 수정에 의례적 계획
/plan 쿠폰 버그 고쳐 줘

원인 위치가 이미 스택 트레이스에 있다. 계획 문서와 승인 단계가 끼어들 뿐, 정할 것이 없다.

GOOD · 범위를 담은 직접 지시
src/coupon/parse.ts의 parseCoupon()이 빈 문자열에서 TypeError를 던진다(스택 트레이스 첨부). 빈 문자열이면 null을 돌려주도록 고치고, 그 경우를 재현하는 테스트를 먼저 추가한 뒤 테스트가 통과하는지 확인해 줘.

파일·증상·완료 조건이 다 들어 있다. 바로 실행해도 방향이 틀릴 여지가 적다.

직접 실행이 무방비 실행을 뜻하지는 않는다. 권한 모드(auto, Manual, acceptEdits)는 그대로 행동을 통제하고, Claude가 방향을 벗어나면 Esc로 멈추고 /rewind로 이전 체크포인트로 되돌릴 수 있다. 다만 체크포인트는 Claude가 파일 도구로 편집한 파일을 대상으로 하며, Bash 명령만 건드린 파일이나 원격 시스템의 변경은 되돌리지 못한다.

04

Explore 서브에이전트로 탐색 격리

Keep discovery noise out of the main thread

탐색 단계는 출력이 많다. 수백 줄의 검색 결과, 읽기만 하고 다시 보지 않을 파일 내용이 메인 대화에 쌓이면 이후 모든 턴이 그 내용을 다시 싣고 간다. Explore는 이런 탐색을 맡는 내장 서브에이전트다. 자기 컨텍스트 창에서 파일을 찾고 읽은 뒤 요약만 메인 대화로 돌려준다.

항목Explore (내장)
도구읽기 전용 도구. Write·Edit는 거부됨
탐색 깊이호출할 때 quick · medium · very thorough 중 하나를 지정
시작 컨텍스트빠르고 저렴하게 돌도록 CLAUDE.md와 git status 스냅샷 없이 시작 (하위 디렉터리 CLAUDE.md·경로 규칙은 해당 파일을 다룰 때 로드)
모델기본은 메인 대화의 모델. 같은 이름 Explore로 사용자·프로젝트 서브에이전트를 정의하면 내장을 덮어쓰고 그 정의의 model(예: haiku)을 쓴다
재개일회성. agent ID를 돌려주지 않아 이어서 작업시킬 수 없음 → 이어 가야 하면 general-purpose나 커스텀 서브에이전트

플랜 모드 안에서는 Plan이라는 내장 서브에이전트가 같은 역할을 한다. 계획에 필요한 조사를 별도 컨텍스트에서 수행해, 메인 대화는 읽기 전용 상태를 유지하면서 결과만 받는다. 직접 요청할 때는 "서브에이전트로 결제 모듈에서 RetryPolicy를 생성하는 모든 경로를 찾아 파일별 한 줄 요약만 보고해 줘"처럼 돌려받을 형태를 짧게 지정한다. 서브에이전트 여러 개가 각자 상세한 결과를 돌려주면 결국 메인 컨텍스트가 그만큼 찬다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 Explore를 "컨텍스트 창 고갈을 막기 위해" 쓴다고 표현한다. 2026년 10월 best practices 문서는 대부분의 현행 모델이 1M 토큰 창과 자동 compaction을 갖춰 "컨텍스트가 바닥나는 일은 드물다"고 보고, "컨텍스트 창을 지키려고 서브에이전트를 쓴다"를 이제 버려도 되는 옛 조언 표에 올려 두었다. 대신 서브에이전트의 가치는 장황한 출력을 메인 대화 밖에 두기, 병렬 작업, 독립 리뷰로 설명한다(각각 토큰 비용이 든다). 시험에서는 가이드 표현대로 "탐색 출력 격리 → 메인 컨텍스트 보존"을 고르면 되지만, 실무 근거는 "고갈 방지"보다 "집중과 비용"이다.

05

계획 후 구현: 두 단계 이어 붙이기

Plan the investigation, execute the plan

큰 작업이라고 처음부터 끝까지 플랜 모드에 머무는 것은 아니다. 플랜 모드는 조사와 설계까지이고, 승인된 계획의 구현은 편집 가능한 모드에서 진행한다. 예: 날짜 처리 라이브러리를 사내 표준 라이브러리로 옮기는 작업.

  1. 플랜 모드로 시작 — /plan 날짜 라이브러리 이전. Claude가 Plan/Explore 서브에이전트로 사용처, 타임존 처리 방식이 다른 호출, 테스트 커버리지를 조사한다
  2. 계획 검토 — 패키지별 이전 순서, 호환 어댑터를 둘지 여부, 위험 지점을 확인한다. 고칠 점이 있으면 No, keep planning이나 Ctrl+G
  3. 승인하며 실행 모드 선택 — 위험한 패키지부터라면 manually approve edits, 기계적인 나머지는 auto mode
  4. 계획을 기준으로 구현 — 플랜 모드에서 쓴 계획은 compaction 뒤에도 디스크에서 다시 주입되므로, 긴 세션에서 대화 이력이 요약돼도 기준이 남는다
  5. 검증 — 패키지마다 테스트를 돌리고 결과(명령과 출력)를 증거로 받는다
계획 컨텍스트 비우기

showClearContextOnPlanAccept 설정을 켜면 승인 선택지에 "계획을 승인하고 계획 단계 컨텍스트를 비우는" 항목이 맨 앞에 추가된다. 조사 과정의 잡다한 출력 없이 계획만 들고 구현을 시작하고 싶을 때 쓴다. 대형 코드베이스 문서도 여러 패키지에 걸친 변경은 플랜 모드로 먼저 계획을 파일로 남기라고 권한다.

시험 함정 · 흔한 오해

오해플랜 모드에서는 파일을 읽을 때마다 승인을 받아야 한다.
사실읽기는 어느 모드에서든 묻지 않고 실행된다. 플랜 모드가 막는 것은 승인 전 소스 편집이다.
오해계획을 다 쓰면 Claude가 알아서 편집 모드로 넘어간다.
사실계획 승인 프롬프트에서 사용자가 승인해야 모드가 바뀐다. 승인하지 않고 나가려면 Shift+Tab.
오해Explore 서브에이전트는 프로젝트 CLAUDE.md 규칙을 그대로 안다.
사실Explore와 Plan은 CLAUDE.md와 git status 없이 시작한다. 규칙을 지켜야 하는 작업이면 지시에 담거나 다른 서브에이전트를 쓴다.
오해큰 작업은 서브에이전트에 넘기면 더 좋은 답이 나온다.
사실기본적으로 같은(또는 더 작은) 모델이 같은 작업을 할 뿐이다. 얻는 것은 출력 격리·병렬성·새로운 시각이고, 그 대가로 토큰을 더 쓴다.
