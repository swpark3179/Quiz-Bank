모델 선택은 능력, 속도, 비용 사이의 절충이다. 이 절충은 티어를 바꿔서만 움직이는 것이 아니다. 같은 모델 안에서도 effort로 토큰 지출을, fast mode로 출력 속도를 조절할 수 있다. 그리고 모델을 바꾸는 순간 사고의 기본 동작이 달라져, 어떤 설정은 400 오류를 내고 어떤 변화는 오류 없이 코드를 깨뜨린다. 워크로드에 맞는 가장 작은 출발점을 고르고, 모델을 바꾸기 전에 effort부터 조정하며, 마이그레이션 때는 사고 설정과 응답 구조를 다시 확인하는 것이 이 레슨의 핵심이다.

습득 포인트
  • 현재 라인업 네 모델의 자리(능력, 지연, 가격, 기본 effort)를 알고 워크로드에 맞는 시작 모델을 고른다
  • 효율 우선과 성능 우선 접근의 단계를 순서대로 설명하고, 판단 근거가 평가임을 안다
  • 비용·속도 문제에서 effort, fast mode, 모델 교체 가운데 먼저 쓸 레버를 고른다
  • 모델별 thinking 설정(필드 없음, adaptive, enabled, between_tools, disabled)의 결과를 예측한다
  • 마이그레이션에서 400으로 드러나는 변경과 오류 없이 동작을 바꾸는 변경을 구분하고 고친다
01

현재 라인업과 티어의 자리

The current Claude lineup

현재 모델은 모두 텍스트·이미지 입력, 텍스트 출력, 다국어, 비전, 도구 사용을 지원한다. 그래서 "도구를 불러야 한다", "이미지를 읽어야 한다"는 요구는 모델을 가르지 못한다. 실제로 갈리는 것은 품질, 속도, 토큰당 가격이다.

모델자리지연가격 (입력/출력, MTok당)사고기본 effort
Claude Fable 5.1까다로운 추론, 장기 에이전트 작업느림$10 / $50적응형 (항상 켜짐)high
Claude Opus 5.5장시간 에이전트 코딩, 지식 업무보통$4 / $20적응형 (항상 켜짐)medium
Claude Sonnet 5.5속도와 지능의 최적 조합빠름$2 / $10적응형high
Claude Haiku 5.5분류·추출·라우팅 같은 대량·저지연 작업가장 빠름$0.10 / $0.50부터 (프롬프트 100k 토큰 초과 시 $0.50 / $2.50)적응형medium

네 모델 모두 1M 토큰 컨텍스트와 최대 128k 출력이다. 레거시로 계속 쓸 수 있는 모델은 Fable 5, Opus 5, Opus 4.8·4.7·4.6·4.5, Sonnet 5, Sonnet 4.6, Haiku 4.5(200k 컨텍스트, 확장 사고만, effort 미지원)다. 모델 ID는 날짜 접미사가 없는 것도 모두 고정 스냅샷이다.

CertSafari와 다른 점

CertSafari 레슨은 가장 작은 티어를 Claude Haiku 4.5로 소개하고, 그 표에 맞춰 체크포인트도 Haiku 4.5를 정답으로 둔다. 현재 공식 라인업의 최소 티어는 Claude Haiku 5.5이고 Haiku 4.5는 레거시다. 또한 CertSafari 체크포인트 일부는 표에 없는 모델(Opus 4.8, Sonnet 5 등)을 정답으로 쓴다. 이 가이드와 문제는 공식 라인업을 기준으로 하고, 레거시 모델은 이름을 밝혀 쓴다.

02

시작 모델을 고르는 두 방법

Efficiency-first vs capability-first

공식 가이드는 출발점을 정하는 두 접근을 제시한다. 어느 쪽이든 결정은 평가로 내린다. 사용 사례에 맞는 벤치마크를 만들고, 실제 프롬프트와 데이터로 정확도·응답 품질·엣지 케이스 처리를 모델별로 비교한 뒤 성능과 비용을 저울질한다.

효율 우선 (efficiency-first)

① Claude Haiku 5.5로 구현 시작 → ② 사용 사례를 철저히 테스트 → ③ 성능이 요구사항을 충족하는지 평가 → ④ 특정 능력 격차가 있을 때만 업그레이드.

맞는 경우: 프로토타입, 엄격한 지연 요구, 비용 민감, 단순한 대량 작업.

성능 우선 (capability-first)

① Claude Opus 5.5로 구현 → ② 이 모델에 맞게 프롬프트 최적화 → ③ 요구사항 충족 여부 평가 → ④ effort를 낮추거나 모델을 내려 효율 개선 → ⑤ xhigh·max에서도 모자라면 Claude Fable 5.1.

맞는 경우: 복잡한 추론, 과학·수학, 정확도가 비용보다 중요한 작업, 고급 코딩과 높은 자율성.

필요한 것시작 후보예
가장 높은 능력Claude Fable 5.1몇 시간씩 도는 에이전트 세션, 다단계 심층 리서치
복잡한 에이전트 코딩, 엔터프라이즈 업무Claude Opus 5.5여러 시간짜리 자율 코딩 에이전트, 대규모 리팩터링, 컴퓨터 사용
일상적인 코딩·에이전트 작업의 속도와 능력Claude Sonnet 5.5코드 생성, 데이터 분석, 콘텐츠 작성, 에이전트 도구 사용
가장 낮은 지연과 가격Claude Haiku 5.5실시간 애플리케이션, 대량 처리, 서브에이전트 작업
기본 출발점

공식 문서는 "확실하지 않다면 대부분의 워크로드는 Claude Opus 5.5에서 시작하라"고 적는다. 효율 우선은 지연·비용·규모가 분명한 제약일 때 고르는 선택지다. 시험에서 "실시간, 대량, 빠듯한 예산, 단순 분류" 같은 신호가 보이면 효율 우선, 즉 Haiku 5.5에서 시작한다.

한 모델만 고를 필요도 없다. 공식 가이드는 저비용 모델과 최상위 모델을 짝지어 대부분의 토큰이 낮은 단가로 과금되게 하는 다중 모델 전략을 소개한다. 흔한 형태는 두 가지다.

패턴구조
실행자 + 조언자저비용 모델이 일을 진행하다가 어려운 결정만 상위 모델에 올려 묻는다
오케스트레이터 + 작업자상위 모델이 계획과 종합을 맡고, 대량의 반복 작업은 저비용 모델 작업자에게 나눠 준다
03

모델을 바꾸기 전에 effort부터

Tune effort before switching tiers

공식 가이드는 effort를 "한 모델 안에서 지능과 지연·비용을 맞바꾸는 레버"로 소개하며, effort 조정이 모델 교체보다 나은 레버인 경우가 많다고 말한다. 모델을 바꾸면 프롬프트 재조정, 품질 회귀, 응답 구조 변화를 다시 검증해야 하지만, effort는 요청마다 값 하나만 바꾸면 된다.

상황먼저 쓸 레버
품질은 충분한데 비용이 크다같은 모델에서 effort를 낮추고 평가 재실행. 그래도 크면 더 작은 모델
품질이 모자란다effort를 올린다. xhigh·max로도 모자라면 상위 모델
긴 출력이 너무 늦게 끝난다 (모델 유지)fast mode (지원 Opus 모델, 비용 증가 감수)
응답 시작이 늦고 예산이 빠듯하다작은 모델 + 낮은 effort (fast mode는 TTFT 개선용이 아니다)

effort 값은 output_config.effort에 low·medium·high·xhigh·max 중 하나로 넣는다. adaptive는 사고 모드이지 effort 값이 아니다. 기본값이 모델마다 다르다는 점이 특히 중요하다. Opus 5.5의 기본값은 medium이라, effort를 생략한 요청은 Opus 5(기본 high)보다 한 단계 낮게 실행된다. 그래서 Opus 5.5로 옮길 때는 effort를 명시하고, 이전 설정을 옮기지 말고 자체 평가로 effort 스윕을 하라고 권한다.

# 장시간 자율 리팩터링 에이전트 (Opus 5.5) client.messages.create( model="claude-opus-5-5", max_tokens=64000, # xhigh·max에서는 64k부터 조정 output_config={"effort": "xhigh"}, # 스윕으로 확인한 수준 messages=history, # temperature·top_p·top_k는 넣지 않는다 )
CertSafari와 다른 점

CertSafari는 여러 시간짜리 자율 리팩터링 에이전트의 정답을 'Claude Opus 4.8 + xhigh'로 둔다. Opus 4.7·4.8에 대해 "코딩·에이전트는 xhigh로 시작"이라는 공식 지침은 실제로 있다. 다만 현재 모델 선택 매트릭스는 이런 작업에 Claude Opus 5.5를 권하고, Opus 5.5는 정해진 시작 수준 대신 effort 스윕을 권한다.

04

fast mode의 자리

Where fast mode fits

fast mode(speed: "fast")는 같은 모델을 더 빠른 추론 구성으로 돌려 초당 출력 토큰을 최대 약 2.5배 높인다. 능력은 그대로이고 가격은 프리미엄이다(Opus 5.5 기준 $8 / $40, 표준의 두 배). 이득은 출력 속도에 있지 첫 토큰까지의 시간에 있지 않다.

레버바뀌는 것비용맞는 문제
effort 낮추기쓰는 토큰 양 (사고·텍스트·도구 호출 모두)감소품질 여유가 있는데 비싸다
fast mode출력 속도 (같은 토큰을 더 빨리)증가모델을 바꾸지 않고 긴 출력을 빨리 끝내야 한다
더 작은 모델능력, 지연, 단가 전부감소단순 작업, 대량, 엄격한 지연
fast mode 판별 기준
  • 지원 모델: Claude Opus 5.5(정식, 베타 헤더 불필요), Claude Opus 5·Opus 4.8(연구 프리뷰, fast-mode-2026-02-01 헤더). Sonnet·Haiku에 요청하면 오류
  • Batch API와 Priority Tier에서는 쓸 수 없다. 별도의 속도 제한이 있고, 적용 여부는 usage.speed로 확인한다
  • "비용이 문제"인 문항에서 fast mode는 거의 항상 오답이다. 더 비싸기 때문이다
05

모델별 thinking 설정 표

Thinking behavior, model by model

같은 요청이라도 모델에 따라 사고가 켜지기도, 꺼지기도, 400으로 거부되기도 한다. 공식 사고 문서의 표에서 시험에 나오는 모델만 추리면 다음과 같다. "high 이하"는 effort가 low·medium·high일 때만 받고 xhigh·max에서는 400이라는 뜻이다.

Sonnet 5.5의 between_tools는 사전(up-front) 사고만 끈다. 도구 호출 사이의 짧은 진행 상황 업데이트는 계속 사고 블록으로 돌아오고, 도구가 없으면 응답은 텍스트만 담는다. 이 설정은 다른 필드(display, budget_tokens 등)를 함께 받지 않는다.

보내기 전에 확인하기

Models API의 capabilities.thinking.types.disabled.supported와 capabilities.thinking.types.between_tools.supported로 모델이 각 값을 받는지 미리 알 수 있다. 예를 들어 Sonnet 5.5는 between_tools가 true, disabled가 false다. 다만 true여도 effort 조건 같은 다른 이유로 거부될 수 있다.

# GET /v1/models 응답에서 Sonnet 5.5 항목의 일부 (필드 경로 예시) "capabilities": { "thinking": { "types": { "between_tools": { "supported": true }, "disabled": { "supported": false } } } }

400으로 드러나는 변경

Request settings newer models reject

시끄러운 변경은 오히려 고치기 쉽다. 요청이 바로 400 invalid_request_error로 실패하고, 메시지가 대개 대안을 알려 준다.

07

오류 없이 코드를 깨는 변경

Silent behavior changes after a model switch

더 위험한 것은 200이 돌아오는데 동작이 달라지는 변경이다. 모델 ID 한 줄만 바꿨는데 화면이 비거나 비용이 뛰면 다음을 의심한다.

변화예와 대응
사고가 조용히 켜진다thinking 필드가 없는 요청이 Sonnet 4.6·Opus 4.8에서는 사고 없이 돌았지만, Sonnet 5.5·Opus 5.5에서는 적응형 사고로 돈다. 사고 토큰은 출력으로 과금되고 max_tokens에 포함되므로 상한과 비용을 다시 잡는다
응답이 thinking 블록으로 시작한다content[0].text나 "첫 content_block_start는 텍스트"라는 가정이 깨진다. 블록은 type으로 고른다
사고 텍스트가 비어 온다Claude 5 계열과 Opus 4.7·4.8의 display 기본값은 "omitted". 사고를 보여 주던 UI는 긴 멈춤처럼 보이므로 "summarized"를 명시한다
기본 effort가 바뀐다Opus 5.5는 medium(Opus 5는 high). effort를 생략한 요청은 한 단계 낮게 돈다
이전 사고 블록이 빠진다대화 중 모델을 바꾸면, 새 모델이 읽을 수 없는 사고 블록은 오류 없이, 과금 없이 제거된다. 요청은 200으로 성공한다
토큰 수와 캐시 최소 길이가 바뀐다Opus 4.7 이후 토크나이저는 약 30% 더 많은 토큰을 만든다. 캐시 최소 길이도 달라진다(Opus 4.8은 1,024, Opus 5.5·Sonnet 5.5는 512)
위치로 읽는 핸들러

reply = response.content[0].text. Opus 5.5에서는 첫 블록이 빈 thinking 블록이라 JavaScript에서는 undefined, 화면에는 빈 답이 뜬다. stop_reason은 end_turn이라 로그상 정상이다.

유형으로 읽는 핸들러

type == "text"인 블록만 모아 텍스트를 만든다. 도구 사용 루프에서는 사고 블록을 걸러 내지 말고 assistant 메시지를 받은 그대로 돌려보낸다(빈 사고 블록 포함).

// 비스트리밍: 텍스트 블록만 모은다 const reply = response.content .filter((b) => b.type === "text") .map((b) => b.text) .join(""); // 스트리밍: 블록 유형으로 분기한다 if (event.type === "content_block_start") { kind[event.index] = event.content_block.type; // "thinking", "text" ... } if (event.type === "content_block_delta" && kind[event.index] === "text") { render(event.delta.text); }
마이그레이션 점검 순서
  • 요청: 거부되는 설정(budget_tokens, disabled, 샘플링 파라미터, 강제 tool_choice, prefill)을 걷어 내고 effort를 명시한다
  • 응답: 블록을 type으로 읽고, 스트림 핸들러도 블록 유형으로 분기하며, max_tokens를 사고까지 담게 늘린다
  • 비용·지연: 선택한 effort에서 비용과 지연을 다시 측정하고, 토큰 카운트도 새 모델 ID로 다시 잰다

시험 함정 · 흔한 오해

오해도구 호출이 필요한 작업이라 작은 모델은 쓸 수 없다.
사실현재 모델은 모두 도구 사용과 비전을 지원한다. 기능 요구가 아니라 품질·속도·가격으로 고른다.
오해비용이 너무 크면 먼저 더 싼 모델로 바꾼다.
사실품질에 여유가 있다면 같은 모델에서 effort부터 낮춘다. 공식 가이드는 effort 조정이 모델 교체보다 나은 레버인 경우가 많다고 말한다.
오해fast mode는 가벼운 모델로 바꿔 빠르고 싸게 만든다.
사실같은 모델에 더 빠른 추론 구성이다. 출력 속도만 오르고 가격은 프리미엄이다.
오해Sonnet 5.5에서 between_tools는 어떤 effort에서도 쓸 수 있다.
사실low·medium·high에서만 받고 xhigh·max에서는 400이다.
오해대화 중 모델을 바꾸면 이전 사고 블록 때문에 오류가 난다.
사실새 모델이 읽을 수 없는 블록은 오류 없이 제거되고 과금되지 않는다. 요청은 200으로 성공한다.
오해모델 ID만 바꾸면 응답 구조는 그대로다.
사실기본 사고 동작이 바뀌면 응답이 thinking 블록으로 시작한다. 위치로 읽는 코드는 오류 없이 빈 답을 낸다.
