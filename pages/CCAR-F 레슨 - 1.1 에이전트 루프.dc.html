에이전트 루프와 stop_reason 제어

stop_reason 분기 · tool_use / tool_result · 대화 이력 누적 · 모델 주도 결정 · 종료 안티패턴

에이전트의 뼈대는 단순하다. 도구를 쓸 수 있는 모델을 루프 안에서 돌리고, 매 바퀴 도구 실행 결과라는 '환경의 피드백'을 다시 넣어 준다. 그래서 시험은 거창한 아키텍처보다 이 루프의 기본기를 집요하게 묻는다. 언제 계속하고 언제 멈추는지, 결과를 어떤 모양으로 돌려주는지, 다음 행동을 누가 정하는지. 루프를 계속할지 멈출지는 응답 텍스트가 아니라 stop_reason 필드로 판단한다.

습득 포인트
  • 요청 → stop_reason 확인 → 도구 실행 → tool_result 반환 → 재요청으로 이어지는 한 바퀴를 직접 구현한다
  • "tool_use"면 계속하고, 그 밖의 값("end_turn" 등)이면 루프를 빠져나와 값별로 처리한다
  • 도구 결과를 정해진 형식(user 메시지, tool_result 먼저, tool_use_id 짝 맞춤)으로 이력에 붙여 다음 추론의 재료로 만든다
  • 모델 주도 결정(model-driven)과 미리 짜 둔 결정 트리·도구 순서의 차이를 구분한다
  • 종료 안티패턴 세 가지(자연어 신호 파싱, 반복 상한을 주 종료 장치로 사용, 텍스트 유무로 완료 판단)를 알아본다
01

한 바퀴의 해부

Anatomy of one iteration

Claude는 도구를 직접 실행하지 않는다. 응답에 '이 도구를 이 인자로 불러 달라'는 구조화된 요청(tool_use 블록)을 담아 보낼 뿐이고, 실행은 애플리케이션이 맡는다. web_search 같은 서버 실행 도구는 예외지만, 직접 정의한 클라이언트 도구를 쓰는 한 루프를 돌리는 주체는 내 코드다.

① REQUEST
messages + tools 전송
→
② RESPONSE
stop_reason 확인
→
③ EXECUTE
앱이 tool_use 실행
→
④ RETURN
tool_result를 user 메시지로 → ①
단계내 코드가 할 일놓치기 쉬운 점
요청원래 메시지, 직전 assistant 응답, 도구 결과를 모두 담아 다시 보낸다이력 전체가 곧 에이전트의 작업 기억이다
판정stop_reason을 읽는다텍스트 블록과 tool_use 블록이 한 응답에 함께 올 수 있다
실행블록의 name·input으로 내 함수를 호출한다실패도 결과다 — is_error: true와 원인·대처를 담아 돌려준다
반환assistant 응답을 이력에 넣고, 이어서 tool_result를 담은 user 메시지를 붙인다결과와 호출은 순서가 아니라 tool_use_id로 짝이 맞는다
02

stop_reason으로 분기하기

Branch on the field, not the prose

공식 문서가 제시하는 정석은 "stop_reason이 "tool_use"인 동안 도구를 실행하고 대화를 이어 간다"이다. 다른 값이 오면 루프를 빠져나오되, 값마다 뜻이 달라 후처리도 다르다.

값의미루프에서의 처리
tool_use클라이언트 도구 호출 요청실행 → 결과 반환 → 계속
end_turn응답이 자연스럽게 끝남최종 답으로 쓰고 종료
max_tokensmax_tokens 한도에서 잘림잘린 응답으로 취급. 마지막 블록이 미완성 tool_use면 한도를 올려 다시 요청
stop_sequence지정한 정지 시퀀스를 출력어떤 시퀀스였는지 확인하고 처리
pause_turn서버 도구 루프가 반복 한도(기본 10회)에 도달받은 응답을 이력에 그대로 붙여 다시 보내 이어 가게 한다
refusal응답을 거절stop_details를 확인하고 필요하면 대체 모델 등으로 폴백
model_context_window_exceeded모델 컨텍스트 창이 가득 참잘린 응답으로 취급

회의실 예약 에이전트의 최소 루프다. 분기 근거는 stop_reason뿐이다.

def run_agent(client, user_text, tools, handlers): messages = [{"role": "user", "content": user_text}] while True: resp = client.messages.create(model=MODEL, max_tokens=4096, tools=tools, messages=messages) messages.append({"role": "assistant", "content": resp.content}) if resp.stop_reason == "tool_use": results = [run_one(b, handlers) for b in resp.content if b.type == "tool_use"] messages.append({"role": "user", "content": results}) continue # 결과를 들고 다음 바퀴로 if resp.stop_reason == "pause_turn": continue # 서버 도구 진행 중 — 붙여 둔 응답째 재전송 return resp # end_turn·max_tokens·refusal 등은 호출한 쪽에서 값별 처리 def run_one(block, handlers): try: out = handlers[block.name](**block.input) return {"type": "tool_result", "tool_use_id": block.id, "content": json.dumps(out, ensure_ascii=False)} except Exception as e: # 실패도 결과로 돌려준다 return {"type": "tool_result", "tool_use_id": block.id, "is_error": True, "content": f"{type(e).__name__}: {e}"}
시험 가이드 표현 vs 현재 문서

시험 가이드는 분기를 "tool_use면 계속, end_turn이면 종료"의 두 갈래로 설명한다. 현재 문서는 위 표처럼 일곱 가지 값을 정의하고, tool_use가 아니면 루프를 빠져나오되 값마다 다르게 처리하라고 안내한다. 시험에서는 두 갈래를 기본으로 답하되, max_tokens·refusal 같은 값을 '정상 완료'로 간주하는 보기는 오답으로 본다.

03

결과를 이력에 붙이는 규칙

Tool results become context

결과를 돌려주는 목적은 Claude가 새 정보를 근거로 다음 행동을 추론하게 하는 것이다. 그래서 결과는 따로 요약하거나 시스템 프롬프트에 끼우지 않고, 직전 tool_use에 대응하는 tool_result 자리에 넣는다.

  • 직전 assistant 응답은 content 전체를 그대로 이력에 넣고, 바로 다음 user 메시지에 tool_result를 담는다. 사이에 다른 메시지를 끼울 수 없다.
  • 한 응답에 tool_use가 여럿이면 결과도 전부 하나의 user 메시지에 모은다. 실행하지 않기로 한 호출에도 is_error: true와 짧은 이유를 담은 결과를 돌려준다.
  • tool_result 블록은 content 배열의 맨 앞에 와야 한다. 텍스트는 그 뒤에만 둘 수 있다.
BAD · 결과를 메시지마다 쪼갬
{"role": "assistant", "content": [tu_room, tu_cal]} {"role": "user", "content": [res_room]} {"role": "user", "content": [res_cal]}

이력이 '한 번에 하나씩'을 가르쳐 이후 병렬 호출이 줄어든다.

GOOD · 한 메시지에 모음
{"role": "assistant", "content": [tu_room, tu_cal]} {"role": "user", "content": [res_room, res_cal]}

각 결과의 tool_use_id가 해당 호출의 id와 같으면 순서는 상관없다.

작지만 자주 나는 문제

결과 뒤에 습관처럼 "다음엔 뭘 할까요?" 같은 텍스트를 덧붙이면, Claude가 '도구 결과 뒤에는 사용자 입력이 온다'는 패턴을 따라 내용 없는 end_turn 응답을 내는 원인이 될 수 있다. 또 웹 페이지·메일처럼 외부에서 온 내용은 신뢰할 수 없으므로 시스템 프롬프트나 일반 텍스트가 아니라 tool_result 안에 둔다.

04

모델 주도 결정 vs 미리 짠 순서

Model-driven vs scripted

Anthropic은 에이전트형 시스템을 둘로 나눈다. 워크플로(workflow)는 LLM과 도구가 미리 정의된 코드 경로를 따라 움직이고, 에이전트(agent)는 LLM이 스스로 다음 단계와 도구 사용을 정한다. 1.1의 에이전트 루프는 후자다. 매 바퀴 Claude가 쌓인 결과를 보고 다음 도구를 고른다.

미리 짠 결정 트리

코드가 "예약 조회 → 대체 회의실 검색 → 알림 발송"을 고정한다. 예측·테스트가 쉽지만, 대체 회의실이 없는 것처럼 예상 경로를 벗어나면 막힌다.

모델 주도 루프

목표와 도구만 준다. 대체 회의실이 없으면 Claude가 시간대를 바꿔 다시 검색하거나 참석자 일정을 먼저 확인한다. 유연한 대신 비용·지연이 늘고 오류가 누적될 수 있어 가드레일이 필요하다.

시험 판단 축
  • 단계 수와 순서를 미리 알 수 있고 매번 같다 → 워크플로(코드로 순서 고정)가 더 예측 가능하다
  • 다음 행동이 중간 결과에 따라 달라지는 개방형 문제 → 에이전트 루프
  • 함정 보기: 에이전트 루프 안에서 "첫 바퀴엔 A 도구, 둘째 바퀴엔 B 도구"를 코드로 강제하는 설계는 모델 주도 결정의 장점을 버린다
  • 단, 반드시 지켜야 하는 순서(본인 확인 후 환불)는 모델 판단에 맡기지 않고 코드로 강제한다 → 1.4
05

종료 안티패턴과 안전장치

Stop on the signal, cap as a backstop
안티패턴왜 위험한가대신
응답 문구 파싱 ("완료", "Done"이 보이면 종료)표현은 언어·맥락마다 달라지고 "완료하려면 먼저…" 같은 문장에서 오탐이 난다stop_reason. 모델 출력에서 정규식으로 결정을 뽑고 있다면 그 결정은 도구 호출로 설계했어야 한다는 신호다
반복 상한을 주된 종료 장치로정상 작업이 상한에서 잘리면 미완성 결과가 완료처럼 나간다정상 종료는 end_turn. 상한에 걸리면 '미완료'로 처리
텍스트 블록 유무로 완료 판단tool_use 응답에도 "확인해 볼게요" 같은 텍스트가 함께 온다블록 종류가 아니라 stop_reason

안전장치 자체는 필요하다(Anthropic도 최대 반복 횟수 같은 정지 조건을 흔히 둔다고 설명한다). 요점은 우선순위다. 1차 종료 신호는 stop_reason, 반복 상한과 예산은 폭주를 막는 2차 방어선이다.

06

루프를 대신 돌려 주는 도구

Tool Runner and the Agent SDK
방식루프를 누가 돌리나종료와 상한
직접 구현 (Messages API)내 코드 (사람 승인·맞춤 로깅·조건부 실행이 필요할 때)stop_reason 분기 + 직접 둔 상한
Tool Runner (SDK, 베타)SDK가 도구 실행·결과 포맷·대화 상태를 관리tool_use가 없는 메시지가 오면 끝나고, max_iterations를 주면 그 횟수에서 멈춘다. 도구 예외는 is_error: true 결과로 Claude에게 전달된다
Claude Agent SDKClaude Code와 같은 루프. 내장 도구(Read·Bash 등)까지 SDK가 실행도구 호출 없는 응답이 나오면 끝나고 ResultMessage를 낸다. max_turns·max_budget_usd에 걸리면 subtype이 error_max_turns·error_max_budget_usd이고 result 필드가 없다
Agent SDK 턴 세기

max_turns는 '도구를 부른 턴 + 마지막 텍스트 응답 1턴'으로 센다. 도구를 세 번 부르고 답하는 작업에 max_turns=3을 주면 최종 답 없이 error_max_turns로 끝난다. 결과를 읽기 전에 subtype부터 확인한다.

시험 함정 · 흔한 오해

오해응답에 텍스트가 있으면 그게 최종 답이다.
사실tool_use 응답에도 텍스트가 함께 올 수 있다. 계속할지는 stop_reason으로만 판단한다.
오해반복 상한만 걸어 두면 종료 조건으로 충분하다.
사실상한은 안전망이다. 상한 도달은 정상 완료가 아니라 미완료로 다뤄야 한다.
오해end_turn이 아닌 값은 모두 오류다.
사실pause_turn은 응답을 붙여 다시 보내면 이어지고, max_tokens는 한도를 올려 재요청하는 식으로 값마다 처리가 다르다. HTTP 오류와 stop_reason은 별개다.
오해병렬 호출 결과는 도착하는 대로 각각 user 메시지로 보내면 된다.
사실한 user 메시지에 모두 담고 tool_use_id로 짝을 맞춘다. 나눠 보내면 이후 병렬 호출이 줄어든다.
