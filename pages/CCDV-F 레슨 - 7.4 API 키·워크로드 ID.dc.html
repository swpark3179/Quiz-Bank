7.1 프롬프트 인젝션 방어7.2 가드레일·안전한 배포7.3 Claude Code 훅7.4 API 키·워크로드 ID

API 키는 '비밀 문자열' 이전에 누구로서 행동하는 자격 증명인가의 문제다. 개인 키는 사람으로, 서비스 계정 키는 워크로드로, 레거시 워크스페이스 키는 워크스페이스 자체로 행동한다. 그래서 사람이 조직을 떠날 때 어떤 키가 멈추는지, 어떤 요청이 400·401·403·404를 받는지가 키 유형과 범위에서 바로 나온다. 레슨 후반은 정적 키를 아예 없애는 워크로드 ID 페더레이션(WIF)이다. 시험은 세 자원(서비스 계정·발급자·규칙)의 역할, 토큰 교환 때의 워크스페이스 선택, 그리고 SDK가 여러 자격 증명 중 무엇을 먼저 쓰는가를 묻는다.

습득 포인트
  • 개인·서비스 계정·레거시 워크스페이스·Admin API 키가 누구로서 행동하고 언제 멈추는지 구분한다
  • 워크스페이스 헤더 누락(400), 만료·폐기된 키(401), 범위 밖 요청(403), 접근할 수 없는 워크스페이스(404)를 구분한다
  • 만료는 생성 시 고정된다는 점, 비활성화·삭제·만료 상태의 차이, 교체 절차의 순서를 설명한다
  • 유출이 의심될 때와 공개 GitHub에 노출되었을 때의 대응, 사용량 감시 수단을 안다
  • 서비스 계정·페더레이션 발급자·페더레이션 규칙의 역할과 규칙 매칭 의미(접두어·AND)를 설명한다
  • SDK 자격 증명 우선순위에서 남은 API 키·없는 프로필·빈 변수가 일으키는 문제를 진단한다
01

키 유형: 그 키는 누구로서 행동하나

Key types and whose identity a key carries
키 유형행동 주체쓸 수 있는 곳멈추는 때
개인 키나(사용자)의 역할과 권한워크스페이스 하나, 또는 내 역할이 API 사용을 허용하는 워크스페이스들(생성 시 선택)내가 조직 접근을 잃을 때. 조직에서 제거되면 보관(archived) 처리되고, 다시 초대되어도 복원되지 않는다
서비스 계정 키서비스 계정워크스페이스 하나, 또는 서비스 계정이 접근할 수 있는 곳 전체서비스 계정이 보관될 때. 키를 만든 사람이 떠나도 계속 동작한다
워크스페이스 키 (레거시)아무도 아님. 만든 워크스페이스에 속한다그 워크스페이스만료·비활성화·삭제, 또는 워크스페이스 보관. 만든 사람이 떠나도 계속 동작한다
Admin API 키조직 관리 (sk-ant-admin…)Admin API (x-api-key 헤더)admin 역할 구성원만 발급할 수 있다

개인 키와 서비스 계정 키는 신원 기반(identity-backed)이라, 그 신원이 조직에서 사라지면 키도 멈춘다. 키가 주인보다 오래 살아남지 않게 하려는 설계이므로 새 통합에는 이쪽을 쓴다. 공유되거나 무인으로 도는 워크로드(CI, 운영 서비스)에는 조직 관리자가 서비스 계정을 만들어 고유한 신원을 준다. 개인 키를 공유하면 한 사람으로 행동하고, 그 사람이 떠나면 깨진다.

02

오류 코드로 읽는 인증과 권한

400, 401, 403, 404
응답이 레슨에서의 원인대응
400 invalid_request_error워크스페이스 범위가 없는 키가 anthropic-workspace-id 헤더를 빠뜨림, 또는 헤더 값이 올바른 ID 형식이 아님헤더를 추가하거나 워크스페이스 범위 키를 쓴다
401 authentication_error키가 형식이 틀렸거나, 폐기되었거나, 만료됨새 키를 만든다. 만료된 키는 되살릴 수 없다
403 permission_error자격 증명은 유효하지만 그 리소스에 대한 권한이 없음(예: WIF 토큰의 OAuth 범위 밖 엔드포인트)같은 종류의 키로 바꾸는 대신 역할·범위·워크스페이스 설정을 확인한다
404 not_found_error워크스페이스가 없거나, 키의 사용자·서비스 계정이 그 워크스페이스에 접근할 수 없음. 두 경우 응답이 같다ID가 맞다면 신원의 워크스페이스 멤버십을 확인한다
왜 '권한 없음'이 404인가

존재하지만 접근할 수 없는 워크스페이스에 403을 주면, 그 ID가 실제로 있다는 사실이 새어 나간다. 그래서 API는 모르는 워크스페이스와 똑같이 Workspace `<id>` not found.를 돌려준다. WIF 토큰 교환의 401이 늘 똑같은 Authentication failed인 것도 같은 이유(규칙 구성 탐색 방지)다.

03

워크스페이스 선택

Workspace-scoped keys and the workspace header

특정 워크스페이스로 범위를 정해 만든 키는 그 워크스페이스에서만 동작하고, 요청에 워크스페이스 ID를 쓰지 않아도 된다. 범위가 없는 키(여러 워크스페이스에 걸치는 키)는 요청마다 anthropic-workspace-id 헤더를 보내야 하고, 빠뜨리면 400이다. Admin API는 개인 키나 서비스 계정 키를 받기도 하지만, 워크스페이스 범위가 없는 키일 때만이다.

from anthropic import Anthropic # 범위 없는 키: 클라이언트 단위로 헤더를 한 번 고정해 두면 누락을 막는다 client = Anthropic(default_headers={ "anthropic-workspace-id": "wrkspc_01Hq7...", }) # 워크스페이스 범위 키라면 헤더 없이 Anthropic()만으로 충분하다
04

만료·순환·교체

Expiration is fixed at creation

Console에서 키를 만들 때 만료를 고른다. 프리셋(3시간·1일·7일·30일), 직접 지정한 기간, 또는 비밀 관리자에 보관하고 직접 순환할 키를 위한 Never다. 조직에 최대 만료 정책이 있으면 그 한도 안에서만 고를 수 있고 Never는 사라진다. 만료는 생성 시점에 정해지고 이후 바꿀 수 없다. 기간을 늘리고 싶다면 새 키를 만들어 교체하는 수밖에 없다.

만료가 다가오면 Anthropic이 키를 만든 사람에게 메일을 보낸다(수명 14일 이상 키는 7일 전, 7일 이상 키는 1일 전, 더 짧은 키는 경고 없음). 만료된 키로 보낸 요청은 401이고, 만료된 키는 재활성화할 수 없으며 삭제만 할 수 있다. 감사·순환 계획은 Admin API의 키 목록에서 expires_at을 확인해 세운다. 만료가 없는 키는 이 값이 null이다. Admin API는 키를 조회·이름 변경·상태 변경할 수 있지만 새 키를 만들 수는 없다.

curl "https://api.anthropic.com/v1/organizations/api_keys?status=active&limit=100" \ -H "x-api-key: $ANTHROPIC_ADMIN_KEY" \ -H "anthropic-version: 2023-06-01" \ | jq '.data[] | {name, expires_at}' # null = 만료 없음

레거시 워크스페이스 키를 신원 기반 키로 바꾸는 공식 절차는 다음 순서다. 옛 키를 지우는 것은 새 키로 요청이 성공하는 것을 확인한 뒤다.

① TYPE
키 유형 결정 (내 도구 = 개인, 공유·무인 = 서비스 계정)
→
② ACCOUNT
필요하면 서비스 계정 생성·워크스페이스 추가
→
③ CREATE
새 키 생성 (가능하면 그 워크스페이스 범위로)
→
④ DEPLOY
환경 변수·비밀 관리자 항목 교체 (범위 없는 키면 헤더도)
→
⑤ DELETE
요청 성공을 확인한 뒤 옛 키 삭제

유출 감지와 대응, 사용량 감시

Disable, delete, expire, auto-deactivate
상태·사건Admin API 상태되돌릴 수 있나 · 특징
비활성화 (Disable)inactive예. Re-enable로 active로 돌아온다
삭제 (Delete)archived아니요. 영구적이다. 목록에는 archived로 계속 보인다
만료(요청 시 401)아니요. 삭제만 가능하고, 접근을 되찾으려면 새 키를 만든다
공개 GitHub 저장소에서 발견자동 비활성화GitHub 비밀 스캔 파트너 프로그램이 Anthropic에 즉시 알리고, Anthropic이 키를 자동 비활성화한 뒤 사용자에게 메일을 보낸다

유출이 의심되면 키를 즉시 폐기(Console의 Delete API key)하고 새 키를 만들어 비밀 관리자에 보관한다. 이후에도 의심스러운 활동이 보이면 지원팀에 연락한다. 피해를 줄이는 평소 장치는 용도·환경별 키 분리, Console의 Logs·Usage 정기 확인, 지출 한도와 워크스페이스 속도 제한, 저장소 비밀 스캔이다. 만료는 유출 키의 수명을 줄이지만 비밀 관리를 대신하지는 않는다.

06

접근 수준: 키 범위, OAuth 범위, 에이전트 도구 승인

Access levels

Admin API 키 목록의 각 항목에는 principal(개인 키면 사용자, 서비스 계정 키면 서비스 계정, 워크스페이스 키면 null)과 scope(워크스페이스 하나 또는 조직 전체)가 있어 누가 어디서 행동하는 키인지 감사할 수 있다. WIF로 발급한 토큰의 접근 수준은 규칙의 OAuth 범위가 정한다.

OAuth 범위허용하는 것
workspace:developer (기본)규칙 워크스페이스의 비관리용 API 전부(Messages, Models, Managed Agents, Files, Skills). 워크스페이스 API 키와 같은 수준
workspace:inference추론 엔드포인트만(Messages, Models, OpenAI 호환 채팅). Files·Skills 관리가 필요 없는 워크로드용
workspace:manage_tunnelsMCP 터널 API
org:adminAdmin API 전체. 대상 서비스 계정의 조직 역할이 admin이어야 한다

범위 밖 엔드포인트를 부르면 403이다. 규칙의 범위는 상한선이고, 실제 권한은 규칙 범위와 서비스 계정 역할의 교집합이다.

에이전트 쪽의 '접근 수준'은 별개다

Agent SDK의 allowed_tools는 나열한 도구를 자동 승인할 뿐 다른 도구를 막지 않는다. 목록에 없는 도구 호출은 권한 모드로 넘어가므로, allowed_tools=["Read"]와 permission_mode="bypassPermissions"를 함께 쓰면 Bash·Write·Edit까지 모두 승인된다. 특정 도구를 막으려면 disallowed_tools, 고정된 도구 표면이 필요하면 allowed_tools + dontAsk 모드를 쓴다.

07

워크로드 ID 페더레이션의 세 자원

Service accounts, federation issuers, federation rules

WIF에서 워크로드는 정적 키 대신 이미 신뢰하는 ID 제공자(IdP, 예: AWS IAM, Google Cloud, GitHub Actions, 쿠버네티스, Entra ID, Okta)가 발급한 서명된 JWT를 내민다. Anthropic은 Console에 구성한 신뢰 규칙으로 이를 검증하고, 조직의 서비스 계정에 묶인 단기 토큰을 돌려준다. 세 자원이 모여 "발급자 X가 서명했고, 클레임이 Y처럼 생긴 토큰은 서비스 계정 Z로 행동할 수 있다"를 표현한다.

서비스 계정 svac_…
조직 안의 이름 있는 비인간(non-human) 신원. 이메일·비밀번호·Console 로그인이 없다. 기본 워크스페이스에는 암묵적으로 속하고, 다른 워크스페이스에는 멤버로 추가해야 한다.
페더레이션 발급자 fdis_…
신뢰할 OIDC 제공자를 조직에 등록한다. 발급자 URL(JWT의 iss와 정확히 같아야 함)과 JWKS 출처(discovery·explicit_url·inline)를 가진다.
페더레이션 규칙 fdrl_…
발급자와 서비스 계정을 잇는다. 매칭 조건, 대상 서비스 계정, OAuth 범위, 토큰 수명(60~86400초, 기본 3600초)을 정한다.
규칙 매처의미
subject_prefixJWT sub와 정확히 일치. 끝에 *를 붙이면 접두어 일치(* 앞의 문자 그대로로 시작해야 함). 대소문자를 구분한다
audienceaud에 이 문자열이 정확히 들어 있어야 한다(배열이면 원소 하나가 정확히 일치)
claims최상위 클레임 이름 → 정확한 문자열 값
conditionCEL 식이 true여야 한다. 너무 넓게 쓰면 의도보다 넓은 접근을 준다

subject_prefix·claims·condition 중 하나 이상은 있어야 하고(audience만 있는 규칙은 거부), 채운 매처는 모두 통과(AND)해야 한다. 매처가 하나뿐이어도 된다. 접두어 비교는 문자열 그대로라서, system:serviceaccount:prod:* 규칙은 system:serviceaccount:staging:worker 토큰을 받지 않는다. 그리고 페더레이션은 IdP 구성만큼만 강하다. IdP 토큰을 찍어 낼 수 있는 장기 클라우드 자격 증명이 한 단계 앞에 있으면 정적 비밀이 그 자리로 옮겨 갈 뿐이다.

08

토큰 교환과 워크스페이스 선택

Exchanging a JWT for a short-lived token
① JWT

→
② EXCHANGE
SDK가 POST /v1/oauth/token(jwt-bearer 그랜트)으로 교환
→
③ USE
sk-ant-oat01-… 토큰을 요청마다 보내고 만료 전에 갱신
교환 요청 필드필수비고
assertion, grant_type예IdP가 발급한 JWT, 고정된 jwt-bearer 그랜트 타입
federation_rule_id, organization_id, service_account_id예규칙은 ID로 지정한다. 암묵적인 규칙 탐색은 없다
workspace_id조건부규칙이 둘 이상의 워크스페이스에 켜져 있으면 필수. 생략하면 규칙의 유일한 워크스페이스로 범위가 정해지고, 여러 개인데 생략하면 401(workspace_id_required)

발급된 토큰의 수명은 규칙의 token_lifetime_seconds와 제시한 JWT 남은 수명의 두 배 중 작은 값이고, 최소 60초다. jti 클레임이 있는 JWT는 한 번만 교환할 수 있다. 실패한 교환은 어떤 검사에서 떨어졌든 똑같은 401을 받으므로, 진단은 Console의 인증 기록(authentication history)에서 한다. 평가한 발급자·규칙, 확인한 클레임, 실패한 검증 단계(예: match_subject_prefix, jti_reused)가 남아 접근 감시 수단이 된다.

SDK는 어떤 자격 증명을 쓰나

Credential precedence
순서출처주의
1생성자 인자 (api_key=, auth_token=, credentials=)항상 나머지를 이긴다
2ANTHROPIC_API_KEY / ANTHROPIC_AUTH_TOKEN페더레이션을 통째로 가린다. 남아 있는 옛 키가 조용히 이긴다
3ANTHROPIC_PROFILE이름 붙인 프로필이 없으면 오류다. 다음 단계로 넘어가지 않는다
4페더레이션 환경 변수규칙 ID·조직 ID·서비스 계정 ID·ID 토큰(파일 또는 문자열)이 모두 있어야 켜진다. 워크스페이스 ID는 활성화 조건이 아니다
5활성 프로필active_config 파일, 없으면 default 프로필

운영에서는 같은 컨테이너 이미지를 쓰고 환경마다 변수만 주입하는 인자 없는 생성자(Anthropic())가 권장 패턴이다.

# 페더레이션 경로가 켜지는 네 가지 (+ 조건부 워크스페이스) export ANTHROPIC_FEDERATION_RULE_ID=fdrl_... export ANTHROPIC_ORGANIZATION_ID=00000000-0000-... export ANTHROPIC_SERVICE_ACCOUNT_ID=svac_... export ANTHROPIC_IDENTITY_TOKEN_FILE=/var/run/secrets/anthropic.com/token export ANTHROPIC_WORKSPACE_ID=wrkspc_... # 규칙이 여러 워크스페이스에 걸칠 때 필수 unset ANTHROPIC_API_KEY # 남아 있으면 2단계에서 이긴다 ant auth status # 어느 출처가 이겼는지 확인
자주 나는 사고

API 키에서 WIF로 옮기면서 CI 비밀에 ANTHROPIC_API_KEY를 남겨 두었다. 페더레이션 변수를 다 넣어도 SDK는 2단계의 옛 키로 인증하고, 그 키가 만료되거나 폐기되면 그때서야 터진다. 서비스 계정 ID 하나를 빠뜨려도 페더레이션은 켜지지 않고 "no credentials"가 난다. 빈 문자열로 둔 변수도 자기 순서 자리를 차지할 수 있다.

안전한 이전 순서

① 페더레이션을 병행 구성하고 규칙이 토큰과 맞는지 확인 → ② ant auth status로 어느 출처가 이기는지 확인(이 시점엔 아직 API 키) → ③ 워크로드가 도는 모든 곳에서 ANTHROPIC_API_KEY를 unset(빈 값이 아니라 제거) → ④ 페더레이션 토큰으로 동작하면 옛 키 삭제.

시험 함정 · 흔한 오해

오해사람을 조직에서 제거하면 그 사람이 만든 키는 모두 멈춘다.
사실개인 키만 보관 처리되어 멈춘다. 그 사람이 만든 레거시 워크스페이스 키와 서비스 계정 키는 계속 동작한다.
오해403이 나오면 키가 잘못된 것이니 같은 종류의 새 키로 바꾼다.
사실403은 인증은 되었지만 권한·범위가 부족하다는 뜻이다. 역할·범위·워크스페이스를 확인한다. 무효·만료 키는 401이다.
오해만료가 다가온 키는 Console에서 기간을 연장하면 된다.
사실만료는 생성 시 고정되고 바꿀 수 없다. 만료된 키도 되살릴 수 없다. 새 키를 만들어 교체한다.
오해키 삭제는 비활성화처럼 나중에 되돌릴 수 있다.
사실비활성화(inactive)만 되돌릴 수 있다. 삭제는 영구적이며 키는 archived로 남는다.
오해페더레이션 환경 변수를 설정하면 남아 있는 API 키보다 우선한다.
사실ANTHROPIC_API_KEY가 먼저 확인되어 페더레이션을 조용히 가린다. 이전할 때 반드시 unset한다.
오해ANTHROPIC_PROFILE에 적은 프로필이 없으면 SDK가 다음 자격 증명으로 넘어간다.
사실없는 이름 붙은 프로필은 오류다. 조용히 다른 자격 증명을 쓰지 않는다.
오해subject_prefix는 비슷한 주체도 너그럽게 받아 준다.
사실정확한 문자열 비교이고, 끝의 *만 접두어 일치로 바꾼다. 대소문자도 구분한다.
