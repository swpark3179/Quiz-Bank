5.1 LLM 기초·사고·effort5.2 REST·스트리밍5.3 모델 선택·사고 모드5.4 토큰 비용·캐싱

Claude 비용은 결국 "어떤 범주의 토큰을 몇 개, 어떤 단가로 썼나"의 합이다. 입력과 출력의 단가가 다르고, 배치·캐싱·데이터 레지던시·fast mode가 그 단가에 배수를 곱한다. 캐싱은 반복되는 접두사를 싸게 만들지만, 접두사가 한 글자라도 바뀌면 다시 비싸게 쓴다. 그래서 usage의 네 범주(캐시되지 않은 입력, 캐시 쓰기, 캐시 읽기, 출력)를 각자의 단가로 읽고, 바뀌지 않는 내용을 앞에 두어 접두사를 지키는 것이 비용 관리의 핵심이다. 시험은 단가 계산, 수정자 결합 규칙, 토큰 카운팅의 한계, usage 필드의 의미, 브레이크포인트·TTL·적중률 판단을 묻는다.

습득 포인트
  • 입력·출력 단가로 요청 비용을 계산하고, 도구 정의처럼 입력에 숨어 있는 토큰을 찾는다
  • 배치, 캐시, 데이터 레지던시, fast mode 배수가 어떻게 겹치고 무엇이 함께 쓰일 수 없는지 안다
  • count_tokens로 보내기 전에 입력 크기를 재고, 캐싱·토크나이저와 관련된 한계를 안다
  • usage의 input_tokens, cache_creation_input_tokens, cache_read_input_tokens를 정확히 해석한다
  • 브레이크포인트 위치, 무효화 규칙, 최소 길이, TTL과 사전 워밍을 이용해 캐시 적중률을 높인다
01

입력과 출력은 값이 다르다

Input and output token prices

가격은 100만 토큰(MTok)당으로 매긴다. 현재 라인업은 모두 출력 단가가 입력의 5배다. 사고 토큰도 출력으로 과금되므로, 긴 답변과 깊은 사고가 비용의 큰 몫을 차지하기 쉽다.

모델입력출력비고
Claude Fable 5.1$10$50
Claude Opus 5.5$4$20Opus 5와 Opus 4.5~4.8은 $5 / $25
Claude Sonnet 5.5$2$10Sonnet 4.6은 $3 / $15
Claude Haiku 5.5$0.10$0.50프롬프트 100k 토큰 초과 요청은 $0.50 / $2.50 (Haiku 4.5는 $1 / $5)
# Sonnet 5.5, 입력 30,000 / 출력 6,000 토큰 input = 30_000 / 1_000_000 * 2.00 # $0.06 output = 6_000 / 1_000_000 * 10.00 # $0.06 (토큰은 1/5, 단가는 5배) total = input + output # $0.12

입력에는 눈에 덜 띄는 토큰도 들어간다. tools 파라미터의 이름·설명·스키마, 요청과 응답의 tool_use·tool_result 블록, 그리고 도구를 쓸 때 API가 자동으로 넣는 도구 사용 시스템 프롬프트(예: Opus 5.5는 tool_choice가 auto·none일 때 286토큰)가 모두 입력 토큰으로 과금된다. 웹 검색처럼 서버 도구는 사용량 요금(1,000회당 $10)이 따로 붙는다.

결합 규칙
  • 캐시 배수는 Batch 할인, 데이터 레지던시와 겹쳐 적용된다. 예: Opus 5.5 배치 + US 추론의 캐시 읽기 = $4 × 0.05 × 0.5 × 1.1 = $0.11/MTok

03

보내기 전에 세기: count_tokens

Counting tokens before you send

POST /v1/messages/count_tokens는 메시지 생성과 같은 구조의 입력(system, messages, tools, 이미지, PDF)을 받아 input_tokens 하나만 돌려준다. 생성을 하지 않으므로 출력 토큰은 알 수 없다. 사용은 무료이고, 메시지 생성과 별개의 분당 요청 수 제한을 쓴다.

count = client.messages.count_tokens( model="claude-opus-5-5", # 이 모델의 토크나이저로 센다 system=SYSTEM_PROMPT, tools=TOOLS, messages=history, ) print(count.input_tokens) # 입력 토큰 수만
특성의미
추정치실제 생성 시 입력 토큰과 아주 조금 다를 수 있다
캐싱을 적용하지 않음cache_control을 넣을 수는 있지만 결과는 캐시와 무관한 전체 입력 크기다. 캐싱은 실제 생성에서만 일어난다
모델별 토크나이저Opus 4.7 이후·Claude 5 계열은 약 30% 더 많은 토큰. 모델을 옮길 때는 같은 요청을 두 모델 ID로 각각 세어 비교한다
사고 블록이전 턴의 사고 블록은 그것을 유지하는 모델에서만 입력으로 센다. 현재 assistant 턴의 사고는 센다

쓰임새는 세 가지다. 요청이 컨텍스트 윈도에 들어가는지 확인하고, 입력 비용을 미리 계산하고, 프롬프트 크기에 따라 모델을 고르는 라우팅 판단을 내린다.

04

usage 필드로 실제 지출 읽기

Usage fields and spend tracking

모든 응답의 usage가 그 요청이 실제로 쓴 토큰을 알려 준다. 캐싱을 쓰면 입력이 세 필드로 나뉜다는 점이 핵심이다.

필드의미
cache_read_input_tokens기존 캐시 항목에서 읽은 접두사 토큰
cache_creation_input_tokens이번 요청에서 브레이크포인트에 새로 쓴 토큰. cache_creation 객체가 5분·1시간 TTL별로 나눠 준다
input_tokens마지막 브레이크포인트 뒤의 캐시되지 않는 토큰. 전체 입력이 아니다
output_tokens사고를 포함한 출력. output_tokens_details.thinking_tokens는 그중 사고 몫(스트리밍은 마지막 message_delta에만)
speedfast mode 요청에서 실제 적용된 속도
total_input = cache_read_input_tokens \ + cache_creation_input_tokens \ + input_tokens # 예: 200,000 캐시 읽기 + 0 쓰기 + 50 → 전체 입력 200,050
캐시는 속도 제한에도 유리하다

대부분의 모델에서 입력 토큰 분당 제한(ITPM)에는 input_tokens와 cache_creation_input_tokens만 들어가고 cache_read_input_tokens는 들어가지 않는다. 캐시 적중률 80%면 같은 ITPM 한도로 훨씬 많은 전체 입력을 처리할 수 있다.

조직 단위 추적은 Claude Console의 Usage·Cost 페이지와 Admin API로 한다. 새 연동에는 Usage and Cost Analytics API를 권하며, 기존 Usage and Cost API(/v1/organizations/usage_report/messages, /v1/organizations/cost_report)도 계속 지원된다. 사용량은 모델, 워크스페이스, API 키, 서비스 티어, 데이터 레지던시(inference_geo), 속도(speed)로 묶어 볼 수 있다. 응답의 anthropic-ratelimit-* 헤더는 현재 속도 제한의 남은 양과 초기화 시각을 알려 준다.

05

캐시 적중의 조건: 똑같은 접두사

How a prompt prefix becomes a cache hit

캐시는 tools → system → messages 순서로 이어지는 접두사를 cache_control이 붙은 블록까지 통째로 해시한다. 적중하려면 그 구간이 텍스트와 이미지까지 100% 같아야 하고, 어느 단계가 바뀌면 그 단계와 뒤의 모든 단계가 무효화된다. 브레이크포인트는 요청당 최대 4개이며 브레이크포인트 자체에는 비용이 없다. 비용은 쓰기·읽기·캐시되지 않은 입력 토큰에서만 생긴다.

바뀌는 것도구시스템메시지비고
도구 정의 (이름·설명·파라미터)무효무효무효맨 앞이라 전부 다시 쓴다
웹 검색·인용 토글, speed유지무효무효시스템 프롬프트가 바뀐다
tool_choice, 이미지 추가·제거유지유지무효
thinking 설정, 최상위 effort모델별모델별무효기본값과 같은 값을 명시하는 것은 생략과 같다
새 턴을 뒤에 덧붙임유지유지기존 부분 유지정상적인 대화 패턴
그 밖의 규칙

가장 쉬운 시작은 요청 최상위에 cache_control 하나를 넣는 자동 캐싱으로, 대화가 길어지면 브레이크포인트를 알아서 옮긴다(4개 슬롯 중 하나를 쓴다). 캐시는 조직 단위로 분리되고, Claude API에서는 워크스페이스 단위로도 분리된다. 새 항목은 첫 응답이 시작된 뒤에야 쓸 수 있으므로, 같은 접두사로 병렬 요청을 보낼 때는 첫 응답이 시작된 다음에 보내야 적중한다.

06

브레이크포인트 위치와 최소 길이

Where to put cache_control breakpoints

원칙은 하나다. 요청 간에 그대로 유지되는 마지막 블록에 브레이크포인트를 두고, 요청마다 바뀌는 내용(타임스탬프, 사용자 입력, 요청 ID)은 그 뒤로 보낸다. 바뀌는 속도가 다른 층(도구, 고정 지시, 참고 문서, 대화)은 브레이크포인트를 나눠 두면 한 층이 바뀌어도 앞쪽 층은 계속 적중한다.

맨 앞의 타임스탬프

시스템 프롬프트 첫 줄이 Current time: 09:14이고 그 뒤 6,000토큰 고정 지시 끝에 브레이크포인트가 있다. 분이 바뀔 때마다 접두사 전체가 새 항목이 되어 쓰기 비용만 내고 적중률은 바닥이다. 자동 캐싱으로 바꿔도, TTL을 늘려도 해결되지 않는다.

안정 블록 뒤로

고정 지시 끝에 명시적 브레이크포인트를 두고, 시각 정보는 최근 user 턴에 넣는다. 접두사가 매번 같아 캐시를 읽고, 바뀌는 부분은 input_tokens로만 과금된다.

최소 캐시 길이모델
512토큰Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5, Opus 5, Fable 5
1,024토큰Opus 4.8, Sonnet 5, Sonnet 4.6
2,048토큰Opus 4.7
4,096토큰Opus 4.6, Opus 4.5, Haiku 4.5

최소 길이보다 짧은 접두사는 cache_control을 붙여도 오류 없이 캐싱 없이 처리된다. 캐시 쓰기와 읽기가 모두 0이면 가장 먼저 이것을 의심한다. 또 캐시 미스가 나면 시스템은 이전 쓰기를 찾아 최대 20개 블록까지만 거슬러 확인하므로, 대화가 길어져 브레이크포인트가 마지막 쓰기에서 20블록 이상 멀어질 것 같으면 중간에 브레이크포인트를 하나 더 둔다.

07

TTL 고르기와 캐시 데우기

5-minute vs 1-hour TTL, pre-warming

기본 TTL은 5분이고 적중할 때마다 무료로 갱신된다. "ttl": "1h"를 주면 1시간 동안 유지되지만 쓰기가 2배다. 문서 기준으로 5분 캐시는 읽기 1번, 1시간 캐시는 읽기 2번이면 본전이다. 한 요청에서 TTL을 섞을 때는 1시간 항목이 5분 항목보다 앞에 와야 한다.

트래픽 모양고를 TTL
몇 초~몇십 초 간격으로 이어지는 대화5분. 계속 갱신되므로 비싼 1시간 쓰기가 필요 없다
5분보다 긴 간격으로 몰려오는 요청1시간. 5분이면 매번 만료되어 1.25배로 다시 쓴다
생성·사고가 길어 다음 요청이 늦게 시작1시간. 수명은 요청 시작 시점부터 재므로 생성 시간만큼 창이 줄어든다

실시간 서비스는 max_tokens: 0 요청으로 캐시를 미리 데울 수 있다. 응답은 content: [], stop_reason: "max_tokens"이고 출력 토큰은 과금되지 않는다(새로 쓰면 캐시 쓰기 비용은 든다).

# 트래픽 전·주기적으로 (5분 TTL이면 5분 안쪽 간격) client.messages.create( model="claude-opus-5-5", max_tokens=0, # 출력 없이 접두사만 캐시 system=SYSTEM_BLOCKS, # 마지막 공유 블록에 cache_control output_config={"effort": "high"}, # 실제 요청과 같은 effort messages=[{"role": "user", "content": "warmup"}], )
사전 워밍의 조건

브레이크포인트는 자리표시 메시지가 아니라 실제 요청과 공유하는 마지막 블록에 둔다(자동 캐싱 대신 명시적 브레이크포인트). thinking 설정과 effort도 실제 요청과 같아야 한다. max_tokens: 0은 stream: true, 확장 사고, 구조화 출력, tool_choice tool·any, Message Batches와 함께 쓰면 거부된다. 토큰 카운팅 호출로는 캐시가 데워지지 않는다.

08

적중률 측정과 비용 모델

Measuring hit rate and blended cost

적중률은 전체 입력 가운데 캐시에서 읽은 비율로 본다. 비용 모델은 네 범주를 각자의 단가로 곱해야 청구서와 맞는다.

total_in = u.cache_read_input_tokens + \ u.cache_creation_input_tokens + u.input_tokens hit_rate = u.cache_read_input_tokens / total_in # Sonnet 5.5, 5분 TTL 기준 (MTok당 단가) cost = (u.input_tokens * 2.00 # 기본 입력 + u.cache_creation_input_tokens * 2.50 # 쓰기 1.25배 + u.cache_read_input_tokens * 0.10 # 읽기 0.05배 + u.output_tokens * 10.00 # 사고 포함 ) / 1_000_000
적중률이 낮을 때 확인할 것
  • 접두사 앞쪽에 요청마다 바뀌는 값(타임스탬프, ID, 사용자 이름)이 있는가
  • 도구 정의, thinking 설정, 최상위 effort, speed를 요청마다 바꾸고 있는가
  • 접두사가 모델의 최소 캐시 길이보다 짧은가 (쓰기·읽기 모두 0)
  • 요청 간격이 TTL보다 긴가, 생성이 길어 수명이 먼저 소진되는가
  • 같은 접두사로 첫 응답이 시작되기 전에 병렬 요청을 보내고 있는가
CertSafari와 다른 점

CertSafari 레슨의 캐시 가격표는 Claude Sonnet 5.5의 캐시 읽기를 0.1배($0.20/MTok)로 적는다. 현재 공식 가격표는 Opus 5.5와 Sonnet 5.5의 캐시 읽기를 0.05배로 정하고 있어, Sonnet 5.5는 $0.10/MTok다. 이 가이드와 문제의 계산은 공식 가격표를 따른다.

시험 함정 · 흔한 오해

오해input_tokens가 요청 전체의 입력 크기다.
사실마지막 브레이크포인트 뒤의 캐시되지 않은 부분일 뿐이다. 전체 입력은 캐시 읽기 + 캐시 쓰기 + input_tokens다.
오해캐시된 접두사가 있으면 count_tokens도 그만큼 적게 센다.
사실토큰 카운팅은 캐싱 로직을 쓰지 않는다. 캐시와 무관한 전체 입력 크기를 보고한다.
오해브레이크포인트를 많이 두면 그만큼 비용이 든다.
사실브레이크포인트 자체는 무료다. 비용은 캐시 쓰기, 캐시 읽기, 캐시되지 않은 입력 토큰에서만 생긴다.
오해캐시 수명은 응답이 끝난 시점부터 잰다.
사실캐시를 쓰거나 읽은 요청이 시작된 시점부터 잰다. 3분 걸린 응답이면 5분 캐시의 남은 창은 약 2분이다.
오해1시간 TTL이 언제나 더 싸다.
사실쓰기가 2배라 읽기 2번은 있어야 본전이다. 몇 초 간격으로 이어지는 대화는 5분 TTL이 더 싸다.
오해할인은 하나만 적용되고, fast mode는 어떤 수정자와도 함께 쓸 수 있다.
사실캐시·배치·데이터 레지던시 배수는 겹쳐 적용된다. fast mode는 캐싱·레지던시와는 되지만 Batch API와는 함께 쓸 수 없다.
