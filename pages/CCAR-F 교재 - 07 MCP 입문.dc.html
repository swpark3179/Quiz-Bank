MCP 입문

N×M → N+M · Tools/Resources/Prompts · Host–Client–Server · 트랜스포트 · 통지

원문 · koding.kr — 제8장  |  출제 도메인: 도메인 2 (18%)

⓪ 시험 개요① 환경② 모델③ API④ 프롬프트⑤ 구조화 출력⑥ Tool Use⑦ MCP⑧ 이후 장⑨ 자가진단

MCP(Model Context Protocol)는 LLM과 툴·데이터 소스를 잇는 오픈 표준 프로토콜이다. 회사마다 독자 단자를 만들던 시대에서 USB Type-C 같은 공통 규격으로 옮겨 가는 것과 같다. 한 번 만든 MCP 서버는 Claude Desktop · Claude Code · 다른 IDE/LLM에서 그대로 재사용된다. 도메인 2의 핵심 주제다.

습득 포인트
  • MCP의 목적 — 연동 조합을 N × M에서 N + M으로
  • Tools / Resources / Prompts의 차이와 구분 기준 (시험 최중요)
  • Host → Client → Server 구조와 트랜스포트(stdio · Streamable HTTP)
  • Claude Code에 서버 등록(스코프 · .mcp.json), 통지(notifications), 직접 Tool Use와의 구분
01

등장 배경

From N × M to N + M
MCP 이전

LLM 3종 × 툴 3종 = 9개의 전용 연동을 각각 구현·유지보수. 조합이 늘수록 폭발한다.

MCP 이후

각 LLM과 각 툴이 MCP 사양에만 맞추면 된다 → 3 + 3 = 6개의 표준 구현. 툴 제공자와 LLM 제공자가 느슨하게 결합된다.

  • 사양 공개: modelcontextprotocol.io — Anthropic이 제창했지만 다른 모델 제공자·IDE도 지원
  • 최대 가치는 "한 번 만들어 N번 재사용" — 벤더 종속(lock-in)을 피하는 효과도 따른다
02

3요소 — Tools · Resources · Prompts

The three primitives
Tools
모델이 제어
LLM이 골라 호출해 부수 효과를 일으키는 함수
예: create_issue, send_email, 파일 쓰기
비유: 의뢰할 수 있는 작업
Resources
앱이 제어
LLM이 읽어 들이는 참조 데이터 · URI로 공개
예: file://…, wiki://articles/123
비유: 열람할 수 있는 자료
Prompts
사용자가 제어
재사용 가능한 프롬프트 템플릿
예: code-review, bug-triage — 슬래시 커맨드로 호출
비유: 정형 업무 매뉴얼
관점ToolsResources
용도실행 · 갱신 (부수 효과)읽기 · 참조
호출 방식LLM이 판단해 부른다앱이 가져와 컨텍스트에 공급
파라미터임의의 input_schemaURI 기반 (템플릿 가능)
BAD · 읽기 전용을 Tool로
@mcp.tool() def read_file(path: str) -> str: return Path(path).read_text()
GOOD · 읽기는 Resource, 쓰기는 Tool
@mcp.resource("file://{path}") def file_resource(path: str) -> str: return Path(path).read_text() @mcp.tool() def write_file(path: str, content: str) -> None: Path(path).write_text(content)
구분의 판단 축 — "호출하면 외부 상태가 바뀌는가?"
  • 바뀐다(쓰기·발송·이체) → Tool · 바뀌지 않는다(조회·열람) → Resource · 정형 지시문 → Prompt
  • 경계 사례: 'URL의 웹 페이지 가져오기'는 본질이 읽기이므로 Resource가 기본. 다만 인증·외부 레이트 리밋처럼 호출 시점을 모델이 제어해야 할 이유가 있으면 Tool로 두는 선택지도 있다 (양쪽으로 공개하는 하이브리드도 가능)

04

최소 MCP 서버

FastMCP (Python SDK)
from mcp.server.fastmcp import FastMCP mcp = FastMCP("hello-server") @mcp.tool() def get_weather(city: str) -> str: """지정한 도시의 날씨를 반환한다.""" return f"{city}: 맑음, 22도" @mcp.resource("greeting://{name}") def greeting(name: str) -> str: """이름에 맞는 인사말을 반환한다.""" return f"안녕하세요, {name}님!" @mcp.prompt() def code_review(language: str, code: str) -> str: """코드 리뷰용 프롬프트 템플릿.""" return f"다음 {language} 코드를 리뷰하고 개선점 3가지를 짚어 주세요:\n\n{code}" if __name__ == "__main__": mcp.run() # 기본 트랜스포트: stdio

데코레이터와 타입 힌트·docstring에서 스키마와 설명이 자동으로 만들어진다.

05

Claude Code에 등록하기

claude mcp add · .mcp.json
claude mcp add hello-server --scope project -- python /path/to/hello_mcp_server.py claude mcp list # 등록 상태 확인 (세션 안에서는 /mcp)
스코프저장 위치공유 범위
local (기본)~/.claude.json의 해당 프로젝트 항목나만 · 이 프로젝트에서만
project리포지터리 루트의 .mcp.json팀 공유 (버전 관리에 포함)
user~/.claude.json나의 모든 프로젝트
{ "mcpServers": { "hello-server": { "command": "python", "args": ["/path/to/hello_mcp_server.py"], "env": { "API_KEY": "${MY_API_KEY}" } } } }
주의

최상위 키는 mcpServers다(없으면 로드되지 않는다). API 키 같은 비밀은 값에 직접 쓰지 말고 ${VAR}로 환경 변수를 참조한다 — 특히 저장소에 커밋되는 project 스코프에서 중요하다. -- 뒤에 서버 기동 명령과 인자를 쓴다.

통지 기능

Notifications
통지용도

플러그인처럼 툴이 동적으로 늘고 주는 구조에서 중요하다. 단, 모든 클라이언트가 통지를 처리한다는 보장은 없으므로 중요한 변경에는 재접속을 유도하는 설계도 함께 고려한다.

07

MCP vs 직접 Tool Use

When to choose which
관점직접 Tool UseMCP
표준화앱마다 독자 구현오픈 사양
재사용성그 앱 안에서만여러 LLM · IDE에서 재사용
트랜스포트—stdio / HTTP를 투명하게 추상화
Resources · Prompts없음3요소를 모두 제공
구성 복잡도단순표준 준수로 약간 복잡
선택 기준
  • 단일 앱 안의 단순한 함수 호출 → 직접 Tool Use
  • 여러 LLM · IDE에서 같은 툴을 재사용하고 싶다 → MCP
  • Claude Code / Claude Desktop에 외부 기능을 붙인다 → MCP

대표 유스케이스: 파일 시스템 · GitHub · Slack · Google Drive 연동, 사내 DB 검색(자체 서버). MCP는 추론 정확도나 통신 속도를 높여 주는 기술이 아니라, 통합과 재사용을 표준화하는 기술이다.

흔한 오해

오해MCP는 Claude 전용 프로토콜이다.
사실오픈 사양이며 다른 모델 제공자·IDE도 지원한다.
오해Tools와 Resources는 둘 다 데이터를 돌려주니 같은 것이다.
사실부수 효과(Tools) / 읽기(Resources)로 의도를 분리한다. 기준은 '호출하면 무언가 바뀌는가'.
오해MCP 서버는 항상 켜 둬야 하는 상주 서비스다.
사실stdio 서버는 클라이언트가 필요할 때 띄우고 내리는 자식 프로세스다.

자가 점검 퀴즈

점수 0 / 8
Q1목적
MCP가 제공하는 가장 큰 가치는?
정답 (C)

각 LLM과 툴이 MCP 사양에만 맞추면 되므로 조합 수가 크게 준다. 정확도나 속도를 높이는 기술이 아니며, 여러 언어의 SDK가 있다.

Q23요소
다음 중 MCP의 Tool로 공개해야 하는 것은?
정답 (D)

메시지 게시는 외부 상태를 바꾸는 부수 효과이므로 Tool이다. 나머지는 읽기 전용 참조 데이터라 Resource가 적절하다.

Q33요소
팀이 자주 쓰는 '장애 회고 작성' 지시문을 사용자가 슬래시 커맨드로 불러 쓰게 하고 싶다. 어떤 요소로 공개하는가?
정답 (A)

정형 프롬프트를 사용자가 직접 호출하게 하는 것이 Prompts의 역할이다. 제어 주체로 기억하면 쉽다: Tools=모델, Resources=앱, Prompts=사용자.

Q4아키텍처
MCP의 구조를 올바르게 나타낸 것은?
정답 (B)

Host(Claude Code 등) 안의 Client가 MCP 프로토콜로 Server와 통신하고, Server가 3요소를 공개한다.

Q5트랜스포트
사내 여러 팀이 네트워크 너머에서 함께 쓰는 원격 MCP 서버를 새로 만든다. 권장 트랜스포트는?
정답 (C)

stdio는 로컬 자식 프로세스용이다. 원격은 Streamable HTTP가 현행 표준이고, HTTP+SSE는 하위 호환용으로만 남았다. 원격 서버는 인증·인가 설계가 필수다.

Q6통지
MCP 서버가 플러그인을 로드해 툴이 새로 추가됐다. 클라이언트에 알리는 올바른 방법은?
정답 (D)

통지를 받은 클라이언트가 툴 목록을 다시 가져온다. 다만 통지 처리는 클라이언트마다 다를 수 있어, 중요한 변경에는 재접속 유도도 함께 고려한다.

Q7Claude Code 등록
팀 전원이 같은 MCP 서버 설정을 저장소로 공유하려 한다. 서버는 외부 서비스 API 키가 필요하다. 가장 적절한 구성은?
정답 (A)

project 스코프는 저장소 루트의 .mcp.json으로 팀과 공유된다. 비밀은 환경 변수 참조로 분리해야 커밋에 노출되지 않는다. 최상위 키는 mcpServers여야 로드된다.

Q8MCP vs Tool Use
사내 이슈 트래커 연동을 Claude Code와 다른 두 IDE의 AI 도우미에서 똑같이 쓰고 싶다. MCP를 택하는 가장 큰 이유는?
정답 (B)

'한 번 만들어 여러 곳에서 재사용'이 MCP의 본질이다. 비용이 없다는 점은 사실이어도 선택의 핵심 이유는 아니다.
