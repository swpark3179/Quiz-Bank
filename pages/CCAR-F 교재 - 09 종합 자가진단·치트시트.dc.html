제1~8장 범위를 섞은 20문항 종합 자가진단과 빠른 복습 치트시트다. 실제 시험처럼 시나리오를 읽고 4개 중 가장 적절한 것을 고른다. 장별 퀴즈와 겹치지 않는 새 시나리오로 구성했다.

진단 방법

먼저 해설을 보지 않고 20문항을 끝까지 푼다 → 점수 확인 → 틀린 문항의 태그(기초 · 도메인 4 · 도메인 2)를 보고 해당 장으로 돌아간다. 16문항(80%) 이상이면 공개 장 범위는 안정권으로 보고, ⑧ 로드맵의 다음 장으로 넘어간다.

종합 자가진단 20문항

점수 0 / 20
Q1기초 · 모델
법률 사무소가 판례 수백 건을 비교해 새 소송 전략의 논리적 허점을 찾는 에이전트를 만든다. 요청은 하루 수십 건이고, 답변 품질이 비용보다 훨씬 중요하다.기본 모델로 가장 적절한 것은?
정답 (B)

'요건을 충족하는 가장 저렴한 모델'에서 요건이 고난도 추론이다. 소량·고품질 요구라 Opus의 비용이 정당화된다. Batches는 모델을 고르지 않는다.

Q2기초 · 모델
새 모델 버전이 나왔을 때 프로덕션을 안전하게 운영하는 방식으로 가장 적절한 것은?
정답 (D)

고정은 재현성을, 정기 평가는 개선·수정 반영을 담보한다. 영구 고정은 개선을 놓치고, 최신 추종은 예기치 않은 동작 변화를 부른다.

Q3기초 · API
다음 요청 중 Anthropic Messages API가 거부하는 것은?
정답 (A)

Messages API에는 system role 메시지가 없다 — system은 최상위 필드다. 블록 리스트 content와 교대 배치 이력은 모두 정상 요청이다.

Q4기초 · API
사용자가 채팅 화면에서 긴 보고서 생성을 요청한다. 완성까지 20초가 걸려 사용자가 '멈췄다'고 느끼고 이탈한다.가장 적절한 개선은?
정답 (C)

사람이 화면 앞에서 기다리는 상황이므로 Batches(최대 24시간)는 부적합하다. 스트리밍은 총 시간을 줄이지 않지만 첫 글자가 바로 보여 체감 대기를 크게 줄인다. 무리한 max_tokens 축소는 출력 잘림을 부른다.

Q5기초 · 비용
사내 문서 1,000페이지를 대상으로 하루 1만 건의 다양한 질문에 답한다. 질문마다 참조하는 부분이 다르다.비용과 품질의 균형이 가장 좋은 설계는?
정답 (B)

필요한 정보만 필요한 만큼 넣는 것이 원칙이다. 전량 투입은 캐시를 써도 과잉이고 Lost in the Middle 위험이 있으며, 매번 요약은 품질이 불안정하다. RAG는 검색 Recall 평가가 품질의 관건이다.

Q6기초 · API
긴 답변의 끝이 문장 중간에서 끊겨 돌아왔다. 응답에서 가장 먼저 확인할 값은?
정답 (D)

stop_reason이 멈춘 이유를 알려 준다. max_tokens로 끝났다면 상한을 올리거나 이어받기 처리를 한다. usage.output_tokens가 max_tokens에 가까운지도 함께 본다.

Q7도메인 4 · 프롬프트
상품 문의 분류 프롬프트에 Few-shot 예시 4개를 넣었는데, 모두 '배송 문의'였다. 이후 환불 문의까지 배송으로 분류되는 일이 잦다.가장 직접적인 원인은?
정답 (A)

Few-shot은 개수보다 균형이 중요하다(3~5개면 대개 충분). 모든 카테고리의 전형 예와 경계 예를 고르게 넣는다.

Q8도메인 4 · 프롬프트
긴 계약서를 넣고 위험 조항을 찾게 하는 프롬프트다. 지시문과 계약서 본문이 섞여 Claude가 본문의 문장을 지시로 오해하는 일이 생긴다. 가장 효과적인 수정은?
정답 (C)

XML 태그는 지시와 데이터의 경계를 명확히 하는 Claude 권장 기법이다. 같은 원리가 프롬프트 인젝션 방어에도 쓰인다.

Q9도메인 4 · 프롬프트
고객 리뷰 한 줄에 대해 '긍정/부정' 라벨만 붙이는 대량 처리에 Extended Thinking을 켜 두었다.이 설정에 대한 평가로 옳은 것은?
정답 (B)

CoT/Extended Thinking은 다중 제약·복잡 추론에서 효과가 크고, 답이 바로 정해지는 단순 분류에는 토큰과 지연만 늘린다.

Q10도메인 4 · 프롬프트
팀원마다 "이렇게 바꿔 보니 좋아진 것 같다"며 프롬프트를 수정해, 무엇 때문에 좋아지고 나빠졌는지 아무도 모른다. 가장 먼저 도입할 것은?
정답 (D)

반복 세련의 핵심은 '관찰하고 개선하는' 재현 가능한 구조다. TDD식 기대 출력 정의와 실패 예 축적, 버전 관리가 있어야 개선/개악을 판정할 수 있다.

Q11도메인 4 · 구조화 출력
영수증 이미지에서 금액·날짜·가맹점을 뽑아 DB에 넣는다. 가끔 JSON 앞에 "다음은 추출 결과입니다:" 같은 문장이 붙어 파싱이 실패한다. 근본적인 해결책은?
정답 (C)

프롬프트 지시만으로 강제하면 앞뒤 잡텍스트가 생길 수 있다. Tool Use 기반이면 스키마에 맞춘 input을 API가 파싱해 돌려준다. 정규식 절단은 증상 완화일 뿐이다.

Q12도메인 4 · 구조화 출력
스키마의 amount 필드에 어떤 때는 원 단위, 어떤 때는 천 원 단위 값이 들어온다. 가장 효과적인 수정은?
정답 (A)

description은 Claude에게 주는 필드 단위 지시다. 단위·형식·범위를 구체적으로 쓰면 해석 흔들림이 사라진다.

Q13도메인 4 · 구조화 출력
하루 30만 건의 짧은 고객 메모를 태그로 분류하는 파이프라인에 draft→review→refine 3패스를 적용했더니 비용이 3배가 됐다.가장 적절한 판단은?
정답 (B)

멀티패스는 패스 수에 비례해 비용·지연이 늘어난다. '품질을 극대화할 중요 출력인가?'가 적용 기준이다. Best of N도 여러 안을 생성하므로 비용이 줄지 않는다.

Q14도메인 2 · Tool Use
에이전트 루프를 직접 구현했는데, 두 번째 요청에서 "tool_use 블록에 대응하는 tool_result가 없다"는 에러가 난다. 가장 가능성 높은 원인은?
정답 (D)

각 tool_use에는 같은 id를 가진 tool_result가 1:1로 대응해야 한다. 병렬 호출로 tool_use가 여러 개 왔다면 결과도 모두 돌려줘야 한다.

Q15도메인 2 · Tool Use
여행 에이전트가 '항공권 검색'과 '호텔 검색'(서로 독립)을 매번 순서대로 한 턴씩 호출해 응답이 느리다.가장 적절한 개선은?
정답 (A)

의존 관계가 없는 조회는 병렬 호출로 왕복 횟수를 줄인다. 병렬을 끄는 것은 순차 의존이 있을 때의 처방이다. none은 툴 호출 자체를 막는다.

Q16도메인 2 · Tool Use
에이전트가 같은 검색 툴을 결과도 없이 열 번 넘게 반복 호출하다 멈춘다. 가장 적절한 대응 조합은?
정답 (C)

반복 호출은 에러 처리 부족이나 모호한 description의 신호다. Claude가 상황을 이해하도록 구조적인 피드백을 주고, 루프 상한으로 종료를 보장한다.

Q17도메인 2 · MCP
사내 인사 시스템을 MCP로 연동한다. '직원 조직도 열람'과 '휴가 신청 제출'은 각각 어떻게 공개하는가?
정답 (B)

'호출하면 외부 상태가 바뀌는가'로 나눈다. 열람은 읽기(Resource), 신청 제출은 부수 효과(Tool)다.

Q18도메인 2 · MCP
개발자 PC에서만 쓰는 작은 MCP 서버를 Claude Code에 붙인다. 가장 일반적인 구성은?
정답 (D)

로컬 서버는 stdio가 가장 단순하고 일반적이다. 상시 가동이 필요 없고, 원격 공유가 필요할 때 Streamable HTTP를 쓴다.

Q19도메인 2 · MCP
MCP 3요소의 '제어 주체'를 올바르게 짝지은 것은?
정답 (A)

모델이 판단해 호출하는 Tools, 앱이 가져와 컨텍스트에 공급하는 Resources, 사용자가 슬래시 커맨드 등으로 직접 고르는 Prompts.

Q20도메인 2 · MCP vs Tool Use
사내 단일 웹앱 백엔드에서만, 환율 변환 함수 하나를 Claude가 호출하게 하고 싶다. 다른 클라이언트에서 재사용할 계획은 없다.가장 합리적인 선택은?
정답 (C)

단일 앱 안의 단순한 함수 호출이면 직접 Tool Use가 단순하고 충분하다. MCP는 여러 LLM·IDE에서 재사용하거나 Claude Code/Desktop에 붙일 때 가치가 커진다.

빠른 복습 치트시트

모델 선정

  • 원칙요건을 충족하는 가장 저렴한 모델
  • Haiku대량 · 단순 분류/추출 · 최저 비용
  • Sonnet일반 앱 · 균형
  • Opus복잡 추론 · 코딩 · 에이전트
  • 혼합라우팅 + 임곗값 · 폴백
  • ID프로덕션은 고정, 검증 환경에서 새 버전 평가

Messages API

  • 필수model · max_tokens · messages
  • system최상위 필드 (system role 없음)
  • temperature0~1 · 구조화/분류는 0
  • max_tokens출력 상한 · 생성분만 과금
  • content문자열 = 블록 리스트 (혼합 시 리스트)
  • 429지수 백오프 + jitter

stop_reason

  • end_turn정상 완료 → 최종 답변
  • tool_use툴 실행 → tool_result 반환
  • max_tokens잘림 → 이어받기 · 상한 조정
  • stop_sequence지정 문자열에서 중단

비용 최적화

  • 캐시정적 앞 · 동적 뒤 · cache_control · 기본 TTL 5분
  • Batches약 50% · 24시간 이내 · custom_id · 실시간/멀티턴 X
  • RAG필요한 청크만 · 전량 투입 X
  • 판단 축"사용자를 기다리게 하는가?"

프롬프트

  • 6요소역할 · 태스크 · 입력 · 예시 · 제약 · 출력 지정
  • XML경계 · 중첩 · 파싱 (JSON 보장 X)
  • Few-shot균형 + 전형 + 경계 · 3~5개
  • CoT다중 제약·복잡 추론에만
  • 인젝션태그로 데이터 분리 + 다층 방어
  • 반복 세련실패 예 반영 · TDD식 · interview

구조화 출력

  • 최선Tool Use + tool_choice 강제
  • description= 필드 단위 프롬프트 (단위·형식·범위)
  • 리트라이에러 피드백 + 상한 → 설계 재검토 → HITL
  • enum"그대로, 번역 금지" 명시
  • 멀티패스draft→review→refine · 중요 출력만
  • Best of N여러 안 독립 생성 → 선택

Tool Use

  • 분업Claude 판단 · 앱 실행
  • 결과tool_result는 user role · tool_use_id 1:1
  • 에러is_error: true + 원인·대처 (내부 정보 X)
  • 병렬독립 조회 O · 순차 의존이면 disable
  • tool_choiceauto · any · tool (+none)
  • 설계단일 책무 · 5~15개 · 과다 시 서브에이전트

MCP

  • 목적N × M → N + M · 재사용
  • Tools부수 효과 · 모델 제어
  • Resources읽기 · URI · 앱 제어
  • Prompts템플릿 · 사용자 제어 · 슬래시 커맨드
  • 트랜스포트로컬 stdio · 원격 Streamable HTTP
  • 스코프local · project(.mcp.json) · user · 비밀은 ${VAR}
