문서에서 값을 뽑아 DB나 다음 단계로 넘기는 파이프라인은 출력이 매번 같은 모양이어야 돌아간다. 프롬프트에 "JSON으로만 답하라"고 적는 것만으로는 괄호 누락·타입 불일치·필드 누락을 막지 못한다. 시험은 이 문제를 도구의 input_schema와 tool_choice로 푸는 방법, 그리고 스키마가 보장하는 범위의 경계를 묻는다. 스키마 강제는 출력의 '모양'을 보장할 뿐, 값이 맞는지는 보장하지 않는다.

습득 포인트
  • 원하는 결과 구조를 도구의 input_schema로 정의하고, 응답의 tool_use 블록 input에서 결과를 꺼낸다
  • tool_choice의 auto · any · tool · none 차이 — 문서 유형을 모를 때는 any, 특정 추출을 먼저 돌려야 할 때는 도구 지정
  • strict: true와 output_config.format이 보장하는 것(문법·타입·필수 키)과 보장하지 않는 것(값의 정확성)
  • 원문에 없을 수 있는 필드는 nullable/optional로, 범주는 enum + "other"·"unclear" + 상세 문자열로 설계
  • 스키마와 함께 형식 정규화 규칙을 프롬프트에 둔다
  • 최신 모델의 forced tool use 제한과 그 대안
01

추출 도구: 실행하지 않는 함수

The schema is the deliverable

구조화 출력용 도구는 무언가를 실행하려고 만드는 것이 아니다. 받고 싶은 결과 구조를 input_schema로 적어 두면, Claude가 그 도구를 "호출"하면서 채운 input 객체가 곧 추출 결과다. 앱은 이 도구를 실행하지 않고 tool_use 블록의 input만 꺼내 쓴다. 아래는 물류 회사가 선하증권(B/L) 스캔본에서 선적 정보를 뽑는 예다.

tools = [{ "name": "record_bill_of_lading", "description": "선하증권(B/L) 한 건의 선적 정보를 기록한다. 입력 문서가 B/L일 때만 쓴다.", "strict": True, # 도구 입력을 스키마에 맞게 강제 "input_schema": { "type": "object", "properties": { "bl_number": {"type": "string"}, "shipper": {"type": "string"}, "consignee": {"type": "string"}, "port_of_loading": {"type": "string"}, "port_of_discharge": {"type": "string"}, "onboard_date": {"type": ["string", "null"], "description": "YYYY-MM-DD. 문서에 없으면 null"} }, "required": ["bl_number", "shipper", "consignee", "port_of_loading", "port_of_discharge", "onboard_date"], "additionalProperties": False } }] resp = client.messages.create( model="claude-haiku-5-5", max_tokens=1024, tools=tools, tool_choice={"type": "tool", "name": "record_bill_of_lading"}, messages=[{"role": "user", "content": doc_text}]) block = next(b for b in resp.content if b.type == "tool_use") # stop_reason == "tool_use" record = block.input # dict — 그대로 검증·적재 단계로

tool_use 블록에는 id · name · input이 있다. 추출만 하고 끝내는 파이프라인이면 여기서 멈춘다. 같은 대화를 이어 가려면 그 id에 대응하는 tool_result를 user 메시지로 돌려줘야 한다.

02

보장의 수준: 무엇을 켜야 '보장'인가

Prompt · tool schema · strict · JSON outputs
방식강제되는 곳보장 범위
프롬프트로 "JSON으로 답하라"없음보장 없음. 문법 오류·필드 누락이 생기면 파싱 단계에서 처리해야 한다
도구 + input_schema (strict 없음)도구 입력대체로 스키마를 따르지만, 문서는 strict 없이는 "2"처럼 다른 타입이 오거나 필수 필드가 빠질 수 있다고 적는다
도구 + strict: true도구 입력grammar-constrained sampling으로 input이 스키마를 따르고 name도 항상 유효하다
output_config.format (type: "json_schema")응답 본문도구 없이 응답 text 블록 자체가 스키마에 맞는 JSON. 두 기능은 한 요청에서 함께 쓸 수 있다

제약 디코딩에도 남는 예외

  • stop_reason: "refusal" — 안전상 거절이 스키마보다 우선한다
  • stop_reason: "max_tokens" — 출력이 잘려 스키마를 채우지 못할 수 있다. max_tokens를 늘려 다시 요청한다
  • enum·const 문자열의 대소문자는 보장되지 않는다 → 대소문자를 무시하고 비교하고, 대소문자만 다른 enum 값은 만들지 않는다

스키마에 쓸 수 있는 것과 없는 것

객체에는 additionalProperties: false가 필요하고, minimum·maximum 같은 수치 제약과 minLength·maxLength는 지원되지 않으며(400 오류), 배열 minItems는 0과 1만 된다. 한 요청 안에서 strict 도구는 20개, optional 파라미터는 전체 합쳐 24개, union 타입(anyOf나 ["string", "null"]) 파라미터는 16개까지다. 스키마는 처음 쓸 때 문법(grammar) 컴파일로 지연이 생기고, 마지막 사용 후 24시간 캐시된다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 "도구 사용 + JSON 스키마"를 스키마 준수를 보장하는 가장 확실한 방법이라고 설명한다. 현재 문서에서 문법 수준의 보장은 strict: true(도구 입력)나 output_config.format(응답 본문)을 켤 때 생기는 제약 디코딩의 결과다. 스키마만 붙인 일반 도구 호출은 '대체로 따르는' 수준으로 설명된다. 문항이 가이드 표현대로 나오면 가이드 기준으로 답하되, 실무에서는 strict를 함께 켠다.

auto · any · tool · none
값동작구조화 출력에서의 쓰임
{"type": "auto"}
(도구가 있을 때 기본값)		도구를 부를지 Claude가 정한다. 텍스트로만 답할 수도 있다대화형 에이전트. 구조화 출력이 '반드시' 나오지는 않는다
{"type": "any"}제공된 도구 중 하나는 반드시 호출, 어느 것인지는 Claude가 고른다문서 유형을 미리 모르고 유형별 추출 도구가 여러 개일 때
{"type": "tool", "name": "…"}지정한 도구를 반드시 호출특정 추출이 다음 단계(보강·조회)보다 먼저 끝나야 할 때

B/L·상업송장·포장명세서 도구 3개 + any
→
2 · 선행 추출 고정

any나 tool을 쓰면 API가 assistant 턴을 미리 채워(prefill) 도구 호출부터 시작하게 만든다. 그래서 tool_use 앞에 자연어 설명이 붙지 않으며, 요청해도 마찬가지다. 강제 호출은 thinking도 건너뛰어 응답에 thinking 블록이 없다. 설명이나 사고가 필요하면 auto로 두고 user 메시지에 "record_… 도구로 답하라"고 지시한다. 또 tool_choice를 바꾸면 prompt caching에서 메시지 블록 캐시가 무효화된다(도구 정의와 system 캐시는 유지).

시험 가이드 표현 vs 현재 문서 — 모델별 지원

시험 가이드는 any와 강제 도구 지정을 어디서나 쓸 수 있는 것처럼 다룬다. 2026년 10월 문서 기준으로 Claude Opus 5.5 · Sonnet 5.5 · Fable 5.1 · Mythos 5.1은 any와 tool을 받으면 400 invalid_request_error를 돌려준다(토큰 카운팅 엔드포인트 포함). 수동 extended thinking(thinking: {type: "enabled"})을 켠 요청도 마찬가지로 오류가 난다. Claude Opus 5와 Haiku 5.5는 강제 호출을 받는다. 지원하지 않는 모델에서는 auto + strict: true로 도구 입력을 보장하고 어떤 도구를 쓸지는 프롬프트로 유도하거나, 응답 자체가 고정 JSON이어야 하면 output_config.format을 쓴다.

04

지어내지 않게 하는 스키마

Nullable fields · open enums

필수(required)이면서 null을 허용하지 않는 필드는, 원문에 그 정보가 없을 때 모델이 그럴듯한 값을 만들어 넣게 만든다. 스키마가 "반드시 채워라"고 요구하기 때문이다. Agent SDK 문서도 작업에 필요한 정보가 없을 수 있으면 해당 필드를 optional로 두라고 권한다.

방법출력 모양한도에 미치는 영향
required에서 뺀다 (optional)정보가 없으면 키 자체가 빠질 수 있다. 출력 순서는 required 필드가 먼저, optional이 나중optional 파라미터 24개 한도에 계산
required 유지 + ["string", "null"]키는 항상 있고 값이 null. 후처리 코드가 단순하다union 타입 16개 한도에 계산
BAD · 닫힌 enum + 필수
"incoterm": { "type": "string", "enum": ["FOB", "CIF", "EXW"] }

송장에 DAP가 적혀 있거나 조건이 아예 없어도 세 값 중 하나를 골라야 한다.

GOOD · 열린 enum + 상세 + 판단 보류
"incoterm": { "type": "string", "enum": ["FOB", "CIF", "EXW", "DAP", "DDP", "other", "unclear", "not_stated"] }, "incoterm_detail": {"type": ["string", "null"]}

목록 밖 조건은 other + 원문 표기, 읽혔지만 해석이 갈리면 unclear, 문서에 없으면 not_stated.

"없음"은 다른 문서를 찾으라는 신호이고, unclear는 사람이 원문을 보라는 신호다. 둘을 구분해야 후속 처리가 갈린다(4.4·5.5).

05

스키마가 통과시키는 오류와 정규화 규칙

Valid JSON, wrong values

아래는 모두 스키마 검사를 통과하는 출력이다. 제약 디코딩은 이런 오류를 잡지 못한다.

  • 품목별 금액을 더한 값이 송장 총액과 다르다
  • shipper와 consignee가 서로 뒤바뀌었다 (둘 다 string이라 타입 검사는 통과)
  • 수량 단위를 혼동했다 (박스 수를 개수 칸에)
  • 03/04/2026을 3월 4일로 읽었는데 원문은 일/월 순서였다

형식이 제각각인 원문은 스키마만으로 통일되지 않는다. 출력 스키마와 함께 정규화 규칙을 프롬프트에 적어 둔다.

# system 프롬프트 일부 — 스키마와 함께 보내는 정규화 규칙 - 날짜는 YYYY-MM-DD로 쓴다. 원문 날짜가 일/월 순서인지 월/일 순서인지 문서 안에 단서(발행국, 13 이상인 숫자가 들어간 다른 날짜)가 없으면 추측하지 말고 date_ambiguous를 true로 둔다. - 금액은 통화 기호와 천 단위 구분자를 뺀 숫자로, 통화는 ISO 4217 코드(USD, KRW)로 쓴다. - 회사명은 원문 표기 그대로 옮기고 번역하거나 약칭으로 바꾸지 않는다.

값의 정확성은 앱의 검증과 오류 피드백 재요청으로 다룬다(4.4).

시험 판단 기준
  • "JSON 파싱이 가끔 실패한다" → strict: true 또는 output_config.format (프롬프트 강조가 아니다)
  • "도구를 안 부르고 텍스트로 답한다" → 지원 모델이면 any/tool, 아니면 output_config.format
  • "문서 유형을 모르는데 스키마가 여러 개" → any / "이 추출이 반드시 먼저" → 도구 지정
  • "없는 값을 지어낸다" → nullable·optional, unclear·other 값
  • "합계가 안 맞는다·필드가 뒤바뀐다" → 스키마 문제가 아니라 의미 검증 문제

시험 함정 · 흔한 오해

오해tool_choice를 any로 두면 Claude가 도구를 부르기 전에 판단 근거도 텍스트로 설명해 준다.
사실any·tool은 assistant 턴을 prefill해 tool_use부터 시작한다. 요청해도 앞선 설명이 없다. 설명이 필요하면 auto + 사용자 지시로 바꾼다.
오해strict: true를 켜면 추출한 값도 정확해진다.
사실보장되는 것은 형식·타입·필수 키다. 합계 불일치나 필드 뒤바뀜은 그대로 통과하므로 별도 검증이 필요하다.
오해누락을 막으려면 모든 필드를 null 불가 필수 필드로 만드는 것이 안전하다.
사실원문에 없는 정보까지 채우도록 강요해 날조를 부른다. 없을 수 있는 필드는 nullable 또는 optional로 둔다.
오해어느 모델에서든 tool_choice: {"type": "tool"}로 특정 도구를 강제할 수 있다.
사실2026년 10월 기준 Opus 5.5 · Sonnet 5.5 · Fable 5.1 · Mythos 5.1은 400 오류를 낸다. auto + strict 또는 output_config.format으로 설계한다.

계약서 추출 스키마에 renewal_notice_days(integer, required)를 넣었다. 갱신 통지 조항이 없는 계약서에서도 30이나 60 같은 값이 채워져 나온다.가장 좋은 수정은?
정답 (B)

null 불가 필수 필드는 없는 정보를 지어내게 만든다. nullable로 바꾸면 "없음"을 정직하게 표현할 수 있다. A의 0은 "통지 기간 0일"과 구분되지 않는 가짜 값이고, C는 같은 압박을 그대로 둔다.

Q5확장 가능한 범주
반품 사유를 enum: ["파손", "오배송", "단순 변심"]으로 분류한다. 새로운 사유가 계속 생기는데, 그런 건이 가장 비슷해 보이는 범주로 억지로 들어가 통계가 왜곡된다.가장 적절한 개선은?
정답 (C)

열린 enum 패턴은 기존 범주의 일관성을 지키면서 새 유형을 따로 모아 나중에 범주로 승격할 근거를 남긴다. A는 집계 일관성을 잃고, B도 결국 닫힌 목록이라 같은 문제가 반복된다.

Q6보장의 예외
output_config.format으로 structured outputs를 켰다. 그래도 응답이 스키마와 맞지 않을 수 있는 경우는?
정답 (A)

잘린 출력과 refusal은 문서가 명시한 예외다. enum 대소문자도 보장되지 않는다. 첫 사용 시 컴파일은 지연만 늘리고, JSON outputs와 strict 도구는 한 요청에서 함께 쓸 수 있다.
