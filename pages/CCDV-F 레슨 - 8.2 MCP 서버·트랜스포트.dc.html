MCP(Model Context Protocol)는 LLM 애플리케이션과 외부 데이터·도구를 잇는 개방형 프로토콜로, JSON-RPC 2.0 메시지를 쓴다. 서버를 한 번 만들면 MCP를 지원하는 어떤 호스트에서도 쓸 수 있다는 것이 핵심 가치다. 시험은 역할 구분, 프리미티브별 규칙, 트랜스포트 규칙, 그리고 Claude Code·Agent SDK의 연결 설정 문법을 묻는다. 이 페이지는 2026년 10월 기준 최신 명세인 2026-07-28 개정을 따른다. 이 개정에서 프로토콜이 무상태(stateless)로 바뀌었으니, 예전 자료의 initialize 핸드셰이크 설명과 구분해서 읽는다.

습득 포인트
  • 호스트·클라이언트·서버의 책임과 클라이언트-서버 1:1 관계를 설명한다
  • 요청별 _meta와 server/discover로 이뤄지는 기능 선언을 이해하고, 선언하지 않은 기능은 쓸 수 없다는 규칙을 적용한다
  • 도구(모델 제어)·리소스(애플리케이션 주도)·프롬프트(사용자 제어)의 메서드·스키마·오류 코드를 구분한다
  • stdio와 Streamable HTTP의 메시지 규칙, 종료 절차, 보안 요구 사항을 안다
  • claude mcp add·.mcp.json·mcpServers로 서버를 연결하고 allowedTools로 MCP 도구를 승인한다
01

호스트·클라이언트·서버

Client-host-server architecture

MCP는 호스트 하나가 여러 클라이언트 인스턴스를 돌리는 구조다. IDE나 데스크톱 앱이 Git 서버, DB 서버, 원격 API 서버에 동시에 붙어 있다면, 호스트 안에 클라이언트가 서버 수만큼 있다.

역할하는 일헷갈리는 점
호스트클라이언트를 만들고 관리한다. 연결 권한과 수명을 통제하고, 보안 정책과 사용자 동의를 집행하며, 권한 결정을 처리한다. LLM 통합과 여러 클라이언트의 컨텍스트 취합도 맡는다동의·보안의 주체는 서버가 아니라 호스트다
클라이언트호스트가 만들며 정확히 한 서버와 통신한다. 요청마다 프로토콜 버전과 기능을 붙이고, 메시지를 양방향으로 중계하고, 서버 사이의 보안 경계를 지킨다클라이언트 하나가 여러 서버를 맡지 않는다(1:1)
서버MCP 프리미티브로 리소스·도구·프롬프트를 노출한다. 로컬 프로세스일 수도, 원격 서비스일 수도 있다대화 전체를 읽거나 다른 서버를 들여다볼 수 없다. 필요한 맥락만 받는다
설계 원칙 한 줄

"서버는 아주 쉽게 만들 수 있어야 한다." 복잡한 오케스트레이션은 호스트가 맡고, 서버는 잘 정의된 한 가지 능력에 집중한다. 그래서 여러 서버를 조합하기 쉽고, 서버끼리의 상호작용은 호스트가 통제한다.

02

기능 선언과 무상태 프로토콜

Capabilities in revision 2026-07-28

2026-07-28 개정에는 협상 핸드셰이크가 없다. 모든 요청이 스스로 완결되어 _meta에 프로토콜 버전(io.modelcontextprotocol/protocolVersion), 클라이언트 정보, 클라이언트 기능을 싣고, 서버는 요청마다 받거나 거절한다. 지원하지 않는 버전이면 지원 목록을 담은 UnsupportedProtocolVersionError(-32022)를 돌려준다.

서버의 기능은 server/discover 응답으로 광고한다. 서버는 이 메서드를 반드시 구현해야 하고, 클라이언트는 다른 요청 전에 부를 수도 있지만 꼭 부를 의무는 없다.

{"jsonrpc": "2.0", "id": "d-1", "result": { "resultType": "complete", "supportedVersions": ["2026-07-28"], "capabilities": { "tools": {"listChanged": true}, "resources": {} }, "_meta": {"io.modelcontextprotocol/serverInfo": {"name": "handbook-server", "version": "2.3.0"}}, "instructions": "Search and read the staff handbook." }}
기능 선언 규칙
  • 구현한 서버 기능은 서버의 capabilities에 광고해야 한다. 핸들러를 구현한 것만으로는 부족하다
  • 도구 호출은 서버가 tools 기능을 선언해야 가능하다. 리소스는 resources, 프롬프트는 prompts
  • 변경 알림(listChanged)이나 리소스 구독(subscribe)은 기능 안의 선택 항목이고, 알림은 subscriptions/listen 스트림으로 받는다
  • 양쪽 모두 선언된 기능을 존중해야 한다. 클라이언트도 sampling·elicitation 같은 자기 기능을 선언한다
예전 개정과의 차이

2025-11-25와 그 이전(레거시)은 initialize 핸드셰이크로 세션을 열고 그때 기능을 협상했다. 지금 개정을 지원하는 서버는 legacy와 modern을 함께 지원할 수도 있다. 시험 문항이 "초기화 때 선언한 기능"이라고 쓰더라도 묻는 원리는 같다. 선언되지 않은 기능은 쓸 수 없다.

03

세 프리미티브 한눈에

Tools, resources, prompts

세 프리미티브는 누가 사용을 결정하느냐로 갈린다. 시나리오에 '모델이 알아서', '앱이 골라 넣는', '사용자가 명시적으로 고르는'이라는 신호가 있으면 각각 도구·리소스·프롬프트다.

모델 제어
Tools
모델이 문맥을 보고 찾아 호출하는 함수. tools/list로 발견, tools/call로 실행. 사람이 호출을 거부할 수 있어야 한다(SHOULD)
애플리케이션 주도
Resources
URI로 식별되는 데이터(파일, DB 스키마 등). resources/list, resources/read, resources/templates/list. 호스트가 어떻게 컨텍스트에 넣을지 정한다
사용자 제어
Prompts
재사용 메시지 템플릿. prompts/list, prompts/get. 보통 슬래시 명령처럼 사용자가 골라 실행한다. 내용은 서버가 정한다

목록 메서드는 페이지네이션과 캐싱을 지원하고, 목록이 바뀌면 서버는 notifications/tools/list_changed 같은 알림을 구독 스트림으로 보낸다. 도구 목록은 같은 집합이면 결정적 순서로 돌려주는 것이 권장된다(클라이언트 캐시와 프롬프트 캐시 적중률 때문).

04

도구 정의와 오류의 두 갈래

Tools in detail
{"jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": {"name": "convert_currency", "arguments": {"amount": 120, "from": "EUR", "to": "KRW"}}} // 매개변수가 없는 도구도 inputSchema는 객체여야 한다 {"name": "get_server_time", "description": "Returns the server's current UTC time", "inputSchema": {"type": "object", "additionalProperties": false}}
필드·규칙내용
inputSchema유효한 JSON Schema 객체여야 하고 null은 안 된다. $schema가 없으면 2020-12로 본다. 매개변수가 없으면 {"type":"object","additionalProperties":false}(권장, 빈 객체만 허용) 또는 {"type":"object"}
도구 이름1~128자, 대소문자 구분, 영문자·숫자·_·-·.만 쓰는 것이 권장된다. 유일성은 서버 하나 안에서만 보장되므로, 여러 서버를 합치는 클라이언트는 서버 식별자 접두사 같은 구분 전략을 둔다
outputSchema·structuredContent출력 스키마를 주면 서버는 그에 맞는 구조화 결과를 내야 한다. 하위 호환을 위해 직렬화한 JSON을 텍스트 블록으로도 함께 주는 것이 권장된다
annotations도구 동작을 설명하는 힌트. 신뢰할 수 있는 서버에서 온 것이 아니면 믿지 않는다
프로토콜 오류

알 수 없는 도구, 요청 스키마 위반, 서버 오류. 표준 JSON-RPC error로 돌려준다(예: -32602 "Unknown tool"). 모델이 고쳐서 회복하기 어렵다.

도구 실행 오류

API 실패, 입력값 검증 실패(날짜 형식·범위), 업무 규칙 위반. result 안에 "isError": true로 돌려준다. 모델이 읽고 인자를 고쳐 다시 시도할 수 있으니 클라이언트는 모델에 전달해야 한다(SHOULD).

05

리소스와 프롬프트의 규칙

Resources and prompts

리소스는 URI로 식별한다. file://은 파일시스템처럼 동작하는 자원(실제 디스크와 대응하지 않아도 된다), https://는 클라이언트가 웹에서 직접 가져올 수 있을 때만, git://은 버전 관리 연동에 쓴다. 매개변수가 있는 자원은 file:///{path} 같은 URI 템플릿으로 노출한다.

상황명세가 요구하는 것
file:// 리소스 제공서버는 모든 리소스 URI를 검증하고, 디렉터리 순회 공격을 막도록 파일 경로를 정제해야 한다(MUST). 민감한 리소스에는 접근 제어, 작업 전 권한 확인(SHOULD)
없는 리소스를 읽음JSON-RPC -32602(Invalid params). 예전 개정의 -32002도 클라이언트가 받아 줘야 한다. 빈 contents 배열로 답하면 안 된다(존재하지만 비었는지, 없는지 모호하다)
프롬프트 이름이 틀림 · 필수 인자 누락둘 다 -32602(Invalid params). 내부 오류는 -32603
프롬프트 인자 처리서버는 처리 전에 인자를 검증하고(SHOULD), 입력·출력을 검증해 인젝션과 무단 접근을 막아야 한다(MUST)
Claude Code에서 보이는 모습

MCP 프롬프트는 슬래시 명령으로 나타나 /mcp__github__pr_review 456처럼 실행하고, 리소스는 @server:protocol://path 형식으로 대화에 참조한다(예: @docs:file://api/auth). 프롬프트가 '사용자 제어', 리소스가 '애플리케이션 주도'라는 설계가 그대로 드러난다.

06

stdio 트랜스포트

Local subprocess over standard streams

stdio에서는 클라이언트가 서버를 하위 프로세스로 실행한다. 서버는 stdin에서 JSON-RPC 메시지를 읽고 stdout에 쓴다. 메시지는 줄바꿈으로 구분되며, 메시지 안에 줄바꿈을 넣으면 안 된다.

흔한 버그

디버그용 print()나 console.log()를 stdout에 남긴다. stdout은 프로토콜 채널이라 MCP 메시지가 아닌 내용을 쓰면 안 된다(MUST NOT). 클라이언트의 파싱이 깨진다.

올바른 방법

로그는 stderr에 UTF-8 문자열로 쓴다. 클라이언트는 stderr를 수집·전달·무시할 수 있고, stderr 출력이 곧 오류라고 가정하지 않는다.

① CLOSE STDIN
클라이언트가 서버로 가는 입력 스트림을 닫는다
→
② WAIT
서버가 스스로 종료하기를 기다린다
→
③ SIGTERM
적당한 시간 안에 끝나지 않으면 강제 종료 시작
→
④ SIGKILL
그래도 남아 있으면 단계를 올린다 (Windows는 TerminateProcess·Job Objects)

stdin이 닫히거나 EOF를 읽으면 서버는 즉시 종료해야 한다(SHOULD). 이것이 주된, 그리고 유일하게 이식 가능한 정상 종료 신호다. 서버가 예기치 않게 죽으면 클라이언트는 재시작하고, 무상태 프로토콜이므로 진행 중이던 요청은 새 프로세스에 다시 보내면 된다. 취소는 notifications/cancelled로 알린다.

// 공식 TypeScript SDK 클라이언트: 서버를 하위 프로세스로 띄운다 import { Client } from "@modelcontextprotocol/client"; import { StdioClientTransport } from "@modelcontextprotocol/client/stdio"; const transport = new StdioClientTransport({ command: process.execPath, // node args: ["build/inventory-server.js"], }); await client.connect(transport); const { tools } = await client.listTools();
07

Streamable HTTP

Remote servers over a single endpoint

Streamable HTTP에서 서버는 여러 클라이언트를 받는 독립 프로세스이고, POST를 받는 MCP 엔드포인트 하나(예: https://example.com/mcp)를 둔다. 클라이언트는 JSON-RPC 요청이나 알림을 하나씩 각자의 POST로 보낸다.

POST 본문서버 응답
JSON-RPC 알림을 받아들임202 Accepted, 본문 없음
알림을 받아들일 수 없음400 Bad Request 같은 HTTP 오류 상태 (본문에 id 없는 JSON-RPC 오류를 담을 수 있다)
JSON-RPC 요청application/json(단일 객체) 또는 text/event-stream(그 요청에 한정된 SSE 스트림). 클라이언트는 둘 다 지원해야 한다
서버가 모르는 메서드404 Not Found + -32601

POST마다 MCP-Protocol-Version, Mcp-Method 헤더를, tools/call·resources/read·prompts/get에는 Mcp-Name도 붙인다. 헤더가 본문과 다르면 400 + -32020(HeaderMismatch). 이 개정에서 클라이언트는 JSON-RPC 응답을 POST하지 않으며, 서버가 클라이언트 입력이 필요하면 별도 요청 대신 결과 안에 InputRequiredResult를 담는다.

보안 요구와 바뀐 점
  • 서버는 모든 연결에서 Origin 헤더를 검증해야 한다(DNS 리바인딩 방지). 잘못된 Origin에는 403
  • 로컬에서 돌리는 서버는 0.0.0.0이 아니라 127.0.0.1에만 바인딩한다(SHOULD). 모든 연결에 인증을 둔다(SHOULD)
  • 2026-07-28에서 프로토콜 수준 세션(Mcp-Session-Id)과 GET 스트림 엔드포인트가 없어졌다. GET·DELETE에는 405, 세션 ID는 무시한다
  • 2024-11-05의 HTTP+SSE 트랜스포트는 사용 중단(deprecated) 상태다. 새 구현은 Streamable HTTP를 쓴다
08

Claude Code에 서버 연결하기

claude mcp add and .mcp.json

트랜스포트 선택은 공급자가 무엇을 줬느냐로 정한다. 실행할 명령을 줬다면 stdio, URL을 줬다면 HTTP다.

# 원격 서버 (권장 트랜스포트) claude mcp add --transport http trackly \ https://mcp.trackly.example/mcp # 로컬 stdio 서버: -- 뒤는 서버 명령으로 그대로 전달된다 claude mcp add --transport stdio --env GEO_KEY=abc123 \ geodata -- uvx geodata-mcp --region eu # 팀과 공유: 저장소 루트의 .mcp.json에 기록 claude mcp add --scope project --transport http metrics \ https://metrics.example.com/mcp
스코프로드되는 곳팀 공유저장 위치
local (기본값)현재 프로젝트만아니요~/.claude.json
project현재 프로젝트만예 (버전 관리)프로젝트 루트 .mcp.json
user내 모든 프로젝트아니요~/.claude.json
건너뛰어지는 항목

"metrics": {"url": "https://metrics.example.com/mcp"}
Claude Code는 type이 없는 항목을 stdio 서버로 읽는다. url만 있으면 설정 오류로 그 서버를 건너뛰고, "type": "http"(또는 sse·ws)를 넣으라는 메시지를 낸다.

올바른 항목

"metrics": {"type": "http", "url": "https://metrics.example.com/mcp"}
type 값은 http(별칭 streamable-http), 사용 중단된 sse, add-json으로만 넣는 ws, 로컬 stdio. sdk는 SDK 호스트만 등록할 수 있다.

09

Agent SDK에 연결하고 MCP 도구 승인하기

mcpServers and allowedTools
options = ClaudeAgentOptions( mcp_servers={ "geodata": { # 명령을 받았다 → stdio "command": "uvx", "args": ["geodata-mcp", "--region", "eu"], }, "billing": { # URL을 받았다 → http "type": "http", "url": "https://billing.example.com/mcp", "headers": {"Authorization": f"Bearer {token}"}, }, }, allowed_tools=[ "mcp__geodata__*", # 이 서버의 모든 도구 "mcp__billing__get_invoice", # 이 도구 하나만 ], )
규칙 형태뜻
mcp__<server>__<tool>MCP 도구의 전체 이름이자 그 도구 하나만 승인하는 규칙. <server>는 mcpServers에 등록한 키이고, .이나 공백은 _로 바뀐다
mcp__<server>__*그 서버의 모든 도구. 도구를 하나씩 나열하지 않아도 된다
mcp__<server>__get_*그 서버에서 get_으로 시작하는 도구들
mcp__*, *allow 규칙으로는 무시된다(서버 부분이 glob이면 안 된다). deny 규칙으로는 모든 MCP 도구·모든 도구에 적용된다
권한 모드보다 allowedTools

MCP 도구는 승인 없이는 호출되지 않는다. acceptEdits 모드는 파일 편집과 파일시스템 명령만 승인하므로 MCP 도구에는 효과가 없다. bypassPermissions는 MCP 도구도 승인하지만 다른 안전 장치까지 대부분 끈다. 원하는 서버만 정확히 여는 것은 allowedTools의 와일드카드나 전체 이름이다. 도구가 보이는데 호출되지 않으면 먼저 allowedTools를 확인한다.

시험 함정 · 흔한 오해

오해핸들러만 구현하면 클라이언트가 그 기능을 쓸 수 있으니 기능 선언은 선택 사항이다.
사실구현한 기능은 capabilities에 광고해야 하고, 도구 호출에는 tools 기능 선언이 필요하다.
오해stdio 서버는 디버그 출력을 stdout에 찍어도 된다. 클라이언트가 모르는 텍스트는 무시한다.
사실stdout은 프로토콜 전용이다. MCP 메시지가 아닌 출력은 금지이고, 로그는 stderr로 보낸다.
오해매개변수가 없는 도구는 inputSchema를 null로 두거나 생략하면 된다.
사실inputSchema는 유효한 JSON Schema 객체여야 한다. {"type":"object","additionalProperties":false}가 권장형이다.
오해로컬 HTTP MCP 서버는 어디서든 붙을 수 있게 0.0.0.0에 바인딩하는 편이 낫다.
사실로컬 서버는 127.0.0.1에만 바인딩하고 Origin 헤더를 검증한다. 그러지 않으면 DNS 리바인딩에 노출된다.
오해.mcp.json에 url만 적으면 Claude Code가 원격 서버로 알아서 판단한다.
사실type이 없으면 stdio로 읽혀 설정 오류로 건너뛴다. "type": "http"를 함께 쓴다.
오해MCP는 지금도 initialize 핸드셰이크로 세션을 열고 Mcp-Session-Id로 상태를 유지한다.
사실2026-07-28 개정은 무상태다. 요청마다 _meta로 버전·기능을 싣고, 서버 기능은 server/discover로 광고한다.
