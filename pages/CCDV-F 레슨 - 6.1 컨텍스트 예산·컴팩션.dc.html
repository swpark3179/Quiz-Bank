컨텍스트 예산: 도구 출력 정리·컴팩션·서브에이전트 격리

6.1 컨텍스트 예산·컴팩션6.2 프롬프트 엔지니어링6.3 구조화 출력·응답 검증

컨텍스트 창은 크기가 정해진 작업 기억이고, 커질수록 정확도와 재현율이 떨어지는 context rot도 생긴다. 그래서 장기 실행 에이전트를 설계할 때는 '얼마나 넣을 수 있나'보다 무엇이 창을 채우고 있고, 그 출처에 맞는 처방이 무엇인가를 먼저 따져야 한다. 시험은 캐시된 토큰도 창을 차지한다는 사실, 도구 결과 정리의 기본 동작과 캐시와의 충돌, 컴팩션 방식의 선택 기준, 컴팩션 뒤에 무엇이 다시 돌아오는지, 서브에이전트가 부모에게 무엇을 돌려주는지를 시나리오로 묻는다.

습득 포인트
  • 요청의 어느 부분이 컨텍스트 창에 계산되는지 설명하고, 캐시는 비용을 바꿀 뿐 공간을 바꾸지 않는다는 점을 안다
  • 도구 결과 정리(clear_tool_uses_20250919)의 파라미터와 기본값, 자리 표시 텍스트, 캐시 무효화와 clear_at_least를 설명한다
  • 도구 검색·프로그래밍 방식 도구 호출·프롬프트 캐싱·컨텍스트 편집을 압력의 출처에 맞게 고른다
  • 온디맨드(백그라운드·최근 턴 유지)와 토큰 임계값 컴팩션의 차이를 알고 요구사항에 맞게 고른다
  • Claude Code·Agent SDK에서 컴팩션 후 다시 주입되는 것과 요약에만 남는 것을 구분하고, PreCompact 훅의 용도를 안다
  • 서브에이전트 위임이 부모 컨텍스트를 얼마나 늘리는지, 동시 실행 시 경과 시간이 어떻게 되는지 예측한다
01

컨텍스트 창에 무엇이 쌓이는가

What actually fills the window

요청에 들어간 것은 전부 창을 차지한다. 시스템 프롬프트, messages 안의 모든 메시지(도구 결과·이미지·문서 포함), 도구 정의, 그리고 그 턴에 Claude가 생성하는 출력(extended thinking 포함)까지다. 응답의 usage 필드가 요청이 소비한 양을 알려 준다.

구성 요소창에 계산되는가헷갈리는 점
도구 정의계산된다쓰지 않는 도구라도 정의를 보내면 매 요청 자리를 차지한다
tool_result 블록계산된다로그 덤프·파일 내용처럼 큰 결과가 턴마다 누적된다
캐시된 프리픽스계산된다input_tokens, cache_read_input_tokens, cache_creation_input_tokens 셋 모두 창에 합산된다
이전 턴의 thinking 블록모델에 따라 다르다Opus 4.5 이후·Sonnet 4.6 이후·Haiku 5.5 등은 기본으로 유지되어 계산되고, 그 이전 모델은 API가 자동으로 걷어 낸다
넘치면 어떻게 되나

입력만으로 창을 넘으면 모든 모델에서 400 invalid_request_error("prompt is too long")가 난다. Claude 4.5 이후 모델은 입력 + max_tokens가 창을 넘어도 요청을 받아 주고, 생성 중 한계에 닿으면 stop_reason: "model_context_window_exceeded"로 멈춘다. 2026년 10월 기준 Opus 5.5·Sonnet 5.5·Haiku 5.5·Fable 계열 등은 1M 토큰 창이 기본이다.

컨텍스트 엔지니어링의 출발점

Anthropic 엔지니어링 글은 컨텍스트를 한계 효용이 줄어드는 유한한 자원으로 보고, 원하는 결과의 가능성을 최대로 높이는 가장 작은 고신호 토큰 집합을 찾으라고 권한다. 모든 자료를 미리 넣지 않고 파일 경로·저장된 쿼리·링크 같은 가벼운 식별자만 들고 있다가 필요할 때 불러오는 just-in-time 방식, 창 밖에 메모를 남기는 구조화된 노트, 컴팩션, 서브에이전트가 그 도구들이다.

시험 판단 축
  • "캐시했으니 창 공간이 생긴다"는 보기는 오답이다. 문서 표현 그대로, 캐시는 그 토큰에 얼마를 내는지를 바꿀 뿐 계산되는지를 바꾸지 않는다
  • 더 큰 창이 답이 아닌 경우가 많다. 창이 커도 context rot 때문에 '작고 신호가 강한 컨텍스트'가 기본 원칙이다
02

도구 결과 정리: 컨텍스트 편집

Tool result clearing with context editing

긴 에이전트 루프는 그때는 필요했지만 지금은 쓸모없는 도구 결과를 수백 개 남긴다. 컨텍스트 편집(context editing)은 이런 결과를 규칙에 따라 지운다. 베타 헤더 context-management-2025-06-27와 함께 context_management.edits에 전략을 넣는다.

response = client.beta.messages.create( model="claude-sonnet-5-5", max_tokens=4096, betas=["context-management-2025-06-27"], tools=tools, messages=history, context_management={"edits": [{ "type": "clear_tool_uses_20250919", "trigger": {"type": "input_tokens", "value": 120000}, "keep": {"type": "tool_uses", "value": 4}, "clear_at_least": {"type": "input_tokens", "value": 20000}, "exclude_tools": ["read_runbook"], # 이 도구 결과는 지우지 않음 }]}, ) print(response.context_management.applied_edits) # 실제로 지운 양
파라미터기본값역할
trigger입력 100,000 토큰정리를 시작하는 시점. input_tokens 또는 tool_uses로 지정
keep도구 사용 3개남겨 둘 최근 도구 사용/결과 쌍의 수. 가장 오래된 것부터 지운다
clear_at_least없음한 번에 최소한 지워야 할 토큰 수. 그만큼 지울 수 없으면 그 회차는 적용하지 않는다 (→ 03)
exclude_tools없음절대 지우지 않을 도구 이름 목록
clear_tool_inputsfalsetrue면 도구 호출의 입력 파라미터도 함께 지운다. 기본값에서는 Claude의 원래 호출이 보인다
지운 자리에 Claude가 보는 것

지운 결과 자리에는 결과가 제거되었음을 알리는 자리 표시 텍스트가 들어간다. 호출 자체는 남아 있으므로 Claude는 '그 도구를 그 입력으로 불렀다'는 사실은 알지만 그때 받은 내용은 볼 수 없다. 편집은 프롬프트가 Claude에 닿기 전 서버에서 일어나고, 클라이언트는 수정되지 않은 전체 이력을 그대로 가진다. 클라이언트가 편집 결과에 맞춰 이력을 고칠 필요도 없다.

  • 응답의 context_management.applied_edits에 지운 도구 사용 수와 토큰 수가 나온다. 스트리밍에서는 마지막 message_delta 이벤트에 실린다
  • 토큰 카운팅 엔드포인트는 편집 후 input_tokens와 함께 편집 전 값 context_management.original_input_tokens를 돌려준다

thinking 블록을 정리하는 별도 전략 clear_thinking_20251015도 있다. 두 전략을 함께 쓰면 thinking 정리 전략을 edits 배열의 첫 번째에 둔다. 메모리 도구(memory_20250818)와 함께 쓰면 정리 임계값에 가까워질 때 Claude가 중요한 내용을 메모리 파일에 저장하라는 경고를 자동으로 받는다.

03

정리와 캐시는 서로 부딪힌다

Why clear_at_least exists

도구 결과를 지우면 지운 지점부터 캐시된 프롬프트 프리픽스가 무효화되고, 정리할 때마다 캐시 쓰기 비용이 다시 든다. 트리거를 낮게 잡아 매 턴 수백 토큰씩 지우면, 아낀 토큰보다 캐시를 다시 쓰는 비용이 더 커지고 캐시 적중률이 무너진다.

BAD · 자주, 조금씩

낮은 trigger, clear_at_least 없음. 거의 매 턴 정리가 일어나 그때마다 캐시가 깨진다. 지운 양은 작은데 캐시 쓰기 비용은 매번 낸다.

GOOD · 가끔, 크게

clear_at_least로 최소 정리량을 정한다. 그만큼 지울 수 없는 회차는 건너뛰므로, 캐시를 깨뜨릴 가치가 있을 때만 정리가 일어난다.

시험 판단 축
  • "도구 결과 정리는 토큰을 빼기만 하니 캐시에 영향이 없다"는 오답이다
  • 정리를 아예 막는 처방(exclude_tools에 모든 도구 넣기)이나 지우는 범위를 넓히는 처방(clear_tool_inputs: true)은 빈도 문제를 고치지 못한다
  • thinking 블록 정리도 지운 지점부터 캐시를 무효화한다. thinking을 유지하면 캐시가 보존된다
04

압력의 출처에 맞는 처방

Match the fix to the source of bloat

도구 컨텍스트 관리 문서는 네 가지 접근을 토큰이 어디서 새는가로 고르라고 정리한다. 넷은 파이프라인의 서로 다른 지점을 다루므로 함께 써도 충돌하지 않는다.

05

서버 측 컴팩션: 누가, 언제 요약하는가

Compaction on demand vs at a threshold

컴팩션(compaction)은 대화의 오래된 턴을 Claude가 서버에서 쓴 요약으로 바꾼다. 컨텍스트 창 문서는 장기 대화와 에이전트 작업의 기본 전략으로 서버 측 컴팩션을 들고, 컨텍스트 편집은 더 세밀한 통제가 필요할 때 쓰라고 한다. 컴팩션 개요 문서는 쓸 수 있는 곳에서는 온디맨드를 쓰라고 권한다.

온디맨드 (on demand)토큰 임계값 (threshold)
설정베타 compact-2026-09-04, 최상위 compaction: {"type": "summarize"}베타 compact-2026-01-12, context_management.edits에 {"type": "compact_20260112"}
시점애플리케이션이 요청을 보낼 때입력이 trigger(기본 150,000, 최소 50,000 토큰)에 닿을 때 API가
응답답변 없이 compaction 블록 하나, stop_reason: "compaction"응답 맨 앞에 compaction 블록, 이어서 평소 답변
되돌려 보낼 것블록을 messages 맨 앞에, 요약된 메시지 자리에응답을 평소처럼 덧붙임. API가 블록 앞의 내용을 무시
백그라운드가능: 요약 요청이 도는 동안 대화는 전체 이력으로 계속불가: 트리거에 닿은 요청 안에서 실행
최근 턴 원문 유지가능: 자를 지점 이전만 요약 요청에 보내고, 나머지는 블록 뒤에 그대로pause_after_compaction: true로 멈춘 뒤 다시 넣는 방식
# 백그라운드 + 최근 2턴 유지: 오래된 턴만 요약 요청에 보낸다 older, recent = history[:-4], history[-4:] pending = executor.submit( client.beta.messages.create, model="claude-sonnet-5-5", max_tokens=4096, system=SYSTEM, betas=["compact-2026-09-04"], messages=older, compaction={"type": "summarize"}, ) # ... 대화는 그동안 계속된다 ... summary = pending.result() if summary.stop_reason == "compaction": history = [{"role": "assistant", "content": summary.content}, *history[len(older):]] # 요약 뒤에 나머지 그대로
실수해도 오류가 안 나는 두 가지

요약된 메시지가 블록 뒤에 남아 있으면 API는 그 메시지를 Claude에게 다시 보낸다. 이후 요청에서 블록을 빼먹으면 Claude는 요약을 받지 못한다. 블록은 signature까지 받은 그대로 보내야 한다. 자를 지점은 도구 호출과 그 결과가 같은 쪽에 오도록 잡는다. 결과가 없는 도구 호출로 끝나는 요청은 거부된다.

시험 판단 축
  • "멈출 수 없다(음성·실시간)" → 백그라운드 온디맨드. 임계값 방식은 트리거를 낮춰도 요청 안에서 돈다
  • "최근 턴을 글자 그대로" → keep-tail 온디맨드. 이를 정하는 전용 파라미터는 없고, 자를 지점을 코드가 고른다
  • 임계값 방식의 instructions는 기본 요약 프롬프트를 대체한다(덧붙이지 않는다)
06

Claude Code·Agent SDK에서 컴팩션 후 남는 것

What survives compaction

Claude Code와 Agent SDK는 창이 한도에 가까워지면 자동으로 컴팩션한다. SDK는 이때 type: "system", subtype: "compact_boundary" 메시지를 낸다. 컴팩션 뒤에 무엇이 남는지는 그 내용이 어떻게 로드되었는가로 정해진다.

내용컴팩션 후
프로젝트 루트 CLAUDE.md, 경로 조건 없는 규칙, 자동 메모리디스크에서 다시 주입
읽거나 편집한 파일최근 수정 순으로 최대 5개를 다시 읽음. 5,000 토큰이 넘는 파일은 내용 없이 경로 참조(Referenced file)로
paths: 규칙, 하위 디렉터리 CLAUDE.md대상 파일을 다시 다룰 때 필요에 따라 다시 로드 (그 전까지는 요약에 묻힘)
호출된 스킬 본문스킬당 5,000 토큰, 합계 25,000 토큰까지 다시 주입. 오래된 것부터 빠짐
대화에서 한 번만 말한 지시요약에 남은 경우에만 유지
지켜야 할 규칙은 디스크에

컴팩션은 오래된 메시지를 요약으로 바꾸므로 초반의 구체적 지시가 사라질 수 있다. SDK 문서는 지속 규칙을 첫 프롬프트가 아니라 CLAUDE.md에 두라고 한다. CLAUDE.md는 매 요청 다시 주입되고, 요약할 때 보존할 항목을 적은 섹션을 넣어 두면 요약기도 그것을 읽는다.

원본이 필요하면 PreCompact

PreCompact 훅은 컴팩션 전에 실행되며 trigger 필드(manual 또는 auto)를 받는다. 문서가 드는 대표 용도가 '요약하기 전에 전체 대화 기록 보관'이다. 훅은 애플리케이션 프로세스에서 돌므로 컨텍스트를 쓰지 않는다.

직접 시점을 고를 수도 있다. /compact focus on …처럼 초점을 주면 자동 요약이 추측하는 대신 내가 고른 것을 남기고, /clear는 무관한 작업으로 넘어갈 때 대화를 비운다.

서브에이전트로 대량 읽기를 격리한다

Context isolation with subagents

많이 읽어야 하지만 메인 컨텍스트는 작게 유지해야 할 때의 정석은 위임이다. 서브에이전트는 새 컨텍스트에서 시작하고(포크 제외), 중간 도구 호출과 결과는 그 안에 남으며, 최종 메시지만 부모가 호출한 Agent 도구의 결과로 돌아온다.

여기서 '빨라진다'는 같은 서브에이전트를 차례로 돌릴 때와 비교한 이야기다. 단일 에이전트 하나로 처리할 때와 비교하면 멀티에이전트는 총 토큰을 더 쓰고, 조정 비용 때문에 전체 시간이 더 걸리는 경우도 많다(1.1 참조). 이 레슨의 관점은 부모의 컨텍스트 예산이다. 서브에이전트는 기본으로 백그라운드에서 실행되며 Agent 도구 결과가 status: "async_launched"로 먼저 오고, 보고는 이후 턴에 도착한다.

시험 함정 · 흔한 오해

오해프롬프트 캐시를 쓰면 캐시된 프리픽스가 컨텍스트 창을 덜 차지한다.
사실캐시 읽기·쓰기 토큰도 모두 창에 계산된다. 캐시가 바꾸는 것은 가격과 지연이다.
오해컨텍스트 편집을 켜면 클라이언트가 지워진 결과를 자기 이력에서도 지워야 한다.
사실편집은 서버에서 Claude에게 보내는 프롬프트에만 적용된다. 클라이언트는 원본 이력을 그대로 보내면 된다.
오해도구 결과 정리는 토큰을 빼기만 하므로 캐시 측면에서 공짜다.
사실지운 지점부터 캐시가 무효화되고 캐시 쓰기 비용이 다시 든다. 그래서 clear_at_least가 있다.
오해임계값 컴팩션의 트리거를 낮추면 대화를 멈추지 않고 요약할 수 있다.
사실임계값 방식은 항상 트리거에 닿은 요청 안에서 돈다. 멈출 수 없는 앱은 백그라운드 온디맨드 컴팩션을 쓴다.
오해첫 프롬프트에서 한 번 말한 규칙은 컴팩션 후에도 유지된다.
사실디스크에서 다시 주입되는 것은 CLAUDE.md 같은 파일이다. 대화 속 지시는 요약에 남은 경우에만 살아남는다.
오해서브에이전트가 읽은 파일과 도구 결과는 끝나면 부모 이력에 합쳐진다.
사실부모는 최종 메시지만 도구 결과로 받는다. 위임의 컨텍스트 비용은 보고서 길이로 정해진다.
