2.1 도구 설명2.2 오류 응답2.3 도구 범위2.4 MCP 서버2.5 내장 도구

Claude Code의 내장 도구는 저마다 좁은 질문 하나에 답한다. 시험은 "이 상황에 맞는 도구는?", "Edit가 실패하면?", "낯선 코드베이스를 어떤 순서로 파악하나?"를 시나리오로 묻는다. 먼저 찾기 도구로 범위를 좁히고, 가리킨 곳만 읽고, 바꿀 부분만 고친다.

습득 포인트
  • Grep = 파일 내용 검색(함수명·오류 메시지·import 문), Glob = 파일 경로 패턴 매칭(**/*.test.tsx)
  • Read·Write = 파일 전체 단위, Edit = 고유한 문자열을 찾아 바꾸는 부분 수정
  • Edit가 "고유하지 않음"으로 실패할 때의 복구 순서와 Read + Write 대안
  • Grep으로 진입점을 찾고 Read로 import를 따라가는 점진적 탐색
  • 래퍼·배럴 모듈을 거치는 사용처는 export 이름을 먼저 모은 뒤 이름마다 검색

시험 가이드 표현 vs 현재 문서

가이드는 Grep·Glob을 항상 있는 도구로 다룬다. 현재 문서에 따르면 Windows에서는 기본 도구지만 macOS·Linux·WSL에서는 Grep·Glob이 기본 도구 세트에서 빠지고, Claude는 Bash 안의 find·grep(내장 bfs·ugrep)으로 검색한다. 이 검색은 hook과 권한 규칙에 Bash 호출로 보인다. --tools·--allowedTools에 이름을 적거나, Bash를 제거하거나, 서브에이전트 tools에 Glob·Grep을 넣고 Bash를 빼면 돌아온다. "내용 검색 vs 경로 검색"이라는 판단 기준 자체는 그대로다.

Bash에서 기억할 동작

  • 명령마다 별도 프로세스에서 실행된다. 메인 세션에서 프로젝트 디렉터리 안으로 한 cd는 이어지지만(서브에이전트는 이어지지 않음), export한 환경 변수는 다음 명령에 남지 않는다.
  • 기본 타임아웃은 2분, 상한은 10분이다(BASH_DEFAULT_TIMEOUT_MS, BASH_MAX_TIMEOUT_MS).
  • 파이프·리다이렉트 없이 파일 하나에 실행한 cat, head, sed -n 'X,Yp', grep 등은 Edit·Write 전의 "읽기"로 인정된다.
02

Grep과 Glob, 함정이 되는 세부 동작

Content search vs path matching
항목GrepGlob
보는 대상파일 안의 줄파일 경로(이름)
문법ripgrep 정규식 — 메타문자는 이스케이프 (retry\()**(하위 전체), *, {json,yaml}
결과files_with_matches(기본·경로만) · content(줄·줄 번호) · count(파일별 개수)수정 시각 순 정렬, 최대 100개 — 넘으면 잘림 표시
범위 좁히기glob(**/*.tsx) · type(py) 파라미터, 여러 줄은 multiline: true패턴 자체를 구체적으로
.gitignore따른다 — 무시된 파일은 건너뜀기본적으로 따르지 않는다 — 무시된 파일도 찾음
시험에서 자주 엇갈리는 판단
  • "함수 chargeCard를 호출하는 모든 곳" → 내용이므로 Grep. Glob으로는 파일 이름에 chargeCard가 들어간 파일만 나온다.
  • "모든 Storybook 파일" → 이름 규칙이므로 Glob **/*.stories.tsx.
  • "이 파일 형식 안에서만 내용 검색" → Grep + glob/type 필터. 두 도구를 순서대로 부를 필요가 없다.
  • Grep으로 안 나오던 dist/ 파일이 Glob에서는 나온다 → .gitignore 처리 차이 때문이다.
03

Read·Write·Edit: 전체냐 부분이냐

Full-file vs targeted changes
Read
줄 번호가 붙은 내용을 돌려준다. 이미지·PDF·노트북도 읽는다. 한 번에 기본 25,000토큰, 256KB를 넘는 파일 전체는 거부되어 offset·limit로 나눠 읽는다.
Write
새 파일을 만들거나 기존 파일을 전체 내용으로 덮어쓴다. 덧붙이기·병합은 없다. 부분 변경에는 Edit를 쓴다.
Edit
old_string을 new_string으로 바꾸는 정확한 문자열 치환. 정규식·유사 매칭이 아니다.

Edit가 통과해야 하는 세 가지 검사

  1. 먼저 읽기: 이 대화에서 파일을 읽었어야 한다(PARTIAL view로 잘린 읽기는 불인정). Claude Opus 4.6·Haiku 4.5와 그 이전 모델은 항상 요구하고, 더 새로운 모델은 권한 프롬프트 없이 읽을 수 있는 파일이고 Read 도구가 있으면 생략할 수 있다.
  2. 일치: old_string이 공백·들여쓰기까지 그대로 있어야 한다. 한 글자 차이로도 실패한다.
  3. 고유성: old_string은 파일에 정확히 한 번만 나와야 한다. 여러 번이면 앞뒤 문맥을 더 넣어 하나로 특정하거나, 전부 바꿀 의도라면 replace_all: true를 준다.
BAD · 앵커가 세 번 나온다
# deploy.yaml 안에 [dev] [staging] [prod] 섹션마다 같은 줄 old_string: " replicas: 2" new_string: " replicas: 4"

고유하지 않아 실패한다. replace_all을 주면 세 섹션이 모두 바뀐다.

GOOD · 섹션 머리를 앵커에 포함
old_string: "staging:\n image: api:1.8\n replicas: 2" new_string: "staging:\n image: api:1.8\n replicas: 4"

staging 블록 하나로 특정된다.

시험 가이드 표현 vs 현재 문서

가이드는 "Edit가 고유하지 않은 매칭으로 실패하면 Read + Write로 대체"를 정답 패턴으로 든다. 현재 도구 문서가 먼저 설명하는 복구는 앵커를 넓히거나 replace_all을 쓰는 것이다. Read + Write는 고유한 앵커를 만들 수 없거나 파일 대부분을 다시 써야 할 때의 확실한 대안으로 이해하면 된다. Write로 기존 파일을 덮어쓸 때도 먼저 읽기 규칙이 적용되며, 이전 내용을 읽지 않고 기억으로 다시 쓰면 다른 변경을 잃을 수 있다.

04

점진적 탐색: 찾고, 읽고, 따라간다

Just-in-time context

Anthropic의 컨텍스트 엔지니어링 글은 에이전트가 데이터를 미리 다 싣지 않고, 파일 경로 같은 가벼운 식별자를 들고 있다가 필요할 때 도구로 불러오는 "just in time" 방식을 설명한다. Claude Code는 CLAUDE.md는 처음부터 싣고, glob·grep 같은 기본 동작으로 파일을 그때그때 찾아 읽는 혼합형으로 소개된다. 탐색할수록 파일 크기·이름 규칙·수정 시각 같은 정보가 다음 판단의 단서가 된다(점진적 공개, progressive disclosure).

예: "환불 승인 후 포인트가 두 번 적립된다"

  1. Grep으로 진입점을 찾는다: 라우트 문자열 "/refunds/approve" 또는 로그 메시지 "points credited"
  2. 찾은 핸들러 파일 하나만 Read한다
  3. 핸들러가 import하는 rewards/service를 Read해 흐름을 따라간다
  4. 적립 함수 creditPoints를 부르는 다른 곳을 Grep(content 모드)으로 찾는다 — 두 번째 호출 지점이 여기서 드러난다
  5. 관련 테스트만 Glob(**/rewards/**/*.test.ts)으로 찾아 읽고, 수정은 Edit로 한다
BAD · 전부 먼저 읽기
src/ 아래 파일 300개를 차례로 Read

컨텍스트가 무관한 코드로 차고, 정작 중요한 연결을 놓치기 쉽다.

GOOD · 검색으로 좁힌 뒤 읽기
Grep → Read(1개) → import 따라 Read → Grep(호출부) → Edit

읽는 파일 수가 질문에 비례한다.

타입 언어라면 code intelligence 플러그인을 설치해 LSP 도구의 정의 이동·참조 찾기를 쓸 수 있다. 공식 문서는 심볼 조회가 넓은 파일 읽기를 대신해 컨텍스트 사용을 줄일 수 있다고 본다.

05

래퍼 모듈 너머로 사용처 추적하기

Trace through re-exports

함수가 배럴(index.ts)이나 래퍼 모듈에서 다른 이름으로 재export되면, 원래 이름 하나로 Grep해서는 호출부가 빠진다. 먼저 래퍼가 내보내는 이름을 모두 확인하고, 그 이름마다 검색한다.

// packages/money/src/index.ts ← 1단계: Read로 export 이름 목록 확보 export { toMinorUnits } from "./convert"; export { toMinorUnits as toCents } from "./convert"; // 별칭 export { default as Money } from "./money"; # 2단계: 이름마다 Grep (content 모드, TS 파일로 한정) pattern: "\btoMinorUnits\b" glob: "**/*.{ts,tsx}" pattern: "\btoCents\b" glob: "**/*.{ts,tsx}" pattern: "from \"@acme/money\"" # 패키지째 가져와 Money.xxx로 쓰는 곳
추적 순서
  • 정의 파일보다 공개 경계(배럴·래퍼)를 먼저 읽는다 — 외부에서 실제로 쓰는 이름이 거기 있다
  • 별칭·default export·네임스페이스 import(import * as m)까지 이름 목록에 넣는다
  • 각 이름을 Grep한 결과 중 필요한 파일만 Read한다. 처음부터 패키지 전체를 읽지 않는다

시험 함정 · 흔한 오해

오해함수가 쓰이는 파일을 찾으려면 Glob에 함수 이름을 넣으면 된다.
사실Glob은 경로만 본다. 파일 안의 내용은 Grep(또는 Bash의 grep)으로 찾는다.
오해Edit는 비슷한 문자열이면 알아서 맞춰 준다.
사실정확히 일치하고 한 번만 나와야 한다. 정규식·유사 매칭이 없다.
오해Grep과 Glob은 둘 다 .gitignore를 따른다.
사실Grep은 무시된 파일을 건너뛰지만 Glob은 기본적으로 포함한다(CLAUDE_CODE_GLOB_NO_IGNORE=false로 바꿀 수 있다).
오해Write로 기존 파일 끝에 몇 줄을 덧붙일 수 있다.
사실Write는 전체 내용으로 덮어쓴다. 부분 변경은 Edit다.

자가 점검 퀴즈

점수 0 / 6
Q1내용 검색
운영 로그에 PAYMENT_GATEWAY_TIMEOUT이 찍혔다. 이 코드를 만드는 곳을 저장소 전체에서 찾아야 한다.알맞은 도구는?
정답 (C)

파일 안의 문자열을 찾는 것은 내용 검색이다. A는 파일 이름에 그 문자열이 들어간 경우만 찾는다. B는 컨텍스트를 낭비한다.

Q2경로 검색
여러 패키지에 흩어진 *.stories.tsx 파일 목록을 얻으려 한다. 가장 직접적인 방법은?
정답 (A)

이름 규칙으로 파일을 찾는 것은 Glob의 일이다. B는 내용에 "stories"가 들어간 줄을 주므로 목적과 다르고, C의 Read는 디렉터리를 읽지 못한다.

Q3Edit 실패
설정 파일에서 staging 섹션의 replicas: 2만 4로 바꾸려는데, Edit가 "old_string이 3번 나온다"며 실패했다.다음 조치로 가장 알맞은 것은?
정답 (D)

고유성 검사를 통과하도록 문맥을 넓히는 것이 기본 복구다. A는 세 섹션을 모두 바꿔 의도와 다르다. B는 다른 변경을 잃을 위험이 있고, 기존 파일을 덮어쓸 때도 먼저 읽기 규칙이 적용된다.

Q4Read + Write
Edit 대신 Read 후 Write로 파일을 바꾸는 것이 합리적인 경우는?
정답 (B)

Read로 현재 내용을 모두 확보한 뒤 Write로 통째로 쓰는 방법은 부분 치환이 어려울 때 확실하다. A·D처럼 범위가 분명한 수정은 Edit가 맞고, C도 Write는 덧붙이기가 아니라 전체 덮어쓰기이므로 Edit가 더 알맞다.

Q5재export 추적
toMinorUnits의 시그니처를 바꾸려 한다. 이 함수는 packages/money/src/index.ts에서 별칭으로도 재export된다. Grep toMinorUnits 결과가 예상보다 적다.누락 없이 호출부를 찾는 방법은?
정답 (A)

외부 코드는 래퍼가 내보낸 이름(별칭 포함)으로 쓴다. 공개 경계에서 이름 목록을 얻고 각각 검색해야 누락이 없다. D는 별칭 사용처를 놓친 채 결론을 내리는 대표 오답이다.

Q6.gitignore
빌드 산출물 폴더 dist/는 .gitignore에 있다. Grep으로 검색할 때는 dist/ 파일이 나오지 않았는데, Glob **/*.js에는 나왔다.이유는?
정답 (C)

두 도구의 .gitignore 처리가 다르다. Glob 결과는 수정 시각 순으로 정렬될 뿐 최근 파일로 거르지 않으며(A), 최대 100개에서 잘린다.
