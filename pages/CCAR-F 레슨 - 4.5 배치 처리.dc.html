Message Batches API와 배치 전략

50% 할인 · 최대 24시간 · 지연 SLA 없음 · custom_id · 제출 주기 계산 · 실패분 재제출

참고 레슨 · CertSafari 4.5  |  출제 도메인: 도메인 4 · Prompt Engineering & Structured Output (20%)

4.1 명시적 기준4.2 퓨샷4.3 구조화 출력4.4 검증·재시도4.5 배치 처리4.6 다중 리뷰

모든 요청에 즉시 응답이 필요하지는 않다. 야간 리포트, 주간 감사, 대량 평가처럼 결과를 몇 시간 뒤에 받아도 되는 작업은 Message Batches API로 보내면 비용이 절반으로 준다. 시험은 어떤 워크플로를 배치로 보내고 어떤 것을 동기 호출로 남길지, SLA에서 제출 주기를 어떻게 정할지, 실패한 요청만 골라 다시 내는 방법을 묻는다. 배치는 기다림을 비용 절감과 맞바꾸는 선택이며, 완료 시간은 보장되지 않는다.

습득 포인트
  • 비용 50% 절감, 대부분 1시간 안에 끝나지만 최대 24시간이 걸리고 만료될 수도 있다 — 지연 SLA가 없다
  • 블로킹 워크플로(머지 전 검사)는 동기 API, 지연을 견디는 작업(야간·주간 분석)은 배치
  • 배치의 요청 하나는 Messages 호출 한 번이다 — 우리 코드가 실행하는 도구를 요청 도중에 돌려 결과를 넣을 수 없다
  • custom_id로 요청과 결과를 맞춘다 (결과 순서는 보장되지 않는다)
  • SLA에서 제출 주기를 역산하고, 실패분만 custom_id로 골라 수정한 뒤 재제출한다
  • 대량 제출 전에 표본으로 프롬프트를 다듬어 첫 통과율을 높인다
01

배치의 계약 조건

What you gain, what you give up
항목내용 (2026년 10월 문서 기준)
비용모든 사용량이 표준가의 50%. 예: Claude Sonnet 5.5는 입력 $2 → $1 / MTok, 출력 $10 → $5 / MTok. prompt caching 할인과 중첩된다
처리 시간대부분 1시간 안에 끝난다. 결과는 모든 요청이 끝나거나 24시간이 지나면 받을 수 있고, 24시간 안에 처리되지 못한 요청은 expired가 된다
크기배치 하나에 요청 100,000개 또는 256 MB 중 먼저 닿는 쪽까지
결과 보관배치 생성 후 29일. 결과는 .jsonl로 스트리밍해 받는다
쓸 수 없는 파라미터stream: true, fast mode의 speed, 서버 측 fallbacks, max_tokens: 0
수정제출 후에는 고칠 수 없다. 취소하고 새로 제출한다
레이트 리밋Batches HTTP 요청 수와 처리 대기 중인 요청 수에 별도 한도가 있고, Messages API 한도에는 영향을 주지 않는다
batch = client.messages.batches.create(requests=[ {"custom_id": f"call-{c.id}", # 1~64자, 영숫자·-·_ 만 "params": {"model": "claude-sonnet-5-5", "max_tokens": 1024, "system": QA_RUBRIC, "messages": [{"role": "user", "content": c.transcript}]}} for c in yesterdays_calls ]) # processing_status: in_progress → ended (취소 시 canceling → ended)

배치 요청들이 같은 긴 system 프롬프트를 공유하면 캐싱으로 비용을 더 줄일 수 있다. 다만 요청이 동시에, 순서 없이 처리되므로 캐시 적중은 best-effort이고, 문서는 5분보다 오래 걸릴 수 있는 배치에 1시간 캐시 사용을 고려하라고 권한다.

02

지연 요구로 API 고르기

Who is waiting for the answer?

판단 질문은 하나다. 결과가 나올 때까지 누군가 멈춰 서서 기다리는가? 기다린다면 배치의 "대부분 1시간"은 아무것도 보장하지 않는다.

워크플로결과를 기다리는 쪽선택
PR 머지 전에 통과해야 하는 보안 리뷰 체크개발자와 CI 파이프라인이 멈춰 대기동기 Messages API
고객 채팅 응답고객이 실시간 대기동기
전날 상담 통화 전체의 품질 채점다음 날 아침 회의배치
주간 오픈소스 라이선스·의존성 감사주간 리포트배치
프롬프트 수정 후 3,000건 회귀 평가다음 날 배포 판단배치
야간 테스트 케이스 초안 생성다음 날 출근한 개발자배치
시험 판단 기준
  • "머지 전", "사용자 응답", "차단(blocking)" → 동기. 배치를 쓰면 최악의 경우 24시간을 기다리거나 만료된다
  • "야간", "주간", "다음 날까지", "대량", "비용 절감" → 배치
  • 배치는 전체가 끝나야(또는 24시간이 지나야) 결과를 받는다 — 일부 결과를 먼저 쓰는 흐름이 필요하면 배치를 더 작게 나눈다
03

배치 요청 하나 = Messages 호출 한 번

No client-side tool loop inside a request

배치 안의 각 요청은 서로 독립적으로, 한 번의 Messages 호출로 처리된다. 요청에 다회 대화 이력이나 도구 정의를 넣는 것은 괜찮다. 하지만 Claude가 우리 쪽 코드가 실행해야 하는 도구(client tool)를 부르면, 그 요청은 stop_reason: "tool_use"로 끝난 결과가 될 뿐이다. 처리 도중 우리 코드가 끼어들어 도구를 실행하고 tool_result를 넣어 줄 통로가 없다. 이어 가려면 도구를 실행한 뒤 다음 요청(새 배치 또는 동기 호출)을 보내야 하고, 왕복마다 최대 24시간이 더해진다.

BAD · 도구 왕복을 배치에 맡김
requests = [{"custom_id": f"sku-{s}", "params": {..., "tools": [get_inventory], "messages": [{"role": "user", "content": f"{s}의 재고를 조회해 발주량을 정하라"}]}}]

결과 대부분이 tool_use에서 멈춘다. 발주량은 하루 뒤 두 번째 배치에서야 나온다.

GOOD · 필요한 데이터를 미리 조회해 넣음
stock = inventory_db.lookup(skus) # 제출 전에 실행 requests = [{"custom_id": f"sku-{s}", "params": {..., "messages": [{"role": "user", "content": f"<stock>{stock[s]}</stock> 발주량을 정하라"}]}}]

한 번의 호출로 끝나는 모양으로 바꿔 배치에 맞춘다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 "배치 API는 한 요청 안에서 다회 도구 호출을 지원하지 않는다(요청 도중 도구를 실행해 결과를 돌려줄 수 없다)"고 쓴다. 우리 코드가 실행하는 client tool에 대해서는 지금도 맞는 말이다. 다만 현재 문서는 web search · web fetch · code execution · MCP connector 같은 server tool이 배치 안에서도 동기 API와 같은 서버 측 에이전트 루프로 돈다고 명시한다. 오히려 연결 유지 부담이 없어 한 턴에 더 많이 반복할 수 있고, 끝나지 않은 턴은 pause_turn으로 돌아와 후속 요청으로 이어 간다. "배치에서는 도구를 전혀 못 쓴다"로 외우면 틀린다.

04

SLA에서 제출 주기 역산하기

Submission cadence from the SLA

문서가 쌓이는 대로 모아 두었다가 정해진 시각에 배치로 낸다고 하자. 가장 운이 나쁜 문서는 제출 직후에 도착해 한 주기 내내 기다리고, 배치 처리에도 최대 시간이 걸린다.

최악 지연 = 다음 제출까지의 대기(≤ 제출 간격) + 배치 처리(≤ 24h) + 후처리 제출 간격 ≤ SLA − 24h − 후처리 시간 − 안전 여유
  1. 보험 청구 서류: SLA "도착 후 36시간 안에 판정 결과", 후처리(검증·적재) 2시간, 안전 여유 2시간
  2. 제출 간격 ≤ 36 − 24 − 2 − 2 = 8시간 → 하루 3회(00시·08시·16시) 제출
  3. SLA가 24시간 + 후처리보다 짧으면 배치만으로는 보장할 수 없다 → 동기 API, 또는 배치를 기본으로 두고 마감이 가까운 건은 동기로 돌리는 혼합 구성

만료도 설계에 넣는다. 24시간 안에 처리되지 못한 요청은 expired로 돌아오는데, 그 시점이면 SLA 여유가 거의 남지 않는다. 만료분은 다음 배치를 기다리지 말고 동기 API로 즉시 처리하는 경로를 미리 만들어 두는 편이 안전하다.

05

결과 처리와 실패분만 재제출

Resubmit by custom_id
결과 유형의미과금조치
succeeded메시지가 생성됨과금내용 검증. stop_reason이 max_tokens면 한도를 늘려 재제출
errored · invalid_request_error요청 본문이 잘못됨 (예: 입력이 컨텍스트 창을 넘는 "prompt is too long")없음요청을 고쳐서 재제출 — 긴 문서는 나눈다
errored · 그 밖의 오류내부 서버 오류 등없음그대로 재제출 가능
canceled취소로 모델에 보내지지 않음없음필요하면 재제출
expired24시간 안에 처리되지 못함없음재제출 (SLA가 급하면 동기)
resubmit_as_is, needs_fix = [], [] for r in client.messages.batches.results(batch.id): # 순서 보장 없음 → custom_id로 매칭 res = r.result if res.type == "succeeded": store(r.custom_id, res.message) elif res.type == "errored" and res.error.error.type == "invalid_request_error": needs_fix.append(r.custom_id) # 예: claim-20817 → claim-20817-p1, -p2로 분할 else: # 서버 오류 · expired · canceled resubmit_as_is.append(r.custom_id)

요청은 서로 독립이라 한 요청의 실패가 다른 요청에 영향을 주지 않는다. 그러니 배치 전체를 다시 낼 이유가 없다. 실패한 custom_id만 골라 새 배치로 낸다. 문서를 쪼갤 때는 claim-20817-p2처럼 원래 ID에 조각 번호를 붙여 나중에 다시 합칠 수 있게 한다.

대량 제출 전 표본 다듬기

배치는 제출 후 수정할 수 없고, 재제출마다 처리 시간이 다시 든다. 4만 건을 내기 전에 수십~백 건 표본을 먼저 돌려 출력 형식과 검증 통과율을 보고 프롬프트를 고친다. 문서도 요청 형태 하나를 Messages API로 먼저 시험해 검증 오류를 피하라고 권한다.

시험 함정 · 흔한 오해

오해배치는 보통 1시간 안에 끝나니 머지 전 체크에 써도 된다.
사실1시간은 보장이 아니라 경향이다. 최대 24시간이 걸리거나 만료될 수 있으므로 블로킹 워크플로에는 동기 API를 쓴다.
오해결과 파일은 요청을 넣은 순서대로 나온다.
사실순서는 보장되지 않는다. 각 줄의 custom_id로 요청과 맞춘다.
오해일부 요청이 실패하면 배치 전체를 다시 제출해야 한다.
사실요청은 독립적으로 처리된다. 실패한 custom_id만 고쳐서 재제출하고, errored·canceled·expired 요청에는 과금되지 않는다.
오해배치에서는 도구를 아예 쓸 수 없다.
사실server tool은 배치 안에서도 서버 측 루프로 돈다. 안 되는 것은 우리 코드가 실행하는 client tool을 요청 도중에 실행해 결과를 넣는 일이다.
