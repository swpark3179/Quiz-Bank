어제와 똑같이 돌던 시스템이 오늘 다르게 행동한다면, 코드보다 먼저 구성을 의심해야 한다. 지시 파일이 하나 더 로드됐거나, 상위 범위의 설정이 내 값을 덮었거나, 별칭이 새 모델을 가리키게 됐거나, 의존 플러그인이 새 버전으로 올라갔을 수 있다. 이 레슨의 축은 하나다. 값을 고정(pin)할 것인가, 최신을 따라가는 포인터(pointer)로 둘 것인가. 시험은 CLAUDE.md와 settings가 어떤 순서로 쌓이는지, 관리형 설정이 무엇을 강제하고 무엇은 못 하는지, 어떤 모델 ID와 에이전트 참조가 정말 고정인지를 묻는다.

습득 포인트
  • 모델·프롬프트·플러그인 의존성 각각에서 무엇이 핀이고 무엇이 포인터인지 구분한다
  • CLAUDE.md 네 범위의 위치, 시작 시 로드와 지연 로드, AGENTS.md가 읽히는 조건을 설명한다
  • settings의 우선순위(관리형 → 명령줄 → local → project → user)와 목록 병합, 관리형 설정의 예외를 적용한다
  • 실행 중 세션에 바로 반영되는 설정과 세션 시작 때만 읽는 설정을 구분한다
  • 날짜 없는 ID·날짜 ID·API 별칭·Claude Code 별칭의 차이와 model·availableModels·enforceAvailableModels의 역할을 안다
  • Managed Agents 프롬프트 버전을 고정·승격·롤백하고, 플러그인 의존성 범위가 어떻게 해석되는지 예측한다
01

핀과 포인터

Pin versus pointer

핀은 누군가 직접 고치기 전까지 같은 대상을 가리킨다. 포인터는 해석하는 시점의 '현재 최신'을 가리킨다. 재현성과 회귀 방지가 중요하면 핀을, 자동 개선을 받는 것이 중요하면 포인터를 고른다. 프로덕션에서는 보통 핀을 두고, 새 버전은 평가를 거친 뒤 핀을 옮겨 받아들인다.

영역핀 (고정)포인터 (움직임)
모델 (API)4.6 세대 이후 ID(claude-sonnet-4-6, claude-opus-5-5), 그 이전의 날짜 ID(claude-haiku-4-5-20251001)4.6 이전 모델의 API 별칭(claude-sonnet-4-5): 그 마이너 버전의 최신 날짜 스냅샷
모델 (Claude Code)전체 모델 이름, ANTHROPIC_DEFAULT_OPUS_MODEL 같은 별칭 고정 변수opus·sonnet·haiku·best 별칭
프롬프트 (Managed Agents){"type": "agent", "id": …, "version": 3}에이전트 ID 문자열만 넘김: 최신 버전
플러그인 의존성=2.1.0 정확한 핀범위 없음(마켓플레이스 최신), ~2.1.0·^2.0(범위 안의 최신 태그)
02

CLAUDE.md 범위와 로드 시점

Scopes, stacking and lazy loading
범위위치공유 대상
관리형 정책macOS /Library/Application Support/ClaudeCode/CLAUDE.md, Linux·WSL /etc/claude-code/CLAUDE.md, Windows C:\Program Files\ClaudeCode\CLAUDE.md조직의 모든 사용자
사용자~/.claude/CLAUDE.md나 (모든 프로젝트)
프로젝트./CLAUDE.md 또는 ./.claude/CLAUDE.md버전 관리로 팀 전체
로컬./CLAUDE.local.md (.gitignore에 추가)나 (이 프로젝트)

범위들은 서로 덮어쓰지 않고 이어 붙는다. 넓은 범위부터 로드되므로 프로젝트 지시가 사용자 지시보다 컨텍스트에서 뒤에 온다. 두 지시가 충돌하면 Claude가 어느 쪽을 따를지 정해져 있지 않으니, 충돌 자체를 없애야 한다. 디렉터리 트리에서는 작업 디렉터리와 그 위의 모든 디렉터리에서 CLAUDE.md와 CLAUDE.local.md를 찾는다. 모노레포 /repo/apps/checkout/에서 시작했다면 이렇게 로드된다.

파일로드 시점
/repo/CLAUDE.md → /repo/apps/CLAUDE.md → /repo/apps/checkout/CLAUDE.md시작할 때. 루트에서 작업 디렉터리 쪽으로 쌓이므로 가까운 파일이 마지막에 읽힌다. 각 디렉터리에서 CLAUDE.local.md는 CLAUDE.md 뒤에 붙는다
/repo/apps/checkout/legacy/CLAUDE.mdClaude가 legacy/ 안의 다른 파일을 읽거나 쓰거나 고칠 때. 시작 시점의 /context Memory files 목록에는 없다
운영 요령

파일당 200줄 이하를 목표로 하고, 일부 영역에만 필요한 지시는 paths 규칙으로 옮긴다. 블록 단위 HTML 주석(<!-- … -->)은 컨텍스트에 넣기 전에 제거되므로 관리자용 메모로 쓸 수 있다. 다른 팀의 상위 CLAUDE.md는 claudeMdExcludes로 건너뛸 수 있지만 관리형 CLAUDE.md는 제외할 수 없다. 관리형 CLAUDE.md는 안내용이며, 반드시 막아야 하는 행동은 관리형 settings의 permissions.deny로 강제한다.

AGENTS.md fallback and .claude/rules

Claude Code(v2.1.277 이상)는 다른 코딩 에이전트용으로 만든 AGENTS.md를 프로젝트 지시로 읽을 수 있다. 다만 기본값에서 AGENTS.md는 CLAUDE.md의 대체물이지 추가물이 아니다.

AGENTS.md만 있다AGENTS.md
작업 디렉터리나 그 위에 CLAUDE.md·.claude/CLAUDE.md·CLAUDE.local.md 중 하나가 있다CLAUDE.md 쪽만. AGENTS.md는 읽지 않는다
CLAUDE.md 안에 @AGENTS.md 가져오기가 있다CLAUDE.md와, 가져오기로 포함된 AGENTS.md

판정에서 ~/.claude/CLAUDE.md, 조직의 관리형 CLAUDE.md, .claude/rules/ 파일은 세지 않는다. 이들은 AGENTS.md와 함께 로드된다. 반대로 개인 메모용 CLAUDE.local.md를 하나 만들면 그것이 판정에 걸려 AGENTS.md가 더는 읽히지 않는다. 둘 다 읽게 하려면 CLAUDE.md에 @AGENTS.md를 넣거나, /config의 Project instructions를 다음 값 중 하나로 바꾼다.

04

settings.json 범위와 우선순위

Precedence and managed settings

settings는 CLAUDE.md와 달리 키 단위로 이긴 값 하나가 적용된다. 같은 키가 여러 곳에 있으면 가장 높은 단계의 값을 쓴다.

① MANAGED
서버 관리형·MDM/OS 정책·managed-settings.json
>
② COMMAND LINE
--settings로 준 JSON (그 세션만)
>
③ LOCAL
.claude/settings.local.json
>
④ PROJECT
커밋한 .claude/settings.json
>
⑤ USER
~/.claude/settings.json
규칙내용
목록은 합쳐진다permissions.allow 같은 목록 키는 파일마다 항목을 더한다. 예외로 관리형 설정이 정한 availableModels는 그대로 쓰고 하위 범위의 항목을 무시하며, fallbackModel은 순서가 의미이므로 가장 높은 파일의 값을 통째로 쓴다
환경 변수는 단계가 아니다키마다 따로 정한다. 셸에서 export한 ANTHROPIC_MODEL은 어느 파일의 model보다 우선하고, ANTHROPIC_DEFAULT_MODEL은 어떤 파일도 model을 정하지 않을 때만 쓰인다
보안 키의 예외몇몇 제한 키는 낮은 범위의 더 엄격한 값을 관리형보다 존중한다. 예: disableClaudeAiConnectors: true, permissions.blockReadsOutsideWorkingDirectories: true는 어느 범위에서든 켜진다
저장소 파일이 못 하는 것permissions.defaultMode의 auto·bypassPermissions는 project·local 파일에서 효과가 없다. 커밋한 파일의 allow 규칙은 각 팀원이 폴더를 신뢰한 뒤에 적용되고, deny·ask는 바로 적용된다

개인 예외는 커밋 없이 .claude/settings.local.json에 둔다. 팀 파일이 "model": "claude-sonnet-5"여도 내 local 파일에 다른 모델을 적으면 내 세션만 바뀐다. 관리형 설정은 내 파일이나 --settings로 덮을 수 없고, /status의 Setting sources 줄에서 어떤 관리형 소스가 적용됐는지 확인한다.

05

고친 설정은 언제 반영되나

Hot reload vs read-once keys

Claude Code는 settings 파일을 지켜보다가 바뀌면 다시 읽는다. 그래서 대부분의 수정은 재시작 없이 실행 중 세션에 반영된다. 몇몇 키는 세션 시작 때 한 번만 읽는다.

저장하면 바로 반영

permissions, hooks, apiKeyHelper 같은 자격 증명 도우미. 세션 중에 새로 만든 settings 파일도 폴더가 있었다면 로드된다. user·project·local·관리형 파일이 대상이고, 파일 변경을 감지할 때마다 ConfigChange 훅이 돈다.

시작할 때만 읽음

model, effortLevel, modelSettings. 파일을 고쳐도 지금 세션은 그대로이고 다음 세션부터 적용된다. 지금 바꾸려면 /model, /effort를 쓴다. MDM이나 claude.ai 콘솔로 오는 관리형 설정은 저장 즉시가 아니라 정해진 주기로 도착한다.

/model은 즉시 전환하고 그 선택을 사용자 settings에 새 세션의 기본값으로 저장한다. 선택기에서 s를 누르면 저장하지 않고 이번 세션만 바꾼다. 모델마다 프롬프트 캐시가 따로라서 전환 직후 첫 요청은 대화 전체를 캐시 없이 다시 읽는다.

참고 레슨과 다른 점

CertSafari 본문은 "모델을 바꾸는 데 재시작은 필요 없다"고 하지만, 체크포인트는 settings 파일의 model을 고치면 재시작이 필요하다고 설명해 서로 어긋난다. 공식 Settings 문서 기준으로는 둘 다 일부만 맞다. /model은 실행 중에 바로 바꾸고, 파일의 model 키는 세션 시작 때만 읽으므로 새 세션에서 적용된다. 권한·훅 수정은 재시작 없이 반영된다.

07

시작 모델과 모델 제한은 다르다

model vs availableModels vs enforcement

조직이 "이 팀은 Sonnet과 Haiku만 쓴다"를 강제하고 싶을 때 관리형 model만 정하는 것은 답이 아니다. model은 처음 선택일 뿐 잠금이 아니어서, 사용자는 /model을 열어 Default를 고를 수 있다. 아래는 조직이 배포하는 관리형 설정의 예다. settings 파일은 엄격한 JSON이라 // 주석을 넣으면 구문 오류가 된다.

{ "model": "sonnet", "availableModels": ["sonnet", "haiku"], "enforceAvailableModels": true }
키역할
model세션이 시작할 때 활성인 모델. project·관리형 값은 다음 실행 때 다시 적용되고, /model은 이번 세션만 바꾼다
availableModels허용 목록. 계열(sonnet), 버전 접두사(claude-sonnet-4-5), 전체 ID를 쓸 수 있다. /model·--model·ANTHROPIC_MODEL·model 키·ANTHROPIC_DEFAULT_MODEL·재개 세션에 모두 적용된다. 막힌 선택은 /model에서 거부되고, 플래그·환경 변수·model 키는 시작 시 경고와 함께 교체된다
enforceAvailableModelsv2.1.175 이상. 이것 없이 availableModels만 두면 Default 옵션은 계정의 기본 모델 그대로다. 켜면 계정 기본값이 목록 밖일 때 Default가 목록에서 허용되고 쓸 수 있는 첫 항목으로 풀린다
deniedModelsv2.1.283 이상, 관리형에서만 읽는다. 허용 목록이 허락해도 차단한다. availableModelsMatch: "exact"와 짝지으면 항목이 정확히 그 버전만 허용한다
시험 판단 축
  • "사용자가 다른 모델을 고르지 못하게"는 availableModels(필요하면 deniedModels), "Default도 목록 안에서"는 enforceAvailableModels까지 필요하다
  • 관리형 설정이 availableModels를 정하면 그 목록만 적용된다. 사용자·프로젝트 파일에 항목을 더해도 늘어나지 않는다
  • availableModels: []는 이름으로 고르는 선택을 모두 막고, 이때 enforceAvailableModels는 효과가 없다
08

프롬프트 버전: 고정·승격·롤백

Managed Agents versioning

Claude Managed Agents의 에이전트는 모델·시스템 프롬프트·도구를 묶은 버전이 있는 구성이다. agents.create는 version 1을 만들고, 구성을 바꾸는 agents.update마다 새 버전이 생긴다. 바뀐 것이 없는 업데이트는 새 버전을 만들지 않고 기존 버전을 돌려준다. 옛 버전은 서버에 남고 agents.versions.list로 전체 이력을 본다.

agent = client.beta.agents.create( name="Refund triage", model="claude-sonnet-5-5", system=PROMPT_V1, ) # agent.version == 1 agent = client.beta.agents.update( agent.id, version=agent.version, # 그사이 누가 고쳤으면 409 system=PROMPT_V2, ) # agent.version == 2 session = client.beta.sessions.create( agent={"type": "agent", "id": agent.id, "version": cfg.refund_agent_version}, # 설정에서 읽은 핀 environment_id=ENV_ID, )
① CREATE
v1 생성
→
② EVAL
v1로 고정한 세션으로 라벨 데이터 채점
→
③ UPDATE
v2 생성. 아직 트래픽은 v1
→
④ PROMOTE
v2 평가 통과 후 설정의 핀을 2로 변경
→
⑤ ROLLBACK
회귀가 보이면 핀을 1로 되돌림. 재배포·업데이트 없음
sessions.create의 agent실행되는 버전
ID 문자열생성 시점의 최신 버전. 누가 update를 부르면 다음 세션부터 새 버전
{"type": "agent", "id", "version"}지정한 버전으로 고정
{"type": "agent_with_overrides", …}지정 버전(생략하면 최신)에 이 세션만 모델·프롬프트·도구를 덮어씀. 새 버전을 만들지 않는다
승인 절차는 직접 만든다

agents.update에는 승인 단계가 없어 워크스페이스의 어떤 키로도 부를 수 있다. 그래서 프로덕션 호출부는 명시적 버전을 고정하고, 승격은 그 버전 번호를 바꾸는 설정 변경으로 만들어 일반 코드 리뷰를 거치게 한다. 새 버전 생성은 승격 전까지 트래픽을 받지 않으므로 위험이 낮다. version 인자를 주면 낙관적 동시성 검사가 되어 불일치 시 409를 받고, 생략하면 마지막 쓰기가 조용히 이긴다.

플러그인 의존성 범위와 정확한 핀

Dependency ranges, tags and conflicts

플러그인은 .claude-plugin/plugin.json의 dependencies 배열로 다른 플러그인에 기댈 수 있다. 항목은 이름 문자열이거나 name·version·marketplace를 가진 객체다. 범위를 두지 않으면 의존 플러그인은 마켓플레이스가 새 릴리스를 낼 때마다 따라 올라가고, 그 릴리스가 내가 부르는 MCP 도구 이름을 바꾸면 내 플러그인이 깨진다.

{ "name": "incident-kit", "version": "1.4.0", "dependencies": [ "pager-bridge", { "name": "log-search", "version": "~3.2.0" }, { "name": "status-page", "version": "=1.0.2" } ] }
선언받는 버전
"pager-bridge"마켓플레이스가 제공하는 버전을 계속 따라간다
~3.2.03.2.x 패치는 받고 3.3으로는 가지 않는다
^3.0같은 주 버전 3.x 안에서 최신
=1.0.2정확히 그 버전. 이 플러그인이 설치되어 있는 동안 자동 업데이트도 더 새 버전을 건너뛴다

범위는 plugin.json의 version이 아니라 의존 플러그인 저장소의 git 태그 <plugin-name>--v<version> 중 범위를 만족하는 가장 높은 것으로 풀린다. 그 커밋의 plugin.json이 뒤처져 있어도 태그의 버전으로 검사한다. 맞는 태그가 없을 때 자체 저장소를 가진 플러그인은 설치가 실패하고, 마켓플레이스 안에 상대 경로로 들어 있는 플러그인은 현재 사본을 설치한 뒤 로드할 때 범위를 검사해 벗어나면 의존하는 쪽을 비활성화한다. 릴리스 태그는 claude plugin tag --push로 만든다.

A의 요구B의 요구결과
^2.0>=2.1둘을 모두 만족하는 가장 높은 2.x 태그 하나를 설치. 두 플러그인 모두 로드
~2.1~3.0B 설치가 has conflicting version requirements로 실패. A와 의존성은 그대로
=2.1.0없음2.1.0에 머문다. A가 있는 동안 자동 업데이트가 새 버전을 건너뛴다
시험 판단 축
  • 범위는 2.0.0-beta.1 같은 프리릴리스를 고르지 않는다. 받으려면 ^2.0.0-0처럼 명시한다
  • npm·archive·command 소스처럼 git이 아닌 의존성은 범위가 내려받을 버전을 고르지 못하고, 로드할 때 그 plugin.json의 version으로 검사만 한다
  • 다른 마켓플레이스의 플러그인에 의존하려면 설치하는 플러그인이 있는 마켓플레이스의 marketplace.json에 allowCrossMarketplaceDependenciesOn을 둔다

시험 함정 · 흔한 오해

오해저장소에 AGENTS.md와 CLAUDE.md가 함께 있으면 Claude Code는 둘 다 읽는다.
사실기본값에서 AGENTS.md는 작업 디렉터리와 그 위에 CLAUDE.md·.claude/CLAUDE.md·CLAUDE.local.md가 없을 때만 읽힌다. 둘 다 읽히게 하려면 @AGENTS.md를 가져오거나 claude-md-and-agents-md를 쓴다.
오해관리형 settings에 model을 넣으면 모든 사용자가 그 모델에 묶인다.
사실관리형 model은 시작 기본값이다. 제한은 availableModels·deniedModels가 하고, Default 옵션까지 묶으려면 enforceAvailableModels가 필요하다.
오해claude-sonnet-4-6처럼 날짜가 없는 ID는 새 버전이 나오면 자동으로 올라간다.
사실4.6 세대부터는 날짜 없는 ID가 곧 고정 스냅샷이다. 업데이트는 새 ID로 나온다. 움직이는 것은 4.6 이전 모델의 API 별칭과 Claude Code의 opus·sonnet 같은 별칭이다.
오해sessions.create에 평가를 마친 에이전트의 ID만 넘기면 그 버전으로 계속 돈다.
사실ID 문자열은 최신 버전으로 풀린다. 누가 update를 부르면 다음 세션부터 바뀐다. 고정하려면 {"type": "agent", "id", "version"} 객체를 넘긴다.
오해settings 파일의 model을 고치면 권한 규칙처럼 실행 중인 세션에 바로 반영된다.
사실model은 세션 시작 때만 읽는다. 지금 바꾸려면 /model을 쓴다. 권한·훅 수정은 재시작 없이 반영된다.
오해플러그인 의존성의 버전 범위는 의존 플러그인의 plugin.json version 필드와 비교된다.
사실git 기반 소스는 <plugin-name>--v<version> 태그와 비교해 가장 높은 일치 태그를 설치한다. 태그를 달지 않으면 범위가 풀리지 않는다.
