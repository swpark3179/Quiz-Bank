습득 포인트

  • 정밀 수정에는 Edit를 쓰고, 대규모 마이그레이션은 claude -p 루프를 소수 파일로 먼저 시험한 뒤 확장한다
01

Messages API는 JSON을 주고받는 REST 엔드포인트다

Endpoint, headers, size limits, errors

Claude API는 https://api.anthropic.com의 RESTful API이고, 대화 호출은 POST /v1/messages에 JSON 본문을 보내는 것이다. SDK를 쓰면 인증·버전·content-type 헤더를 자동으로 붙여 주지만, 직접 HTTP 래퍼를 만들면 이것을 손으로 챙겨야 한다.

curl https://api.anthropic.com/v1/messages \ -H "Authorization: Bearer $ANTHROPIC_API_KEY" \ -H "anthropic-version: 2026-10-21" \ -H "content-type: application/json" \ -d '{"model": "claude-sonnet-5-5", "max_tokens": 512, "messages": [{"role": "user", "content": "반품 규정을 세 줄로 요약해 줘"}]}'
요청 헤더필수 여부설명
Authorization: Bearer <token>x-api-key가 없으면 필수API 키 또는 워크로드 아이덴티티 페더레이션으로 받은 단기 토큰
x-api-key선택Authorization의 레거시 대안. 여전히 지원된다
anthropic-version필수API 버전. 최신은 2026-10-21이고 2023-06-01도 목록에 남아 있다
content-type필수application/json
anthropic-workspace-id조건부워크스페이스에 묶이지 않은 키를 쓸 때 필수. 워크스페이스 전용 키는 생략하면 그 워크스페이스에서 실행. SDK도 이 헤더는 자동으로 붙이지 않는다

응답 헤더의 request-id(예: req_…)는 지원 문의 때 쓰는 요청 식별자이고, 오류 본문에도 request_id로 들어간다. 오류는 언제나 {"type": "error", "error": {"type", "message"}} 모양의 JSON이다. 대표 상태 코드는 400 invalid_request_error, 401 인증, 403 권한, 404, 413 request_too_large, 429 rate_limit_error, 500 api_error, 504 timeout_error, 529 overloaded_error다.

요청 크기 한도값
Claude API · Messages, Token Counting128MB
Claude API · Message Batches / Files256MB / 500MB
Claude API · Sessions, Agents, Environments32MB
Claude Platform on AWS, Anthropic 관리형 Google Cloud, FoundryMessages·Token Counting 32MB
Bedrock / Google 관리형 Google Cloud20MB / 30MB
참고: 32MB는 어디의 한도인가

CertSafari 1부는 Messages·Token Counting 한도를 32MB로 적었지만, 공식 API 개요와 오류 문서는 1차 Claude API의 Messages·Token Counting 한도를 128MB로 적는다. 32MB는 Claude Platform on AWS·Anthropic 관리형 Google Cloud·Foundry의 Messages 한도이자 Claude API의 Sessions·Agents·Environments 한도다. 이 가이드는 공식 문서를 따른다.

버전 헤더가 바꾸는 것

2026-10-21부터는 temperature·top_p·top_k를 보내면 모든 모델에서 400이 난다. 각 SDK 메이저 버전은 기본으로 하나의 API 버전을 보낸다(Python SDK는 2.0.0부터 2026-10-21). 그래서 SDK 메이저 버전을 올리는 일은 API 버전을 올리는 변경으로 다뤄야 한다.

02

같은 요청, 기다리는 방식만 넷

Choosing a call pattern by workload shape

네 방식 모두 같은 요청 본문을 보내고 같은 Message 객체를 얻는다. 바뀌는 것은 결과를 기다리는 방법뿐이므로, 고르는 기준은 지연 허용치와 작업량의 모양이다.

방식어떻게 기다리나맞는 작업
블로킹 호출messages.create가 끝날 때까지 스레드가 멈춤짧은 스크립트, 순서대로 한 건씩 처리하는 배치 잡의 한 단계
비동기 클라이언트await 동안 이벤트 루프가 다른 일을 처리요청을 동시에 많이 받는 웹 서버·봇, 여러 호출을 겹쳐 보내는 서비스
스트리밍토큰이 생기는 대로 SSE로 받음사용자가 화면에서 답을 기다리는 채팅 UI, 출력이 긴 요청
제출 후 폴링Message Batches에 넣고 상태를 주기적으로 확인아무도 응답을 기다리지 않는 대량 작업. 비용 50%

어느 방식이든 API는 이전 턴을 기억하지 않는다. 대화를 이어 가려면 대화별 이력을 애플리케이션 저장소에 두고 매 요청에 전체를 담는다. 비동기 서버에서 여러 대화를 동시에 처리할 때는 대화마다 이력을 따로 두어, 한 코루틴이 다른 대화의 이력 목록에 메시지를 덧붙이지 않게 설계한다.

03

동기 호출과 비동기 클라이언트

Anthropic vs AsyncAnthropic, retries, timeouts

Python SDK는 동기 Anthropic과 비동기 AsyncAnthropic 두 클라이언트를 제공하고 인터페이스는 같다. 비동기 클라이언트의 messages.create는 대기 가능한(awaitable) 객체를 돌려주므로 코루틴 안에서 await를 붙여야 결과 Message를 얻는다.

import asyncio from anthropic import AsyncAnthropic client = AsyncAnthropic() # ANTHROPIC_API_KEY를 환경에서 읽음 async def triage(ticket: str) -> str: msg = await client.messages.create( # await 없으면 결과가 아니다 model="claude-haiku-5-5", max_tokens=200, messages=[{"role": "user", "content": ticket}], ) return next(b.text for b in msg.content if b.type == "text") async def main(tickets: list[str]) -> list[str]: return await asyncio.gather(*(triage(t) for t in tickets))
SDK 동작기본값과 조절법 (Python SDK 문서)
자동 재시도연결 오류, 408, 409, 429, 500 이상을 짧은 지수 백오프로 2번 재시도. retry-after 헤더를 따른다. max_retries로 바꾸거나 0으로 끈다
타임아웃기본 10분. timeout에 초 단위 실수나 세분화된 타임아웃 객체를 준다. 시간 초과는 APITimeoutError이고 역시 2번 재시도된다
오류 클래스상태 코드별 타입이 있다. 429는 RateLimitError, 500 이상은 InternalServerError, 연결 실패는 APIConnectionError. 문자열 매칭보다 타입으로 잡는다
비동기 처리량기본 HTTP 백엔드 대신 pip install "anthropic[aiohttp]" 후 http_client=DefaultAioHttpClient()를 넘기면 동시성이 좋아진다
요청 ID응답 객체의 _request_id 속성에 request-id 헤더 값이 들어 있다
04

긴 요청: 스트리밍하거나, 제출하고 폴링하거나

Long outputs, mid-stream errors, submit-and-poll

스트리밍은 화면용 기능만이 아니다. 출력이 길면 응답이 올 때까지 연결이 오래 놀게 되고, 일부 네트워크는 유휴 연결을 끊는다. 그래서 Python SDK는 비스트리밍 요청이 약 10분을 넘을 것으로 예상되면 ValueError를 낸다. stream=True를 쓰거나 timeout을 직접 지정하면 이 검사는 꺼진다. 사람이 보지 않는 긴 작업이라도 SDK가 스트림을 대신 소비하고 완성된 Message만 돌려주게 할 수 있다.

with client.messages.stream( # 야간 감사 보고서, 보는 사람 없음 model="claude-opus-5-5", max_tokens=96000, messages=[{"role": "user", "content": audit_prompt}], ) as stream: report = stream.get_final_message() # create()와 같은 Message 객체
재시도를 켰는데도 답이 중간에 끊긴다

스트리밍 응답은 HTTP 200으로 시작한 뒤에 실패할 수 있다. 사용량이 몰리면 스트림 안에 event: error로 overloaded_error가 오는데, 비스트리밍이었다면 529였을 오류다. 이때는 상태 코드 기반의 표준 오류 처리가 적용되지 않는다고 문서에 적혀 있다. 529 재시도 설정만으로는 막을 수 없다.

스트림 오류를 따로 처리한다

스트림을 읽는 코드에서 오류 이벤트(SDK에서는 스트림 반복 중 발생하는 예외)를 잡고, 받은 부분을 저장한 뒤 다시 요청하거나 이어 쓰기를 요청한다(2.3 05 참고). 모르는 이벤트 타입은 무시하도록 짠다.

연결을 오래 붙잡아 둘 이유조차 없다면 제출 후 폴링이 낫다. 오류 문서는 10분이 넘는 긴 요청에 스트리밍 또는 Message Batches를 권하는데, 배치는 끊기지 않는 연결 대신 결과를 폴링하므로 네트워크 위험이 줄어든다. 배치를 제출하면 응답의 배치 id를 DB에 저장해 두고, 프로세스가 재시작돼도 그 ID로 processing_status가 ended가 될 때까지 폴링을 이어 간다. 결과는 순서가 보장되지 않으므로 custom_id로 원래 요청과 맞춘다(배치 세부 규칙은 2.3 08·09).

브랜치·커밋·PR 흐름 속의 Claude Code

Plan, implement with a check, commit, open a PR

공식 문서의 권장 흐름을 이어 붙이면 다음과 같다. 핵심은 설계에 합의하기 전에 파일이 바뀌지 않게 하고, 통과·실패로 답하는 검사를 Claude 손에 쥐여 주는 것이다.

① 탐색
관련 파일을 찾고 동작 흐름을 질문
→
② 계획

→

테스트·빌드·린터를 돌려 통과할 때까지 수정, 실행한 명령과 출력이라는 증거 요구

독립 리뷰어코드를 쓴 세션과 다른 세션, 또는 /code-review가 띄우는 새 서브에이전트가 리뷰하면 작성 과정의 추론에 끌려가지 않는다
06

GitHub Actions에서 Claude Code 돌리기

claude-code-action, modes, who can trigger

Claude Code GitHub Actions는 anthropics/claude-code-action@v1 액션이다. 가장 쉬운 설정은 로컬 Claude Code에서 /install-github-app을 실행하는 것으로, GitHub 앱 설치·시크릿 등록·워크플로 PR 생성까지 해 준다(github.com 저장소만, 저장소 관리자 권한 필요). 수동으로 하려면 Claude GitHub 앱을 설치하고 ANTHROPIC_API_KEY(API 키) 또는 CLAUDE_CODE_OAUTH_TOKEN(claude setup-token으로 만든 구독 토큰) 시크릿을 넣은 뒤 예시 워크플로를 복사한다.

모드언제 이 모드가 되나결과가 남는 곳
대화형prompt 입력이 없을 때. 이슈·PR 댓글, PR 리뷰, 새 이슈 본문·제목의 트리거 문구(기본 @claude)를 기다린다트리거한 이슈·PR의 댓글로 진행 상황과 결과를 갱신
자동화prompt 입력이 있을 때. 멘션 없이 어떤 GitHub 이벤트(cron 포함)에서도 실행기본은 워크플로 실행 로그. 프롬프트가 지시하고 게시할 도구가 있을 때만 이슈·PR에 남긴다
name: Weekly TODO Digest on: schedule: - cron: "0 1 * * 1" # 매주 월요일 01:00 UTC jobs: digest: runs-on: ubuntu-latest timeout-minutes: 20 # 폭주 방지 permissions: contents: read id-token: write steps: - uses: actions/checkout@v6 with: fetch-depth: 1 - uses: anthropics/claude-code-action@v1 with: anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} prompt: "Summarize TODO and FIXME comments in src/ by module" claude_args: | --max-turns 8 --allowedTools "Read,Bash(grep *)"

위 워크플로는 prompt가 있으니 자동화 모드이고, 요약은 PR이 아니라 실행 로그에 남는다. 평문 프롬프트는 claude_args의 --allowedTools나 settings의 허용 규칙으로 도구를 주기 전까지 셸·GitHub API를 쓰지 못한다.

누가 실행을 일으킬 수 있나
  • 쓰기 권한: 이슈·PR 이벤트에서는 트리거한 사용자에게 저장소 쓰기 권한이 있어야 한다. 예외를 두려면 allowed_non_write_users와 직접 만든 github_token을 함께 준다. schedule처럼 작성자가 없는 이벤트는 이 검사를 건너뛴다
  • 사람 행위자: 모든 이벤트에서 봇 행위자는 allowed_bots에 없으면 거부된다. 봇끼리 서로 깨우는 무한 루프를 막는 장치다. 예약 실행은 cron을 마지막으로 바꾼 사용자에게 귀속되므로, 그 사용자가 봇이면 목록에 넣어야 한다
  • 기본 GITHUB_TOKEN으로 만든 커밋은 다른 워크플로를 트리거하지 않는다. Claude의 커밋에 CI가 안 돈다면 github_token 입력을 빼서 Claude GitHub 앱으로 인증하게 한다

비용은 GitHub Actions 실행 시간과 API 토큰 두 가지다. 구체적인 @claude 요청, 짧은 CLAUDE.md(매 실행마다 읽힌다), --max-turns, 잡 타임아웃, 동시 실행 제한으로 줄인다. Bedrock·Google Cloud·Foundry로 추론을 돌리려면 use_bedrock·use_vertex·use_foundry를 켜고 OIDC로 인증한다. @beta에서 올라올 때는 @v1로 바꾸고, mode를 지우고, direct_prompt를 prompt로, CLI 옵션은 claude_args로 옮긴다.

07

자동 PR 리뷰: 관리형 Code Review와 직접 만든 리뷰

Triggers, comment commands, where findings land

Code Review는 Team·Enterprise 플랜의 관리형 서비스다. 조직 Owner가 claude.ai 관리자 설정에서 켜면 Anthropic 인프라에서 여러 에이전트가 diff와 주변 코드를 읽고, 검증 단계로 오탐을 거른 뒤, 줄 단위 인라인 댓글·요약·Claude Code Review 체크 런을 남긴다. 리뷰는 PR을 승인하거나 막지 않고 체크 런도 실패로 끝나지 않는다. Zero Data Retention이나 HIPAA 구성을 쓰는 조직, CMEK 조직에서는 쓸 수 없다.

저장소별 Review runs리뷰가 도는 때와 비용
Once after PR creationPR을 열거나 다시 열거나 초안을 ready로 바꿀 때 한 번
After every pushPR 브랜치에 푸시할 때마다. 새로 추가한 저장소의 기본값이고 리뷰 횟수와 지출이 가장 많다. 비용은 PR 수가 아니라 푸시 수에 비례한다
Manual (@claude review)댓글로 요청할 때만. 트래픽이 많은 저장소에서 골라 리뷰할 때
댓글 명령동작
@claude review리뷰를 한 번 시작. 이후 푸시에 구독하지 않는다(2026년 7월 이전에는 구독도 했다)
@claude review always리뷰를 시작하고 그 PR을 이후 푸시마다 리뷰하도록 구독
@claude review stop푸시 구독만 해제. 리뷰를 시작하거나 진행 중인 리뷰를 취소하지 않는다

명령은 새 최상위 PR 댓글의 첫 줄에 있어야 하고, 쓰기 이상 권한이 있는 사람이 열린 PR에 달아야 한다. 봇 댓글은 리뷰를 시작하지 않는다. 초안과 포크 PR은 자동 리뷰가 건너뛰므로 댓글로 요청한다. 발견 사항은 Important(병합 전에 고칠 버그), Nit(사소함), Pre-existing(이번 PR이 만든 것이 아닌 기존 버그) 세 단계로 표시되고, 리뷰 강도는 Quick·Standard(기본)·Deep 중에서 고른다.

CLAUDE.md

모든 작업에 읽히는 프로젝트 지시. 리뷰는 이것을 프로젝트 맥락으로 읽고, 규칙 위반을 문제에 맞는 심각도의 발견 사항으로 올린다. 변경 파일의 상위 디렉터리에 있는 CLAUDE.md도 읽는다.

REVIEW.md

리뷰 전용 규칙. Important의 정의, Nit 개수 상한, 건너뛸 경로(생성 파일, CI가 이미 검사하는 것), 항상 볼 항목을 적는다. PR 자신의 변경이 아니라 base·기본 브랜치의 사본을 읽고, 심각도 낮추기·제외·Nit 상한은 기본 브랜치가 보호되어 있어야 지켜진다.

참고: CLAUDE.md 위반의 심각도

CertSafari는 CLAUDE.md 위반이 Nit로 표시된다고 적었지만, 현재 Customize Code Review 문서는 위반이 문제에 맞는 심각도로 올라간다고 하고, REVIEW.md로 위반을 Important로 격상할 수도 있다고 설명한다. 이 가이드는 공식 문서를 따른다.

플랜에 Code Review가 없거나 프롬프트·모델·트리거를 직접 정하고 싶으면 Actions에 code-review 플러그인을 설치해 돌린다. 이때 결과가 PR에 남으려면 두 가지가 필요하다.

- uses: anthropics/claude-code-action@v1 with: anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }} plugin_marketplaces: >- https://github.com/anthropics/claude-plugins-official.git plugins: "code-review@claude-plugins-official" prompt: >- # 접힌 문자열: 두 줄이 한 줄로 합쳐짐 /code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }} claude_args: >- --allowedTools "mcp__github_inline_comment__create_inline_comment"
  • --comment가 없으면 Claude는 PR에 아무것도 게시하지 않고, 발견 사항은 워크플로 실행 로그에만 있다
  • 인라인 댓글용 MCP 서버는 claude_args의 --allowedTools가 그 도구를 지정할 때만 시작된다. 스킬 frontmatter에 같은 도구가 있어도 이 줄을 지우면 안 된다
  • 공개 저장소에서는 포크 PR 실행에 시크릿이 전달되지 않아 같은 저장소 브랜치의 PR만 리뷰된다. 대화형 액션과 Code Review가 함께 있으면 @claude review가 액션도 깨우므로 액션의 trigger_phrase를 바꾼다
참고: 플러그인 마켓플레이스 이름

CertSafari 2부의 예시는 마켓플레이스 anthropics/claude-code와 code-review@claude-code-plugins를 쓰지만, 현재 GitHub Actions 문서의 리뷰 워크플로는 anthropics/claude-plugins-official 마켓플레이스와 code-review@claude-plugins-official를 쓴다. plugins 값의 @ 뒤는 저장소 URL이 아니라 마켓플레이스 매니페스트에 적힌 이름이다. 이 가이드는 공식 문서를 따른다.

로컬에서는 어떤 플랜에서든 세션 안에서 /code-review를 쓴다. --fix는 리뷰 뒤 발견 사항을 작업 트리에 적용하고(편집은 권한 모드를 따른다), --comment는 GitHub PR에 인라인 댓글로 올린다. 로컬 명령은 CLAUDE.md를 따르고 REVIEW.md는 읽지 않는다.

08

작게 리팩터링하고, 일괄 마이그레이션은 시험 후 확장

Edit vs Write, claude -p loops, migration discipline
도구하는 일고를 때
Editold_string을 new_string으로 바꾸는 정확한 문자열 치환. 정규식·퍼지 매칭 없음. old_string은 파일에서 정확히 한 번 나와야 하고, 여러 곳이면 문맥을 늘리거나 replace_all: true함수 이름 하나, 조건문 하나처럼 국소적인 변경
Write파일을 새로 만들거나 전체 내용으로 덮어쓴다. 덧붙이거나 병합하지 않는다새 파일, 통째로 다시 쓰는 파일. 부분 변경에는 Edit
Read · Bash파일 읽기 / 셸 명령 실행Bash는 정밀 편집용 도구가 아니다. 테스트 실행에 쓴다

리팩터링은 동작을 유지하라고 명시하고, 작게 테스트 가능한 단위로 나눠 단위마다 테스트를 돌린다. 수백 개 파일에 같은 기계적 변경을 할 때는 비대화형 claude -p를 셸 루프로 돌린다.

TOOLS="Read,Edit,Bash(npm test *),Bash(git add *),Bash(git commit *)" while read -r f; do out=$(claude --bare -p "Convert $f from callbacks to async/await, run its unit test, then commit. Reply OK or FAIL." \ --allowedTools "$TOOLS" \ --permission-mode dontAsk --max-turns 15) [ "$out" = "OK" ] || echo "$f" >> retry.txt # 실패만 따로 모음 done < handlers.txt
플래그역할
--bare훅·스킬·플러그인·MCP 서버·CLAUDE.md를 건너뛰어 어디서 돌려도 같게 동작. 필요한 규칙은 --append-system-prompt·--settings로 명시해 넘긴다
--allowedTools쓸 도구를 미리 승인. 커밋까지 하려면 Bash(git commit *)도 넣는다
--permission-mode dontAsk물어봐야 할 호출은 모두 거부해 실행이 멈춰 기다리지 않게 한다
--max-turns반복 상한. 상한에 닿은 실행은 오류로 끝난다
① 목록
바꿀 파일·작업 목록을 만든다
→
② 스크립트
위 같은 루프와 OK/FAIL 출력 규약
→
③ 시험
파일 서너 개로 돌려 보고 프롬프트를 고친다
→
④ 전체
나머지에 확장, 실패분만 재시도

세션 안에서는 /batch가 큰 기계적 변경을 5~30개 단위로 나눠 계획을 보여 주고, 단위마다 별도 워크트리에서 실행해 PR을 연다. Anthropic의 대규모 코드 마이그레이션 글은 여기에 규율을 더한다. 먼저 원본에서는 통과하고 일부러 망가뜨린 코드에서는 실패하는 판정 기준(테스트)을 세우고, 변환 규칙을 소수 파일로 시험한 뒤 그 출력은 버리고 규칙만 다듬는다. 같은 실수가 반복되면 파일을 하나씩 고치지 말고 규칙을 고쳐 해당 파일을 다시 생성한다. 작업 큐는 디스크 상태에서 다시 계산해 중단돼도 이어 갈 수 있게 한다.

시험 함정 · 흔한 오해

오해같은 API 키로 연달아 호출하면 Claude가 앞 대화를 이어서 기억한다.
사실Messages API는 무상태다. 애플리케이션이 대화별 이력을 저장하고 매 요청에 전체를 다시 보낸다.
오해보는 사람이 없는 야간 작업이면 max_tokens를 크게 잡고 그냥 create()를 부르면 된다.
사실약 10분을 넘을 것으로 예상되는 비스트리밍 요청은 Python SDK가 ValueError로 막는다. stream()과 get_final_message()로 완성된 Message를 받거나 배치를 쓴다.
오해529 재시도를 설정했으니 과부하 때문에 답이 반쯤 끊기는 일은 없다.
사실스트리밍에서는 200 뒤에 overloaded_error 이벤트가 올 수 있고, 상태 코드 기반 재시도가 적용되지 않는다. 스트림 오류를 따로 잡는다.
오해Actions에 code-review 플러그인을 설치하고 프롬프트로 실행하면 PR에 리뷰 댓글이 달린다.
사실--comment 인자와 인라인 댓글 도구를 허용하는 claude_args가 있어야 게시된다. 없으면 결과는 실행 로그에만 남는다.
오해의존성 업데이트 봇이 PR 댓글에 @claude를 쓰면 액션이 실행된다.
사실봇 행위자는 allowed_bots에 등록하지 않으면 모든 이벤트에서 거부된다. 봇끼리 무한히 깨우는 것을 막기 위해서다.
오해파일의 함수 이름 하나를 바꾸는 데는 Write로 새 내용을 쓰는 것이 확실하다.
사실Write는 파일 전체를 덮어쓴다. 국소 변경은 정확한 문자열 치환인 Edit가 맞다.
