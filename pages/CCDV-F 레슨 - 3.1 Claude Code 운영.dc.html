3.1 Claude Code 운영

Claude Code는 디스크의 파일에서 지속되는 맥락을 읽는다. 지시는 CLAUDE.md와 규칙 파일에, Claude가 스스로 배운 것은 자동 메모리에, 권한과 동작 설정은 settings.json에 있다. 도메인 3의 배점은 작지만 문항은 구체적이다. 어떤 내용을 어느 파일·어느 범위에 두어야 하는가, 같은 이름이나 같은 키가 여러 곳에 있으면 누가 이기는가를 정확히 묻는다. 팀원에게 퍼지면 안 되는 설정, 반드시 막아야 하는 명령, CI에서 이벤트를 받아야 하는 출력 형식처럼 시나리오가 요구하는 '범위'와 '강제력'을 읽어 내면 된다.

습득 포인트
  • managed·user·project·local CLAUDE.md의 위치와 공유 범위를 구분하고, 개인용 프로젝트 지시를 둘 곳을 고른다
  • @path 가져오기, /init, paths 프런트매터 규칙이 언제 무엇을 로드하는지 설명한다
  • 자동 메모리의 네 유형과 MEMORY.md 로드 한도(첫 200줄 또는 25KB)를 안다
  • settings.json 범위의 우선순위, 목록 병합, deny 우선 원칙을 적용한다
  • 스킬·서브에이전트의 이름 충돌 우선순위, 세션 재개 명령, 헤드리스 출력 형식을 고른다
  • 권한 모드와 auto 모드의 판단 순서를 알고, '절대 실행 금지'에는 deny 규칙을 쓴다
01

CLAUDE.md 계층과 개인 지시의 자리

Managed, user, project, local
범위위치공유 대상용도
Managed policyOS별 시스템 경로(예: Linux /etc/claude-code/CLAUDE.md)조직의 모든 사용자회사 코딩 표준, 보안·규정 정책
User~/.claude/CLAUDE.md나만(모든 프로젝트)개인 스타일, 개인 도구 단축키
Project./CLAUDE.md 또는 ./.claude/CLAUDE.md소스 관리로 팀 전체빌드·테스트 명령, 아키텍처, 팀 규칙
Local./CLAUDE.local.md나만(현재 프로젝트)내 샌드박스 URL, 내가 쓰는 테스트 데이터. .gitignore에 추가

작업 디렉터리와 그 위 디렉터리의 CLAUDE.md·CLAUDE.local.md는 실행 시점에 로드되고, 하위 디렉터리의 파일은 Claude가 그 디렉터리의 파일을 다룰 때 로드된다. 파일들은 서로 덮어쓰지 않고 이어 붙는다. 루트에서 작업 디렉터리 쪽으로 순서대로 놓이고, 같은 디렉터리 안에서는 CLAUDE.local.md가 CLAUDE.md 뒤에 붙는다.

개인 지시를 둘 곳

"이 프로젝트에서만, 나만" 적용할 지시는 CLAUDE.local.md다. Claude Code가 자동으로 git에서 빼 주지는 않으므로 .gitignore에 직접 추가한다(CLAUDE_CODE_NEW_INIT=1로 /init을 돌려 개인 옵션을 고르면 대신 해 준다). 여러 git worktree에서 같은 개인 지시를 쓰려면, gitignore된 파일은 만든 worktree에만 있으므로 홈 디렉터리의 파일을 @로 가져오는 방법이 권장된다.

CLAUDE.md 하나는 200줄 이하를 목표로 한다. 길수록 컨텍스트를 더 쓰고 지시 준수가 떨어진다. CLAUDE.md는 강제되는 설정이 아니라 맥락이므로, 어떤 행동을 반드시 막아야 하면 훅이나 권한 규칙을 쓴다.

CLAUDE.md가 이미 있으면 /init은 덮어쓰지 않고 개선안을 제안한다. CLAUDE_CODE_NEW_INIT=1을 설정하면 CLAUDE.md·스킬·훅 중 무엇을 만들지 묻고, 서브에이전트로 탐색한 뒤 질문으로 빈칸을 채워 검토 가능한 제안을 먼저 보여 주는 다단계 흐름으로 바뀐다.

@path 규칙내용
경로 해석상대 경로는 작업 디렉터리가 아니라 가져오는 파일 기준. 절대 경로도 된다
재귀가져온 파일이 또 가져올 수 있고, 최대 네 단계까지
코드 스팬·코드 블록가져오기 해석이 건너뛴다. `@README`처럼 백틱으로 감싸면 글자 그대로 남는다
공백이 든 경로공백마다 백슬래시를 붙인다. 따옴표로 감싼 경로는 가져오지 않는다
외부 파일작업 디렉터리 밖 파일을 가져오면 프로젝트마다 한 번 승인 대화상자가 뜬다
컨텍스트 비용가져온 파일은 CLAUDE.md와 함께 실행 시점에 로드된다. 정리에는 좋지만 컨텍스트를 줄이지 않는다
03

경로 규칙: 필요할 때만 로드되는 지시

.claude/rules/ with paths frontmatter

큰 프로젝트는 주제별 파일을 .claude/rules/에 둔다. 규칙 파일의 YAML 프런트매터에서 Claude Code가 읽는 필드는 paths 하나뿐이고, 다른 필드는 오류 없이 무시된다.

--- paths: - "services/payments/**/*.go" - "services/payments/**/*_test.go" --- # Payments rules - Amounts are integer minor units. Never use float64. - Every handler logs the idempotency key.
언제 로드되나
  • paths가 없는 규칙은 실행 시점에 .claude/CLAUDE.md와 같은 우선순위로 매번 로드된다. 파일로 나누기만 하면 정리만 될 뿐 로드량은 같다
  • paths가 있는 규칙은 Claude가 일치하는 파일을 Read·Write·Edit하거나 cat처럼 읽기로 치는 Bash 명령으로 볼 때 로드된다
  • 프런트매터 YAML이 깨지면 paths가 없는 것처럼 매번 로드된다. claude --debug로 파싱 오류를 확인한다
  • 개인 규칙은 ~/.claude/rules/에 두면 모든 프로젝트에 적용된다
04

자동 메모리: Claude가 직접 쓰는 노트

Auto memory alongside CLAUDE.md
CLAUDE.md

내가 쓴다. 지시와 규칙. 프로젝트·사용자·조직 범위. 로드되는 파일은 전체가 매 세션 들어간다.

자동 메모리 (auto memory)

Claude가 쓴다. 배운 것과 패턴. 저장소 단위로 worktree끼리 공유. 매 세션 MEMORY.md의 첫 200줄 또는 25KB만 들어간다.

type담는 내용
user사용자의 역할, 전문성, 작업 선호
feedback사용자가 준 교정과, 사용자가 확인해 준 접근법
project코드나 git 기록으로 알 수 없는 진행 중 작업·마감·결정
reference프로젝트 밖 정보의 위치(이슈 트래커, 대시보드 등)

Claude는 코드베이스에서 알아낼 수 있는 것(아키텍처, 파일 경로, 디버깅 수정)과 CLAUDE.md에 이미 있는 것은 저장하지 않는다. 메모리 디렉터리에는 한 줄에 메모리 하나씩 적는 색인 MEMORY.md와 메모리마다 하나의 주제 파일이 있다. 세션 시작 때는 MEMORY.md의 첫 200줄 또는 첫 25KB 중 먼저 닿는 쪽까지만 로드되고, 그 뒤는 시작 시점에 들어가지 않는다. 주제 파일은 시작 때 로드되지 않고 Claude가 필요할 때 일반 파일 도구로 읽는다. 색인이 한도에 가까워지면 Claude Code가 줄이라고 알리고, 넘으면 쓰기는 되지만 색인을 다시 쓰라는 오류를 돌려준다.

끄는 방법은 /memory의 토글(사용자 설정에 autoMemoryEnabled 저장), 프로젝트 설정의 "autoMemoryEnabled": false, 환경 변수 CLAUDE_CODE_DISABLE_AUTO_MEMORY=1이다.

settings.json 범위와 우선순위

Scopes, precedence, and merging
1 Managed
조직 배포. 무엇으로도 덮어쓸 수 없다
›
2 Command line
--settings로 넘긴 JSON(그 세션만)
›
3 Project local
.claude/settings.local.json
›
4 Shared project
.claude/settings.json(커밋)
›
5 User
~/.claude/settings.json

같은 키는 위쪽 값이 이긴다. 단 permissions.allow 같은 목록 키는 병합된다. 권한 규칙은 deny → ask → allow 순으로 평가되고, 어느 단계에서든 deny된 도구는 다른 단계가 허용할 수 없다. managed의 deny는 --allowedTools로도 뚫리지 않는다. .claude/settings.local.json은 Claude Code가 처음 쓸 때 전역 git excludes에 자동 추가하지만, 직접 만든 파일이면 .gitignore에 넣어야 한다.

프로젝트 파일이 할 수 없는 것
  • permissions.defaultMode의 auto·bypassPermissions는 .claude/settings.json·.claude/settings.local.json에서 효과가 없다. 사용자·managed 설정이나 --permission-mode로 정한다
  • auto 모드 분류기 설정 autoMode도 프로젝트 설정에서는 읽지 않는다. 저장소가 스스로 허용 규칙을 주입하지 못하게 하기 위해서다
  • 커밋된 permissions.allow는 각 팀원이 폴더를 신뢰한 뒤에 적용되고, deny·ask는 즉시 적용된다

스킬과 슬래시 명령

Skills, commands, and name clashes
위치경로범위
Enterprisemanaged 설정 디렉터리의 .claude/skills/<name>/SKILL.md조직 배포 대상 전원
Personal~/.claude/skills/<name>/SKILL.md내 모든 프로젝트
Project.claude/skills/<name>/SKILL.md이 저장소(커밋하면 팀 공유)
Plugin<plugin>/skills/<name>/SKILL.md/plugin-name:skill-name으로 네임스페이스가 붙어 충돌하지 않는다

이름이 겹치면 enterprise > personal > project다. 같은 deploy가 ~/.claude/skills/와 프로젝트 .claude/skills/에 모두 있으면 /deploy는 개인 것을 실행한다. 사용자 정의 명령은 스킬로 합쳐졌다. .claude/commands/deploy.md도 계속 동작하며 같은 /deploy를 만들지만, 같은 이름의 스킬이 있으면 스킬이 이긴다.

세션 시작 때는 스킬의 description만 로드되고, 본문은 호출될 때 들어온다. Claude가 설명을 보고 자동으로 쓰거나, 내가 /skill-name으로 직접 부른다. disable-model-invocation: true는 자동 호출을 막고, user-invocable: false는 / 메뉴에서 숨긴다. /help·/compact 같은 내장 명령은 고정 로직이고, /code-review 같은 번들 스킬은 프롬프트 기반이다.

07

서브에이전트: 우선순위와 시작 시 로드되는 것

Built-in and custom subagents

내장 서브에이전트로 읽기 전용 탐색용 Explore, 플랜 모드에서 맥락을 모으는 Plan, 탐색과 실행을 모두 하는 general-purpose 등이 있다. 커스텀 서브에이전트는 마크다운 파일로 정의하며, 같은 이름이 여러 곳에 있으면 아래 순서로 위가 이긴다.

순위위치
1Managed settings
2--agents CLI 플래그
3프로젝트 .claude/agents/
4사용자 ~/.claude/agents/
5플러그인의 agents/

스킬은 개인이 프로젝트를 이기지만, 서브에이전트는 프로젝트가 사용자를 이긴다. 둘을 혼동시키는 보기가 나올 수 있다. 서브에이전트는 자기 컨텍스트에서 시작하지만 비어 있지 않다. 커스텀 서브에이전트는 메인 대화가 로드하는 CLAUDE.md 계층 전체(사용자·프로젝트·local·규칙·managed)를 받는다. omitClaudeMd: true를 설정해야 사용자·프로젝트·local CLAUDE.md 없이 시작하고(managed 정책 파일은 여전히 로드), 내장 Explore·Plan은 기본적으로 CLAUDE.md 없이 시작한다. 위임 여부는 description으로 정해지며, 적극적 위임을 원하면 "use proactively" 같은 표현을 넣는다.

세션 관리와 헤드리스 실행

Sessions, -p, and output formats
명령하는 일
claude --continue (-c)현재 디렉터리의 가장 최근 세션을 다시 연다
claude --resume (-r)세션 선택기를 연다. 이름·세션 ID를 주면 바로 재개
/resume세션 안에서 다른 세션으로 전환
--fork-session · /branch원본을 그대로 두고 대화의 사본으로 갈라진다
claude -n · /rename세션 이름을 붙여 나중에 이름으로 재개

-p(--print)는 비대화형 실행이다. 출력 형식은 세 가지다.

--output-format결과
text (기본)일반 텍스트
json결과·세션 ID·메타데이터를 담은 JSON 하나. --json-schema와 쓰면 structured_output 필드
stream-json줄마다 JSON 이벤트 하나씩 실시간으로. 도구 호출·재시도 이벤트·마지막 result 메시지를 차례로 받는다. 토큰 단위로 받으려면 --verbose --include-partial-messages를 더한다
claude -p "Run the unit tests and fix failures" \ --bare --allowedTools "Bash(npm test *),Read,Edit" \ --output-format stream-json --verbose

--bare는 훅·스킬·서브에이전트·플러그인·MCP 서버·자동 메모리·CLAUDE.md의 자동 탐색을 건너뛰어 어느 기계에서나 같은 결과를 내는 CI용 모드다. 필요한 맥락은 플래그로 직접 넘긴다. -p로 만든 세션은 선택기와 --continue에 나타나지 않지만, 세션 ID로 --resume하거나 -p --continue로 이어 갈 수 있다.

09

권한 모드와 auto 모드의 경계

Permission modes and firm limits
모드묻지 않고 실행되는 것
default (UI 이름 Manual)읽기만
acceptEdits읽기, 파일 편집, 흔한 파일 시스템 명령(mkdir·mv·cp 등)
plan읽기(auto 모드를 쓸 수 있으면 분류기가 승인한 명령도)
auto전부. 단 별도 분류기 모델이 배경에서 검사
dontAsk작업 디렉터리 안 읽기와 미리 승인된 도구. 물어야 할 것은 거부
bypassPermissions전부(격리 환경 전용)

auto 모드에서는 allow·ask·deny 규칙에 걸리는 행동이 먼저 즉시 결정되고, 작업 디렉터리 안 읽기·편집은 자동 승인되며, 나머지가 분류기로 간다. 분류기는 요청 범위를 넘는 행동, 모르는 인프라를 겨냥한 행동, 읽은 콘텐츠에 조종된 듯한 행동을 막는다.

원하는 경계수단auto 모드에서의 동작
실행 전에 꼭 묻기permissions.ask일치하는 명령은 항상 확인을 띄운다. 분류기가 자동 승인할 수 없다
절대 실행 금지permissions.deny분류기에 묻기 전에 막는다. 분류기도 사용자 의도도 뒤집지 못한다

시작 모드와 프로젝트 설정

새 터미널 세션의 모드는 --permission-mode 플래그 → 설정 파일의 permissions.defaultMode → 내장 기본값 순으로 정해진다. 팀원이 .claude/settings.json에 "defaultMode": "auto"를 커밋해도 그 값은 효과가 없다. 다만 최신 버전에서는 대화형 터미널 세션의 내장 기본값 자체가 auto(auto 모드를 쓸 수 있을 때)이므로, 세션이 auto로 시작했다면 그것은 커밋된 설정이 아니라 내장 기본값 때문이다. 프로젝트 파일의 "bypassPermissions"도 무시되고 세션은 Manual로 시작한다. claude -p와 Agent SDK 실행의 기본은 default다.

시험 함정 · 흔한 오해

오해긴 CLAUDE.md를 @ 가져오기로 쪼개면 컨텍스트가 줄어든다.
사실가져온 파일도 실행 시점에 함께 로드된다. 로드량을 줄이려면 paths가 있는 규칙 파일이나 스킬로 옮긴다.
오해자동 메모리는 매 세션 전부 로드된다.
사실MEMORY.md의 첫 200줄 또는 25KB만 시작 때 들어가고, 주제 파일은 필요할 때 읽는다.
오해스킬이 나왔으니 .claude/commands/ 파일은 더 이상 동작하지 않는다.
사실계속 동작한다. 새 작업에는 스킬을 권할 뿐이고, 같은 이름이면 스킬이 이긴다.
오해프로젝트 설정에 defaultMode: "auto"를 커밋하면 팀원 모두의 세션이 그 설정으로 auto가 된다.
사실프로젝트·local 설정의 auto·bypassPermissions는 효과가 없다. 사용자·managed 설정이나 플래그로만 정할 수 있다.
오해CLAUDE.md에 "절대 terraform destroy 금지"라고 쓰면 auto 모드에서 확실히 막힌다.
사실분류기도 CLAUDE.md를 읽지만 보장은 아니다. 확실한 금지는 permissions.deny다.
오해프로젝트 설정의 allow가 더 구체적이니 managed의 deny보다 앞선다.
사실어느 단계든 deny된 도구는 다른 단계가 허용할 수 없고, managed 규칙은 명령줄로도 뒤집히지 않는다.
