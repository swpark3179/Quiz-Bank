에이전트 하나로 버거운 일 — 여러 갈래를 동시에 파야 하는 조사, 한 컨텍스트 창에 다 담기지 않는 자료 — 은 코디네이터(coordinator)가 일을 나눠 서브에이전트(subagent)에게 맡기는 구조로 푼다. 이 구조의 성패는 모델 성능보다 코디네이터 설계, 즉 무엇을 누구에게 얼마나 맡기고 돌아온 결과를 어떻게 검토하느냐에 달려 있다. 서브에이전트는 서로를 모르고 코디네이터가 건넨 것만 안다. 그래서 분해·전달·검토는 모두 코디네이터의 책임이다.

습득 포인트
  • 허브 앤 스포크(hub-and-spoke) 구조에서 코디네이터가 맡는 일: 분해, 위임, 결과 취합, 오류 처리, 정보 라우팅
  • 서브에이전트의 격리된 컨텍스트 — 부모 대화를 자동으로 물려받지 않는다
  • 질의 복잡도를 보고 필요한 서브에이전트만 고르는 동적 선택
  • 중복과 누락을 함께 줄이는 범위 분할(하위 주제별·출처 유형별)
  • 종합 결과의 빈틈을 찾아 표적 재위임하고 다시 종합하는 반복 개선 루프
  • 모든 통신을 코디네이터로 모으는 이유: 관측 가능성, 일관된 오류 처리, 정보 흐름 통제
01

허브가 하는 일, 스포크가 하는 일

Who owns what

허브 앤 스포크에서는 코디네이터 하나가 중심에 있고 서브에이전트들은 코디네이터와만 연결된다. Anthropic의 Research 기능도 이 형태(orchestrator-worker)다. 리드 에이전트가 질의를 분석해 전략을 세우고, 서로 다른 측면을 맡은 서브에이전트를 병렬로 띄운 뒤, 돌아온 결과를 종합한다. 단순 병렬화와 다른 점은 하위 과제가 미리 정해져 있지 않고 입력을 본 코디네이터가 런타임에 정한다는 것이다.

책임코디네이터서브에이전트
분해질의를 분석해 하위 과제로 나눈다—
선택어떤 서브에이전트를 몇 개 부를지 정한다맡은 범위만 자기 컨텍스트에서 수행
전달각자 필요한 맥락을 위임 프롬프트에 넣는다받은 프롬프트와 자기 정의만 안다
취합보고를 검토·종합하고 빈틈이면 재위임최종 메시지(요약) 하나만 반환
오류실패한 과제를 재시도·대체·보고하는 정책을 적용자기 범위 안에서만 복구
통신을 전부 허브로 모으는 이유
  • 관측 가능성: 누가 무엇을 받고 무엇을 돌려줬는지가 코디네이터의 대화 한곳에 남아 추적·디버깅이 된다
  • 일관된 오류 처리: 실패 판단, 재시도, 사용자 보고를 한 정책으로 처리한다
  • 정보 흐름 통제: 어느 서브에이전트가 어떤 정보를 보는지 코디네이터가 정한다 — 민감 정보 노출과 중복 작업을 막는다
시험 가이드 표현 vs 현재 문서

가이드는 코디네이터가 서브에이전트 간 통신을 '모두' 관리하는 평면 구조를 전제한다. 현재 Claude Code 문서에는 이름 붙은 에이전트끼리 메시지를 보내는 SendMessage 도구와 agent teams 기능이 있고, 서브에이전트가 기본적으로 자기 서브에이전트를 3단계 깊이까지 만들 수 있다(CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH, 1이면 중첩 금지). 시험 문항은 가이드의 원칙, 즉 '코디네이터 경유'를 기준으로 답한다.

02

격리된 컨텍스트: 서브에이전트가 모르는 것

Context isolation

포크(fork)가 아닌 서브에이전트는 새 컨텍스트 창에서 시작한다. Agent SDK 문서 기준으로 부모가 넘길 수 있는 내용은 Agent 도구의 prompt 문자열 하나뿐이다. 파일 경로, 오류 메시지, 앞서 내린 결정처럼 서브에이전트가 알아야 할 것은 그 프롬프트에 직접 써야 한다. 자기 몫의 하위 과제만이 아니라 원래 질문도 함께 넣어야 서브에이전트가 전체 목적에 맞게 판단한다.

서브에이전트가 받는 것받지 않는 것
자기 시스템 프롬프트(AgentDefinition.prompt)와 위임 프롬프트부모의 대화 이력과 도구 결과
프로젝트 CLAUDE.md(설정 소스로 불러올 때)부모의 시스템 프롬프트
도구 정의(상속, 또는 tools로 지정한 부분집합)skills 필드에 없는 스킬 내용

반대 방향도 좁다. 서브에이전트의 중간 도구 호출과 결과는 서브에이전트 안에 머물고 부모에게는 최종 메시지만 돌아온다. 이것이 메인 컨텍스트를 깨끗하게 유지하는 장점이자, 보고가 빈약하면 코디네이터가 근거를 잃는 약점이다. 그래서 위임할 때 '무엇을 어떤 형식으로 보고할지'까지 정해 준다.

보고를 다루는 법

코디네이터는 서브에이전트 보고를 자기 말로 요약할 수 있다. 원문을 사용자 응답에 그대로 살려야 한다면 메인 프롬프트에 그렇게 지시한다. 큰 산출물(코드, 데이터, 보고서)은 서브에이전트가 외부 저장소에 쓰고 가벼운 참조만 코디네이터에 넘기는 방식도 Anthropic이 소개한다. 여러 단계를 거치며 내용이 깎이는 것을 줄인다.

03

질의에 맞춰 고르기

Select per query, not the full pipeline
BAD · 고정 파이프라인
모든 질의 → 검색 → 분석 → 종합 → 검증 "올해 공휴일이 며칠이야?"도 4단계 전부

단순한 질문에도 비용과 지연이 최대치로 든다.

GOOD · 코디네이터가 판단
단순 사실 → 검색 1개 비교 질문 → 검색 2~3개 + 종합 광범위 조사 → 범위별 검색 여럿 + 분석 + 종합

질의 요구를 먼저 분석하고 필요한 서브에이전트만 부른다.

Anthropic은 초기 리서치 에이전트가 단순한 질의에도 서브에이전트를 50개씩 띄우는 실패를 겪었고, 규모 규칙을 프롬프트에 넣어 해결했다고 밝힌다. 단순 사실 확인은 에이전트 1개와 도구 호출 3~10회, 직접 비교는 서브에이전트 2~4개, 복잡한 조사는 10개 이상에 역할을 분명히 나누는 식이다. Claude Code와 Agent SDK에서는 각 서브에이전트 정의의 description을 보고 Claude가 위임 대상을 고르므로, description을 '언제 쓰는가' 중심으로 쓰는 것이 동적 선택의 출발점이다.

비용 감각과 상한

Anthropic 측정에서 에이전트는 채팅보다 약 4배, 멀티에이전트 시스템은 약 15배의 토큰을 쓴다. 모든 에이전트가 같은 맥락을 공유해야 하거나 에이전트 간 의존이 많은 작업(대부분의 코딩 작업 등)은 아직 멀티에이전트에 잘 맞지 않는다. Agent SDK에서는 중첩 깊이(기본 3), 동시 실행 수(CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS, 기본 20), 비용(max_budget_usd)으로 상한을 건다. Managed Agents의 서브에이전트 위임은 한 단계 깊이이고 세션당 하위 스레드는 동시에 25개까지다.

04

범위 분할: 겹치지 않게, 빠짐없이

Partition the scope

분해는 두 방향으로 실패한다. 경계가 모호하면 서브에이전트들이 같은 검색을 반복하고(중복), 분해가 지나치게 좁으면 질문의 일부가 아무에게도 배정되지 않는다(누락). Anthropic은 서브에이전트마다 목표, 출력 형식, 쓸 도구와 출처에 대한 안내, 명확한 과제 경계를 주라고 권한다. 짧고 모호한 지시는 서브에이전트들이 같은 일을 하게 만든다.

질문 예: "국내 전기차 충전 인프라의 현황과 향후 3년 전망"

분할 방식배정 예잘 맞는 경우
하위 주제별설치 현황 / 요금 체계 / 정부 정책 / 사업자 경쟁 구도질문이 여러 측면을 요구할 때
출처 유형별정부 통계 / 업계 보고서 / 뉴스·공시같은 주제를 교차 검증해야 할 때
너무 좁은 분할 ✗급속 충전기 수 / 급속 충전 요금'전망'과 '정책'이 누구에게도 배정되지 않아 보고서에 구멍이 난다
분할 점검표
  • 원래 질문의 모든 요구(현황 + 전망)가 어느 서브에이전트엔가 배정됐는가
  • 범위가 맞닿는 곳은 경계를 문장으로 밝혔는가 — "요금은 B 담당, A는 다루지 않음"
  • 모두 같은 출력 형식으로 돌려줘 종합하기 쉬운가
05

반복 개선 루프

Evaluate, re-delegate, re-synthesize
DELEGATE
분해·병렬 위임
→
SYNTHESIZE
결과 종합
→
EVALUATE
요구 대비 빈틈 점검
→
RE-DELEGATE
빈틈만 표적 재위임 → 재종합

한 번의 팬아웃(fan-out)으로 끝내지 않는다. Research 시스템의 리드 에이전트도 결과를 종합한 뒤 조사가 더 필요한지 판단하고, 필요하면 서브에이전트를 더 만들거나 전략을 고친다. 생성과 평가를 번갈아 돌리는 evaluator-optimizer 패턴과 같은 발상이다.

  1. 종합 결과를 원래 질문의 요구 목록과 대조한다 — 빠진 측면, 출처가 하나뿐인 주장, 서로 충돌하는 수치
  2. 빈틈마다 구체적인 질의를 만든다 — "더 조사해" 대신 "2027년 이후 충전 요금 정책 변경안, 정부 발표 자료 위주"
  3. 그 빈틈을 맡을 서브에이전트에만 재위임하고, 이미 찾은 내용은 프롬프트에 넣어 중복을 막는다
  4. 새 결과를 기존 종합본과 합쳐 다시 종합하고, 기준을 채우면 끝낸다
종료 기준을 미리 적는다

"요구 항목마다 독립 출처 2개 이상", "수치마다 기준일 표기"처럼 충분함의 기준을 코디네이터 프롬프트에 적어 둔다. 기준이 없으면 Anthropic의 초기 사례처럼 존재하지 않는 자료를 끝없이 찾거나, 반대로 너무 일찍 멈춘다.

시험 함정 · 흔한 오해

오해서브에이전트는 코디네이터와 같은 대화를 보고 일한다.
사실포크가 아니면 새 컨텍스트로 시작한다. 부모 이력은 자동으로 넘어가지 않고, 위임 프롬프트에 쓴 것만 전달된다.
오해서브에이전트를 많이 띄울수록 품질이 오른다.
사실토큰이 채팅의 약 15배까지 늘고 조정 비용도 커진다. 질의 복잡도에 맞춰 개수를 정한다.
오해잘게 나눌수록 커버리지가 넓어진다.
사실지나치게 좁은 분해는 질문의 일부를 아무에게도 배정하지 않는 누락을 만든다. 분할은 원래 질문 전체를 덮어야 한다.
오해서브에이전트끼리 결과를 직접 주고받게 하면 더 효율적이다.
사실시험이 묻는 원칙은 코디네이터 경유다. 관측 가능성, 일관된 오류 처리, 정보 흐름 통제를 잃는다.
