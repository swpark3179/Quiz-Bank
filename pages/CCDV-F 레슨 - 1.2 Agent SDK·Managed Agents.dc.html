에이전트를 만드는 방법은 여러 가지지만, 갈림길은 하나로 모인다. 모델의 루프를 돌리는 코드(하네스, harness)를 누가 운영하느냐다. 직접 루프를 짜면 Client SDK, Claude Code의 루프를 내 프로세스에 들이면 Agent SDK, 루프와 실행 환경까지 Anthropic에 맡기면 Managed Agents다. 시험은 요구사항(인프라 운영 여력, 사설망 접근, 데이터 보존 조건)을 보고 경로를 고르게 하고, 고른 뒤에는 query()가 내보내는 메시지 순서, 도구 허용 옵션의 진짜 의미, 훅이 끼어드는 지점을 정확히 아는지 묻는다.

습득 포인트
  • Client SDK·Agent SDK·Managed Agents·Claude Code CLI를 '루프를 누가 돌리고 도구를 누가 실행하나'로 구분한다
  • Managed Agents의 agent·environment·session·events를 설명하고, 클라우드 샌드박스와 자체 호스팅 샌드박스에서 무엇이 어디서 실행되는지 말한다
  • query() 한 번의 메시지 흐름과 ResultMessage의 subtype으로 종료 원인을 읽는다
  • allowedTools·disallowedTools·권한 모드·canUseTool이 각각 무엇을 하는지 구분한다
  • 훅으로 도구 호출을 막거나 입력을 고치는 방법과, 훅 결정이 권한 모드보다 앞선다는 점을 안다
  • agents 옵션으로 서브에이전트를 선언하고, description이 위임을 좌우한다는 점을 안다
01

네 가지 구축 경로

Who runs the agent harness

하네스는 "모델에 묻고, 도구 호출 요청을 받아 실행하고, 결과를 다시 넣는" 반복을 맡는 코드다. 네 경로는 이 하네스와 도구 실행을 누가 맡느냐로 갈린다.

경로루프·도구 실행실행 위치맞는 상황
Client SDK내가 루프를 짠다(또는 beta tool runner에 맡긴다). 도구도 내가 정의·실행내 애플리케이션Claude API를 직접 호출하며 세밀하게 제어하고 싶을 때
Agent SDKClaude Code의 루프·내장 도구·권한·세션·훅이 라이브러리로 들어온다내가 운영하는 프로세스(Python·TypeScript)Claude Code 수준의 에이전트를 내 제품 안에 넣을 때
Managed AgentsAnthropic이 호스팅하는 하네스가 루프를 돌린다Anthropic 관리 클라우드 샌드박스 또는 자체 호스팅 샌드박스오래 걸리는 비동기 작업, 인프라를 직접 운영하기 싫을 때
Claude Code CLI터미널 앱이 루프를 돌린다개발자 터미널일상적인 대화형 개발, 일회성 작업

Agent SDK는 Claude Code 바이너리를 함께 묶어 배포하므로 대부분 별도 설치가 필요 없다. Python·TypeScript 밖의 언어에서 같은 루프를 쓰려면 CLI를 -p와 --output-format json으로 하위 프로세스처럼 부른다.

시험 판단 축
  • "도구 정의와 실행을 직접 하고 루프도 직접 짠다" → Client SDK
  • "Claude Code의 내장 도구·훅·세션을 우리 프로세스 안에서" → Agent SDK
  • "루프도 샌드박스도 운영하고 싶지 않다, 몇 시간짜리 작업" → Managed Agents
  • Agent SDK로 만든 제품에 claude.ai 로그인이나 구독 한도를 제공하는 것은 사전 승인 없이는 허용되지 않는다. API 키 인증을 쓴다
02

Managed Agents의 네 개념

Agent, environment, session, events

Managed Agents는 미리 만들어진 설정형 하네스를 관리형 인프라에서 돌려 준다. 공식 문서는 Messages API를 '직접 루프와 세밀한 제어', Managed Agents를 '장시간·비동기 작업'에 맞는 선택으로 나눈다. 모든 엔드포인트에 managed-agents-2026-04-01 베타 헤더가 필요하고, SDK는 이 헤더를 자동으로 붙인다.

개념정의헷갈리는 점
Agent모델·시스템 프롬프트·도구·MCP 서버·스킬을 묶은 설정. 한 번 만들고 ID로 여러 세션에서 재사용실행 중인 것이 아니라 '재사용 설정'이다. 모델은 environment가 아니라 agent에 정한다
Environment세션이 어디서 도는지에 대한 설정. Anthropic 관리 클라우드 샌드박스 또는 내 인프라의 자체 호스팅 샌드박스코드를 실행할 장소의 설정이지 에이전트의 성격이 아니다
Sessionenvironment 안에서 특정 작업을 수행하며 산출물을 만드는 실행 중인 에이전트 인스턴스상태를 가진다. 대화 기록·샌드박스 상태·산출물이 서버 측에 저장된다
Events내 애플리케이션과 에이전트 사이를 오가는 메시지(사용자 턴, 도구 결과, 상태 업데이트)결과는 SSE로 스트리밍되고, 이벤트 기록은 서버에 남아 전체를 다시 조회할 수 있다
① AGENT
모델·프롬프트·도구 정의, ID 발급
→
② ENVIRONMENT
클라우드 또는 자체 호스팅 선택
→
③ SESSION
agent + environment를 참조해 시작
→
④ EVENTS
사용자 이벤트 전송, 결과 스트림 수신
→
⑤ STEER
실행 중 추가 지시나 중단
데이터 보존 조건

Managed Agents는 설계상 상태를 가진다. 세션 기록·샌드박스 상태·산출물을 서버에 저장하므로 현재 Zero Data Retention(ZDR)과 HIPAA BAA 적용 대상이 아니다. 이 제한은 자체 호스팅 샌드박스를 포함한 모든 하위 기능에 똑같이 적용된다. 데이터는 API로 세션과 업로드 파일을 지워 직접 정리할 수 있다. ZDR이 필수 요건이면 Managed Agents는 후보에서 빠진다.

03

내 프로세스, Anthropic 클라우드, 내 샌드박스

Where each part runs

같은 '에이전트'라도 루프, 모델 호출, 도구 실행이 각각 어디서 일어나는지가 경로마다 다르다. 특히 자체 호스팅 샌드박스(self-hosted sandbox)를 '완전한 온프레미스'로 착각하기 쉽다.

구성에이전트 루프도구 실행내가 운영할 것
Agent SDK 자체 호스팅내 프로세스(하위 claude 프로세스)내 컨테이너샌드박싱, 세션 저장(재시작하면 로컬 기록이 사라짐), 확장, 관측, 테넌트 격리
Managed Agents + 클라우드 샌드박스AnthropicAnthropic 관리 샌드박스agent·environment 설정과 이벤트 처리
Managed Agents + 자체 호스팅 샌드박스Anthropic내 인프라의 워커워커 프로세스(아웃바운드 HTTPS만 필요)와 그 호스트

자체 호스팅 environment는 작업 큐처럼 동작한다. 세션을 만들면 Anthropic이 작업 항목을 큐에 넣고, 내 인프라의 environment worker가 그것을 가져가 스킬과 메모리 저장소를 내려받는다. Claude는 Anthropic 쪽에서 실행되며 도구 호출을 요청하고, 워커는 그 호출을 로컬에서 실행해 결과를 돌려 보낸다. 모델이 다음 행동을 정하려면 결과를 받아야 하므로 도구 입력과 출력은 여전히 Anthropic 제어 평면을 거친다. 연결된 워커가 없으면 세션은 실패하지 않고 큐에서 기다린다.

자체 호스팅이 맞는 경우

에이전트의 셸 명령이 사내망에서만 닿는 빌드 서버·파일 저장소를 다뤄야 할 때, 도구 실행·파일·네트워크 송신을 내 경계 안에 두어야 할 때. 루프는 여전히 Anthropic이 돌리므로 루프 운영 부담은 없다.

MCP 터널과의 차이

자체 호스팅은 에이전트의 코드가 어디서 도는가, MCP 터널은 Anthropic이 내 망의 MCP 서버에 어떻게 닿는가를 다룬다. 둘은 독립적이다. 클라우드 샌드박스 세션도 터널로 사설 MCP 서버에 닿을 수 있다(터널은 현재 제한된 연구 프리뷰).

시험 판단 축
  • "인프라를 운영하지 않고 몇 시간짜리 비동기 작업" → Managed Agents. 서버리스나 VM에 Agent SDK를 올리면 샌드박싱·오케스트레이션·세션 저장을 내가 맡는다
  • "Anthropic이 루프를 돌리되 도구는 사설망에서" → Managed Agents + 자체 호스팅 샌드박스
  • "모델 추론까지 전부 우리 데이터센터에서" → 자체 호스팅 샌드박스로는 충족되지 않는다

query() 한 번의 메시지 흐름

The query() agent loop

Agent SDK의 query()는 프롬프트를 받아 루프를 돌리면서 메시지를 차례로 내보낸다. 한 턴(turn)은 Claude의 출력과, 그 출력에 도구 호출이 있으면 실행과 결과 반환까지를 말한다. 이 반복은 내 코드로 제어권을 넘기지 않고 이어진다.

05

도구·한도·컨텍스트 옵션과 종료 원인

Options and result subtypes

도구 관련 세 옵션은 이름이 비슷해 시험의 단골 함정이다. 평가 순서는 훅 → deny 규칙 → ask 규칙 → 권한 모드 → allow 규칙 → canUseTool이다.

옵션하는 일흔한 오해
allowedTools나열한 도구를 묻지 않고 자동 승인목록에 없는 도구도 그대로 쓸 수 있다. 승인이 필요한 호출은 권한 모드와 canUseTool로 넘어간다
disallowedTools나열한 도구를 차단. 이름만 쓰면 도구 정의가 요청에서 빠진다Bash(rm *)처럼 범위를 주면 도구는 남고 일치하는 호출만 모든 모드에서 거부된다
permissionModedefault·acceptEdits·plan·dontAsk·auto·bypassPermissionsbypassPermissions에서는 allowedTools에 없는 도구까지 승인된다. 막으려면 disallowedTools
maxTurns · maxBudgetUsd턴 수 상한, 추정 지출 상한(서브에이전트 지출 포함). 기본은 둘 다 제한 없음턴은 '도구를 부른 턴 + 마지막 텍스트 1턴'으로 센다
effort추론 깊이(low~max). 서브에이전트별로 덮어쓸 수 있다확장 사고(thinking)와는 별개 설정이다
settingSourcesCLAUDE.md·스킬·설정 파일 훅을 어느 출처에서 읽을지CLAUDE.md는 매 요청에 들어가지만 프롬프트 캐시된다
ResultMessage.subtype의미 (result 필드는 success에만 있다)
success정상 완료
error_max_turns · error_max_budget_usd턴·예산 상한 도달. 세션 ID로 재개해 이어 갈 수 있다
error_during_execution요청 취소 등 실행 중 오류
error_max_structured_output_retries재시도 한도 안에 유효한 구조화 출력이 나오지 않음
오류 결과 뒤의 예외

단발성 query()는 오류 결과 메시지를 내보낸 뒤 예외를 던진다. 의도된 동작이므로 루프를 try 블록으로 감싸고, 결과의 subtype부터 확인한다. 모든 subtype에 total_cost_usd·usage·num_turns·session_id가 있어 실패 후에도 비용 추적과 재개가 가능하다.

06

훅: 루프의 정해진 지점에 끼어드는 콜백

Hooks for control, logging, and lifecycle

훅은 내 애플리케이션 프로세스에서 실행되므로 컨텍스트를 소비하지 않는다. 옵션의 hooks에 이벤트 이름을 키로, 매처(matcher)와 콜백 목록을 값으로 넣는다. 도구 훅의 매처는 도구 이름에만 맞춰지므로, 파일 경로로 거르려면 콜백 안에서 tool_input.file_path를 검사한다.

이벤트발생 시점대표 용도
PreToolUse도구가 실행되기 전위험 명령 차단, 입력 수정, 자동 승인
PostToolUse도구가 결과를 돌려준 뒤감사 로그, 결과에 맥락 추가·교체
UserPromptSubmit프롬프트가 제출될 때추가 맥락 주입
Stop · SubagentStart/SubagentStop에이전트 종료, 서브에이전트 시작·종료상태 저장, 병렬 작업 결과 집계
PreCompact컨텍스트 압축 직전전체 기록 보관
PermissionRequest도구 호출에 권한 결정이 필요할 때맞춤 승인 처리

PreToolUse 콜백은 hookSpecificOutput에 결정을 담아 돌려준다. 빈 객체 {}는 '바꾸지 않고 허용'이다.

permissionDecision효과updatedInput과 함께 쓰면
"allow"호출 승인(단, deny·ask 규칙은 여전히 평가된다)수정된 입력으로 묻지 않고 실행
"deny"호출 차단. 이유는 permissionDecisionReason으로 모델에 전달해당 없음
"ask"사용자 확인 요청수정된 입력을 사람에게 보여 주고 승인받는다
"defer"턴을 끝내고 stop_reason "tool_deferred"로 나중에 재개updatedInput이 무시된다

시험 판단 축
  • 훅은 권한 평가의 첫 단계다. 훅의 deny는 bypassPermissions에서도 유효하다. 반면 canUseTool은 자동 승인된 호출에는 불리지 않으므로 bypass 모드의 안전장치가 되지 못한다
  • 프롬프트의 "절대 .env를 건드리지 마라"는 유도일 뿐 강제가 아니다
  • 위 예시처럼 Write|Edit 매처만 걸면 Bash로 쓰는 경우는 훅이 돌지 않는다. 필요하면 Bash 훅이나 샌드박스 설정을 더한다
  • 여러 훅의 결정이 엇갈리면 deny > defer > ask > allow 순으로 우선한다. 같은 이벤트의 훅은 병렬로 실행되므로 서로의 실행 순서에 기대지 않는다
언어별로 다른 훅 지원

SessionStart·SessionEnd·PostCompact·PostToolBatch 등 상당수 이벤트는 TypeScript SDK에서만 콜백으로 등록할 수 있다. Python SDK에서 SessionStart·SessionEnd가 필요하면 .claude/settings.json 같은 설정 파일의 셸 명령 훅으로 정의하고, setting_sources에 그 출처를 포함한다.

Declaring and spotting subagents

SDK 애플리케이션에서는 query() 옵션의 agents로 서브에이전트를 코드에 선언하는 방식이 권장된다. .claude/agents/의 파일 정의와 이름이 겹치면 코드에서 선언한 쪽이 우선한다. 아무것도 정의하지 않아도 Claude는 내장 general-purpose 서브에이전트를 부를 수 있다.

필드역할

스트림에서 위임을 알아보려면 name이 "Agent"인 tool_use 블록을 찾고, 서브에이전트 안에서 나온 메시지는 parent_tool_use_id로 구분한다. 이 도구는 system:init의 도구 목록에는 "Task"로 나오고 예전 버전의 tool_use도 "Task"였으므로 두 이름을 모두 확인하는 것이 안전하다. 이름으로 지목하면("code-reviewer 에이전트로 검토해") 자동 매칭을 건너뛰고 바로 호출된다.
