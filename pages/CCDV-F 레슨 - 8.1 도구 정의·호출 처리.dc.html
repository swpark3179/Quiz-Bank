도구 사용(tool use)은 애플리케이션과 모델 사이의 계약이다. 애플리케이션은 어떤 작업이 가능하고 입력이 어떤 모양인지 알려 주고, Claude는 언제 무엇을 부를지 정한다. Claude는 아무것도 직접 실행하지 않는다. 구조화된 요청을 낼 뿐이고, 실행은 여러분의 코드나 Anthropic 서버가 맡는다. 시험은 이 계약의 양쪽을 묻는다. 정의 쪽에서는 설명·스키마·strict·tool_choice가 각각 무엇을 바꾸는지, 처리 쪽에서는 결과를 어떤 형식으로 돌려주고 오류·서버 도구·승인을 어떻게 다루는지다.

습득 포인트
  • 도구를 실행 위치(사용자 정의 클라이언트 도구 · Anthropic 스키마 클라이언트 도구 · 서버 실행 도구)로 나누고, 각각에서 앱이 맡는 일을 구분한다
  • 도구 선택 문제는 설명으로, 입력 형태 문제는 strict: true로 고친다는 경계를 지킨다
  • 도구 통합·네임스페이스·고신호 응답·'산문 파싱 대신 도구 호출'로 도구 세트를 설계한다
  • tool_choice 네 옵션과 모델별 강제 호출 제한(Opus 5.5 등은 400)을 알고 대안을 고른다
  • 클라이언트 도구 루프, tool_result 형식 규칙, is_error, pause_turn과 혼합 턴을 정확히 처리한다
  • Agent SDK에서 allowed_tools·disallowed_tools가 권한 평가 순서의 어디에 끼는지 설명한다
01

도구가 실행되는 곳이 앱의 책임을 정한다

Where a tool runs

도구를 가르는 첫 번째 축은 코드가 어디서 실행되느냐다. 모든 도구는 아래 세 갈래 중 하나에 들어가고, 어느 갈래인지에 따라 앱이 해야 할 일이 달라진다.

갈래예앱이 하는 일
사용자 정의 도구 (클라이언트 실행)사내 API 조회, DB 쿼리, 파일 쓰기 등 여러분이 만든 도구스키마를 쓰고, tool_use를 받아 실행하고, tool_result를 돌려준다. 도구 사용 트래픽 대부분이 여기에 속한다
Anthropic 스키마 도구 (클라이언트 실행)bash, text_editor, memory, computer, browser스키마는 Anthropic이 정했지만 실행은 여전히 앱이 한다. 처리 흐름은 사용자 정의 도구와 같다
서버 실행 도구web_search, web_fetch, code_execution, tool_search요청에서 켜기만 하면 Anthropic이 실행한다. tool_result를 만들지 않고, 응답의 server_tool_use와 결과 블록을 읽는다
Anthropic 스키마 도구를 쓰는 이유

이 스키마들은 학습되어 있다(trained-in). Claude는 바로 이 도구 시그니처를 쓴 성공 궤적 수천 건으로 최적화되어 있어, 같은 일을 하는 커스텀 도구보다 더 안정적으로 호출하고 오류에서도 더 잘 회복한다. 이점은 호출 신뢰도이지 실행 대행이 아니다. 셸 명령은 여전히 여러분의 환경에서 돌고, 그 안전도 여러분이 책임진다.

02

도구 정의의 구조

Anatomy of a tool definition

사용자 정의 도구는 요청의 최상위 tools 배열에 넣는다. API는 이 정의들로 도구 사용용 시스템 프롬프트를 만들어 모델에 전달한다. 즉 Claude가 보는 것은 이름·설명·스키마와, 나중에 돌려받는 결과뿐이다. 구현 코드는 모델에 전달되지 않는다.

{ "name": "parcel_track_shipment", "description": "Returns the latest scan events for one parcel shipped with our carrier network. Use it when the user gives a tracking number that starts with PX. It does not return delivery-fee details or customs paperwork.", "strict": true, "input_schema": { "type": "object", "properties": { "tracking_no": {"type": "string", "description": "Tracking number, e.g. PX20481577"}, "max_events": {"type": "integer", "description": "How many recent scans to return"} }, "required": ["tracking_no"], "additionalProperties": false }, "input_examples": [ {"tracking_no": "PX20481577"}, {"tracking_no": "PX99100042", "max_events": 3} ] }
필드역할시험 포인트
name도구 식별자. 정규식 ^[a-zA-Z0-9_-]{1,128}$서비스 접두사로 네임스페이스를 준다 (→ 04)
description무엇을 하는지, 언제 쓰고 언제 쓰지 않는지, 매개변수의 뜻, 한계도구 성능을 좌우하는 가장 중요한 요소
input_schema입력 매개변수를 정의하는 JSON Schema 객체형태를 알려 줄 뿐, strict 없이는 준수를 보장하지 않는다
input_examples (선택)스키마에 맞는 입력 예시 배열스키마에 어긋나는 예시는 400. 서버 도구에는 쓸 수 없다. 단순한 예시 약 20~50토큰, 복잡한 중첩 객체 약 100~200토큰이 든다
strict (선택)문법 제약 샘플링으로 입력이 스키마를 정확히 따르게 한다타입이 맞는 인자를 보장하는 유일한 수단 (→ 05)
03

도구 선택을 이끄는 설명 쓰기

Descriptions drive tool selection

공식 문서는 "매우 자세한 설명"을 도구 성능에서 단연 가장 중요한 요소로 꼽는다. 도구 하나에 최소 3~4문장, 복잡하면 더 길게 쓰라고 권한다. 설명에 담을 것은 다음 네 가지다.

  • 무엇을 하는가: 반환하는 데이터와 그 형식
  • 언제 쓰는가, 언제 쓰지 않는가: 지원 범위와 범위 밖 요청
  • 매개변수마다 무슨 뜻이고 동작에 어떤 영향을 주는가
  • 주의점과 한계: 이 도구가 돌려주지 않는 정보까지
약한 설명

"Gets room availability." 어떤 숙소 체인인지, 날짜 형식은 무엇인지, 요금도 주는지, 단체 예약에도 쓰는지 Claude가 추측해야 한다. 그 결과 범위 밖 요청에도 도구를 부르거나, 써야 할 때 부르지 않는다.

좋은 설명

"Checks free rooms at Harbor Inn properties for given dates. Dates use YYYY-MM-DD. Returns room types and nightly rates in KRW. Use it for stays of up to 14 nights for 1–4 guests; group bookings go to harbor_group_request. It does not hold or book rooms."

설명에 넣을 필요가 없는 것은 구현 내부다. 핸들러가 어떤 언어로 쓰였는지, 어느 DB를 어떤 ORM으로 읽는지는 Claude가 도구를 고르고 인자를 채우는 데 아무 도움이 되지 않는다. Claude는 스키마와 결과만 본다.

시험 판단 축 · 증상별 처방
  • 엉뚱한 도구를 고르거나 범위 밖 입력에도 부른다 → 설명을 다시 쓴다(범위·제외 대상·대체 도구 명시). strict는 입력 형태를 다룰 뿐 도구 선택에는 관여하지 않는다
  • 필수 인자를 빠뜨리거나 타입이 틀린다 → strict: true. 예시와 설명은 올바른 호출 가능성을 높일 뿐 보장하지 않는다
  • 복잡한 중첩 입력·형식에 민감한 값 → 설명을 먼저 다듬고 input_examples를 더한다
04

규모가 커져도 버티는 도구 세트

Designing a tool set that scales

도구가 많아질수록 선택이 흔들린다. 공식 문서와 Anthropic 엔지니어링 글 "Writing tools for agents"가 권하는 원칙을 증상과 짝지어 기억한다.

증상원칙적용 예
동작마다 도구가 따로 있어 서로 헷갈린다관련 동작을 한 도구로 통합create_pr·review_pr·merge_pr 대신 action 매개변수를 가진 도구 하나. 여러 단계를 묶는 것도 통합이다(목록 조회 3개 대신 schedule_event 하나)
여러 서비스에 같은 이름의 도구가 있다서비스 접두사로 네임스페이스github_list_prs, slack_send_message. tool search를 쓸 때 특히 중요하다
응답이 수십 개 열과 내부 참조로 부풀어 있다고신호 정보만 반환다음 단계 추론에 필요한 필드만, 그리고 불투명한 내부 참조 대신 slug·UUID 같은 의미 있고 안정적인 식별자. 간결/상세를 고르는 response_format 매개변수, 페이지네이션·잘라내기도 같은 맥락이다
모델의 판단을 정규식으로 산문에서 뽑아낸다그 판단을 도구 호출로"escalate: yes" 같은 문자열을 파싱하지 말고 escalate_ticket 도구를 정의한다. 구조화된 의도를 텍스트에서 복원하고 있다면 그 구조는 스키마에 있어야 한다
오류 메시지도 도구 설계의 일부

불투명한 오류 코드나 스택 트레이스 대신 무엇이 잘못됐고 무엇을 고치면 되는지 말해 주는 오류가 에이전트의 회복을 돕는다. 매개변수 이름도 user보다 user_id처럼 모호하지 않게 짓는다.

05

tool_choice와 strict: 호출을 어디까지 강제할 수 있나

Controlling calls on today's models
tool_choice동작
{"type": "auto"}도구를 쓸지 말지 Claude가 정한다. tools가 있을 때 기본값
{"type": "any"}제공된 도구 중 하나는 반드시 쓴다. 어느 도구인지는 정하지 않는다
{"type": "tool", "name": "…"}지정한 도구 하나를 반드시 쓴다
{"type": "none"}도구를 쓰지 않는다. tools가 없을 때 기본값

강제 호출(any·tool)은 모든 모델과 설정에서 되지 않는다. 2026년 10월 기준 문서의 제한은 다음과 같다.

모델·설정제한대신 쓸 것
Claude Opus 5.5, Sonnet 5.5, Fable 5.1, Mythos 5.1any·tool이 400 오류auto + strict: true(스키마에 맞는 입력 보장)와 프롬프트 지시, 고정 JSON 응답이 필요하면 structured outputs. none은 쓸 수 있다
수동 extended thinking (thinking: {type: "enabled"})any·tool 미지원auto 또는 none
강제 호출을 받는 모델 (현행 모델 중에는 Claude Haiku 5.5. 레거시 Opus 5도 해당)허용되지만 사고(thinking)를 건너뛴다먼저 생각하게 하려면 auto + 프롬프트 지시
강제 호출의 부수 효과

any나 tool을 쓰면 API가 어시스턴트 메시지를 미리 채워 도구 호출을 강제하므로, 요청해도 tool_use 앞에 자연어 설명이 나오지 않는다. 강제 호출을 지원하는 모델에서는 any와 strict를 함께 써서 '도구가 반드시 호출되고, 입력도 스키마를 따른다'를 둘 다 보장할 수 있다.

strict: true가 보장하는 것은 두 가지다. 도구 input이 input_schema를 정확히 따르고, 도구 name이 항상 유효하다. "2" 대신 2, 필수 필드 누락 없음. 반대로 '이 요청에 이 도구가 맞는가'는 보장하지 않는다.

06

클라이언트 도구 루프와 tool_result 형식

The agentic loop for client tools
① REQUEST
tools 배열과 사용자 메시지를 보낸다
→
② TOOL_USE
stop_reason: "tool_use"와 tool_use 블록을 받는다
→
③ EXECUTE
도구마다 실행하고 출력을 tool_result로 만든다
→
④ CONTINUE
기존 메시지 + 어시스턴트 응답 + 결과를 담은 사용자 메시지를 보낸다
→
⑤ REPEAT
stop_reason이 tool_use인 동안 ②로
messages = [{"role": "user", "content": question}] while True: resp = client.messages.create(model=MODEL, max_tokens=2048, tools=TOOLS, messages=messages) if resp.stop_reason != "tool_use": break # end_turn, max_tokens, refusal 등 messages.append({"role": "assistant", "content": resp.content}) results = [] for block in resp.content: if block.type == "tool_use": out, failed = run_tool(block.name, block.input) results.append({"type": "tool_result", "tool_use_id": block.id, # 호출의 id와 같아야 한다 "content": out, "is_error": failed}) messages.append({"role": "user", "content": results})
형식 규칙어기면
각 tool_result의 tool_use_id는 대응하는 tool_use 블록의 id와 같다결과의 짝은 순서가 아니라 이 ID로 맞춘다. 병렬 호출 결과를 어떤 순서로 넣어도 된다
결과 메시지는 도구 호출 메시지 바로 다음에 온다. 사이에 다른 메시지를 끼우지 않는다"tool_use ids were found without tool_result blocks immediately after" 오류
결과를 담은 사용자 메시지에서 tool_result 블록이 맨 앞에 온다. 텍스트는 결과 뒤에만텍스트가 앞에 있으면 400
tool_use 블록마다 결과가 하나씩 있다일부만 답하면 같은 오류로 실패

content는 생략할 수도 있고, 문자열이나 text·image·document·search_result 블록 목록일 수도 있다. 웹 페이지·메일·업로드처럼 통제할 수 없는 출처의 내용은 시스템 프롬프트가 아니라 tool_result 안에 두고, 간접 프롬프트 인젝션에 대비한다.

07

오류: 실행 실패와 잘못된 호출

Execution failures vs invalid calls
실행 실패

도구 자체가 실패했다(상위 서비스 장애, 네트워크 오류). 같은 tool_use_id로 tool_result를 보내되 "is_error": true를 붙이고, 내용에 무엇이 잘못됐고 다음에 무엇을 하면 되는지를 쓴다. "failed" 한 단어보다 "Rate limit exceeded. Retry after 60 seconds."가 낫다.

잘못된 호출

필수 매개변수가 빠진 호출 등은 대개 정보가 부족했다는 신호다. 개발 단계에서는 설명을 더 자세히 쓰는 것이 우선이다. 대화를 이어 가려면 오류를 담은 tool_result(is_error: true)를 보내면 되고, Claude는 보통 2~3회 고쳐서 다시 시도한다. 잘못된 호출 자체를 없애려면 strict: true.

{"role": "user", "content": [{ "type": "tool_result", "tool_use_id": "toolu_01HqT5…", "content": "Rate provider returned HTTP 503 (scheduled maintenance until 02:00 UTC). No rate was fetched. Retry after 02:00 UTC or tell the user the rate is temporarily unavailable.", "is_error": true }]}

서버 도구의 오류는 다르다. 웹 검색 실패 같은 오류는 Claude가 투명하게 처리해 대안을 내거나 설명하므로, 서버 도구에 대해 앱이 is_error 결과를 만들 필요가 없다.

08

서버 도구가 섞인 응답: pause_turn과 혼합 턴

Server tools at runtime

서버 도구 호출은 server_tool_use 블록(id가 srvtoolu_로 시작)으로 보이고, 보통 같은 응답 안에 결과 블록이 tool_use_id로 짝지어 따라온다. 예외가 두 가지 있고, 둘을 헷갈리게 하는 문항이 단골이다.

응답 상태의미앱이 할 일
server_tool_use와 결과 블록이 같은 응답에 있다서버 도구 호출이 끝났다할 일 없음
stop_reason: "pause_turn"서버 측 루프가 반복 상한에 걸려 멈췄다. 클라이언트 도구를 기다리는 일은 없다멈춘 응답을 그대로 어시스턴트 메시지로 붙여 다시 보낸다. 같은 도구를 포함한다. 다시 멈출 수 있으니 횟수 상한을 둔다
stop_reason: "tool_use"이고, 결과 블록이 없는 server_tool_use와 클라이언트 tool_use가 함께 있다병렬 호출에 클라이언트 도구가 섞여 API가 서버 도구를 실행하지 않고 먼저 돌아왔다. 별도 표시는 없다클라이언트 도구를 실행하고 tool_result 블록만 담은 사용자 메시지를 보낸다. 같은 tools 배열을 유지한다

혼합 턴을 이어 보내면 API가 결과를 아직 열려 있는 어시스턴트 턴에 붙이고, 미뤄 둔 서버 도구를 실행한 뒤 Claude가 이어 간다. 다음 응답은 이전 server_tool_use의 결과 블록으로 시작한다. 두 블록은 서로 다른 응답에 오므로 위치가 아니라 tool_use_id로 짝이 맞는다.

혼합 턴에서 400이 나는 경우
  • 후속 요청의 tools에서 대기 중인 서버 도구를 뺐다 → "…but no `web_fetch` tool was provided"로 끝나는 400
  • 결과 뒤에 텍스트 블록을 붙였다 → 턴이 끝났다고 해석되어, 해결되지 않은 서버 도구 호출 때문에 400
  • 결과 앞에 내용을 두었거나, 일부 tool_use만 답했거나, tool_result가 하나도 없다 → 클라이언트 도구 오류
  • 더 할 말이 있으면 턴이 끝난 뒤 별도의 사용자 메시지로 보낸다

Approval patterns in the Agent SDK

Claude Agent SDK는 도구 호출마다 아래 순서로 권한을 확인한다. 앞 단계에서 결론이 나면 뒤 단계는 보지 않는다.

① HOOKS
훅이 거부하거나 넘긴다. 훅의 allow도 아래 deny·ask를 건너뛰지 못한다
→
② DENY
disallowed_tools·settings 거부 규칙. bypassPermissions에서도 적용
→
③ ASK
ask 규칙이면 콜백으로
→
④ MODE
권한 모드 적용 (예: bypass는 대부분 승인)
→
⑤ ALLOW
allowed_tools·allow 규칙
→
⑥ CALLBACK
canUseTool이 결정 (dontAsk면 거부)
설정효과
allowed_tools=["Read", "Grep"]나열한 도구를 자동 승인. 목록에 없는 도구는 사라지지 않고 권한 모드와 canUseTool로 넘어간다
disallowed_tools=["Bash"] (도구 이름만)Bash 정의가 요청에서 제거된다. Claude는 도구를 보지 못하고 시도할 수도 없다
disallowed_tools=["Bash(rm *)"] (범위 규칙)Bash는 남고, 적힌 패턴과 일치하는 호출만 bypassPermissions를 포함한 모든 모드에서 거부. 다른 형태(/bin/rm 등)는 모드로 넘어간다
disallowed_tools=["*"]모든 도구 정의 제거. 거부 규칙은 "mcp__*" 같은 이름 glob을 받는다
세션 중 모드가 바뀌어도 남는 규칙

set_permission_mode()로 세션 중에 모드를 바꾸면 이후 모든 요청에 바로 적용된다. 거부 규칙은 모드 확인보다 먼저 평가되므로, 모드를 bypassPermissions로 올려도 범위 거부 규칙은 그대로 막는다. 반대로 canUseTool 안에만 둔 검사는 자동 승인된 호출에서 실행되지 않는다. 모든 호출에 돌아야 하는 검사는 PreToolUse 훅에 둔다.

시험 함정 · 흔한 오해

오해서버 도구도 클라이언트 도구처럼 앱이 tool_result와 is_error를 만들어 돌려줘야 한다.
사실서버 도구는 API가 실행하고 결과도 응답에 넣는다. 혼합 턴에서도 앱이 보내는 것은 클라이언트 도구의 결과뿐이다.
오해Claude가 엉뚱한 도구를 고르면 strict: true를 켜거나 매개변수를 더하면 된다.
사실strict는 입력 형태를, 설명은 도구 선택을 다룬다. 선택이 틀리면 설명에 범위와 제외 대상을 쓴다.
오해tool_choice의 tool 타입은 어떤 모델에서든 그 도구 호출을 강제한다.
사실Opus 5.5·Sonnet 5.5·Fable 5.1·Mythos 5.1은 400을 돌려주고, 수동 extended thinking도 거부한다. 대안은 auto + strict다.
오해결과가 없는 server_tool_use가 응답에 있으면 언제나 pause_turn이다.
사실클라이언트 도구도 함께 불렸다면 stop_reason은 tool_use이고, 클라이언트 결과만 보내야 한다.
오해allowed_tools에서 빠진 도구는 막힌다.
사실목록에 없는 도구는 권한 모드와 canUseTool로 넘어간다. 도구를 없애려면 disallowed_tools에 이름을 넣는다.
오해실패한 도구 호출은 tool_result를 생략하고 사용자 텍스트로 알리면 된다.
사실tool_use마다 짝이 되는 tool_result가 있어야 한다. 실패는 is_error: true와 회복에 쓸 수 있는 메시지로 알린다.
