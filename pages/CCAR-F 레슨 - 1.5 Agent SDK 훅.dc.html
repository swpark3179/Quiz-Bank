Agent SDK 훅: 도구 호출 차단과 결과 정규화

PreToolUse · PostToolUse · permissionDecision · updatedToolOutput · 데이터 정규화 · 결정적 보장

참고 레슨 · CertSafari 1.5  |  출제 도메인: 도메인 1 · Agentic Architecture & Orchestration (27%)

1.1 에이전트 루프1.2 코디네이터1.3 서브에이전트 생성1.4 게이트·핸드오프1.5 SDK 훅1.6 작업 분해1.7 세션 관리

Agent SDK의 훅(hook)은 에이전트 루프의 정해진 지점에서 실행되는 내 코드(콜백)다. 1.4가 '어떤 순서를 강제할까'였다면 1.5는 훅이라는 장치 자체를 다룬다. 나가는 도구 호출을 가로채 정책을 집행하고, 들어오는 도구 결과를 Claude가 읽기 전에 다듬는 방법이다. PreToolUse는 실행 전에 막거나 고치는 자리, PostToolUse는 실행 뒤 Claude가 보기 전에 결과를 바꾸는 자리다.

습득 포인트
  • 도구 호출 경로에서 PreToolUse · PostToolUse · PostToolUseFailure가 끼어드는 위치와 각각 할 수 있는 일
  • 콜백 등록(HookMatcher·matcher)과 입출력(hookSpecificOutput) 구조
  • 정책을 어기는 호출(한도 초과 지급 등)을 막고 사람 에스컬레이션 같은 대체 경로로 돌리기
  • MCP 도구마다 다른 형식(Unix 타임스탬프, ISO 8601, 숫자 상태 코드)을 PostToolUse에서 하나로 정규화하기
  • 보장이 필요한 규칙은 훅, 판단과 스타일은 프롬프트라는 선택 기준
01

훅이 끼어드는 자리

Where hooks sit in the tool path
CLAUDE
tool_use 생성
→
PreToolUse
허용·거부·확인·보류, 입력 수정
→
PERMISSIONS
deny·ask 규칙 → 모드 → allow 규칙
→
EXECUTE
도구 실행
→
PostToolUse
결과 교체·맥락 추가 → Claude

권한 평가에서 훅이 가장 먼저 돈다. 훅이 거부하면 거기서 끝나고, 훅이 allow를 돌려줘도 이후의 deny·ask 규칙은 그대로 평가된다. 훅은 컨텍스트 창이 아니라 애플리케이션 프로세스에서 실행되므로 토큰을 쓰지 않는다.

이벤트시점할 수 있는 일
PreToolUse도구 실행 직전permissionDecision(allow·deny·ask·defer), updatedInput, additionalContext
PostToolUse도구가 성공한 직후updatedToolOutput로 결과 교체, additionalContext, 최상위 decision: "block" + reason
PostToolUseFailure도구가 실패한 직후오류 기록, 맥락 추가
PostToolBatch병렬 호출 묶음이 모두 끝난 뒤 다음 모델 호출 전 1회묶음 단위 맥락 주입 (TypeScript SDK만)
Stop · SubagentStop에이전트·서브에이전트 종료결과 검증, 상태 저장
02

콜백의 모양

Callback anatomy
async def my_hook(input_data, tool_use_id, context): # input_data: hook_event_name, session_id, cwd, tool_name, tool_input, # PostToolUse면 tool_response, 서브에이전트 안이면 agent_id·agent_type # tool_use_id: 같은 호출의 Pre/Post 이벤트를 짝짓는 값 return {} # 빈 객체 = 아무것도 바꾸지 않고 통과 options = ClaudeAgentOptions(hooks={ "PreToolUse": [HookMatcher(matcher="mcp__travel__issue_voucher", hooks=[my_hook])], "PostToolUse": [HookMatcher(matcher="mcp__(booking|crm|loyalty)__.*", hooks=[my_hook], timeout=30)], # timeout 단위는 초 })
출력 위치필드용도
최상위 (모든 이벤트)systemMessage사용자에게 보여 줄 메시지. 모델에는 가지 않는다
최상위 (모든 이벤트)continue (Python: continue_)이 훅 뒤에 에이전트를 계속 돌릴지
hookSpecificOutput · PreToolUsepermissionDecision, permissionDecisionReason, updatedInput결정과 이유(deny면 Claude에게 전달), 입력 통째 교체
hookSpecificOutput · PostToolUseupdatedToolOutput, additionalContextClaude가 볼 결과 교체, 결과 옆에 덧붙일 설명
  • matcher는 도구 이름만 본다. 금액·경로 같은 인자 조건은 콜백 안에서 tool_input으로 검사한다.
  • 글자·숫자·_·-·|만 있으면 정확한 이름 비교, 다른 문자가 섞이면 부분 일치 정규식으로 평가한다. MCP 도구 이름은 mcp__<서버>__<도구>다.
  • PreToolUse 콜백이 timeout을 넘기면 그 호출은 막히고, PostToolUse가 넘기면 원래 결과가 그대로 쓰인다.
  • 비동기 출력(async_: True)은 기다리지 않고 진행하므로 차단·수정·맥락 주입을 못 한다. 로깅·알림 전용이다.
03

정책 위반 호출을 막고 다른 길로 돌리기

Block and redirect

여행사 고객지원 에이전트의 규정: 일정 변경 보상 바우처는 건당 30만 원까지 에이전트가 발급하고, 그 이상은 상급자 승인을 받는다. 시험 가이드의 "500달러 초과 환불 차단 후 사람 에스컬레이션"과 같은 구조다.

VOUCHER_LIMIT = 300_000 async def cap_voucher(input_data, tool_use_id, context): amount = input_data["tool_input"].get("amount_krw", 0) if amount <= VOUCHER_LIMIT: return {} return { "systemMessage": f"바우처 {amount:,}원 요청이 한도를 넘어 차단됐습니다.", # 사용자용 "hookSpecificOutput": { "hookEventName": "PreToolUse", "permissionDecision": "deny", "permissionDecisionReason": ( # Claude용 f"바우처는 건당 {VOUCHER_LIMIT:,}원까지만 발급할 수 있다. 발급하지 말고 " "escalate_to_supervisor로 예약번호·요청 금액·사유를 넘겨라."), }, }

거부 이유는 도구 결과로 Claude에게 전달되므로 '하지 마라'로 끝내지 말고 대체 경로(어떤 도구로 무엇을 넘길지)를 적는다. 그러면 Claude가 그 경로로 방향을 바꾼다. systemMessage는 사용자 쪽 표시용이라 모델은 보지 못한다.

결정효과쓰는 경우
deny실행하지 않고 이유를 Claude에게 전달정책 위반. 가장 흔한 선택
ask사용자에게 승인 프롬프트를 띄운다사람이 지켜보는 대화형 앱
defer턴을 끝내고(stop_reason: "tool_deferred") 나중에 재개-p·SDK 앱에서 외부 승인을 기다릴 때. 한 턴에 도구 호출이 하나일 때만 동작
allow + updatedInput입력을 고쳐서 실행경로 리다이렉트 같은 기술적 보정. 금액 삭감처럼 의미가 바뀌는 수정은 고객 의도와 달라지므로 거부 후 에스컬레이션이 낫다
예전 형식 vs 현재 문서

예전 자료에는 PreToolUse가 최상위 decision: "approve" | "block"을 돌려주는 형태가 보인다. 현재 문서에서 이 형태는 PreToolUse에 대해 더 이상 권장되지 않고, hookSpecificOutput.permissionDecision의 "allow"·"deny"·"ask"·"defer"를 쓴다. 여러 훅의 결정이 엇갈리면 deny > defer > ask > allow 순으로 우선한다.

04

결과 정규화: 서로 다른 형식을 하나로

Normalize heterogeneous results

MCP 서버 여러 개를 붙이면 같은 개념이 다른 모양으로 들어온다. 예약 서버는 1767225600 같은 Unix 초, CRM은 2026-01-01T09:00:00+09:00 같은 ISO 8601, 포인트 서버는 상태를 0/1/2 숫자 코드로 준다. 프롬프트에 "형식이 섞여 있으니 주의해서 읽어라"라고 맡기면 날짜 비교나 기한 계산에서 실수가 난다. PostToolUse 훅에서 한 형식으로 바꿔 Claude가 항상 같은 모양을 보게 한다.

from datetime import datetime, timezone STATUS = {0: "pending", 1: "confirmed", 2: "cancelled"} # 포인트 서버의 숫자 코드 def to_utc_iso(v): if isinstance(v, (int, float)): # Unix epoch(초) return datetime.fromtimestamp(v, tz=timezone.utc).isoformat() if isinstance(v, str): # 오프셋이 붙은 ISO 8601 return datetime.fromisoformat(v).astimezone(timezone.utc).isoformat() return v def normalize(obj): if isinstance(obj, list): return [normalize(x) for x in obj] if not isinstance(obj, dict): return obj out = {} for k, v in obj.items(): if k.endswith("_at"): out[k] = to_utc_iso(v) elif k == "status" and isinstance(v, int): out[k] = STATUS.get(v, f"unknown({v})") else: out[k] = normalize(v) return out async def normalize_result(input_data, tool_use_id, context): # 각 서버가 JSON 객체를 돌려준다고 가정한다. 실제 응답 구조를 확인하고 같은 구조로 되돌린다 return {"hookSpecificOutput": { "hookEventName": "PostToolUse", "updatedToolOutput": normalize(input_data["tool_response"]), "additionalContext": "모든 시각은 UTC ISO 8601, 상태는 문자열로 정규화됨", }} # 등록: HookMatcher(matcher="mcp__(booking|crm|loyalty)__.*", hooks=[normalize_result])
  • updatedToolOutput은 Claude가 보는 값만 바꾼다. 도구는 이미 실행됐고, 텔레메트리 등에는 원본이 남는다.
  • 내장 도구는 출력 모양이 정해져 있어 맞지 않는 값은 무시되고 원본이 쓰인다. MCP 도구 출력은 스키마 검증 없이 그대로 전달되므로 구조를 깨뜨리지 않게 주의한다.
  • 오류 세부를 지우지 않는다. Claude가 필요한 오류 정보를 잃으면 잘못된 가정 위에서 진행한다.
  • 원본은 두고 설명만 붙이면 될 때는 additionalContext만 쓴다.
시험 가이드 표현 vs 현재 문서

가이드는 "PostToolUse로 도구 결과를 변환한다"고만 쓴다. 현재 문서의 교체 필드는 updatedToolOutput(모든 도구, Python·TypeScript SDK 모두)이고, 예전의 updatedMCPToolOutput은 MCP 도구 전용이라 updatedToolOutput을 권한다. PostToolUse의 최상위 decision: "block"은 결과를 숨기지 않는다. 이유를 결과 옆에 덧붙일 뿐이고 Claude는 원래 출력도 본다.

05

훅이냐 프롬프트냐

Deterministic vs probabilistic
요구수단이유
"30만 원 초과 바우처 발급 금지"PreToolUse 훅위반 0건이 요구사항. 모델 판단과 무관하게 실행 전에 막는다
"날짜는 항상 같은 기준으로 해석"PostToolUse 훅입력 형식을 고정하면 해석 실수의 원인이 사라진다
모든 도구 호출 감사 로그PostToolUse (async 가능)항상 일어나야 하는 부수 작업
"사과는 짧고 정중하게"시스템 프롬프트어조는 판단 영역이고 어겨도 사고가 아니다
"화난 고객은 상급자 연결 고려"프롬프트 (+ 사람 검토)판단이 필요한 규칙

Claude Code 설정 훅에는 type: "prompt"·"agent"처럼 모델이 조건을 평가하는 훅도 있다. 판단이 필요한 검사를 위한 것이며, 결정적 보장은 코드로 짠 조건(SDK 콜백, 명령 훅)에서 나온다.

시험 판단 기준
  • 문제에 '반드시', '절대', '규정상', '보장' 같은 요구가 있으면 → 훅(코드)
  • 보기에 "프롬프트에 더 강하게", "few-shot 예시 추가"가 있으면 → 준수율 개선일 뿐 보장이 아니다
  • 도구마다 결과 형식이 달라 생기는 오류 → PostToolUse 정규화 / 실행 자체를 막아야 하면 → PreToolUse
  • 훅이 덮는 범위는 matcher에 걸린 도구뿐이다 → 같은 효과를 내는 다른 도구가 있으면 함께 지정한다(Write|Edit 훅은 Bash로 쓰는 파일을 막지 못한다)

시험 함정 · 흔한 오해

오해PostToolUse 훅으로 위험한 도구 호출을 막을 수 있다.
사실PostToolUse가 돌 때는 이미 실행이 끝났다. 실행을 막는 자리는 PreToolUse다.
오해updatedToolOutput으로 바꾸면 원본 데이터도 고쳐진다.
사실Claude에게 보이는 값만 바뀐다. 시스템의 실제 데이터와 텔레메트리의 원본은 그대로다.
오해matcher에 금액이나 파일 경로 조건을 걸 수 있다.
사실matcher는 도구 이름만 비교한다. 인자 조건은 콜백에서 tool_input을 보고 판단한다.
오해비동기 훅으로 빠르게 차단할 수 있다.
사실async 출력은 에이전트가 기다리지 않으므로 차단·수정·맥락 주입이 불가능하다.
