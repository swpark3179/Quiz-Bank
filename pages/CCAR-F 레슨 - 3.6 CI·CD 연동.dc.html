CI/CD의 Claude Code: -p·권한·JSON 출력

-p (--print) · --bare · --allowedTools · dontAsk · --output-format json · --json-schema · CLAUDE.md · 독립 리뷰 · 재실행

참고 레슨 · CertSafari 3.6 (1) · CertSafari 3.6 (2)  |  출제 도메인: 도메인 3 · Claude Code Configuration & Workflows (20%)

3.1 CLAUDE.md3.2 명령·스킬3.3 경로별 규칙3.4 플랜 모드3.5 반복 개선3.6 CI/CD

CI 러너에는 프롬프트에 답할 사람이 없다. 그래서 파이프라인 속 Claude Code는 시작 시점에 할 일, 허용 도구, 출력 형식, 프로젝트 기준을 모두 받아야 한다. 시험은 이 설정들과, 리뷰·테스트 생성 품질을 좌우하는 맥락 공급 방식을 묻는다. CI의 Claude Code는 "-p로 한 번 실행하고, 권한은 미리 정하고, 결과는 스키마로 받고, 리뷰는 코드를 쓴 세션과 분리한다"로 요약된다.

습득 포인트
  • -p(--print)로 비대화형 실행하기 — 대화형 입력을 기다리며 파이프라인이 멈추는 일 방지
  • --output-format json과 --json-schema로 기계가 파싱할 수 있는 구조화 결과를 받아 PR 인라인 코멘트로 게시하기
  • CLAUDE.md로 테스트 기준·픽스처 규칙·리뷰 기준 같은 프로젝트 맥락을 CI 실행에 공급하기
  • 코드를 생성한 세션이 아닌 독립 인스턴스로 리뷰하기
  • 재리뷰 때 이전 결과를 넘겨 새·미해결 문제만 보고하게 하기, 테스트 생성 때 기존 테스트를 넘겨 중복 막기
01

-p: 한 번 실행하고 끝나는 모드

Non-interactive runs

claude나 claude "질문"은 대화형 세션을 열어 다음 입력을 기다린다. -p(--print)를 붙이면 프롬프트 하나를 처리하고 종료한다(CLI 참조: "Query via SDK, then exit"). Agent SDK를 CLI로 쓰는 것이라 같은 도구·에이전트 루프를 쓴다.

성질CI에서 의미
표준 입력 읽기git diff main | claude -p "..."처럼 diff·로그를 파이프로 넣는다 (파이프 입력 상한 10MB)
종료 코드성공 0, 실패 시 0이 아닌 값 → 스크립트가 분기할 수 있다
--max-turns · --max-budget-usd에이전트 턴 수·추정 비용 상한 (print 모드 전용). 턴 상한에 닿으면 오류로 종료
--barehook·스킬·플러그인·MCP 서버·auto memory·CLAUDE.md 자동 탐색을 건너뛰어 어느 머신에서나 같은 결과. 인증은 ANTHROPIC_API_KEY 등에서만

--bare가 없으면 -p 세션도 대화형 세션처럼 작업 디렉터리와 ~/.claude의 설정(프로젝트 hook, .mcp.json 서버 포함)을 신뢰 확인 없이 로드한다. 헤드리스 문서는 스크립트·SDK 호출에 --bare를 권장하며, 이후 릴리스에서 -p의 기본값이 될 예정이라고 밝힌다.

02

권한은 실행 전에 정한다

Pre-approve, deny the rest

무인 실행에서는 "승인할까요?"에 답할 사람이 없으므로 권한을 시작 시점에 확정한다. 권한 모드를 지정하지 않은 claude -p 실행은 Manual 모드(설정값 default)로 시작하고, 승인이 필요한 호출은 허용 규칙·hook·--permission-prompt-tool 등이 승인하지 않는 한 거부된다(v2.1.302 이후).

수단동작
--allowedTools "Read,Bash(npm test)"나열한 도구·패턴은 묻지 않고 실행. 권한 규칙 문법을 쓴다 — Bash(git diff *)처럼 공백 + *가 접두사 매칭
--permission-mode dontAsk사전 승인되지 않은 것 중 프롬프트가 필요한 호출은 모두 거부. 문서가 "잠긴 CI"용으로 소개하는 모드
--permission-mode acceptEdits파일 쓰기와 mkdir·mv 같은 흔한 파일 명령은 자동 승인, 나머지 셸 명령은 허용 규칙 필요
--permission-mode autoclassifier가 행동을 검토. 비대화형 실행에서는 차단된 행동만 거부되고 실행은 계속된다
--tools · --disallowedTools쓸 수 있는 내장 도구 자체를 제한 / 거부 규칙 (--allowedTools는 "제한"이 아니라 "사전 승인")
# 테스트를 돌리고 실패를 고치는 CI 단계 (이 가이드의 예시) claude --bare -p "npm test를 실행하고 실패한 테스트를 고쳐라. 결과를 한 줄로 보고하라." \ --allowedTools "Read,Edit,Bash(npm test)" \ --permission-mode dontAsk \ --max-turns 20
시험 가이드 표현 vs 현재 문서

시험 가이드는 -p를 "대화형 입력 대기로 멈추는 것을 막는" 플래그로 설명한다. -p 없이 실행하면 세션이 사람 입력을 기다린다는 점에서 맞는 설명이다. 다만 2026년 10월 문서 기준으로 -p 실행 안에서 승인이 필요한 도구 호출은 기다리는 것이 아니라 거부된다. 그래서 실무 실패 양상은 "멈춤"보다 "필요한 도구가 거부돼 작업이 반쪽으로 끝남"이며, 처방은 --allowedTools·dontAsk·auto mode 같은 사전 권한 설정이다. 권한 호스트가 있는 실행이라면 --permission-prompts none(v2.1.259+)으로 호스트 응답을 기다리지 않게 한다.

03

기계가 읽는 결과: JSON과 스키마

--output-format json · --json-schema

--output-format은 text(기본)·json·stream-json을 받는다. json이면 결과 객체 하나에 텍스트 결과(result), session_id, 추정 비용(total_cost_usd) 등이 담긴다. 여기에 --json-schema를 주면 스키마에 맞는 출력이 structured_output 필드에 들어온다. Agent SDK 문서에 따르면 출력을 스키마로 검증해 맞지 않으면 다시 요청하고, 재시도 한도 안에 실패하면 오류가 된다.

# PR 리뷰 결과를 인라인 코멘트용 JSON으로 받기 (이 가이드의 예시) git diff origin/main...HEAD | claude --bare -p \ "이 diff를 리뷰하라. 기준은 첨부한 프로젝트 지침을 따른다." \ --append-system-prompt-file ./CLAUDE.md \ --output-format json \ --json-schema "$(cat .ci/findings.schema.json)" \ --permission-mode dontAsk --max-turns 10 > review.json # structured_output이 없으면(예: 요청 거절) 게시 단계로 넘어가지 않는다 jq -e '.structured_output.findings' review.json > findings.json || exit 1
# .ci/findings.schema.json — 인라인 코멘트에 필요한 위치 정보를 필수로 {"type": "object", "properties": {"findings": {"type": "array", "items": { "type": "object", "properties": { "path": {"type": "string"}, "line": {"type": "integer"}, "severity": {"type": "string", "enum": ["blocker", "major", "minor"]}, "message": {"type": "string"}}, "required": ["path", "line", "severity", "message"]}}}, "required": ["findings"]}

후속 단계는 findings.json의 각 항목을 path·line 위치에 PR 인라인 코멘트로 올린다. 주의점: 유효하지 않은 스키마는 실행 전에 오류로 끝나고, format 키워드는 검증되지 않으며, 유효한 구조화 출력 없이 끝나면 structured_output 필드 자체가 없으므로 사용 전에 존재를 확인한다.

CI에 붙이는 경로
경로특징
스크립트의 claude -p어떤 CI에서든 동작. 위처럼 JSON을 받아 게시 단계를 직접 만든다
GitHub Actions anthropics/claude-code-action@v1prompt가 없으면 @claude 멘션에 응답, 있으면 이벤트마다 자동 실행. CLI 인자는 claude_args로 넘기며, 인라인 코멘트용 MCP 서버는 그 --allowedTools에 mcp__github_inline_comment__create_inline_comment가 있을 때만 시작된다
GitLab CI/CD베타, GitLab이 유지 관리. CLI·Agent SDK 기반, CLAUDE.md를 따른다
관리형 Code ReviewTeam·Enterprise 플랜. 워크플로 없이 PR마다 심각도별 인라인 코멘트
04

CI 실행에 프로젝트 맥락 공급하기

CLAUDE.md and existing tests

CI 실행은 대화 이력 없이 시작하므로 프로젝트 지식은 저장소에서 와야 한다. 프로젝트 CLAUDE.md(./CLAUDE.md 또는 ./.claude/CLAUDE.md)는 매 세션 시작 시 읽히고 버전 관리로 팀과 공유된다. GitHub Actions 문서는 저장소 루트 CLAUDE.md에 코드 스타일, 리뷰 기준, 프로젝트 규칙을 정의하라고 권하고, 매 실행마다 읽히므로 간결하게 유지하라고 한다.

# CLAUDE.md 중 테스트 생성 품질을 좌우하는 부분 (이 가이드의 예시) ## Tests - 한 파일만 실행: pytest tests/billing/test_invoice.py -q - 픽스처: tests/fixtures/factories.py의 make_customer(), make_invoice()를 쓴다. DB를 직접 채우는 새 픽스처를 만들지 않는다. - 가치 있는 테스트: 경계값(0원, 통화 반올림), 과거 장애 회귀, 결제 API 실패 경로. - 쓰지 말 것: 단순 getter/setter 테스트, 구현 세부를 그대로 복사한 assert.

이런 내용은 코드를 읽어서는 알 수 없는 팀의 판단이다. best practices 문서도 코드에서 찾을 수 있는 것은 빼고 확인 명령, 오해를 부르는 지점, 저장소에 없는 결정만 적으라고 한다. "가치 있는 테스트" 기준이 없으면 테스트 생성은 저가치 테스트로 채워지기 쉽다.

테스트 생성 단계에는 기존 테스트 파일도 맥락으로 넘긴다. Common workflows 문서는 Claude가 기존 테스트 파일을 살펴 스타일·프레임워크·assertion 패턴을 맞춘다고 설명한다. 기존 테스트가 무엇을 이미 다루는지 보여 주면 같은 시나리오를 다시 제안하는 중복도 줄어든다. 예: "tests/billing/의 기존 테스트를 읽고, 거기서 다루지 않는 경로에 대해서만 테스트를 추가하라."

시험 가이드 표현 vs 현재 문서

시험 가이드는 CLAUDE.md를 "CI에서 호출된 Claude Code에 프로젝트 맥락을 주는 메커니즘"으로 설명한다. 기본 -p 실행에서는 그대로 맞다. 그러나 현재 문서가 스크립트·CI에 권장하는 --bare는 CLAUDE.md를 자동으로 읽지 않는다. bare 모드에서 같은 지침을 쓰려면 --append-system-prompt-file ./CLAUDE.md처럼 명시적으로 넘겨야 한다(위 예시). --bare가 -p의 기본값이 되면 이 차이는 더 중요해진다.

05

리뷰는 독립 인스턴스로, 재실행은 이전 결과와 함께

Independent reviewer · re-runs

코드를 생성한 세션의 컨텍스트에는 코드를 그렇게 쓴 이유가 이미 가득해, 자기 리뷰는 같은 맹점을 공유하기 쉽다. best practices 문서는 /code-review가 대화를 본 적 없는 새 서브에이전트에서 diff를 리뷰하므로 "코드를 만든 추론에 흔들리지 않는다"고 설명하고, 두 번째 세션을 가장 손쉬운 독립 리뷰어로 소개한다. CI에서는 생성 단계와 리뷰 단계를 별도 claude -p 실행으로 나누고, 리뷰 단계에서 생성 세션을 --continue·--resume으로 이어 붙이지 않는다.

파이프라인으로 보면 생성 실행 → 독립 리뷰 실행(새 세션, diff + 기준만) → structured_output을 인라인 코멘트로 게시 → findings.json을 다음 실행용으로 보관의 순서다.

새 커밋 뒤 재리뷰

PR에 커밋이 추가될 때마다 처음부터 리뷰하면, 이미 단 코멘트가 다시 달리고 고친 문제까지 반복 지적된다. 재실행에는 이전 리뷰 결과를 맥락으로 함께 넘기고, 새로 생긴 문제와 아직 해결되지 않은 문제만 보고하라고 지시한다.

# 재리뷰 프롬프트의 핵심 (이 가이드의 예시) prev-findings.json은 직전 리뷰에서 이미 게시한 지적 목록이다. 1) 이번 diff에서 해결된 항목은 보고하지 마라. 2) 아직 해결되지 않은 항목은 status를 "still_open"으로 표시하되 새 코멘트를 만들지 마라. 3) 이번 커밋에서 새로 생긴 문제만 status "new"로 보고하라.

관리형 Code Review도 비슷하게 동작한다. 푸시 뒤 자동으로 시작된 리뷰는 직전 리뷰 이후 바뀐 부분에 집중하고, 이전 지적에 달린 답글을 읽어 스레드를 해결하거나 후속 답글을 단다.

시험 판단 축
  • 리뷰 품질 문제 → 독립 인스턴스(새 세션·서브에이전트)로 분리했는가
  • 중복 코멘트 문제 → 이전 결과를 넘기고 new/미해결만 보고하게 했는가
  • 중복·저가치 테스트 문제 → 기존 테스트와 CLAUDE.md의 테스트 기준을 맥락으로 줬는가
  • 파싱 실패 문제 → --output-format json + --json-schema, 그리고 structured_output 존재 확인

시험 함정 · 흔한 오해

오해-p만 붙이면 CI에서 필요한 도구를 모두 쓸 수 있다.
사실권한 모드를 정하지 않은 -p 실행은 Manual 모드로 시작해 승인이 필요한 호출을 거부한다. --allowedTools·dontAsk·auto mode로 미리 정한다.
오해--json-schema를 주면 스키마에 맞춘 결과가 result 필드에 문자열로 들어온다.
사실스키마 결과는 structured_output 필드에 들어오고, 유효한 출력 없이 끝나면 그 필드가 없다. 쓰기 전에 존재를 확인한다.
오해코드를 만든 세션에 --continue로 리뷰를 이어 시키면 맥락이 풍부해 더 정확하다.
사실생성 과정의 추론이 남아 같은 맹점을 공유한다. 독립 인스턴스가 리뷰에 낫다.
오해--bare로 돌려도 저장소의 CLAUDE.md는 자동으로 적용된다.
사실bare 모드는 CLAUDE.md 자동 로드를 건너뛴다. 필요한 지침은 --append-system-prompt-file 등으로 넘긴다.
