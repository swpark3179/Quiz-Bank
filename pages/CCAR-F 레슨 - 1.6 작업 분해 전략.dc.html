작업 분해: 프롬프트 체이닝 vs 동적 분해

프롬프트 체이닝 · 게이트 · orchestrator-workers · 파일별 패스 + 통합 패스 · 적응형 조사 계획

참고 레슨 · CertSafari 1.6  |  출제 도메인: 도메인 1 · Agentic Architecture & Orchestration (27%)

1.1 에이전트 루프1.2 코디네이터1.3 서브에이전트 생성1.4 게이트·핸드오프1.5 SDK 훅1.6 작업 분해1.7 세션 관리

복잡한 작업은 어떻게든 쪼개야 한다. 시험이 묻는 것은 쪼갤지 말지가 아니라 계획을 코드가 쥘지, 모델이 쥘지다. 하위 작업이 입력과 상관없이 늘 같다면 코드가 순서를 고정하는 프롬프트 체이닝이 맞고, 하위 작업이 중간 결과를 보고 나서야 정해진다면 모델이 계획을 세우고 고쳐 가는 동적 분해가 맞다. 공식 문서는 이 구분을 "미리 정의된 코드 경로(workflow)"와 "모델이 스스로 과정을 이끄는 에이전트"로 부른다.

습득 포인트
  • 고정 순차 파이프라인(프롬프트 체이닝)과 동적·적응형 분해를 고르는 기준
  • 단계마다 별도 호출을 두고 사이에 코드 게이트를 넣는 체이닝 설계
  • 대형 코드 리뷰를 파일별 로컬 패스 + 교차 파일 통합 패스로 나누는 이유(주의력 희석)
  • 발견에 따라 하위 작업을 만들고 멈춤 조건·노력 상한을 두는 적응형 조사 계획
  • "레거시 코드에 테스트 추가" 같은 열린 과제를 구조 파악 → 우선순위 → 적응형 계획으로 분해
01

계획을 누가 쥐는가

Workflows vs agents

Anthropic의 Building effective agents는 agentic system을 둘로 나눈다. workflow는 LLM과 도구를 미리 정의된 코드 경로로 엮은 시스템이고, agent는 LLM이 자기 과정과 도구 사용을 동적으로 정하는 시스템이다. 같은 글은 가장 단순한 해법에서 출발해 결과가 실제로 좋아질 때만 복잡도를 올리라고 권한다. 검색과 예시를 붙인 단일 호출로 충분한 경우도 많다.

패턴하위 작업을 정하는 주체잘 맞는 경우
프롬프트 체이닝코드 (설계 시점)고정된 하위 작업으로 깔끔하게 나뉘는 일. 지연을 조금 감수하고 각 호출을 쉬운 일로 만들어 정확도를 얻는다
병렬화 (sectioning · voting)코드 (설계 시점)서로 독립인 하위 작업을 동시에 돌리거나, 같은 작업을 여러 관점으로 돌려 신뢰도를 높일 때
orchestrator-workers오케스트레이터 LLM (실행 시점, 입력마다)필요한 하위 작업을 미리 예측할 수 없는 일. 예: 과제마다 고칠 파일 수와 변경 성격이 달라지는 코딩
자율 에이전트모델 (매 턴)필요한 단계 수를 예측하기 어렵고 경로를 하드코딩할 수 없는 열린 문제
02

프롬프트 체이닝: 단계마다 별도 호출, 사이에 게이트

Prompt chaining with gates

체이닝은 작업을 순서 있는 단계로 나누고, 각 LLM 호출이 앞 단계의 출력을 받아 처리하게 한다. 단계 사이에는 programmatic check, 곧 게이트를 두어 진행이 궤도를 벗어나지 않았는지 코드로 확인한다. 예로 법무팀이 매일 들어오는 공급 계약서를 같은 순서로 검토한다고 하자. 어떤 계약서가 들어와도 단계 목록은 바뀌지 않으므로 계획을 모델에게 맡길 이유가 없다.

clauses = call_claude(EXTRACT_PROMPT, contract_text) # 1단계: 조항 추출 missing = REQUIRED_CLAUSES - {c["type"] for c in clauses} if missing: # 게이트: 판단은 코드가 return route_to_human(contract_id, missing=sorted(missing)) risks = [call_claude(RISK_PROMPT, c) for c in clauses] # 2단계: 조항별 평가 memo = call_claude(MEMO_PROMPT, {"clauses": clauses, "risks": risks}) # 3단계
BAD · 한 번의 호출에 단계 나열
system: "1) 조항을 추출하고 2) 누락을 확인하고 3) 위험을 평가한 뒤 4) 메모를 써라."

모델이 단계를 합치거나 건너뛰어도 코드는 알 수 없다. 중간 산출물이 없으니 게이트를 둘 자리도 없다.

GOOD · 코드가 순서를 쥔 별도 호출
extract() → gate() → assess() → memo()

단계마다 출력을 로그로 남기고 평가하며, 실패하면 그 지점에서 분기한다.

현재 문서의 표현

Prompting best practices는 최신 모델이 adaptive thinking과 서브에이전트 오케스트레이션으로 대부분의 다단계 추론을 내부에서 처리한다고 하면서도, 중간 출력을 검사해야 하거나 특정 파이프라인 구조를 강제해야 할 때는 명시적 체이닝이 여전히 유용하다고 적는다. 가장 흔한 형태는 self-correction 체인(초안 → 기준 대비 리뷰 → 수정)이다.

03

큰 코드 리뷰: 파일별 패스 + 통합 패스

Local passes, then one integration pass

수십 개 파일이 바뀐 PR을 한 번에 넣고 리뷰를 시키면 지적이 얕아진다. 원인은 창 크기보다 주의력이다. Effective context engineering 글은 컨텍스트의 토큰이 늘수록 그 안의 정보를 정확히 떠올리는 능력이 떨어지는 context rot이 모든 모델에서 나타난다고 설명하고, 컨텍스트를 수확 체감이 있는 유한한 자원(attention budget)으로 다루라고 한다.

패스입력찾는 것출력
로컬 패스 (파일당 1회)파일 하나의 diff와 그 주변 코드null 처리, 경계값, 자원 해제처럼 파일 안에서 드러나는 결함파일별 발견 목록 + 그 파일이 바꾼 공개 인터페이스 요약
통합 패스 (1회)원본 전체가 아니라 파일별 요약과 인터페이스 변경 목록호출부와 피호출부 불일치, 이름이 바뀐 필드, 순서 가정, 중복 지적중복을 없애고 순위를 매긴 최종 리뷰

예: 결제 모듈 PR에서 serializer.py는 amount_cents를 amount_minor로 바꿨는데 refund_worker.py는 옛 이름을 그대로 읽는다. 두 파일을 따로 보면 둘 다 멀쩡하다. 이 결함은 두 파일의 인터페이스 요약을 나란히 놓는 통합 패스에서만 보인다.

Claude Code에서의 형태

Claude Code의 dynamic workflows 문서에 이 구조를 그대로 요청하는 예시 프롬프트가 있다. PR에서 바뀐 파일마다 리뷰어를 하나씩 돌리고, 파일별 발견을 한 에이전트에 넘겨 순위를 매기고 중복을 없앤 요약을 만든다. 중간 결과는 Claude의 컨텍스트가 아니라 스크립트 변수에 머문다.

시험 판단 축
  • "컨텍스트 창이 더 큰 모델로 한 번에" 보기는 함정이다. 희석은 창 크기로 사라지지 않는다
  • 로컬 패스끼리는 서로 독립이므로 병렬(sectioning)로 돌릴 수 있다
  • 통합 패스에는 원문이 아니라 요약·인터페이스 변경을 넘긴다. 원문을 다 넣으면 통합 패스가 다시 희석된다
04

동적 분해: 발견이 다음 작업을 만든다

Adaptive decomposition

장애 원인 조사처럼 첫 결과를 보기 전에는 무엇을 봐야 할지 모르는 일이 있다. 이때는 orchestrator-workers나 에이전트 루프로 하위 작업을 실행 중에 만든다. orchestrator-workers 쿡북은 이를 두 단계로 설명한다. 분석·계획 단계에서 오케스트레이터가 이 입력에 필요한 하위 작업을 구조화된 설명으로 만들고, 실행 단계에서 각 워커가 원래 과제와 자기 몫의 지시를 함께 받아 수행한다.

예: "앱 푸시 알림이 일부 사용자에게만 하루 늦게 도착한다"

  1. 초기 계획 — 발송 경로와 최근 배포 목록 확인. 아직 가설 없음
  2. 발견: 늦은 알림은 모두 현지 자정 직후로 예약된 건 → 하위 작업 추가: 예약 시각 변환 코드 확인, 발송 스케줄러 설정 확인
  3. 발견: 스케줄러가 서버 시간대로 날짜를 계산함 → 하위 작업 추가: 영향받은 사용자 범위 추정. "배포 diff 전수 검토"는 우선순위를 내림
  4. 멈춤 조건 충족: 재현 시나리오 확보 + 수정 방향 하나 검증 → 결과 정리
동적 분해에 붙여야 할 안전장치 (Anthropic 멀티에이전트 리서치 시스템 글 등)
장치내용
노력을 복잡도에 맞추기리서치 시스템은 규칙을 프롬프트에 넣었다: 단순 사실 확인은 에이전트 1개·도구 호출 3~10회, 직접 비교는 서브에이전트 2~4개, 복잡한 조사는 10개 이상
계획을 밖에 저장리드 에이전트는 컨텍스트가 잘릴 때를 대비해 계획을 메모리에 저장하고 필요할 때 다시 읽었다
멈춤 조건완료 조건과 함께 최대 반복 횟수 같은 정지 조건을 둔다 (Building effective agents)
비용 인식같은 글의 측정으로 멀티에이전트 시스템은 일반 채팅보다 약 15배 토큰을 쓴다. 공유 컨텍스트와 의존성이 많은 작업에는 덜 맞는다
05

열린 과제: 레거시 코드에 테스트 추가

Map, rank, then adapt

"이 레거시 코드베이스에 포괄적인 테스트를 추가하라"는 하위 작업 목록을 처음부터 쓸 수 없는 전형적인 과제다. 그렇다고 파일 순서대로 테스트부터 쓰기 시작하면 가치가 낮은 곳에 노력을 쏟는다. 세 단계로 나누고, 단계 3의 계획은 고정하지 않는다.

1단계

구조 매핑

  • 진입점, 모듈 경계, 외부 의존(DB·시계·네트워크) 목록
  • 기존 테스트와 테스트가 없는 함수 찾기
  • 넓은 질문에서 시작해 좁혀 간다 (Common workflows의 팁)
2단계

고영향 영역 선정

  • 돈·권한·데이터 손실과 닿는 코드
  • 자주 바뀌는 파일, 장애 이력이 있는 경로
  • 결과물: 근거를 붙인 우선순위 목록
3단계

적응형 계획

  • 우선순위대로 진행
  • 테스트를 막는 의존성이 드러나면 계획을 고친다
  • 예: 정산 함수가 내부에서 현재 시각을 직접 읽는다는 게 드러나면, "시계를 주입할 수 있게 하는 작은 리팩터링"이 계획 맨 앞에 끼어든다
여러 세션에 걸칠 때

상태를 파일로

  • 첫 컨텍스트 창은 틀(테스트·setup 스크립트)을 깔고, 이후 창은 todo를 반복
  • 테스트 상태는 tests.json 같은 구조화 형식, 진행 메모는 자유 텍스트, 이력은 git

마지막 칸은 Prompting best practices의 다중 컨텍스트 창 권고를 요약한 것이다.

06

고르는 기준과 Claude Code의 선택지

Choosing a pattern
시험 판단 기준
  • 입력이 달라도 단계 목록이 같다 → 체이닝 + 게이트. 쿡북은 하위 작업을 미리 정의할 수 있으면 orchestrator-workers를 쓰지 말라고 한다(더 단순한 패턴으로 충분, 호출이 늘어 지연도 커짐)
  • 하위 작업이 서로 독립 → 병렬. 앞 결과가 뒤 입력이 된다 → 순차
  • 무엇을 할지가 중간 결과에 달렸다 → 동적 분해. 단, 멈춤 조건과 노력 상한을 함께 설계
  • 섞어도 된다: 큰 틀은 고정하고 한 단계(예: "의심 파일 심층 조사")만 에이전트로. 패턴은 처방이 아니라 조합하는 블록이다
Claude Code 문서가 정리한 "누가 계획을 쥐는가"
수단다음에 무엇을 실행할지 정하는 주체중간 결과가 머무는 곳규모
서브에이전트Claude, 턴마다Claude의 컨텍스트턴당 위임 몇 개
에이전트 팀리드 에이전트, 턴마다공유 작업 목록오래 도는 동료 몇 개
dynamic workflow스크립트스크립트 변수실행당 수십~수백 에이전트
시험 가이드 표현 vs 현재 문서

시험 가이드는 "고정 순차 파이프라인(prompt chaining) vs 동적 적응형 분해"라는 개념어를 쓴다. 현재 Claude Code에는 이를 제품 기능으로 옮긴 dynamic workflows가 있다. Claude가 과제에 맞는 JavaScript 오케스트레이션 스크립트를 쓰고 런타임이 백그라운드에서 실행하므로, 계획은 Claude가 동적으로 만들되 만들어진 계획은 코드로 고정되어 읽고 다시 실행할 수 있다. 개념 구분은 그대로이고, 현재 문서는 이를 "누가 계획을 쥐는가"라는 표로 설명한다.

시험 함정 · 흔한 오해

오해컨텍스트 창이 충분히 크면 PR 전체를 한 번에 리뷰하는 편이 맥락을 잃지 않아 낫다.
사실context rot은 모든 모델에서 나타나며 토큰이 늘수록 회상 정확도가 떨어진다. 파일별 패스 + 요약 기반 통합 패스가 주의를 집중시킨다.
오해오케스트레이터가 매번 계획을 세우는 동적 분해가 체이닝보다 항상 견고하다.
사실workflow는 잘 정의된 작업에 예측 가능성과 일관성을 준다. 하위 작업을 미리 정할 수 있으면 오케스트레이터는 호출과 지연만 늘린다.
오해시스템 프롬프트에 "1단계… 2단계…"를 적으면 프롬프트 체이닝이다.
사실체이닝은 단계마다 별도 API 호출이고 코드가 순서를 정한다. 그래야 중간 출력을 로그·평가하고 게이트에서 분기할 수 있다.
오해적응형 계획이란 처음 세운 조사 계획을 끝까지 충실히 따르는 것이다.
사실새 발견이 하위 작업을 추가·삭제·재정렬한다. 대신 멈춤 조건과 노력 상한이 있어야 비용과 오류 누적을 막는다.
