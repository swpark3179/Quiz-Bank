CCA-F에서 가장 자주 나오는 기초 판단은 "이 시나리오에는 어떤 모델을 써야 하는가"다. 원칙은 하나 — 요건을 충족하는 가장 저렴한 모델. 매일 부치는 계란말이에 셰프 나이프를 꺼내지 않듯, 태스크의 규모·복잡성·속도·비용에 맞춰 Opus / Sonnet / Haiku를 고른다.

습득 포인트
  • Opus / Sonnet / Haiku의 특성·비용·레이턴시와 권장 용도
  • 사용 사례에 따른 모델 선정 기준과 단계적(라우팅) 구성
  • 모델 ID의 구조와 프로덕션에서의 고정 원칙
  • 컨텍스트 윈도우의 감각과 함정, 멀티모달(이미지 입력) 개요
01

설계 사상 — 배경 지식시험 범위 밖

CAI · 3H · RSP

교재는 Anthropic의 미션·Constitutional AI·RSP를 공식 가이드의 Out-of-Scope로 분류한다. 암기 대상이 아니라 Claude의 동작을 이해하는 배경으로만 짚는다.

  • Constitutional AI(CAI) — 사전에 정한 원칙(헌법)에 비추어 AI가 스스로 자기 출력을 비평·수정하도록 훈련하는 기법. 외부 감시자나 금지어 필터와는 다르다.
  • 3H 원칙 — Honest(모르면 모른다고 함) · Harmless(유해 출력 회피) · Helpful(거절로 끝내지 않고 대안 제시). Harmless와 Helpful은 때로 충돌하며, 과도한 거절(over-refusal)도 실점으로 본다.
  • RSP / ASL — 모델 능력에 비례해 보안 대책을 강화하는 Anthropic의 공개 정책. 운영 보안(키 관리·출력 최종 확인·권한 관리)은 이용자와의 공동 책임이다.
02

모델 패밀리

Opus · Sonnet · Haiku
Opus
최고 성능 · 플래그십
느림 · 비용 높음
복잡한 추론 · 코딩 · 에이전트
비유: 난제를 푸는 베테랑 변호사
Sonnet
성능–비용 균형
중간 속도 · 중간 비용
일반 애플리케이션 · 대량 처리
비유: 균형 잡힌 중견 컨설턴트
Haiku
경량 · 고속 · 저비용
가장 빠름 · 가장 저렴
분류 · 추출 · 챗 · 대량 배치
비유: 손 빠른 신입 어시스턴트
축1위2위3위
추론 능력OpusSonnetHaiku
속도HaikuSonnetOpus
비용 효율HaikuSonnetOpus

암기 요령: 이름은 시의 길이에서 왔다 — Opus(대작) > Sonnet(14행시) > Haiku(17음). 시험에서는 '속도'와 '정확도'를 맞바꿔 놓은 디스트랙터가 자주 나온다.

오해최신·최고 모델이니 항상 Opus를 써야 한다.
사실세대 축과 패밀리 축은 다르다. 새 세대의 경량 모델이 이전 세대 상위 모델을 앞서기도 한다. 기준은 '요건 충족 + 최저 비용'.
03

모델 선정의 판단 기준

Cost-aware model selection
BAD · 모든 요청에 최상위 모델
for log in millions_of_logs: classify(log, model=OPUS) # 단순 분류에도 Opus

비용이 요청 수에 비례해 선형으로 불어난다.

GOOD · 태스크별로 나눠 쓴다
for log in millions_of_logs: classify(log, model=HAIKU) # 대량·단순 for incident in critical_incidents: root_cause(incident, model=OPUS) # 소량·복잡

대량 처리는 경량 모델, 소수의 난제만 상위 모델.

시나리오 → 모델 매핑
시나리오의 신호선택
대량 · 단순 분류/추출 · 비용 최우선Haiku — 단, 수백 건 샘플로 정확도를 먼저 검증한 뒤 투입
일반적인 애플리케이션 · 품질과 비용의 균형Sonnet
복잡한 추론 · 코딩 · 장기 에이전트 작업Opus
대부분 단순 + 일부 복잡한 혼합 트래픽 · SLA 존재라우팅 — 경량 모델이 먼저 분류·응답하고, 필요한 건만 상위 모델로 에스컬레이션 (도메인 1의 라우팅형 에이전트)
라우팅 설계 시 주의

라우터(경량 모델)가 '간단하다'고 잘못 판단하면 고객 경험이 나빠진다. 신뢰도 임곗값(confidence threshold)과 폴백(fallback)을 함께 설계한다. 비용은 '전부 상위 모델'보다 크게 줄어든다(다수는 1회 호출, 소수만 2단계 호출).

04

모델 ID와 버저닝

Pinning for reproducibility
# 구조: claude-{family}-{version}[-{snapshot date}] "claude-haiku-4-5" # 패밀리 + 버전 "claude-haiku-4-5-20251001" # 날짜까지 명시한 스냅샷
  • 프로덕션은 고정, 검증 환경은 최신 추종 — 별칭(alias)은 나중에 같은 패밀리의 새 버전을 가리킬 수 있어 재현성을 해친다.
  • 고정의 대가: 버그 수정·개선도 자동으로 따라오지 않는다 → 정기 평가와 업데이트 주기를 함께 설계한다.
교재 최신 정보 노트

명명 규칙은 세대마다 조금 다르다. 교재는 최근 세대에서는 날짜 없는 ID 자체가 고정 스냅샷으로 쓰인다고 보완 설명한다. 어느 세대든 시험의 정답 논리는 같다 — 가장 구체적으로 고정된 ID를 고른다. 실제 ID는 공식 Models 문서에서 확인한다.

05

컨텍스트 윈도우

Context window ≠ performance

컨텍스트 윈도우 = Claude가 한 번에 시야에 넣을 수 있는 토큰 양(모델별로 수십만~백만 토큰급). '책상의 넓이'에 비유된다 — 넓을수록 많이 펼칠 수 있지만, 어디에 무엇이 있는지 파악하는 능력(컨텍스트 관리)은 별개다.

오해윈도우가 1M 토큰이니 전사 문서를 통째로 넣고 질문하면 된다.
사실과하게 채우면 Lost in the Middle(중간부 정보 누락)과 컨텍스트 열화가 일어난다. 정석은 RAG(관련 청크만 검색해 투입) · 요약 압축 · 청크 랭킹.

윈도우 전 구간 활용도를 재는 업계 표준 테스트가 'Needle in a Haystack'이다. 컨텍스트 열화 방지는 도메인 5(교재 제17·18장)에서 본격적으로 다룬다.

자가 점검 퀴즈

점수 0 / 6
Q1모델 선정
고객 문의 메일 하루 200만 건에 5개 카테고리 라벨을 붙인다. 문장은 짧고 판단은 단순하며, 비용 절감이 최우선이다.가장 적절한 모델은?
정답 (C)

대량·단순·비용 최우선 = Haiku의 전형. 상위 모델은 과잉 스펙으로 비용이 수십 배 커지기 쉽다. '단순하다'는 판단도 수백 건 샘플로 정확도를 측정해 검증한 뒤 투입한다.

Q2라우팅
사내 IT 헬프데스크 봇. 문의의 75%는 비밀번호 초기화 같은 정형 FAQ이고, 25%는 로그를 보고 원인을 추론해야 한다. 대부분의 문의에 수 초 안에 답해야 한다.가장 합리적인 설계는?
정답 (B)

단계적 처리(라우팅)는 '요건을 충족하는 가장 저렴한 모델' 원칙을 구현한 패턴이다. 전부 Opus는 비용·지연이 크고, 전부 Haiku는 복잡한 25%에서 품질이 부족하다. 라우터 오판에 대비해 임곗값과 폴백을 둔다.

Q3모델 ID
프로덕션에서 동작 재현성을 최대화하려면 model을 어떻게 지정해야 하는가?
정답 (D)

별칭은 나중에 새 버전을 가리킬 수 있어 동작이 바뀔 위험이 있다. 프로덕션은 고정 ID, 검증 환경은 최신 추종으로 나누고 정기 평가로 업데이트한다.

Q4컨텍스트
1M 토큰 윈도우 모델에 400K 토큰 분량의 규정집 전체를 넣고 질문했더니, 문서 중간에 있는 조항을 자주 놓친다.가장 가능성 높은 원인과 대책은?
정답 (A)

400K는 1M 안에 들어가므로 초과가 아니다. 윈도우 중반부 정보의 참조 정확도가 떨어지는 현상이 원인이며, 필요한 정보만 골라 넣는 RAG·요약·청크 랭킹이 정석 대책이다.

Q5설계 사상
Constitutional AI를 가장 잘 설명한 것은?
정답 (B)

CAI의 핵심은 '자율적 자기 성찰'이다. 금지어 필터는 애플리케이션 계층의 대책이고, 과도한 거절은 Helpful 원칙에 어긋나 오히려 실점으로 본다.

Q6멀티모달
보안 카메라 녹화 영상에서 이상 행동을 찾고 싶다. Claude에 입력하는 방법으로 적절한 것은?
정답 (C)

Claude는 이미지 입력을 지원하지만 동영상·음성은 직접 지원하지 않는다. 필요한 프레임을 뽑아 이미지 블록으로 넣는다.
