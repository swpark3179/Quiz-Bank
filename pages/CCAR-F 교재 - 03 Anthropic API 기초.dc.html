Anthropic API 기초

Messages API 구조 · 주요 파라미터 · stop_reason · 에러·재시도 · 캐시·Batches

원문 · koding.kr — 제4장  |  출제 도메인: 전 도메인 공통 기초

⓪ 시험 개요① 환경② 모델③ API④ 프롬프트⑤ 구조화 출력⑥ Tool Use⑦ MCP⑧ 이후 장⑨ 자가진단

Anthropic API의 중심은 Messages 엔드포인트 — '메시지 리스트를 보내면 어시스턴트 응답이 돌아온다'는 단순한 구조다. 그 위에 system 프롬프트·샘플링 파라미터·툴 호출이 얹히며, Tool Use·MCP 문제에서도 API 파라미터 지식을 전제로 묻는다.

습득 포인트
  • 요청/응답 구조와 role·content 규칙 (특히 system은 최상위 필드)
  • model · max_tokens · temperature · top_p · stop_sequences의 의미
  • stop_reason 값에 따른 분기, 에러 코드와 재시도 전략
  • 프롬프트 캐시와 Message Batches API의 적용 판단 (스트리밍·요금 상세는 시험 범위 밖)

max_tokens✓생성(출력) 토큰의 최대 수

02

메시지 규칙

roles & content
  • 첫 메시지는 user, 이후 user ↔ assistant 교대가 원칙 — 이력을 쌓을 때 같은 role이 연속되면 하나로 합치는 헬퍼를 두는 것이 정석
  • messages 안에 role: "system"은 없다 — system은 최상위 system 인자로 넘긴다 (OpenAI 형식과의 대표적 차이, 이식 시 최대 함정)
BAD · OpenAI 스타일
messages=[ {"role": "system", "content": "정중한 어시스턴트"}, {"role": "user", "content": "안녕하세요"}, ] # invalid_request_error
GOOD · 최상위 system
client.messages.create( model=MODEL, max_tokens=1024, system="정중한 어시스턴트", messages=[{"role": "user", "content": "안녕하세요"}], )

content의 두 가지 형식 — 동등하다

{"role": "user", "content": "Hi"} # 문자열(축약형) {"role": "user", "content": [{"type": "text", "text": "Hi"}]} # 콘텐츠 블록 리스트

텍스트만이면 문자열로 충분하다. 이미지+텍스트처럼 여러 블록을 섞을 때는 리스트 형식이 필수. 응답의 content가 항상 블록 리스트인 것과 같은 구조다.

03

주요 파라미터

temperature · max_tokens · stop_sequences
temperature — '요리사의 기분' (0 = 레시피 그대로, 1 = 기분 따라 변주)
용도권장 값이유
구조화 출력 · 분류 · 추출0.0포맷 위반(키 흔들림·따옴표 혼재)을 최소화
FAQ · 요약0.0~0.3일관성 우선
일반 대화0.5~0.7약간의 다양성
창작 · 브레인스토밍0.7~1.0다양한 발상
범위 주의

Anthropic API의 temperature는 0~1이다(1.0이 최대). 다른 API처럼 0~2 범위로 1.5를 넘기면 invalid_request_error. top_p/top_k는 기본값으로 두고 한 번에 하나씩만 조정한다.

  • max_tokens = 출력 상한이지 입력 상한이 아니다(입력은 컨텍스트 윈도우가 제한). 크게 잡아도 실제 생성분만 과금되지만, 모델별 최대치를 넘으면 에러.
  • stop_sequences — 예: ["</done>"]. 일치하면 생성이 멈추고 stop_reason이 "stop_sequence"가 된다.
04

응답 구조와 stop_reason

Response anatomy
response.id # 메시지 ID response.role # "assistant" response.content # 블록 리스트: text / tool_use / thinking … response.stop_reason # 왜 멈췄는가 response.usage # input_tokens / output_tokens
stop_reason의미앱이 할 일
end_turn모델이 자연스럽게 응답 완료최종 답변으로 사용
max_tokens출력 상한 도달잘림 감지 → 이어받기 또는 상한 조정
stop_sequence지정한 중단 문자열과 일치후처리 진행
tool_use툴 호출 요구툴 실행 → tool_result 반환 (에이전트 루프)

content 블록 종류: text(텍스트) · tool_use(툴 호출) · thinking(Extended Thinking 사고 과정). image는 입력 전용.

05

스트리밍시험 범위 밖

messages.stream()

토큰을 받는 대로 표시해 사용자가 느끼는 대기 시간을 줄인다 — 채팅 UI에 필수급. 전체 결과만 필요한 배치 처리에는 불필요하다. stream.text_stream으로 표시하고, 끝나면 get_final_message()로 최종 메시지(usage 포함)를 얻는다. 도중 연결 끊김에 대비한 예외 처리를 잊지 않는다.

06

에러와 재시도

Errors · rate limits
HTTP종류대처
400invalid_request_error요청 구조·파라미터 확인
401authentication_errorAPI 키 확인
403permission_error모델 접근 권한 확인
404not_found_error엔드포인트·리소스 확인
429rate_limit_error지수 백오프(1→2→4→8초…)로 재시도
500 / 529api_error / overloaded_error서버 측 문제·과부하 → 백오프 후 재시도
429를 받았을 때의 판단 축
  • 429는 '전면 중단'이 아니라 '잠깐 기다려라'는 신호다.
  • SDK의 자동 재시도(max_retries) + 대량 병렬 처리에는 클라이언트 쪽 백오프 구현.
  • 여러 클라이언트가 동시에 재시도하는 썬더링 허드를 피하려면 jitter(무작위 흔들림)를 더한다.
  • 즉시 연속 재시도, 다른 키로 돌려쓰기는 오답 — 후자는 정책 위반 소지도 있다.
07

토큰 과금과 프롬프트 캐시

Pricing · prompt caching
  • 과금 = 입력 토큰 + 출력 토큰 (출력 단가가 입력보다 몇 배 높다) + 캐시 쓰기/읽기. 단가는 Opus > Sonnet > Haiku.
  • 한국어는 영어보다 글자당 토큰이 잘게 쪼개지는 경향이 있어, 같은 분량이라도 토큰·비용이 늘어난다.
BAD · 긴 system을 매번 정가로
for q in questions: client.messages.create( model=MODEL, max_tokens=256, system=LONG_MANUAL, # 10K 토큰 × 매 요청 messages=[{"role": "user", "content": q}], )
GOOD · 정적 접두부를 캐시
system=[{ "type": "text", "text": LONG_MANUAL, "cache_control": {"type": "ephemeral"}, }]

두 번째 요청부터 같은 접두부는 할인된 캐시 읽기 가격으로 재사용된다.

캐시의 성질

캐시는 프롬프트 앞부분부터 일치하는 접두부(prefix)에만 작동한다 → 정적 내용은 앞, 매번 바뀌는 내용은 뒤. 기본 TTL은 5분(1시간 옵션도 있음)이고, 첫 쓰기는 정가보다 조금 비싸므로 짧게 한두 번 쓰고 끝나는 용도에서는 오히려 손해일 수 있다.

08

Message Batches API

Asynchronous batch processing

동기 API가 '창구에서 주문해 바로 받는 패스트푸드'라면, Batches API는 '서류를 한꺼번에 부쳐 두고 나중에 결과를 받는 우편 신청'이다.

항목내용
처리 방식여러 요청을 하나의 배치로 투입 → 나중에 결과를 일괄 회수 (비동기)
비용표준 Messages API의 약 50%
처리 시간배치당 최대 24시간 이내(대부분 더 빠름) · 응답 시간 SLA 없음
결과 대조요청마다 붙인 고유 custom_id로 매칭 (결과 순서로는 알 수 없음)
부적합실시간 응답 · 대화 · 앞 턴 결과를 보고 다음 요청을 짜는 멀티턴 툴 호출
batch = client.messages.batches.create(requests=[ {"custom_id": f"review-{i}", "params": {"model": MODEL, "max_tokens": 50, "messages": [{"role": "user", "content": f"긍정/부정 분류: {r}"}]}} for i, r in enumerate(reviews) ]) print(batch.id, batch.processing_status) # 나중에 상태 확인·결과 회수
API 선택의 판단 축 — "사용자를 기다리게 하는가?"
  • 사람이 화면 앞에서 기다린다 → 동기 Messages API (필요하면 스트리밍)
  • 야간 배치처럼 아무도 기다리지 않는 대량·독립 요청 → Message Batches API
비용 최적화 종합 — 대용량 사내 문서 Q&A

질문마다 다른 부분을 참조하는 1,000페이지 문서라면 전체를 매번 넣거나(캐시를 써도) 통째로 요약하는 것보다, RAG로 관련 청크만 넣고 중간 등급 모델로 처리하는 편이 비용·품질 균형이 가장 좋다. 핵심 원칙: 필요한 정보만, 필요한 만큼.

자가 점검 퀴즈

점수 0 / 8
Q1요청 구조
OpenAI 호환 코드를 Anthropic API로 옮기는 중이다. 시스템 지시문은 어디에 넣어야 하는가?
정답 (B)

Anthropic API에는 system role 메시지가 없고 최상위 system 필드가 정식 사양이다. 별도 필드로 분리돼 있어 프롬프트 캐시와도 궁합이 좋다.

Q2파라미터
송장 PDF 텍스트에서 필드를 뽑아 엄격한 JSON으로 출력하는 작업이다. temperature는?
정답 (A)

구조가 엄격한 출력은 저온도가 원칙이다. 고온도에서는 키 이름·enum 값·따옴표가 흔들린다. 1.8은 Anthropic의 허용 범위(0~1)를 벗어나 에러가 난다.

Q3max_tokens
max_tokens에 대한 설명으로 옳은 것은?
정답 (C)

max_tokens는 출력 쪽 상한이다. 입력은 컨텍스트 윈도우가 제한한다. 크게 잡아도 생성된 만큼만 과금되지만 모델별 최대치는 넘을 수 없다.

Q4stop_reason
응답의 stop_reason이 "max_tokens"였다. 앱이 가장 먼저 고려해야 할 것은?
정답 (D)

max_tokens는 상한에 걸려 멈췄다는 뜻이다. 툴 실행 분기는 tool_use, 정상 완료는 end_turn이다.

Q5재시도
대량 병렬 처리 중 429 rate_limit_error가 늘어났다. 가장 적절한 대응은?
정답 (B)

429는 '조금 기다려라'는 신호다. 대기 시간을 점점 늘리고, 여러 워커가 동시에 몰리지 않도록 무작위 흔들림을 더한다. 연속 재시도는 상황을 악화시키고 키 돌려쓰기는 정책 위반 소지가 있다.

Q6프롬프트 캐시
모든 요청에 똑같은 20K 토큰 제품 매뉴얼을 붙이는 상담 봇이 있다. 매 요청의 질문만 다르다. 비용을 가장 줄이는 구성은?
정답 (C)

캐시는 앞부분부터 일치하는 접두부에만 작동한다. 정적인 매뉴얼을 앞에 두고 캐시해야 두 번째 요청부터 할인된다. 날짜처럼 바뀌는 값이 앞에 오면 매번 캐시 미스가 난다. 과도한 요약은 품질을 떨어뜨린다.

Q7Batches
매일 밤 전날 접수된 상담 기록 50만 건을 요약해 다음 날 아침 리포트에 쓴다. 실시간성은 필요 없고 비용을 최대한 낮추고 싶다.가장 적절한 선택은?
정답 (A)

아무도 기다리지 않는 대량·독립 요청은 Batches API의 전형이다. 스트리밍은 체감 대기 시간을 줄이는 UI 기능이라 비용과 무관하고, temperature는 속도와 무관하다.

Q8Batches
Batches API로 돌려받은 결과를 원래 요청과 짝지으려면?
정답 (D)

배치는 병렬·비동기로 처리돼 순서로는 대응 관계를 알 수 없다. 요청마다 중복 없는 custom_id를 붙여 결과를 매칭한다. batch.id는 배치 전체의 식별자다.
