Tool Use (Function Calling)

에이전트 루프 · tool_use/tool_result · 병렬 호출 · tool_choice · 툴 설계 원칙

원문 · koding.kr — 제7장  |  출제 도메인: 도메인 2 (18%)

⓪ 시험 개요① 환경② 모델③ API④ 프롬프트⑤ 구조화 출력⑥ Tool Use⑦ MCP⑧ 이후 장⑨ 자가진단

LLM은 기본적으로 '텍스트를 넣으면 텍스트를 돌려주는' 존재다. 외부 함수·API·DB를 부를 수 있게 되면 세계의 상태를 가져오고 작업을 실행하는 에이전트가 된다. Claude는 머리가 명석한 상담원이지만 직접 전화를 걸지는 못한다 — Tool Use는 상담원의 지시로 옆의 어시스턴트(앱)가 실제 작업을 하는 분업 구조다. 도메인 2(18%)의 출발점이다.

습득 포인트
  • 요청 → tool_use → 툴 실행 → tool_result → 최종 답변의 흐름
  • 툴 정의 3요소(name · description · input_schema)와 description의 역할
  • 에이전트 루프: stop_reason 분기 · tool_use_id 매칭 · 무한 루프 방지
  • 에러 반환(is_error) · 병렬 툴 호출 · tool_choice · 툴 설계 원칙(단일 책무, 적정 개수)
01

기본 흐름

Claude decides, the app executes
  1. 앱이 messages + tools 정의를 보낸다
  2. Claude가 tool_use 블록을 반환한다 — stop_reason = "tool_use"
  3. 앱이 해당 툴(함수·외부 API)을 실행한다
  4. 실행 결과를 tool_result 블록으로 만들어 user 메시지에 담아 다시 보낸다
  5. Claude가 결과를 통합해 최종 텍스트 답변을 반환한다 — stop_reason = "end_turn"
분업 모델

Claude 자신은 외부 API를 호출하지 않는다. Claude가 "API를 호출했다"고 말해도 실제로는 앱이 tool_use를 받아 실행한 것이다. 덕분에 외부 I/O의 제어권이 앱 쪽에 남아 감사 · 샌드박스 · 타임아웃 제어가 쉬워진다.

02

툴 정의 스키마

name · description · input_schema
요소역할
name툴 식별자 (snake_case 권장). Claude가 선택할 때 쓴다
descriptionClaude가 툴을 고르는 판단 재료 — 무엇을 하는지 + 언제 써야 하는지를 구체적으로
input_schemaJSON 스키마 — 인자 타입 · 필수 항목 · enum
BAD · 판단 재료 부족
{"name": "search", "description": "검색한다"}

무엇을, 언제 검색하는지 알 수 없다.

GOOD · 용도와 사용 시점
{"name": "search_documents", "description": "사내 문서를 전문 검색한다. 사용자가 규정·매뉴얼·과거 안건 정보를 요청할 때 사용."}

툴을 늘리기 전에 description의 질부터 개선하는 편이 선택 정확도에 더 잘 듣는 경우가 많다.

03

에이전트 루프

Loop on stop_reason
messages = [{"role": "user", "content": user_message}] for _ in range(MAX_ITERATIONS): # 무한 루프 방지 (보통 5~10회) resp = client.messages.create(model=MODEL, max_tokens=1024, tools=tools, messages=messages) messages.append({"role": "assistant", "content": resp.content}) # text+tool_use 전체 보존 if resp.stop_reason == "end_turn": return final_text(resp) if resp.stop_reason == "tool_use": results = [] for block in resp.content: if block.type == "tool_use": output = run_tool(block.name, block.input) # 앱이 실행 results.append({"type": "tool_result", "tool_use_id": block.id, # 1:1 매칭 "content": json.dumps(output, ensure_ascii=False)}) messages.append({"role": "user", "content": results}) # user role로 반환 raise RuntimeError("max iterations exceeded")
포인트주의
어시스턴트 응답을 이력에 추가텍스트 + tool_use를 포함한 content 전체를 보존
분기 근거stop_reason == "tool_use" — 응답 길이나 문구가 아니다
결과 반환tool_result는 user role 메시지에 담는다 (assistant 아님, 별도 tool role 없음)
대응 관계tool_use_id = 해당 tool_use.id (불일치 시 에러)
종료 보장MAX_ITERATIONS로 중단
04

블록 구조와 에러 반환

tool_use · tool_result · is_error
tool_use (Claude → 앱)
{"type": "tool_use", "id": "toolu_01ABC…", "name": "get_weather", "input": {"city": "Seoul"}}
tool_result (앱 → Claude)
{"type": "tool_result", "tool_use_id": "toolu_01ABC…", "content": "{\"temp\": 22}", "is_error": false}

툴 실행이 실패하면 is_error: true와 함께 무엇이 일어났고 어떻게 대처할 수 있는지를 구조적으로 알린다 (예: "외부 API 타임아웃. 10초 후 재시도 권장"). Claude는 이를 보고 다른 툴 시도·사용자 안내 등 스스로 복구를 시도한다.

보안

스택 트레이스 같은 내부 정보를 그대로 반환하지 않는다. 같은 툴이 반복 호출된다면 에러 메시지가 모호하거나 description이 불분명한 신호다 — is_error + 명확한 메시지, 그리고 반복 상한으로 막는다.

05

병렬 툴 호출과 tool_choice

parallel tool use · tool_choice

Claude는 한 턴에 여러 tool_use 블록을 낼 수 있다 — 날씨 + 환율 + 주가처럼 독립적인 조회에 효과적이다. 반면 A의 결과로 B의 인자가 정해지는 순차 의존이 있으면 병렬 실행이 잘못된 결과를 낳는다.

tool_choice={"type": "auto", "disable_parallel_tool_use": True} # 병렬 호출 끄기
tool_choice동작용도
{"type": "auto"} (기본값)Claude가 판단일반 대화 에이전트
{"type": "any"}어떤 툴이든 하나는 반드시 호출툴 호출이 필수인 플로
{"type": "tool", "name": "…"}특정 툴을 반드시 호출구조화 출력 (⑤)

참고: 툴을 정의해 두되 이번 턴에는 호출을 막는 {"type": "none"}도 있다.

06

툴 설계 원칙

Single responsibility · right-sized toolset

단일 책무

BAD · 만능 툴
{"name": "user_action", "description": "조회·갱신·삭제·검색·메일·SMS", "input_schema": {"properties": { "action": {"type": "string"}, …}}}

description이 비대해지고 오용이 잦다.

GOOD · 1툴 1역할
get_user · update_user delete_user · search_users

선택 정확도가 오르고 오용이 준다.

툴 개수와 추론 부하

Claude는 매 턴 등록된 모든 툴 정의를 읽고 무엇을 쓸지 판단한다. 툴이 늘면 비교 대상이 늘어 비슷한 툴끼리 헷갈리고, 토큰·지연도 늘어난다.

교재의 경험칙
툴 수영향
5개 이하최적
6~15개허용 범위
16개 이상정확도 저하 · 토큰 소비 증가
30개 이상설계의 근본적 재검토 필요
툴이 너무 많을 때의 판단 축
  • 문제는 개수(count)이지 description 길이가 아니다 → description을 한 줄로 깎으면 판단 재료만 사라져 오히려 악화
  • 정답은 Claude가 한 번에 보는 툴 수를 줄이는 것: 관련 툴을 서브에이전트로 떼어내 상위 에이전트는 소수의 위임 툴만 갖게 하거나, 고수준 → 저수준으로 계층화
  • 비유: 메뉴 100개짜리 식당은 설명문을 줄이는 게 아니라 코스(카테고리)로 묶어야 한다
개선 1단계

현황 분석

  • 툴을 기능 카테고리로 분류
  • 이용 빈도·의존 관계 시각화
개선 2단계

서브에이전트 계층화

  • 카테고리별 서브에이전트가 자기 툴 보유
  • 상위(허브)는 위임 판단만 — 툴 5개 안팎
개선 3단계

툴 정의 리팩터링

  • 복합 툴 분할(단일 책무)
  • 언제 쓰고 언제 쓰지 않는지 description에 명시
참고 (교재 보완)

대규모 툴 환경 옵션

  • Tool Search Tool — 필요할 때 툴 정의를 검색해 로딩
  • Programmatic Tool Calling — 코드 실행 환경에서 툴을 코드로 호출

흔한 오해

오해tool_result는 Claude의 응답이니 assistant role로 보낸다.
사실tool_result는 user role 메시지의 내용으로 보낸다 (API 사양).
오해툴을 많이 붙일수록 에이전트가 똑똑해진다.
사실판단 부하로 정확도·지연이 나빠진다. 적정 개수 + 서브에이전트 분리.
오해병렬 툴 호출은 항상 더 빠르고 좋다.
사실의존 관계가 있으면 잘못된 인자로 실행된다 → disable_parallel_tool_use.

자가 점검 퀴즈

점수 0 / 8
Q1분업 모델
Claude가 "환율 API를 조회해 보니…"라고 답했다. 실제로 환율 API를 호출한 주체는?
정답 (B)

Tool Use는 'Claude는 판단, 앱은 실행'의 분업이다. Claude는 어떤 툴을 어떤 인자로 부를지 결정할 뿐, 실행은 앱이 한다(Anthropic 서버 측에서 실행되는 일부 내장 툴은 예외).

Q2tool_result
툴 실행 결과(tool_result 블록)를 담아 보내는 메시지의 role은?
정답 (C)

Anthropic API에서는 tool_result를 user role 메시지에 담는다. 별도의 tool role은 없다.

Q3에이전트 루프
에이전트 루프에서 '툴을 실행할지, 최종 답변으로 끝낼지'를 판단하는 근거는?
정답 (A)

stop_reason이 루프 제어의 유일하게 신뢰할 수 있는 신호다. 텍스트 내용이나 길이로 추측하면 오작동한다.

Q4병렬 호출
'주문 조회' 툴의 결과로 얻은 송장 번호를 '배송 추적' 툴의 인자로 써야 한다. 가끔 두 툴이 동시에 호출돼 배송 추적이 빈 인자로 실패한다.가장 적절한 조치는?
정답 (D)

순차 의존이 있는 툴은 병렬 실행을 막아야 한다. 만능 툴로 합치는 것은 단일 책무 원칙에 어긋나고, any는 '반드시 호출'일 뿐 병렬 여부와 무관하다.

Q5툴 개수
고객 지원 에이전트에 툴 40개를 등록했더니 지연이 크게 늘고 엉뚱한 툴을 고르는 일이 잦다. 가장 적절한 대응은?
정답 (B)

원인은 Claude가 한 번에 보는 툴의 '수'다. description을 깎으면 판단 재료가 사라져 정확도가 더 떨어진다. 서브에이전트화·계층화로 수 자체를 줄인다.

Q6단일 책무
manage_order(action: string, payload: object) 하나로 생성·취소·조회·환불을 처리하는 툴이 있다. 가장 좋은 개선은?
정답 (C)

1툴 1역할로 나누면 각 툴의 스키마가 명확해지고 선택 정확도가 오른다. '툴 수가 적을수록 좋다'는 개수가 과도할 때의 이야기이며, 복합 책무 툴을 정당화하지 않는다.

Q7에러 처리
툴이 호출한 외부 결제 API가 타임아웃됐다. Claude에게 어떻게 알리는가?
정답 (A)

is_error와 구조적인 메시지를 받으면 Claude가 복구(재시도 제안·대체 경로·사용자 안내)를 판단할 수 있다. 내부 정보 노출은 보안상 피하고, tool_result 누락은 tool_use_id 매칭 에러를 낸다.

Q8tool_choice
워크플로 특성상 Claude가 매 턴 어떤 툴이든 하나는 반드시 호출해야 한다(어느 툴인지는 Claude가 판단). 알맞은 지정은?
정답 (D)

any는 '반드시 하나 이상 호출, 어느 것인지는 Claude가 선택'이다. auto는 호출하지 않을 수도 있고, tool은 특정 툴로 고정한다.
