Claude로 만든 시스템은 출시로 끝나지 않는다. 쓰던 모델은 언젠가 폐기되고, API 버전은 바뀌고, 프롬프트는 계속 고쳐진다. 이 레슨의 앞부분은 바깥에서 오는 변화(모델 폐기·API 변경)를 마감 전에 흡수하는 법이고, 뒷부분은 안에서 만드는 변화(프롬프트·모델 교체)를 평가로 검증하고, 고정된 버전으로 배포하고, 문제가 생기면 되돌리는 법이다. 시험은 deprecated와 retired의 차이, 누구의 일정이 적용되는지, 평가를 언제 시작하는지, 운영 트래픽을 무엇에 고정하는지를 구체적으로 묻는다.

습득 포인트
  • Active·Legacy·Deprecated·Retired 상태별로 요청이 어떻게 처리되고 무엇을 해야 하는지 설명한다
  • Anthropic 운영 플랫폼과 파트너 운영 플랫폼(Bedrock, Google Cloud Google managed)의 폐기 일정이 다르다는 점을 적용한다
  • Console 사용량 내보내기로 폐기 대상 사용처를 찾고, 마이그레이션 가이드로 깨지는 설정을 고친다
  • anthropic-version 헤더와 베타 기능의 성격을 알고 프로덕션 의존 여부를 판단한다
  • 소규모 평가로 바로 시작해 채점을 자동화하고, 사람 검토를 병행하는 평가 주도 반복을 설계한다
  • 모델 ID·에이전트 버전을 고정하고, 승격·회귀 감지·롤백·점진 롤아웃을 변경 통제 절차로 묶는다
01

모델이 거치는 네 가지 상태

Active, legacy, deprecated, retired

Anthropic은 모델 수명주기를 네 단어로 설명한다. 시험에서 가장 많이 헷갈리는 곳은 deprecated(아직 동작)와 retired(요청 실패)의 경계다.

상태의미지금 호출하면
Active완전히 지원되며 사용을 권장한다정상 동작
Legacy더 이상 업데이트를 받지 않고, 나중에 deprecated될 수 있다정상 동작
Deprecated동작은 하지만 권장하지 않는다. 대체 모델과 retirement 날짜가 정해진다. Models API 설명으로는 기존 사용 조직만 호출할 수 있고 신규 도입은 막힌다동작한다. 다만 active 모델보다 안정성이 떨어질 수 있다
Retired더 이상 사용할 수 없다요청이 실패한다. 대체 모델로 자동 전환해 주지 않으므로 호출 코드를 바꿔야 한다

공개 출시된 모델은 retirement 최소 60일 전에 이메일과 문서로 통지된다. 예를 들어 claude-sonnet-4-5-20250929는 2026년 9월 30일 deprecated로 통지되었고, Claude API retirement 날짜는 2026년 11월 30일, 권장 대체 모델은 claude-sonnet-5-5다. 현재 active 모델의 표에 적힌 "Not sooner than …"은 그 날짜 전에는 은퇴시키지 않겠다는 약속이지 은퇴 예정일이 아니다.

코드로 상태 확인하기

Models API(GET /v1/models)의 모델 객체에는 lifecycle(active·deprecated·retired), deprecated_at, retires_at 필드가 있다. 목록은 기본적으로 active와 deprecated만 돌려주고, retired는 lifecycle 필터로 요청할 때만 나온다. deprecated 모델의 retires_at이 지났다면 은퇴가 늦어진 것이고, 실제 은퇴 신호는 lifecycle 값이다. 이 API의 상태 값에는 legacy가 없다.

02

누구의 폐기 일정이 적용되는가

Whose retirement schedule applies

모델 폐기 문서에 적힌 날짜는 Anthropic이 운영하는 플랫폼에만 적용된다. 파트너가 운영하는 플랫폼은 자기 일정으로 모델을 은퇴시키므로, 같은 모델이라도 상태와 날짜가 다를 수 있다.

플랫폼일정의 주인확인할 곳
Claude API, Claude Platform on AWS, Claude Models on Google Cloud (Anthropic managed), Microsoft FoundryAnthropicModel deprecations 문서의 표
Amazon BedrockAWSBedrock 문서의 모델 표
Claude Models on Google Cloud (Google managed)GoogleGoogle managed 문서의 모델 표

실제 차이도 있다. 가격 문서는 Claude Opus 4.1을 "retired, except on Bedrock and Claude Models on Google Cloud (Google managed)"로, Claude Haiku 3.5를 "retired, except on Claude Models on Google Cloud (Google managed)"로 표시한다. Claude API에서는 은퇴했지만 파트너 플랫폼에서는 아직 남아 있는 모델이다. 반대로 Bedrock 사용자가 Claude API 일정만 보고 여유가 있다고 판단해서도 안 된다.

시험 판단 축
  • "같은 모델의 Claude API retirement 날짜가 Google Cloud에서도 그대로인가?" → Google managed라면 아니다. 그 플랫폼의 표를 본다
  • Claude Platform on AWS는 AWS 위에 있어도 Anthropic의 1st-party 수명주기를 따른다. Bedrock과 혼동하지 않는다
03

마감 전에 마이그레이션을 끝낸다

Running a migration before the deadline

deprecated 통지를 받으면 retirement 날짜 전에 모든 사용처를 대체 모델로 옮긴다. 공식 권고는 은퇴 날짜보다 훨씬 앞서 새 모델로 애플리케이션을 테스트하는 것이다. 순서는 다음과 같다.

① AUDIT
Console Usage 페이지 → Export → CSV에서 API 키·모델별 사용량 확인
→
② TARGET
폐기 표의 권장 대체 모델 확인
→
③ PATCH
마이그레이션 가이드로 거부되는 설정 수정
→
④ EVAL
같은 평가 세트로 기존·신규 모델 비교
→
⑤ SWITCH
고정 ID로 전환하고 모니터링

내보낸 CSV는 사용량을 API 키와 모델별로 나눠 보여 주므로, 어느 서비스(키)가 아직 폐기 대상 모델을 부르는지 찾을 수 있다. 모델 이름만 바꾸면 끝나는 경우는 드물다. 예를 들어 Claude Opus 5.5로 옮길 때는 다음 설정이 400 오류로 거부된다.

예전 코드에 있던 설정Opus 5.5에서 바꿀 것
thinking: {"type": "enabled", "budget_tokens": N} (수동 예산)thinking을 생략하거나 {"type": "adaptive"}. 사고량은 output_config.effort로 조절
thinking: {"type": "disabled"}사용 불가. adaptive thinking이 항상 켜져 있다
tool_choice의 any · tool(강제 호출)auto(기본) 또는 none만 허용
temperature · top_p · top_k제거하고 프롬프트로 동작을 안내
assistant 턴 미리 채우기(prefill)구조화 출력이나 시스템 프롬프트 지시로 대체
# 이전: Opus 4.x 시절의 고정 사고 예산 → Opus 5.5에서는 400 resp = client.messages.create( model="claude-opus-4-6", max_tokens=16000, thinking={"type": "enabled", "budget_tokens": 8000}, messages=msgs) # 이후: thinking 필드는 빼고 effort로 깊이를 정한다 resp = client.messages.create( model="claude-opus-5-5", max_tokens=16000, output_config={"effort": "high"}, messages=msgs)
기본값이 바뀌는 것도 변경이다

Opus 5.5의 기본 effort는 medium이다. Opus 5와 이전 Opus의 기본값은 high였으므로, effort를 생략한 코드는 옮기는 순간 한 단계 낮은 effort로 돈다. 오류는 나지 않지만 결과가 달라질 수 있으니 평가로 확인한다. Claude Code에서는 /claude-api migrate this project to claude-opus-5-5로 코드 수정을 맡길 수 있다.

04

API 버전과 기능 라벨

API versions and feature classifications

모든 API 요청에는 anthropic-version 헤더가 필요하다(SDK는 자동으로 붙인다). 최신 버전은 2026-10-21이고, 그 전 버전은 2023-06-01이다. 한 버전 안에서 Anthropic은 기존 입력·출력 파라미터를 유지한다. 대신 선택 입력 추가, 출력 값 추가, 오류 조건 변경, 열거형 출력 값(스트리밍 이벤트 타입 등)의 새 변형 추가는 할 수 있다. 그래서 클라이언트는 모르는 필드나 이벤트 타입이 와도 깨지지 않게 짜야 한다.

버전을 올리면 동작이 바뀐다. 2026-10-21에서는 temperature·top_p·top_k가 제거되어 모든 모델에서 400을 내고, assistant 메시지에 document 블록을 직접 넣어도 400이다. 파라미터 폐기는 새 모델이 먼저 거부하고, 새 API 버전이 모든 모델에서 제거하는 순서로 진행되기도 한다.

라벨의미프로덕션 판단
라벨 없음표준 API의 일부. 버전 안에서 입력·출력이 유지된다핵심 경로에 써도 된다
Betaanthropic-beta: 기능명-YYYY-MM-DD 헤더로 쓰는 실험 기능. 통지 후 호환을 깨는 변경, 폐기·제거, 다른 레이트 리밋·가격, 일부 리전 미제공이 가능하다핵심 업무 흐름이 기대기엔 위험하다. 대체 경로를 두고, 플랫폼마다 지원 여부를 확인한다. HIPAA BAA는 명시된 경우가 아니면 베타를 덮지 않는다
Deprecated아직 동작하지만 권장하지 않는다. 대체 수단과 제거 일정이 제시된다신규 사용 금지, 기존 사용은 이전 계획 수립
Retired더 이상 제공되지 않는다호출이 실패한다
출처 메모

CertSafari는 이 네 라벨의 정의를 Features overview 문서에서 인용하지만, 2026년 10월 현재 그 문서에는 라벨 정의가 보이지 않는다. 이 표는 Beta headers, Model deprecations(파라미터 폐기 포함), API and data retention 문서의 서술로 구성했다.

05

Claude 시스템의 수명주기 틀

A lifecycle frame for Claude-powered systems

Anthropic 지원 문서는 Claude Code 활용 사례를 소프트웨어 개발 수명주기 다섯 단계로 정리한다. 시나리오의 작업이 어느 단계에 속하는지 묻는 문항에 이 틀을 쓴다.

단계속하는 작업
1. Discover코드베이스·이력 탐색, 문서 검색, 온보딩과 학습
2. Design프로젝트 계획, 기술 명세 작성, 아키텍처 정의
3. Build코드 구현, 테스트 작성·실행, 커밋과 PR 생성
4. DeployCI/CD 자동화, 환경 구성, 배포 관리
5. Support and scale오류 디버깅, 대규모 리팩터링, 사용량·성능 모니터링

프롬프트나 모델을 바꾸는 일도 이 고리를 돈다. Build 단계에서 평가로 검증하고, Deploy 단계에서 고정 버전으로 내보내고, Support 단계에서 사용량·품질을 지켜보다가 회귀가 보이면 되돌린다. 이 레슨의 06~08이 그 세 지점을 다룬다.

06

평가 주도 반복: 작게 시작해 채점을 키운다

Eval-driven iteration

큰 평가 세트가 모일 때까지 기다리는 것은 흔한 실수다. Anthropic 리서치 시스템 팀은 실제 사용 패턴을 대표하는 약 20개의 질의로 평가를 시작했다. 개발 초기에는 손볼 곳이 많아 변경 하나의 효과가 크게 나타나므로, 적은 사례로도 개선 여부가 드러난다. 세트는 운영 로그에서 실제 트래픽 비율대로 뽑은 과업을 더해 가며 키운다.

자동
코드 채점
정확 일치, 문자열 매칭, 테스트 통과 여부처럼 기준이 분명한 항목. 빠르고 대량으로 돈다
자동
LLM 심사
루브릭(사실 정확성, 인용 정확성, 완전성, 출처 품질, 도구 효율)을 주고 한 번의 호출로 0.0~1.0 점수와 합격·불합격을 받는다
사람
수동 테스트
자동 채점이 놓치는 문제를 잡는다. 리서치 팀은 사람 검토로 에이전트가 권위 있는 출처 대신 SEO용 콘텐츠 농장을 고르는 경향을 발견했다
  • 성공 기준은 구체적이고(specific), 측정 가능하고(measurable), 달성 가능하고(achievable), 목적에 맞아야(relevant) 한다. 대부분의 사용 사례는 여러 기준을 함께 본다
  • 평가는 실제 작업 분포와 엣지 케이스를 반영하고, 자동 채점이 가능하게 설계한다. 문서는 "신호가 조금 약해도 문항이 많은 자동 채점"이 "적은 수의 정교한 수작업 채점"보다 낫다고 본다
  • LLM 심사는 평가 대상 출력을 만든 모델과 다른 모델로 하는 것이 일반적인 모범 사례다
자동 평가가 있어도 사람은 남는다

LLM 심사를 붙였다고 수동 테스트를 없애는 보기는 오답이다. 공식 글의 결론은 자동 평가와 함께 수동 테스트가 여전히 필수라는 것이다.

07

모델과 프롬프트를 고정된 구성으로 다룬다

Pinned, versioned configuration

평가로 검증한 것과 운영에서 도는 것이 같아야 한다. 그래서 모델과 프롬프트를 둘 다 바뀌지 않는 식별자로 참조한다.

ID 형태예고정되는가
날짜 없는 ID (4.6 세대부터)claude-sonnet-5-5예. 그 자체가 스냅숏이다. 새 버전은 새 ID로 나온다
날짜가 붙은 ID (4.6 이전)claude-haiku-4-5-20251001예
4.6 이전 모델의 별칭claude-sonnet-4-5아니다. 해당 마이너 버전의 최신 날짜 스냅숏을 가리키는 편의 포인터다

같은 ID라면 가중치는 바뀌지 않지만, 요청 라우터·안전 분류기 같은 서빙 인프라는 바뀔 수 있어 관찰되는 동작이 조금 달라질 수 있다. Claude Code를 Bedrock·Google Cloud·Foundry·Claude Platform on AWS로 배포할 때는 ANTHROPIC_DEFAULT_OPUS_MODEL 같은 변수로 모델 버전을 고정해 사용자가 새 모델로 넘어가는 시점을 조직이 정한다.

프롬프트도 버전으로 관리한다. Claude Managed Agents에서는 agents.create가 버전 1을 만들고, agents.update를 부를 때마다 같은 ID에 변경 불가능한 새 버전이 생긴다. 세션이 어느 버전을 쓸지는 호출하는 쪽이 정한다.

# 새 프롬프트로 v4를 만든다 (운영 트래픽은 아직 그대로) agent = client.beta.agents.update( AGENT_ID, version=agent.version, system=REFUND_PROMPT_V4) # 운영 호출부: 검증된 버전에 명시적으로 고정 session = client.beta.sessions.create( agent={"type": "agent", "id": AGENT_ID, "version": 3}, environment_id=ENV_ID) # 고정하지 않은 참조: 다음 세션부터 최신 버전(v4)이 돈다 session = client.beta.sessions.create( agent=AGENT_ID, environment_id=ENV_ID)
bare ID는 운영에서 위험하다

agents.update에는 승인 절차가 따로 없다. 운영 호출부가 버전 없이 에이전트 ID만 넘기면, 누군가 실험 삼아 만든 새 버전이 바로 다음 세션부터 고객에게 나간다. 운영은 명시한 버전에 고정하고, 새 버전은 승격하기 전까지 보이지 않게 둔다.

08

변경 통제와 점진 롤아웃

Change control and gradual rollout

버전을 만드는 일과 운영에 내보내는 일을 분리하면 변경 통제 지점이 하나로 모인다. 새 버전 생성은 탐색이라 자유롭게 하고, 운영 고정값(어떤 버전을 넘길지 정한 설정)을 바꾸는 일을 일반 코드 리뷰 절차에 태운다.

① CREATE
새 프롬프트로 새 버전 생성
→
② EVALUATE
버전 고정 세션으로 같은 평가 세트 채점
→
③ SHIP
리뷰를 거쳐 운영 고정값을 새 버전으로
→
④ DETECT
같은 채점 도구와 모니터링으로 회귀 감지
→
⑤ ROLL BACK
고정값을 이전 버전 번호로 되돌림

이 방식에서 롤백은 재배포가 아니다. 이전 버전이 서버에 그대로 남아 있으므로 호출부가 넘기는 버전 번호만 되돌리면 된다. 새 버전에 일부 트래픽만 보내 비교하면 버전 번호를 기능 플래그처럼 쓰는 카나리 배포가 된다. 비용·지능 최적화 문서도 전환 전에 일부 트래픽에서 새 구성을 그림자(shadow)로 돌려 보고, 전환 후에도 평가 세트를 계속 돌리라고 권한다.

한 번에 교체

장시간 도는 상태 저장형 에이전트는 배포 순간에도 작업 중간 어딘가에 있다. 모든 에이전트를 한꺼번에 새 코드로 바꾸면 진행 중이던 작업이 깨지고, 에이전트에서는 작은 실패 하나가 전혀 다른 경로로 이어질 수 있다.

레인보우 배포

Anthropic 리서치 시스템은 이전 버전과 새 버전을 동시에 띄워 둔 채 트래픽을 조금씩 새 버전으로 옮기는 레인보우 배포(rainbow deployment)를 썼다. 이미 돌고 있는 에이전트는 이전 버전에서 끝까지 가고, 새 작업만 새 버전으로 들어간다.

시험 판단 축
  • 리뷰를 거쳐야 하는 것은 "새 프롬프트 버전 만들기"가 아니라 "운영이 가리키는 버전 바꾸기"다
  • 규제·감사 때문에 동작이 바뀌면 안 되는 시스템은 별칭이 아니라 고정 ID(또는 dated snapshot)를 쓴다
  • 상태 저장형 장기 에이전트의 업데이트에는 즉시 전체 교체보다 레인보우 배포가 맞다

시험 함정 · 흔한 오해

오해deprecated가 되면 그날부터 요청이 실패하거나, 대체 모델로 자동 전환된다.
사실deprecated 모델은 retirement 날짜까지 동작한다. 은퇴한 뒤에는 요청이 실패할 뿐 어디로도 다시 보내 주지 않는다.
오해Claude API의 retirement 날짜는 Bedrock과 Google Cloud에서도 같다.
사실Bedrock과 Google Cloud(Google managed)는 자기 일정으로 은퇴시킨다. Claude API에서 은퇴한 모델이 그쪽에는 남아 있는 경우도 있다.
오해날짜 없는 모델 ID는 최신 버전으로 계속 갱신되는 별칭이다.
사실4.6 세대부터 날짜 없는 ID가 곧 고정 스냅숏이다. 움직이는 포인터는 4.6 이전 모델의 별칭(claude-sonnet-4-5 등)이다.
오해의미 있는 평가를 하려면 수백 건짜리 데이터셋부터 만들어야 한다.
사실실제 사용을 대표하는 20개 안팎으로 바로 시작한다. 초기 변경은 효과가 커서 적은 사례로도 차이가 보인다.
오해LLM 심사로 채점을 자동화했으면 수동 테스트는 그만해도 된다.
사실사람 검토는 자동 평가가 놓치는 출처 품질 같은 문제를 잡는다. 둘을 함께 쓴다.
오해운영 코드가 에이전트 ID만 넘겨도, 새 버전은 승격할 때까지 쓰이지 않는다.
사실버전 없는 참조는 최신 버전을 쓴다. 새 버전을 만드는 즉시 다음 세션부터 반영되므로 운영은 버전을 명시해 고정한다.
