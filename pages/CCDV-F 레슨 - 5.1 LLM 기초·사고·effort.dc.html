비용이 왜 이만큼 나왔는지, 답이 왜 매번 조금씩 다른지, 그럴듯한 인용이 왜 틀렸는지는 모두 LLM이 텍스트를 만드는 방식에서 나온다. 모델은 컨텍스트 윈도 안의 토큰을 보고 다음 토큰을 하나씩 고른다. 그래서 예시와 문서는 요청마다 컨텍스트에 들어 있어야 효과가 있고, 사고와 effort는 출력 토큰을 얼마나 쓸지 정하는 레버다. 시험은 토큰 어림, 환각이 몰리는 자리, 윈도에 들어가는 것, 샘플링과 비결정성, 그리고 사고 모드·effort·fast mode 가운데 상황에 맞는 레버를 고르는 판단을 묻는다.

습득 포인트
  • 토큰과 글자의 관계를 모델과 언어에 따라 어림하고, 정확한 값은 대상 모델로 토큰을 세어 구한다
  • 다음 토큰 생성이 환각을 낳는 이유를 설명하고, 유창한 출력에서 먼저 검증할 지점을 고른다
  • 컨텍스트 윈도에 들어가는 구성 요소(캐시된 접두사, 도구 정의, 출력과 사고)를 빠짐없이 짚는다
  • 퓨샷 예시와 샘플링 파라미터가 작동하는 방식을 알고, 비결정적 출력에 맞는 테스트를 설계한다
  • 적응형·확장 사고, display, effort, fast mode가 각각 무엇을 바꾸고 무엇을 바꾸지 않는지 구분한다
01

토큰: 모델이 읽고 쓰는 단위

Tokens and tokenizers

모델은 글자나 단어가 아니라 토큰(token) 단위로 입력을 읽고 출력을 쓴다. 토큰은 단어, 단어 조각, 글자, 바이트 어느 것이든 될 수 있다. 컨텍스트 윈도 한도, max_tokens, 요금이 모두 토큰 수로 계산되므로, 토큰 수를 어림하는 감각이 곧 비용과 용량을 어림하는 감각이다.

기준어림값주의할 점
이전 토크나이저 (Claude Sonnet 4.6, Opus 4.6 이전 모델)영문 약 3.5자 = 1토큰공식 용어집의 수치. 7,000자 영문 문서면 약 2,000토큰
새 토크나이저 (Claude Opus 4.7 이후, Claude 5 계열)같은 텍스트에서 약 30% 더 많은 토큰증가 폭은 내용과 작업 형태에 따라 다르다
1M 토큰 (현재 토크나이저)약 555k 단어, 약 250만 유니코드 문자모델 개요 표의 환산. 이전 모델은 1M에 약 750k 단어
언어비율이 언어마다 다르다영문 기준 어림을 다른 언어에 그대로 쓰지 않는다
어림은 계획용, 확정은 카운팅으로

비용과 컨텍스트 적합성을 확정할 때는 POST /v1/messages/count_tokens에 실제로 쓸 모델 ID를 넘겨 센다. 카운팅은 넘긴 모델의 토크나이저로 계산하므로, 모델을 바꾸면 같은 요청을 두 모델로 각각 세어 비교한다. 이전 모델에서 잰 값을 새 모델 예산에 재사용하지 않는다. (자세한 내용은 5.4)

CertSafari와 다른 점

CertSafari는 3.5자 비율을 Claude 전반의 수치처럼 소개한다. 공식 용어집은 이 수치를 Claude Opus 4.7 이전 모델에 한정하고, 4.7 이후 모델은 같은 텍스트에서 약 30% 더 많은 토큰을 만든다고 설명한다. 이 가이드와 문제는 공식 설명을 따른다.

02

다음 토큰 생성과 환각

Next-token generation and hallucination

Claude의 바탕이 되는 모델은 앞의 문맥을 보고 다음 단어를 예측하도록 사전 학습(pretraining)되었고, 이후 미세 조정과 RLHF로 도움이 되는 어시스턴트가 되었다. 답을 만들 때도 "이 문맥 뒤에 무엇이 올 법한가"를 따라 토큰을 하나씩 고른다. 이 과정에는 참과 '그럴듯함'을 가르는 별도의 확인 단계가 없다. 문장을 매끄럽게 만드는 성질과 사실을 지어내는 성질(환각, hallucination)이 같은 뿌리에서 나오는 이유다.

그래서 날조는 고르게 퍼지지 않는다. 흔한 설명이나 연결 문장은 패턴이 촘촘해 잘 맞지만, 정답이 하나뿐인 구체적 사항(사람 이름, 날짜, 통계, 인용, URL, 인용문)에서는 그럴듯한 후보가 여럿이고 모델은 그중 하나를 확신 있게 고른다. Anthropic 교육 자료도 날조가 구체성에 몰리며, 주장이 정밀할수록 검증이 필요하다고 설명한다.

검토 우선순위를 잘못 잡은 경우

"문장이 자연스럽고 자신감 있으니 내용도 맞겠지" 하고 어조와 흐름부터 다듬는다. 유창함은 정확성의 신호가 아니다. 틀린 연도와 존재하지 않는 논문은 매끄러운 문장 속에 그대로 남는다.

검증할 수 있는 것부터 확인

시간이 부족하면 이름, 수치, 날짜, 인용, URL처럼 확인 가능하고 틀리면 피해가 큰 주장부터 원문과 대조한다. 출처가 확인되지 않는 주장은 빼거나 표시한다.

공식 문서의 완화 기법방법
모른다고 말할 수 있게 허용정보가 부족하면 그렇다고 답하라고 명시한다. 불확실성 인정만으로도 잘못된 정보가 크게 준다
직접 인용으로 근거 잡기긴 문서(20k 토큰 이상)는 관련 구절을 글자 그대로 먼저 뽑게 한 뒤, 그 인용만으로 작업하게 한다
인용으로 검증주장마다 근거 인용을 붙이게 하고, 근거를 찾지 못한 주장은 철회하게 한다
외부 지식 제한·반복 비교제공 문서만 쓰게 하거나, 같은 프롬프트를 여러 번 돌려 서로 다른 답이 나오는 지점을 의심한다

이 기법들도 환각을 완전히 없애지는 못한다. 중요한 결정에 쓰일 정보는 항상 사람이나 시스템이 검증한다.

03

컨텍스트 윈도는 모델의 작업 기억

What counts toward the context window

컨텍스트 윈도(context window)는 응답을 만들 때 모델이 참조할 수 있는 모든 텍스트이며, 생성 중인 응답 자체도 포함한다. 학습 데이터와 달리 요청마다 채워지는 작업 기억이다. 크다고 무조건 좋은 것도 아니다. 토큰이 많아질수록 정확도와 회상이 떨어지는 컨텍스트 부패(context rot)가 생기므로, 공간만큼이나 무엇을 넣을지 고르는 일이 중요하다.

구성 요소윈도에 포함설명
시스템 프롬프트포함캐시되어 있어도 포함된다. 캐싱은 비용을 바꿀 뿐 공간을 비우지 않는다
messages 전체포함도구 결과, 이미지, 문서까지 모두
도구 정의포함도구가 많으면 상당한 공간을 차지한다. 도구 검색 도구로 정의를 늦게 불러올 수 있다
이번 턴의 출력포함사고(thinking) 토큰도 포함된다
이전 턴의 사고 블록모델에 따라Opus 4.5 이후, Sonnet 4.6 이후, Haiku 5.5, Fable 계열은 기본으로 유지되어 입력에 포함. Haiku 4.5 등 이전 모델은 자동으로 제거

캐싱을 쓰면 usage의 입력이 input_tokens, cache_read_input_tokens, cache_creation_input_tokens로 나뉘어 보고되는데, 셋 모두 윈도에 포함된다. 현재 라인업(Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5)과 Opus 4.6 이후·Sonnet 4.6 이후 모델은 1M 토큰 윈도에 요청당 최대 128k 출력을 쓸 수 있고, Haiku 4.5 같은 그 밖의 모델은 200k 윈도다.

한도를 넘으면
  • 입력만으로 윈도를 넘으면 모든 모델에서 400 invalid_request_error("prompt is too long")가 난다
  • Claude 4.5 이후 모델은 입력 + max_tokens가 윈도를 넘어도 요청을 받고, 생성이 한도에 닿으면 stop_reason: "model_context_window_exceeded"로 멈춘다
  • 공간을 줄이는 수단은 캐싱이 아니라 서버 측 컴팩션(compaction), 컨텍스트 편집(도구 결과·사고 블록 정리), 도구 정의 지연 로딩이다
04

예시는 학습이 아니라 컨텍스트로 작동한다

Few-shot examples steer through context

예시(퓨샷·멀티샷 프롬프팅)는 출력의 형식, 어조, 구조를 이끄는 가장 믿을 만한 방법 중 하나다. 하지만 예시가 모델을 다시 학습시키지는 않는다. Claude API는 현재 파인튜닝을 제공하지 않고, Messages API는 상태가 없어 매 요청이 독립적이다. 예시는 그 요청의 컨텍스트 안에 있을 때만 효과가 있다. 다음 요청에서 예시를 빼면 효과도 사라진다. 매번 보내는 비용이 부담이면 예시를 고정 접두사에 두고 프롬프트 캐싱으로 값을 낮춘다.

관련성 (Relevant)
실제 입력과 닮은 예시. 장난감 같은 예시는 실제 데이터의 난점을 보여 주지 못한다
다양성 (Diverse)
엣지 케이스를 넣고, 모델이 의도치 않은 패턴(길이, 단어 선택)을 따라 하지 않을 만큼 서로 다르게
구조 (Structured)
<example> 태그로 감싸고 여러 개는 <examples>로 묶어 지시·입력과 구분한다
<instructions> Convert each warranty claim into: SKU;DEFECT_CODE;ACTION </instructions> <examples> <example> claim: "Kettle KT-200 stopped heating after a week" output: KT-200;NO_HEAT;REPLACE </example> <example> claim: "lid cracked, no model number on the box" output: UNKNOWN;CRACK;REQUEST_INFO # 엣지 케이스 </example> </examples> <claim>{{CLAIM}}</claim>
개수와 점검

공식 가이드는 3~5개를 권한다. 하나뿐이면 그 예시의 우연한 특징까지 복제되고, 거의 같은 예시를 많이 넣으면 다양성이 없어 드문 입력에서 무너진다. Claude에게 예시의 관련성과 다양성을 평가하게 하거나 추가 예시를 만들게 할 수도 있다. 사고를 쓰는 모델에서는 풀이 예시가 사고 블록 안의 접근 방식까지 이끈다.

05

샘플링과 비결정성

Sampling parameters and non-determinism

같은 프롬프트에 답이 달라지는 이유는 다음 토큰을 확률 분포에서 샘플링하기 때문이다. 샘플링을 조절하는 개념은 다음과 같다.

개념효과
낮은 temperature가장 확률 높은 표현과 답을 고수하는 보수적인 출력
높은 temperature드문 단어 선택까지 탐색하는 다양하고 창의적인 출력
top_k확률 상위 K개 후보 안에서만 샘플링
top_p누적 확률이 p에 이르는 후보 집합 안에서만 샘플링
temperature 0그래도 완전히 결정적이지 않다. 같은 입력이 호출마다 다른 출력을 낼 수 있고, 1st-party와 서드파티 클라우드 모두 같다
개념은 알되 최신 API에서는 쓰지 않는다

Claude Opus 4.7 이후 모델과 Claude 5 계열(Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5 포함)은 기본값이 아닌 temperature·top_p·top_k에 400 오류를 낸다. 이 모델들의 top_p 기본값은 0.99라 1을 보내도 400이다. API 버전 2026-10-21부터는 세 파라미터가 제거되어, 어떤 값이든 보내면 모든 모델에서 400이 난다. 출력 성향은 프롬프트로 조정한다.

비결정성은 버그가 아니라 설계 전제다. 사고를 쓰면 요청마다 사고 토큰 사용량도 달라진다.

문구 일치 테스트

저장해 둔 기준 문자열과 응답을 그대로 비교한다. 내용이 맞는 응답도 표현이 조금만 달라지면 실패하고, 실패한 항목을 재시도로 통과시키면 진짜 회귀까지 가려진다.

요구사항 검사 + 반복 실행

JSON 구조, 필수 필드, 값의 범위, 반드시 들어갈 사실을 검사한다. 평가는 여러 번 돌려 통과율로 보고, 감사가 필요한 응답은 다시 생성하지 말고 저장한다.

06

사고: 적응형과 확장, 그리고 display

Adaptive thinking, extended thinking, and display

사고(thinking)를 쓰면 Claude는 답하기 전에 thinking 블록에서 문제를 풀어 보고, 그 결과를 바탕으로 text 블록을 쓴다. 사고 토큰은 출력 토큰으로 과금되고 max_tokens에 포함된다. 사고 텍스트를 돌려받지 않아도 마찬가지다.

적응형 사고 (adaptive)확장 사고 (extended, 수동)
설정thinking: {"type": "adaptive"}. Claude 5 이후 모델은 필드가 없어도 이 모드{"type": "enabled", "budget_tokens": N}
사고량요청마다 모델이 사고할지와 깊이를 정한다. effort로 조절개발자가 정한 토큰 예산
모델Opus 4.6 이후, Sonnet 4.6 이후, Haiku 5.5, Fable 계열Claude 4.5 이전 모델(Haiku 4.5 포함). Opus 4.6·Sonnet 4.6에서는 deprecated, Opus 4.7 이후 모델은 400

display 필드는 사고 내용을 어떻게 돌려줄지만 정한다. "summarized"는 사고 요약을, "omitted"는 빈 thinking 필드와 서명만 돌려준다. Claude 5 계열과 Opus 4.7·4.8은 기본이 "omitted", Opus 4.6·Sonnet 4.6 이전은 "summarized"다. "omitted"는 스트리밍 시 첫 텍스트 토큰을 앞당기지만 과금되는 사고 토큰은 그대로다. 생략은 지연을 줄이지 비용을 줄이지 않는다.

적응형 사고가 사고를 너무 자주 한다면, 먼저 effort를 낮추고 그 수준에서도 맞지 않을 때 프롬프트로 조정한다. 사고를 유발하는 기준은 프롬프트로 움직일 수 있다.

모델별 예외

Claude Sonnet 5.5와 Haiku 5.5는 프롬프트로 사고를 줄이라고 해도 잘 듣지 않는다고 문서에 적혀 있다. 이 두 모델은 effort를 낮추는 것이 사고를 줄이는 방법이다. 사고를 완전히 끄는 설정(disabled, between_tools)은 모델마다 허용 여부가 달라 5.3에서 표로 정리한다.

CertSafari와 다른 점

CertSafari는 사소한 질문의 사고 지연을 줄이는 방법으로 시스템 프롬프트 안내를 먼저 제시한다. 공식 문서는 사고를 덜 하게 하려면 effort를 먼저 낮추고, 프롬프트 안내는 그 수준에서도 맞지 않을 때 더하라고 순서를 정한다. 문제은행은 effort를 낮출 수 없는 조건을 넣어 두 설명이 어긋나지 않게 했다.

07

effort: 응답 전체의 토큰 지출을 정한다

The effort parameter

effort는 output_config.effort로 정하며, 하나의 모델 안에서 철저함과 토큰 효율을 맞바꾸는 레버다. 사고뿐 아니라 텍스트, 도구 호출, 사고를 포함한 모든 출력 토큰에 영향을 주므로 사고가 꺼져 있어도 의미가 있다. 낮은 effort는 도구 호출 수도 줄이고 더 간결하게 만든다. effort는 행동 신호일 뿐 엄격한 예산이 아니며, 엄격한 상한은 max_tokens다.

수준성격과 대표 용도
max토큰 지출 제약 없이 최대 능력. 최전선 문제용. 대부분의 작업에선 비용 대비 이득이 작고 과도한 사고로 이어질 수 있다
xhigh장기 작업용 확장 능력. 30분을 넘는 에이전트·코딩 작업, 수백만 토큰 예산
high작업에 필요한 만큼 토큰을 써서 좋은 결과. Opus 5.5·Haiku 5.5를 뺀 모든 모델의 기본값
medium균형과 적당한 절감. Opus 5.5·Haiku 5.5의 기본값
low가장 효율적. 단순하고 속도·비용이 중요한 작업, 서브에이전트
모델API 기본값공식 권장 시작점
Claude Fable 5.1highhigh로 시작. 역량에 민감한 에이전트·코딩은 xhigh·max, 일상 작업은 평가 후 낮춘다
Claude Opus 5.5medium사고를 끌 수 없어 effort가 주 레버. 이전 모델 설정을 옮기지 말고 자체 평가로 effort 스윕
Claude Sonnet 5.5high에이전트 코딩은 잘 정의된 작업이면 medium, 어렵거나 길면 high. 채팅은 medium·low
Claude Haiku 5.5medium대부분 medium. 채팅, 짧은 도구 작업, 단순 대량 요청은 low
Claude Opus 4.7·4.8high코딩·에이전트는 xhigh로 시작(직접 설정). xhigh·max에서는 max_tokens를 64k부터
{ "model": "claude-opus-5-5", "max_tokens": 64000, "output_config": { "effort": "xhigh" }, # thinking 안이 아니다 "messages": [{ "role": "user", "content": "..." }] }
어떤 레버를 고를까
  • 사고가 켜진 작업의 비용·지연을 줄이고 싶다 → 먼저 effort를 낮춘다. 사고를 포함한 응답 전체가 줄어든다
  • 사고가 너무 적거나 얕다 → effort를 올린다. adaptive는 사고 모드 값이지 effort 값이 아니다
  • 사고를 완전히 꺼야 한다 → 허용하는 모델에서 thinking: {"type": "disabled"}. effort를 낮추는 것은 줄일 뿐 끄지 않는다
  • 지출에 엄격한 상한이 필요하다 → max_tokens. 최상위 effort를 대화 중에 바꾸면 프롬프트 캐시가 무효화된다(일부 모델은 메시지별 effort 베타로 캐시 유지)
08

fast mode: 같은 모델, 더 빠른 출력

Fast mode

fast mode는 요청에 speed: "fast"를 넣어 켠다. 같은 모델을 더 빠른 추론 구성으로 돌리므로 지능과 능력은 바뀌지 않는다. 이득은 초당 출력 토큰(OTPS)에 집중되어 최대 약 2.5배이고, 첫 토큰까지의 시간(TTFT)은 주된 개선 대상이 아니다. 긴 출력을 스트리밍할 때 효과가 가장 잘 보인다.

모델상태필요한 것가격 (입력/출력, MTok당)
Claude Opus 5.5정식 제공speed: "fast"$8 / $40 (표준 $4 / $20의 두 배)
Claude Opus 5, Opus 4.8연구 프리뷰speed: "fast" + fast-mode-2026-02-01 베타 헤더, 접근 권한$10 / $50
그 밖의 모델미지원요청하면 오류 (Sonnet·Haiku 포함)
effort를 낮춘다

토큰을 덜 쓴다. 비용과 지연이 함께 줄고, 능력도 어느 정도 줄 수 있다. 비용 문제의 첫 레버.

fast mode를 켠다

같은 토큰을 더 빨리 쓴다. 능력은 그대로, 단가는 프리미엄. 모델을 바꾸지 않고 긴 출력을 빨리 끝내야 할 때의 레버.

운영 시 알아 둘 것

Batch API와 Priority Tier에서는 쓸 수 없다. 표준 Opus와 별도의 속도 제한이 있어 초과하면 retry-after 헤더와 함께 429가 오고, SDK가 기본 2회 재시도한다. 실제 적용된 속도는 응답의 usage.speed("fast" 또는 "standard")로 확인한다. 표준 속도로 대체하면 프롬프트 캐시를 공유하지 않아 캐시 미스가 난다.

시험 함정 · 흔한 오해

오해프롬프트를 캐시하면 그만큼 컨텍스트 윈도 공간이 비워진다.
사실캐시된 접두사도 윈도를 차지한다. 캐싱은 그 토큰의 비용과 처리 지연을 줄일 뿐이다.
오해temperature를 0으로 두면 매번 같은 답이 나온다.
사실temperature 0도 완전히 결정적이지 않다. 게다가 최신 모델은 기본값이 아닌 temperature를 400으로 거부한다.
오해예시를 한 번 보여 주면 모델이 형식을 배워 다음 요청에도 따른다.
사실예시는 그 요청의 컨텍스트에서만 작동한다. API는 예시로 학습하지 않으므로 매 요청에 넣어야 한다.
오해display: "omitted"로 사고 비용을 줄일 수 있다.
사실사고는 그대로 생성되고 출력으로 과금된다. 줄어드는 것은 스트리밍 시 첫 텍스트까지의 지연이다.
오해effort는 사고가 켜져 있을 때만 의미가 있다.
사실effort는 텍스트와 도구 호출을 포함한 모든 출력 토큰에 작용하므로 사고가 꺼져 있어도 효과가 있다.
오해fast mode는 더 작은 모델로 바꿔 빠르고 싸게 만든다.
사실같은 모델을 더 빠른 추론 구성으로 돌린다. 능력은 같고 가격은 더 비싸며, 개선되는 것은 출력 속도다.
