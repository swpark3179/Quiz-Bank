Claude Code와의 작업은 한 번에 끝나기보다 몇 차례 다듬으며 수렴한다. 문제는 "다듬는 방식"이다. 같은 불만을 말로 되풀이하면 Claude는 매번 다른 쪽으로 추측한다. 시험은 상황을 주고 어떤 형태의 피드백이 가장 빨리 수렴시키는지 묻는다. 요점은 Claude가 볼 수 없던 정보(예시·답변)와 스스로 돌려 볼 수 있는 확인 수단(테스트)을 주고, 피드백을 문제의 결합 관계에 맞게 묶어 보내는 것이다.

습득 포인트
  • 산문 설명이 매번 다르게 해석될 때 2~3개의 구체적인 입출력 예시로 변환 규칙을 전달하기
  • 기대 동작·엣지 케이스·성능 요구를 담은 테스트를 먼저 쓰고, 실제 실패 출력을 공유하며 반복하기
  • 낯선 영역에서는 구현 전에 Claude가 질문하게 하는 인터뷰 패턴으로 설계 고려 사항 끌어내기
  • 엣지 케이스(예: 마이그레이션의 null 값)는 입력과 기대 출력이 있는 구체적 테스트 케이스로 고치기
  • 서로 얽힌 문제는 한 메시지에 모아서, 독립적인 문제는 하나씩 순서대로 다루기
01

결과가 빗나가는 두 가지 이유

Missing information vs missing check

Claude Code best practices 문서는 세션이 기대와 다르게 흘러가는 대표 원인을 진단해 둔다. 이 서브도메인과 관련된 것은 두 가지다. 하나는 Claude가 저장소를 읽어서는 알 수 없는 정보가 빠져 다른 것을 만든 경우, 다른 하나는 스스로 확인할 수단이 없어 "다 됐다"고 했는데 아닌 경우다. 반복 개선 기법은 이 두 공백을 메우는 도구로 나눠 보면 정리가 쉽다.

정보 공백 — 무엇을 원하는지 모른다

증상: 결과가 매번 다른 방향으로 빗나간다, 같은 사실을 세션마다 다시 묻는다.

처방: 인터뷰 패턴(Claude가 질문해서 빈칸을 채움), 입출력 예시(원하는 변환을 보여 줌), 구체적 프롬프트(파일·증상·완료 상태 명시)

확인 공백 — 다 됐는지 모른다

증상: 겉보기엔 완성인데 엣지 케이스에서 깨진다, 사용자가 테스트 역할을 떠맡는다.

처방: 테스트 우선, 실패 출력 공유, 통과/실패로 답하는 검사(빌드 종료 코드, 린터, 픽스처와 비교하는 스크립트)

문서의 요지는 "통과·실패로 돌아오는 무언가를 주면 Claude가 루프를 스스로 닫는다"는 것이다. 변경하고, 검사를 돌리고, 깨지면 출력을 읽고 고친 뒤 다시 돌린다. 반대로 검사가 없으면 "다 돼 보인다"가 Claude가 가진 유일한 근거가 된다.

02

인터뷰 패턴: 구현 전에 질문받기

Let Claude ask before it builds

원하는 것이 아직 정리되지 않았거나 익숙하지 않은 영역이라면, 사양을 혼자 완성하려 하지 말고 Claude에게 인터뷰를 시킨다. best practices 문서는 이를 "Brainstorm with Claude first"로 소개한다. 사양을 쓸 수 있을 때까지 질문하라고 요청하면 Claude는 정해지지 않은 부분을 객관식 질문으로 묻고(Claude Code에서는 AskUserQuestion 도구), 답이 모여 사양이 될 때까지 계속 묻는다.

# 예: 처음 다뤄 보는 영역 (이 가이드의 예시) 상품 이미지 리사이즈 결과를 CDN 앞단에 캐시하려고 하는데 이 분야는 처음이다. 구현하기 전에 내가 결정해야 할 것들을 질문해 줘. 사양을 쓸 수 있을 만큼 답이 모이면 SPEC.md로 정리하고, 그때까지 코드는 건드리지 마.

이런 요청이면 Claude가 먼저 꺼낼 만한 질문은 원본이 바뀌었을 때의 캐시 무효화 방식(버전 붙인 URL vs 명시적 purge), 리사이즈 서버가 죽었을 때의 실패 모드(원본으로 대체 vs 오류 응답), 허용할 크기 목록 같은 것들이다. 개발자가 미처 생각하지 못한 결정이 구현 전에 드러난다는 점이 핵심 효과다.

사양이 생긴 다음

문서는 SPEC.md가 생기면 새 세션에서 그 파일을 근거로 구현을 시작하라고 권한다. 질문·답변으로 어수선해진 대화 대신 깨끗한 컨텍스트와 글로 적힌 완료 정의를 들고 시작하기 위해서다. 같은 파일은 나중에 리뷰어(서브에이전트 등)가 구현을 대조하는 기준이 된다.

인터뷰는 대화형 세션을 전제로 한다. claude -p 실행에 --permission-prompts none을 주면 AskUserQuestion처럼 사람의 답이 필요한 도구가 제거되고, dontAsk 모드는 이 도구를 거부한다. 무인 실행에서는 질문 대신 사양 파일을 미리 넘겨야 한다.

03

말 대신 입출력 예시

Show the transformation, don't describe it

데이터 변환 규칙을 산문으로 설명하면 단어 하나하나가 해석의 여지가 된다. "전화번호를 국제 형식으로 통일"이라는 지시는 하이픈 위치, 지역번호 처리, 빈 값 처리를 모두 Claude의 추측에 맡긴다. 이때 가장 효과적인 것은 구체적인 입력과 기대 출력 쌍이다. 플랫폼 프롬프팅 문서도 예시를 출력의 형식·구조를 잡는 가장 신뢰할 만한 방법 중 하나로 꼽는다.

BAD · 해석이 갈리는 산문
레거시 고객 CSV의 phone 열을 국제 형식으로 깔끔하게 정규화하는 함수를 만들어 줘.

실행할 때마다 공백·하이픈·괄호 처리가 달라지고, 빈 값을 빈 문자열로 둘지 null로 둘지도 제각각이다.

GOOD · 경계 사례를 포함한 예시 3개
normalize_phone()은 아래처럼 동작해야 한다. "010-1234-5678" -> "+82-10-1234-5678" "(02) 555 0101" -> "+82-2-555-0101" "" 또는 None -> None # 빈 값은 문자열이 아니라 None 이 세 경우를 테스트로 먼저 만들고 통과시켜 줘.

일반 사례 둘과 경계 사례 하나가 규칙을 대신 말한다. 예시를 곧바로 테스트로 바꾸면 확인 공백까지 함께 메워진다.

예시를 고를 때는 서로 다른 축을 하나씩 건드리게 한다. 위 예에서 첫째는 휴대폰 번호, 둘째는 괄호·공백이 섞인 지역번호, 셋째는 빈 값이다. 같은 유형만 세 개 주면 Claude는 그 유형의 우연한 공통점(예: 모두 010으로 시작)을 규칙으로 배울 수 있다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 변환 요구를 분명히 하는 데 2~3개의 입출력 예시를 제시한다. 플랫폼의 Prompting best practices 문서는 일반적인 퓨샷 프롬프팅에 대해 "3–5개 예시가 가장 좋은 결과"라고 안내하고, 예시를 <example> 태그로 감싸 지시와 구분하라고 권한다. 시험 문항에서는 가이드의 "2~3개, 구체적 입출력"을 기준으로 고르되, 예시 수는 고정 규칙이 아니라 다양성을 확보할 만큼이라고 이해하면 된다.

04

테스트를 먼저, 실패는 그대로

Test-driven iteration

테스트 우선 반복은 확인 공백을 메우는 가장 직접적인 방법이다. 테스트가 기대 동작을 고정하고, 실패 출력이 다음 수정의 방향을 정한다. 순서는 다음과 같다.

  1. 테스트부터 — 기대 동작, 엣지 케이스, 성능 요구를 테스트로 쓴다. 예: 레시피 수량 환산기라면 "1.5컵 → 360ml", "0인분 요청 → 오류", "재료 1만 개 환산 2초 이내"
  2. 실패 확인 — 구현 전에 테스트가 실제로 실패하는지 본다. 처음부터 통과하는 테스트는 아무것도 검증하지 않는다
  3. 구현 후 실행 — Claude가 직접 테스트를 돌리게 한다. 실행 명령은 CLAUDE.md에 적어 두면 매번 찾지 않는다
  4. 실패 출력을 그대로 공유 — "아직 안 돼"가 아니라 실패한 테스트 이름, 기대값과 실제값, 스택 트레이스를 넘긴다. Claude가 직접 실행했다면 출력을 이미 읽고 있다
  5. 증거로 마무리 — "모든 테스트 통과"라는 말 대신 실행한 명령과 출력을 받는다

엣지 케이스 버그도 같은 방식으로 고친다. 예를 들어 회원 테이블 마이그레이션 스크립트가 deleted_at이 NULL(= 활성 회원)인 행에 마이그레이션 실행 시각을 채워 넣어 모든 회원을 탈퇴 상태로 만든다면, "null 처리 좀 고쳐 줘" 대신 입력 행과 기대 결과를 담은 테스트 케이스를 준다.

# 이 가이드의 예시: 엣지 케이스를 테스트 케이스로 전달 def test_active_member_keeps_null_deleted_at(): row = {"id": 7, "status": "active", "deleted_at": None} out = migrate_member(row) assert out["deleted_at"] is None # 실행 시각으로 채우지 않음 assert out["status"] == "active" # 탈퇴로 바뀌지 않음
테스트에 맞춘 꼼수 막기

프롬프팅 문서는 Claude가 일반적인 해법 대신 테스트 통과에만 집중하거나 특정 입력에 값을 하드코딩할 수 있다고 경고한다. 권장 지시: 모든 유효한 입력에 맞는 일반 해법을 구현할 것, 테스트는 정답을 정의하는 것이 아니라 검증하는 것, 테스트가 틀렸다고 판단되면 우회하지 말고 알릴 것. 테스트를 지우거나 고쳐서 통과시키지 말라는 지시도 함께 둔다.

"반드시 통과해야 끝"을 프롬프트가 아니라 하네스가 강제하게 하려면 Stop hook을 쓴다. Claude가 턴을 끝내려 할 때 스크립트를 돌리고, 종료 코드 2면 작업으로 돌려보낸다. 프롬프트 속 "테스트 통과할 때까지 계속해"는 대부분 지켜지지만 보장은 아니다.

05

피드백 묶기: 한 번에 vs 하나씩

Interacting issues vs independent issues

여러 문제를 발견했을 때 한 메시지에 다 담을지, 하나씩 고칠지는 수정끼리 영향을 주는가로 정한다. 시험 가이드의 기준이다.

관계예시 (이 가이드의 예)보내는 방식
얽힘예약 시스템에서 ① 타임존 변환 위치, ② 서머타임 전환일 처리, ③ 하루 단위 요금 계산의 경계가 모두 틀림. ①을 어디서 하느냐가 ②·③의 기준 시각을 바꾼다한 메시지에 세 문제와 관계, 각각의 기대 결과를 함께 적는다. 따로 고치면 한쪽 수정이 다른 쪽을 다시 깨뜨린다
독립① 관리자 화면의 오류 문구 오타, ② 리포트 모듈의 느린 쿼리, ③ README의 잘못된 설치 명령하나씩 순서대로. 각 수정을 확인한 뒤 다음으로 넘어가면 원인 추적이 쉽고 리뷰 단위도 작아진다
시험 판단 축
  • A를 고치는 방식이 B의 정답을 바꾸는가 → 그렇다면 한 번에, 자세히
  • 서로 다른 파일·모듈이고 결과가 서로 무관한가 → 순차 반복
  • 얽힌 문제를 하나씩 보내는 것은 "수정 → 다른 곳 깨짐 → 재수정"의 왕복을 만든다

교정이 수렴하지 않을 때의 처방도 문서에 있다. 같은 것을 두 번 고쳐 달라고 했는데도 틀리면, 세 번째 교정은 실패한 시도 두 개가 담긴 대화에 또 한 줄을 더할 뿐이다. best practices 문서는 이때 /clear로 비우고 지금까지 배운 것을 접어 넣은 새 프롬프트 하나로 다시 시작하는 편이 거의 항상 낫다고 말한다. 방향이 틀어지는 순간에는 Esc로 즉시 멈춘다.

시험 함정 · 흔한 오해

오해해석이 갈리면 규칙 설명을 더 길고 자세하게 쓰면 된다.
사실산문이 계속 다르게 읽힌다면 구체적인 입출력 예시가 더 효과적이다. 예시는 형식과 경계를 직접 보여 준다.
오해테스트가 통과했으니 구현은 끝났다.
사실테스트는 검증 수단이지 정답의 정의가 아니다. 하드코딩·테스트 수정 같은 우회를 막는 지시를 두고, 실행 명령과 출력을 증거로 받는다.
오해인터뷰 패턴은 CI의 claude -p 실행에서도 똑같이 쓸 수 있다.
사실질문 도구는 사람의 답을 전제로 한다. --permission-prompts none은 이를 제거하고 dontAsk는 거부한다. 무인 실행에는 사양을 미리 넘긴다.
오해교정이 안 먹히면 같은 지적을 더 강하게 반복한다.
사실두 번 실패했으면 /clear 후 배운 점을 담은 새 프롬프트로 시작하는 편이 낫다.

"주소 문자열에서 시·구·동을 분리해 줘"라고 세 번 요청했는데 매번 건물명 처리와 빈 값 처리가 다르게 나온다.가장 효과적인 다음 단계는?

산문 지시가 일관되게 해석되지 않을 때는 구체적인 입출력 예시가 가장 효과적이다. 서로 다른 축(건물명, 누락, 빈 값)을 하나씩 건드리게 고른다. A는 해석 대상인 산문을 늘릴 뿐이고, C·D는 정보 공백을 그대로 둔다.

Q2테스트 우선
테스트 주도 반복을 가장 잘 따른 순서는?
정답 (D)

테스트를 먼저 써서 기대 동작을 고정하고, 실패 출력을 근거로 반복한다. B는 구현을 추인하는 테스트가 되기 쉽고, C는 테스트를 고쳐 통과시키는 우회이며, A는 사용자가 테스트 역할을 떠맡는다.

Q3인터뷰 패턴
팀에서 처음으로 웹훅 수신 서버를 만든다. 재시도·중복 수신·서명 검증을 어떻게 다룰지 아무도 정리해 본 적이 없다.구현 전에 가장 알맞은 접근은?
정답 (A)

낯선 영역에서는 인터뷰 패턴으로 개발자가 미처 생각하지 못한 고려 사항(중복 수신 처리, 실패 시 동작 등)을 구현 전에 드러낸다. B는 설계 결정을 재작업으로 미루고, C는 검증할 수 없는 모호한 지시이며, D는 질문할 상대가 없는 실행 방식이다.

Q4엣지 케이스
상품 데이터 이전 스크립트가 가격 열의 "1,200"을 1로 변환한다. "숫자 파싱 좀 신경 써 줘"라고 두 번 말했지만 고쳐지지 않았다.다음에 할 일로 가장 알맞은 것은?
정답 (C)

엣지 케이스는 구체적 입력과 기대 출력을 담은 테스트로 전달하고, 두 번 실패한 교정은 /clear 후 배운 점을 담은 새 프롬프트로 다시 시작하는 편이 낫다. A는 실패한 대화에 강조만 더하고, B는 데이터를 잃는 엉뚱한 해결이며, D는 범위가 분명한 수정에 과한 절차다.

Q5한 번에 vs 하나씩
재고 동기화 기능에서 세 가지 문제를 찾았다: 수량 반올림 방식, 동시 갱신 시 잠금 순서, 잠금 실패 후 재시도 간격. 잠금 순서를 바꾸면 재시도 간격의 적정값도 달라진다.피드백을 어떻게 보내는가?
정답 (B)

수정끼리 영향을 주는 문제는 한 번에 자세히, 독립적인 문제는 순차로 다룬다. A는 얽힌 두 문제를 갈라 놓아 수정이 서로를 깨뜨리는 왕복을 만들고, D는 한 메시지이긴 하지만 관계와 기대 결과가 빠져 있다.

Q6테스트 우회 방지
Claude가 실패하던 테스트를 통과시켰는데, 확인해 보니 테스트 입력값일 때만 특정 결과를 돌려주는 분기가 추가돼 있었다. 다음 반복에서 프롬프트에 넣을 지시로 가장 알맞은 것은?
정답 (D)

프롬프팅 문서가 권하는 방향이다. 테스트는 검증 수단이며 정답을 정의하지 않는다는 점, 하드코딩 금지, 테스트 오류는 보고하라는 점을 명시한다. A·B는 우회를 부추기고, C 같은 문구는 effort 설정을 바꾸는 키워드가 아니라 평범한 텍스트일 뿐이다.
