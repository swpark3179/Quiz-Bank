코드를 쓴 세션에게 "방금 쓴 코드를 리뷰해 줘"라고 하면, 리뷰어는 작성할 때의 추론을 그대로 들고 있어 같은 가정을 다시 받아들이기 쉽다. 이 서브도메인은 리뷰를 작성 맥락에서 떼어 내는 방법(독립 인스턴스), 큰 변경을 쪼개서 보는 방법(파일별 패스 + 통합 패스), 지적마다 신뢰도를 붙여 검증과 라우팅에 쓰는 방법을 다룬다. 좋은 리뷰어의 조건은 더 큰 모델이 아니라, 작성자의 추론을 보지 않은 깨끗한 컨텍스트다.

습득 포인트
  • 같은 세션의 자기 리뷰가 약한 이유: 생성 때의 추론이 컨텍스트에 남아 자기 결정을 의심하지 않는다
  • 작성자의 대화·추론 없이 산출물과 기준만 받는 두 번째 Claude 인스턴스로 리뷰한다
  • 큰 리뷰는 파일별 로컬 패스와 파일 간 통합 패스로 나눠 주의 분산과 모순된 지적을 줄인다
  • 지적마다 신뢰도·심각도를 보고하게 하고, 별도 검증 패스에서 걸러 사람·자동 게시로 나눈다
01

작성한 세션이 약한 리뷰어인 이유

Same context, same blind spots

코드를 쓰는 동안 모델은 "이 함수는 null을 받지 않는다", "이 순서면 락이 필요 없다" 같은 판단을 쌓는다. 같은 대화에서 리뷰를 시키면 그 판단들이 근거처럼 컨텍스트에 남아 있어, 리뷰는 새 시선이 아니라 기존 결정의 재확인이 되기 쉽다. 같은 컨텍스트에서 더 오래 생각하게 하는 것도 그 전제들을 지우지는 않는다.

같은 세션 자기 리뷰
작성 추론이 그대로 보인다. 오타·명백한 누락은 잡지만 설계 가정은 잘 의심하지 않는다.
독립 리뷰 인스턴스
산출물·스펙·기준만 받는다. 작성자가 왜 그렇게 했는지 모르므로 결과만 보고 판단한다.
사람 리뷰
최종 책임. 독립 리뷰가 거른 지적과 신뢰도 낮은 지적을 받는다(5.5와 연결).

공식 문서도 같은 이유를 든다. Claude Code의 /code-review는 대화를 본 적 없는 새 subagent에서 diff를 리뷰해 "코드를 만든 추론에 흔들리지 않는다"고 설명하고, 같은 작업을 subagent에 넘긴다고 답이 나아지지는 않지만 추론을 보지 않은 새 리뷰어는 도움이 된다고 구분한다. Managed Agents의 outcome grader도 메인 에이전트의 구현 선택에 영향받지 않도록 별도 컨텍스트 창을 쓴다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 독립 인스턴스가 "자기 리뷰 지시나 extended thinking보다" 효과적이라고 쓴다. 현재 문서도 독립 리뷰어를 권하지만, 자기 점검 지시("끝내기 전에 [기준]으로 답을 검증하라")가 코딩·수학 오류를 잘 잡는다고도 적고, Claude Opus 5는 지시 없이도 스스로 잘 검증해 이런 지시가 오히려 과잉 검증을 부른다고 설명한다. 정리하면 자기 점검은 쓸모없는 것이 아니라 독립 리뷰를 대신하지 못하는 것이다. 또 최신 모델은 extended thinking 대신 adaptive thinking과 effort로 사고량을 조절한다.

02

독립 리뷰 인스턴스 만들기

Fresh context, explicit criteria
환경방법메모
Claude Code 기본/code-review(별칭 /review) — 백그라운드 subagent가 자기 컨텍스트 창으로 브랜치 변경을 리뷰한다--fix로 반영, --comment로 PR 인라인 코멘트. CLAUDE.md를 따른다
Claude Code 커스텀.claude/agents/reviewer.md에 tools: Read, Grep, Glob만 준 리뷰어 subagent편집 불가가 프롬프트 요청이 아니라 Claude Code가 강제하는 제한이 된다
두 번째 세션다른 세션에서 파일을 지정해 리뷰하고, 지적을 첫 세션에 붙여 넣는다가장 간단한 독립 리뷰
API 파이프라인작성 대화를 복사하지 않은 새 messages 배열에 diff·스펙·리뷰 기준만 넣는다출력은 구조화된 지적 목록으로 받는다(4.3)
BAD · 작성 대화에 리뷰를 덧붙임
messages.append({"role": "user", "content": "좋아. 이제 위에서 쓴 마이그레이션을 아주 비판적으로 리뷰해 줘."})

작성 중 내린 가정이 모두 컨텍스트에 남아 있다. 말투를 세게 해도 컨텍스트는 그대로다.

GOOD · 새 요청, 산출물과 기준만
client.messages.create(model=..., system=REVIEWER, messages=[{"role": "user", "content": "<spec>" + spec + "</spec>\n" "<diff>" + diff + "</diff>\n" "정확성에 영향을 주는 문제만 보고하고 스타일은 건너뛴다."}])

작성자의 설명이나 사고 과정은 넣지 않는다. 그것이 바로 편향을 옮기는 통로다.

Claude Code 문서는 리뷰 프롬프트에서 "스타일은 건너뛰라"는 부분을 빼지 말라고 한다. 문제를 찾으라고 하면 리뷰어는 항상 무언가를 찾아내고, 그 지적을 다 고치면 불필요한 추상화와 일어날 수 없는 경우의 테스트가 늘어나기 때문이다.

03

다중 패스: 파일별 로컬 패스 + 통합 패스

Local passes, then an integration pass

예를 들어 환불 로직을 리팩터링한 PR이 18개 파일(API 핸들러, 서비스, 저장소 계층, DB 마이그레이션, 테스트)을 건드렸다. 한 번에 전부 넣고 리뷰하면 주의가 흩어져 어떤 파일은 피상적인 지적만 받고, 서로 모순되는 지적이 나오기도 한다. 한 지적은 필드를 nullable로 바꾸라 하고, 다른 파일에 대한 지적은 그 필드가 항상 있다고 가정하는 식이다.

1 · 로컬 패스 ×18
파일 하나씩, 병렬. 지적 + 이 파일이 노출·소비하는 계약 요약
→
2 · 통합 패스
계약 요약들 + 호출 관계로 파일 간 데이터 흐름 점검
→
3 · 정리
중복 제거, 모순된 지적 해소
→
4 · 검증 패스
신뢰도 구간별 재확인·라우팅
패스입력잘 찾는 것못 찾는 것
로컬파일 하나의 diff와 주변 코드null 처리, 경계값, 예외 처리, 리소스 누수 같은 파일 내부 결함다른 파일과의 계약 불일치
통합파일별 계약 요약, 호출 관계, 변경 목록바뀐 시그니처를 따라가지 않은 호출부, 단위·통화 변환 누락, 트랜잭션 경계·순서파일 내부의 세부 버그

Anthropic의 Building effective agents는 고려할 점이 여럿인 복잡한 작업은 각 고려 사항을 별도 LLM 호출로 처리할 때 대체로 성능이 낫다고 설명한다(sectioning). 같은 코드를 서로 다른 프롬프트로 여러 번 검사해 하나라도 문제를 찾으면 표시하는 voting도 취약점 리뷰의 예로 든다. 파일별 + 통합 구성은 sectioning을 리뷰에 적용한 것이다.

04

신뢰도 보고와 검증 패스

Find for coverage, verify for precision

찾기 단계에서 "높은 심각도만", "보수적으로"라고 요구하면 최신 모델은 이 지시를 충실히 따른다. Claude Opus 4.8 프롬프트 가이드는 이때 모델이 똑같이 깊게 조사하고도 기준 아래로 판단한 지적을 보고하지 않아, 정밀도는 오르지만 측정된 재현율은 떨어질 수 있다고 설명한다. 권장 구성은 찾기 단계는 커버리지를 목표로 불확실한 것까지 모두 보고하되 지적마다 신뢰도와 심각도를 붙이고, 거르는 일은 별도 검증·중복 제거·순위 단계에 맡기는 것이다.

{"file": "refunds/service.py", "line": 88, "issue": "부분 환불에서 결제 수수료가 두 번 차감된다", "severity": "high", "confidence": 0.62, "evidence": "calc_fee()가 L74의 사전 계산과 L88에서 모두 호출된다"}
라우팅 예시 (임계값은 팀이 정한다)
구간처리
신뢰도 높음 + 근거 있음PR 인라인 코멘트로 바로 게시
중간독립 검증 패스: 다른 인스턴스가 evidence를 따라가 재현·확인한 것만 게시
낮음게시하지 않고 기록만 남겨 패턴 분석에 사용(4.4)

모델이 적어 낸 신뢰도를 그대로 확률로 믿으면 안 된다. 과거 지적이 실제로 맞았는지를 구간별로 대조해 임계값을 보정한다(5.5). 단일 패스에서 스스로 거르게 해야 한다면, 가이드는 "중요한"처럼 막연한 말 대신 "잘못된 동작·테스트 실패·오해를 부르는 결과를 낳는 버그는 보고하고, 순수 스타일·명명 취향만 생략"처럼 보고 기준을 구체적으로 쓰라고 권한다. Claude Code의 /code-review도 effort가 low면 가장 확신하는 지적만 내 오탐을 줄이고, medium~max로 갈수록 범위를 넓힌다.

05

리뷰 구성 고르기

Pick the architecture for the change
상황구성이유
파일 몇 개의 작은 변경독립 인스턴스 1회패스를 나눌 만큼 주의가 흩어지지 않는다
여러 계층에 걸친 큰 PR파일별 로컬 패스 + 통합 패스 + 정리깊이와 파일 간 관점을 함께 확보
놓치면 비싼 결함(보안·결제)서로 다른 관점의 프롬프트로 여러 번(voting)재현율을 높이는 대신 비용이 늘어난다
지적이 많아 노이즈가 큰 봇커버리지 찾기 + 검증 패스 + 신뢰도 라우팅재현율을 지키며 게시되는 오탐을 줄인다
시험 판단 기준
  • "같은 세션에서 리뷰했더니 놓쳤다" → 강한 말투나 더 긴 사고가 아니라 컨텍스트 분리
  • "리뷰어에게 무엇을 주나" → 산출물·스펙·기준. 작성자의 추론과 변명은 주지 않는다
  • "파일이 많아 지적이 얕고 서로 모순된다" → 로컬 패스 + 통합 패스
  • "찾기 단계에서 보수적으로" → 재현율 하락. 거르기는 검증 단계로 옮긴다
  • 비용: subagent마다 토큰이 들고, 기본적으로 같은(또는 더 작은) 모델이다. 얻는 것은 더 똑똑한 답이 아니라 새로운 시선과 병렬성이다

시험 함정 · 흔한 오해

오해같은 세션에 "아주 비판적으로 리뷰하라"고 강하게 지시하면 독립 리뷰와 같은 효과가 난다.
사실지시를 바꿔도 작성 추론은 컨텍스트에 그대로 남는다. 작성 대화를 보지 않은 별도 인스턴스가 필요하다.
오해리뷰를 subagent에 맡기면 더 똑똑한 답이 나온다.
사실Claude Code 문서는 위임만으로 답이 나아지지 않는다고 말한다. 이득은 작성 추론을 보지 않은 새 시선에서 온다.
오해파일 간 문제를 잡으려면 모든 파일을 한 번에 넣고 리뷰해야 한다.
사실파일 간 문제는 계약 요약을 받는 통합 패스가 맡고, 파일 내부 결함은 파일별 패스가 맡는다. 한 번에 넣으면 주의가 흩어진다.
오해오탐을 줄이려면 찾기 단계에서 "확실한 것만 보고하라"고 하는 것이 최선이다.
사실재현율이 떨어질 수 있다. 찾기는 커버리지 위주로 신뢰도를 붙여 보고하고, 거르기는 검증 패스에 맡긴다.
