서브에이전트(subagent, 하위 작업을 맡는 별도 에이전트) 하나가 실패했다고 멀티에이전트 시스템 전체가 쓸모없어지지는 않는다. 결과를 망치는 것은 실패 자체보다 실패가 코디네이터(coordinator, 작업을 나눠 맡기고 결과를 모으는 상위 에이전트)에게 어떤 모양으로 전달되느냐다. 시험은 실패를 구분하고, 어디서 처리하고, 무엇을 담아 올리고, 최종 결과에 어떻게 남기는지를 묻는다. 오류는 숨기지도, 과장하지도 말고 "무엇을 시도했고, 무엇이 왜 안 됐고, 무엇은 건졌고, 다음에 무엇을 해 볼 수 있는지"를 구조로 넘긴다.

습득 포인트
  • 구조화된 오류 컨텍스트: 실패 유형, 시도한 질의, 부분 결과, 대안
  • 접근 실패(재시도 판단이 필요한 타임아웃 등)와 정상적인 빈 결과(성공했지만 일치 항목 없음)의 구분
  • "search unavailable" 같은 일반 상태가 코디네이터에게서 정보를 빼앗는 이유
  • 두 가지 안티패턴: 오류를 빈 성공으로 삼키기, 실패 하나로 워크플로 전체 중단
  • 일시적 실패는 서브에이전트 안에서 복구하고, 해결 못 한 것만 시도 내역·부분 결과와 함께 전파
  • 종합 결과에 근거가 탄탄한 결론과 소스 부재로 생긴 공백을 구분해 표시
01

"실패"와 "없음"을 먼저 가른다

Two kinds of nothing

예시 시스템: 장애 회고를 돕는 리서치 에이전트다. 코디네이터가 "어제 오전 결제 지연 장애의 원인 후보를 정리하라"는 요청을 받아 로그 검색, 배포 이력, 고객 문의 티켓 검색을 각각 서브에이전트에 맡긴다. 티켓 검색이 아무것도 가져오지 못했을 때, 그 "아무것도 없음"은 두 가지 전혀 다른 사실일 수 있다.

구분의미보고 신호코디네이터의 결정

두 경우를 같은 모양(빈 배열)으로 돌려주면 코디네이터는 "티켓이 없었다"와 "티켓 시스템에 못 들어갔다"를 구분하지 못한다. 후자를 전자로 믿으면 "고객 영향 없음" 같은 틀린 결론이 최종 보고서에 들어간다.

문구 하나로 두 상황을 덮지 않는다

공식 search results 문서는 검색이 실패하거나 결과가 없을 때 예외를 던지지 말고 결과를 설명하는 텍스트 블록(예: "No results found.")을 돌려주라고 권한다. 이때도 그 텍스트가 "0건"인지 "실패"인지 구별되게 써야 한다. 도구 정의 문서의 권고대로 응답에는 다음 판단에 필요한 신호만 담되, 이 구분은 빠뜨리면 안 되는 신호다.

02

오류 보고서에 들어갈 네 가지

Anatomy of an error report

Agent SDK 문서에 따르면 서브에이전트의 중간 도구 호출과 결과는 서브에이전트 안에 머물고 최종 메시지만 부모에게 돌아간다. 서브에이전트가 무엇을 시도했고 왜 실패했는지를 최종 보고에 담지 않으면 코디네이터는 알 방법이 없다.

BAD · 일반 상태
{"status": "error", "message": "log search unavailable"}

일시 장애인지 권한 문제인지, 일부라도 읽었는지 알 수 없다. 코디네이터의 선택지는 "전부 재실행" 또는 "포기"뿐이다.

GOOD · 구조화된 오류 컨텍스트
{"status": "partial", "failure_type": "timeout", "retryable": true, "attempted": {"source": "log-store", "query": "service:payment level:ERROR", "window": "09:00-12:00", "retries": 2}, "partial_results": {"covered": "09:00-10:40", "error_spikes": 3}, "alternatives": ["10:40 이후만 5분 단위로 재조회", "APM 트레이스로 대체"]}

코디네이터는 "남은 구간만 재시도", "대체 소스", "공백으로 표시" 중에서 고를 수 있다.

API 수준의 근거

Messages API에서 도구 실행이 실패하면 tool_result에 "is_error": true와 오류 내용을 담아 돌려준다(프로그램을 멈추지 않는다). 공식 문서는 "failed" 같은 일반 오류 대신 무엇이 잘못됐고 다음에 무엇을 시도할지 담은 메시지(예: "Rate limit exceeded. Retry after 60 seconds.")를 쓰라고 권한다. Claude는 이를 읽고 입력을 고쳐 재시도하거나, 사용자에게 묻거나, 한계를 설명한다. 서브에이전트 보고도 같은 원칙으로 설계한다.

03

재시도는 실패가 난 자리에서

Retry where the failure happens
  1. 일시적 실패(타임아웃, 429 rate limit, 529 overloaded)는 서브에이전트 안에서 백오프를 두고 제한된 횟수만 재시도한다
  2. 고칠 수 있는 실패(잘못된 파라미터)는 입력을 고쳐 다시 호출한다. 공식 문서에 따르면 Claude는 잘못되었거나 파라미터가 빠진 도구 호출에 대해 보통 2~3회 수정 재시도를 한 뒤 사용자에게 사과한다
  3. 재시도로 안 풀리는 실패(인증·권한)는 재시도하지 말고 바로 올린다
  4. 올릴 때는 무엇을 시도했는지, 부분 결과, 가능한 대안을 함께 붙인다

시험 가이드 표현 vs 현재 문서

① 서브에이전트를 띄우는 Claude Code 도구는 v2.1.63에서 Task에서 Agent로 이름이 바뀌었다(Task(...) 표기는 별칭으로 계속 동작). ② 현재 Agent SDK에서 서브에이전트는 기본적으로 백그라운드로 실행된다. Agent 도구 결과는 status: "async_launched"이고 보고는 이후 턴에 도착하므로, 코디네이터는 실패 알림(task_notification의 status: "failed")도 처리해야 한다. ③ 하네스가 전하는 것은 API 오류 같은 실행 실패다. 도구·데이터 수준의 오류를 어떤 구조로 보고할지는 여전히 설계자의 몫이다. ④ Managed Agents의 예전 coordinator 타입은 지금도 받아들여지지만, 문서는 워크플로 실행까지 지원하는 multiagent_20261001 타입으로 옮기는 방법을 안내한다. 시험의 "coordinator"는 일반적인 역할 이름이다.

04

실패를 지우지도, 흐름을 끊지도 않는다

Neither swallow nor abort
조용한 삼킴

실패를 빈 성공으로 돌려준다. 파이프라인은 매끄럽게 끝나 보이지만 결론이 틀린다. 누구도 실패를 보지 못하므로 가장 늦게 발견된다.

전체 중단

소스 하나가 실패하면 워크플로 전체를 끝낸다. 다른 서브에이전트가 이미 성공한 결과까지 버리고, 사용자는 처음부터 다시 기다려야 한다.

Anthropic의 멀티에이전트 리서치 시스템 글은 에이전트가 상태를 오래 유지하므로 오류가 누적(compound)된다고 설명한다. 오류가 나도 처음부터 재시작하면 비용이 크고 사용자를 지치게 하므로, 오류가 난 지점에서 재개하는 시스템을 만들고, 도구가 실패하고 있다는 사실을 에이전트에게 알려 적응하게 하며, 재시도 로직과 주기적 체크포인트 같은 결정론적 안전장치를 함께 쓴다고 한다.

공식 문서의 지시문 예

Managed Agents 멀티에이전트 문서는 워크플로 실행 지침 예시로 "에이전트 하나의 실패가 실행 전체를 실패시키면 안 된다, 읽지 못한 항목은 '커버되지 않음'으로 표시하고 끝날 때 어떤 항목이 빠졌는지 알려 달라"는 취지의 문장을 든다. 시험 가이드가 말하는 두 안티패턴의 반대 방향을 그대로 프롬프트로 옮긴 형태다.

05

최종 보고서에 빈칸을 남긴다

Leave the gaps visible

최종 종합(synthesis)은 "무엇을 알아냈나"와 함께 "어디를 보지 못했나"를 담는다. 독자가 결론의 강도를 판단하려면 근거가 탄탄한 항목과 소스가 없어서 비어 있는 영역을 구분해서 봐야 한다.

{"findings": [ {"claim": "10:12 배포 직후 결제 API p95 지연 약 4배", "support": "well_supported", "sources": ["deploy-history", "apm"]}, {"claim": "외부 PG 응답 지연 가능성", "support": "single_source", "sources": ["log-store (09:00-10:40)"]} ], "coverage_gaps": [ {"area": "10:40 이후 에러 로그", "reason": "log-store 타임아웃, 2회 재시도 후 실패", "impact": "후반부 원인은 배제할 수 없음"} ]}

스키마는 작업에 맞춘다. Agent SDK 구조화 출력 문서는 작업이 스키마가 요구하는 정보를 다 갖지 못할 수 있으면 그 필드를 선택(optional)으로 두라고 권한다. 소스가 실패할 수 있는 결과 필드는 선택으로 두고, coverage_gaps처럼 "빠진 것"을 적는 자리는 항상 존재하게 두면(빈 배열 허용) 공백이 조용히 사라지지 않는다. 스키마 검증을 끝내 통과하지 못하면 SDK는 error_max_structured_output_retries 결과를 낸다.

시험 판단 축
  • 실패 유형·시도한 내용·부분 결과·대안을 담은 보고 → 정답 쪽
  • "search unavailable" 같은 일반 상태, 실패를 빈 성공으로 반환, 실패 하나에 전체 종료 → 오답
  • 일시 오류는 하위에서 제한적으로 재시도하고, 해결 못 한 것만 위로 올린다
  • 최종 보고서는 공백을 숨기지 않고 "근거 탄탄 / 단일 출처 / 확인 못 함"을 구분한다

시험 함정 · 흔한 오해

오해실패하면 빈 결과를 돌려주면 된다. 코디네이터가 알아서 판단한다.
사실빈 결과로는 "성공했지만 0건"과 "접근 실패"를 구분할 수 없다. 실패는 오류로, 0건은 0건으로 보고한다.
오해소스 하나라도 실패하면 전체를 멈추는 편이 안전하다.
사실성공한 결과를 버리고 재시작 비용을 키운다. 부분 결과를 유지하고 실패 영역을 공백으로 표시하거나 대안을 쓴다.
오해투명성을 위해 모든 오류를 즉시 코디네이터로 올린다.
사실일시적 오류는 서브에이전트 안에서 재시도한다. 위로 올리는 것은 해결하지 못한 오류이며, 그때는 시도 내역과 부분 결과를 붙인다.
오해오류 메시지는 짧을수록 좋다("failed").
사실공식 문서는 무엇이 잘못됐고 다음에 무엇을 시도할지 담은 메시지를 권한다. 그래야 받는 쪽이 추측 없이 복구한다.

자가 점검 퀴즈

점수 0 / 6
Q1일반 상태의 문제
티켓 검색 서브에이전트가 인증 토큰 만료로 실패하자 {"error": "ticket search unavailable"}만 반환했다. 코디네이터는 한 시간 동안 같은 서브에이전트를 거듭 재실행했다.근본적인 개선은?
정답 (B)

일반 상태는 "재시도로 풀리지 않는 실패"라는 핵심 정보를 숨긴다. 실패 유형과 대안이 있으면 코디네이터는 재시도를 멈추고 대체 경로나 공백 표시를 고른다. A는 낭비를 늘리고, C는 조용한 삼킴, D는 전체 중단 안티패턴이다.

Q2빈 결과 vs 실패
로그 검색 도구는 타임아웃이 나면 []를 반환하도록 구현돼 있다. 최종 보고서에 "해당 시간대 에러 로그 없음"이 기재됐다.무엇이 문제인가?
정답 (A)

접근 실패와 0건은 다른 사실이다. 실패는 is_error와 실패 유형으로 보고해야 한다. B는 증상 완화일 뿐 구분 문제를 남기고, D도 실패 유형·시도 내역 없이 모호한 값을 돌려주는 것에 불과하다.

Q3로컬 복구
가격 데이터 서브에이전트가 공급사 API에서 간헐적인 429 응답을 받는다. 대부분 몇 초 뒤 다시 호출하면 성공한다.바람직한 설계는?
정답 (C)

일시적 실패는 하위에서 복구하고, 해결 못 한 것만 맥락과 함께 올린다. A는 코디네이터에게 불필요한 결정을 떠넘기고, B는 일부 누락을 숨기며, D는 실패 하나로 전체를 멈춘다.

Q4커버리지 주석
시장 조사 종합 단계에서 다섯 소스 중 두 개가 끝내 접근 불가였다.최종 보고서는 어떻게 써야 하는가?
정답 (D)

커버리지 주석이 있어야 독자가 결론의 강도를 판단한다. A는 공백을 숨기고, B는 전체 중단과 같은 효과이며, C는 근거 없는 내용으로 공백을 메우는 환각 위험이다.

Q5SDK 오류 값
Agent SDK의 SDKAssistantMessageError 값 중 rate_limit과 overloaded의 차이로 옳은 것은?
정답 (A)

TypeScript 레퍼런스는 overloaded를 서버가 용량 한계에 있어 529를 돌려준 경우로, rate_limit을 할당량에 대한 429로 구분한다. 인증 실패는 authentication_failed라는 별도 값이다. 둘 다 일시적 실패에 가깝지만 원인이 달라 대응(대기·한도 조정)도 다를 수 있다.

Q6부분 실패 대응
서브에이전트 열 개 중 하나가 구조화된 오류 보고와 함께 실패했다. 코디네이터의 대응으로 가장 알맞은 것은?
정답 (B)

구조화된 오류 보고의 목적이 바로 이 선택을 가능하게 하는 것이다. A·D는 성공한 결과를 버리는 전체 중단이고, C는 실패를 결과 없음으로 바꿔 버리는 조용한 삼킴이다.
