Claude의 응답을 코드가 받아 쓰는 순간, 질문은 '답이 좋은가'에서 '이 응답을 그대로 믿고 처리해도 되는가'로 바뀐다. 이 레슨은 그 판단을 세 겹으로 나눈다. 첫째, 형식은 프롬프트가 아니라 Structured Outputs와 strict 도구 사용으로 보장한다. 둘째, 내용을 읽기 전에 stop_reason으로 응답이 끝났는지, 잘렸는지, 거절되었는지 확인한다. 셋째, 형식이 맞아도 사실은 따로 검증한다. 시험은 이 세 겹 각각에서 흔한 착각을 골라낸다.

습득 포인트
  • 프롬프트로 요청한 JSON이 왜 보장되지 않는지 설명하고, output_config.format으로 JSON 출력을 설정한다
  • SDK 도우미가 지원되지 않는 스키마 제약을 어떻게 처리하는지, Structured Outputs를 못 쓸 때 코드가 무엇을 맡아야 하는지 안다
  • strict: true의 위치와 보장 범위, 컴퓨터·브라우저 사용 툴셋에서의 예외를 안다
  • 도구 실패를 is_error와 구체적인 메시지로 돌려줘 같은 호출의 반복을 막는다
  • stop_reason 값별 처리, 특히 잘린 tool_use, 잘린 JSON, 빈 end_turn을 구분한다
  • 거절이 HTTP 200으로 온다는 점과 대체 모델 재시도 절차, 환각 검증 기법을 설명한다
01

프롬프트로 요청한 JSON이 깨지는 이유

Why prompted JSON breaks pipelines

"JSON으로만 답하라"는 지시와 예시는 올바른 JSON이 나올 확률을 높일 뿐, 형식을 강제하지 않는다. 대량 처리에서는 드문 실패도 매일 일어난다. 일관성 문서는 스키마를 항상 지키는 유효한 JSON이 필요하면 프롬프트 기법 대신 Structured Outputs를 쓰라고 못 박는다.

프롬프트 JSON의 실패다음 단계에서 생기는 일제약 디코딩에서는
앞뒤에 붙는 설명 문장json.loads 실패스키마 밖의 토큰이 나올 수 없다
필수 필드 누락KeyError, 빈 값이 조용히 저장됨required 필드가 항상 있다
타입 오류("2" 대신 2가 필요)계산·비교 오류타입이 스키마대로 나온다

Structured Outputs는 토큰 샘플링 자체를 스키마에 맞는 출력으로 제한한다(문법 제약 샘플링, grammar-constrained sampling). 그래서 대문자 강조나 예시 추가, 정규식 후처리, 무조건 재시도로는 같은 보장을 얻을 수 없다.

response = client.messages.create( model="claude-sonnet-5-5", max_tokens=1024, messages=[{"role": "user", "content": card_text}], output_config={"format": { "type": "json_schema", "schema": { "type": "object", "properties": { "name": {"type": "string"}, "email": {"type": "string", "format": "email"}, "phone": {"anyOf": [{"type": "string"}, {"type": "null"}]}, }, "required": ["name", "email", "phone"], "additionalProperties": False, }, }}, ) contact = json.loads(response.content[0].text)
알아 둘 점내용
옛 파라미터output_format은 사용 중단되어 output_config.format으로 옮겨졌고 베타 헤더도 필요 없다. 옛 이름을 쓰려면 structured-outputs-2025-11-13 헤더가 필요하며, 없으면 400
지원되지 않는 스키마 기능재귀 스키마, 외부 $ref, 숫자 제약(minimum·maximum·multipleOf), 문자열 길이 제약, minItems 0·1 이외 값 등. 쓰면 400 오류
첫 요청 지연스키마를 처음 쓸 때 문법 컴파일로 지연이 생기고, 컴파일 결과는 마지막 사용 후 24시간 캐시된다. name·description만 바꾸면 캐시가 유지된다
SDK 도우미는 제약을 '옮겼다가 다시 검사'한다

Python의 client.messages.parse()에 Pydantic 모델을 넘기면 SDK가 스키마를 변환해 보내고, 응답을 검증해 parsed_output으로 돌려준다. 변환 과정에서 지원되지 않는 제약은 스키마에서 빠져 필드 설명(description)으로 옮겨지고, 응답이 오면 도우미가 원래 제약을 코드에서 다시 검증한다. Field(ge=100)은 일반 정수 + 설명 속 {minimum: 100}이 되는 식이다. TypeScript의 jsonSchemaOutputFormat()처럼 응답을 검증하지 않는 도우미는 이런 위반을 잡지 못한다.

Structured Outputs를 쓸 수 없는 경우(예: 재귀 스키마가 꼭 필요할 때)에는 프롬프트 기반 JSON으로 돌아가되, 코드가 파싱 오류 처리 + 스키마 검증 + 재시도를 모두 맡아야 한다.

03

strict 도구 사용: 도구 입력을 보장한다

Strict tool use

도구 정의의 최상위, name·description·input_schema와 나란히 "strict": true를 둔다. 그러면 tool_use 블록의 input이 input_schema를 엄격히 따르고, 도구 name도 항상 유효하다. JSON 출력과 같은 문법 파이프라인을 쓰므로 스키마 제약 목록도 같다.

JSON 출력strict 도구 사용
설정 위치요청의 output_config.format도구 정의의 최상위 strict: true
보장하는 것Claude의 응답 본문이 스키마에 맞음도구 입력이 input_schema에 맞고 도구 이름이 유효함
결과를 읽는 곳텍스트 블록tool_use 블록의 input
쓰는 상황응답 자체가 고정 형식 데이터여야 할 때에이전트가 함수를 정확한 타입으로 호출해야 할 때
모든 tools 항목에 붙이면 안 된다

컴퓨터 사용·브라우저 사용 툴셋 항목(computer_toolset_20260801, browser_toolset_20260801)은 strict: true를 받지 않으며, 둘 중 어디에든 설정하면 요청이 거부된다. 사용자가 input_schema를 정의하는 사용자 정의 도구에만 붙인다. 여러 사용자 정의 도구에 각각 붙이는 것은 정상이다.

strict 없이 쓰면 필수 파라미터가 빠지는 등 잘못된 호출에 대해 Claude가 오류 결과를 보고 2~3번 고쳐 재시도한 뒤 사용자에게 사과한다. strict는 이런 잘못된 호출 자체를 없앤다.

04

도구 실패는 구체적으로 돌려준다

is_error with instructive messages

도구가 실행 중 실패하면 tool_result의 content에 오류 내용을 담고 "is_error": true를 붙인다. 문서는 여기에 더해 지시가 담긴 오류 메시지를 쓰라고 한다. 무엇이 잘못됐고 다음에 무엇을 해야 하는지를 알아야 Claude가 추측 없이 회복하거나 방향을 바꾼다.

BAD · 일반 오류
{"type": "tool_result", "tool_use_id": "toolu_01…", "is_error": true, "content": "failed"}

일시적 장애인지, 입력이 틀렸는지 알 수 없어 Claude가 같은 입력으로 곧바로 다시 부른다.

GOOD · 원인 + 다음 행동
{"type": "tool_result", "tool_use_id": "toolu_01…", "is_error": true, "content": "Stock service timed out (temporary). Retry in 30 s, or answer from the 09:00 snapshot."}

대기 후 재시도하거나 대안을 쓰는 판단을 Claude가 스스로 내린다.

형식 규칙
  • tool_result는 대응하는 tool_use 바로 다음 메시지에 와야 한다. 결과를 빼먹으면 "tool_use ids were found without tool_result blocks immediately after" 류의 오류가 난다
  • 사용자 메시지 안에서 tool_result 블록이 맨 앞에 오고, 텍스트는 그 뒤에 온다. 텍스트를 앞에 두면 400
  • 실패를 내용이 빈 성공 결과로 꾸미지 않는다. Claude가 '결과 없음'을 사실로 받아들인다

잘린 JSON

JSON 디코딩 오류가 max_tokens 중단과 함께 나타나면 형식 문제가 아니라 잘림이다. 응답을 불완전한 것으로 처리하고 한도를 높여 재시도한다. Structured Outputs를 써도 마찬가지로, max_tokens로 멈춘 응답은 불완전해 스키마에 맞지 않을 수 있다. 스트리밍에서는 stop_reason이 message_start가 아니라 message_delta에서 온다.

06

거절은 성공 응답으로 온다

Refusals arrive as HTTP 200

Claude Fable 5.1·Fable 5·Opus 5.5·Opus 5·Sonnet 5.5·Haiku 5.5에는 요청을 거절할 수 있는 안전 분류기가 있다. 거절은 API 오류가 아니라 HTTP 200 응답으로 오고, stop_reason이 "refusal"이며, 출력 전에 거절되면 content가 빈 배열일 수 있다. 따라서 try/except만으로는 잡히지 않는다.

{ "role": "assistant", "content": [], "stop_reason": "refusal", "stop_details": { "type": "refusal", "category": "cyber", // null일 수도 있다 "explanation": "…" // 표시용. 파싱하지 않는다 } }
상황처리
스트리밍 도중 부분 출력 뒤 거절부분 출력은 불완전한 것으로 보고 폐기한다
직접 재시도같은 요청을 model만 대체 모델(예: Claude Opus 4.8)로 바꿔 보내고, 이후 턴도 그 모델을 유지. fallback credit으로 캐시 재작성 비용을 돌려받는다
재시도를 맡기고 싶을 때서버 측 폴백(fallbacks: "default" + server-side-fallback-2026-07-01) 또는 SDK 폴백 미들웨어. 둘 중 하나만 쓴다. Haiku 5.5는 서버 측 폴백이 없어 미들웨어나 직접 재시도
같은 모델로 재시도대개 다시 거절된다. 재시도는 대체 모델로
시험 판단 축
  • 분기는 stop_reason == "refusal"로 한다. content나 stop_details.category(null 가능)로 분기하지 않는다
  • 거절은 HTTP 200이라 오류율·5xx 기반 모니터링에 보이지 않는다. 거절을 별도 지표로 계측한다
  • Structured Outputs 요청에서도 거절 메시지가 스키마보다 우선하므로 출력이 스키마에 맞지 않을 수 있다
07

빈 응답을 다루는 법

Guard against empty end_turn

Claude가 내용 없이(2~3토큰) stop_reason: "end_turn"으로 답할 때가 있다. 주로 도구 결과 뒤에서, Claude가 턴이 끝났다고 판단할 때다.

원인
  • 도구 결과 바로 뒤에 텍스트 블록을 붙이는 습관. 이력 패턴을 따라 Claude가 턴을 끝낸다
  • 완료된 응답을 아무것도 더하지 않고 다시 보내기. 이미 끝났다고 판단했으므로 계속 끝난 상태다
처방 (순서대로)
  • tool_result만 담은 사용자 메시지를 보낸다
  • 빈 응답을 수정 없이 재시도하지 않는다. 빈 응답을 붙여 다시 보내도 소용없다
  • 최후의 수단으로 새 사용자 메시지에 "계속해 주세요" 같은 요청을 추가한다
08

형식이 맞아도 내용이 맞는 것은 아니다

Well-formed output is not correct output

스키마 검증은 모양을 확인할 뿐 사실을 확인하지 않는다. 사실성은 환각 줄이기 기법으로 따로 다룬다. 문서는 이 기법들이 환각을 크게 줄이지만 완전히 없애지는 못하므로, 중요한 결정에 쓰이는 정보는 항상 검증하라고 덧붙인다.

기법방법
"모른다" 허용불확실하면 그렇다고 말해도 된다고 명시적으로 허락한다
직접 인용 근거화긴 문서(2만 토큰 이상)에서 작업 전에 글자 그대로의 인용을 뽑고 그것으로만 작업하게 한다
인용 검증작업 후에 주장마다 뒷받침하는 인용을 찾게 하고, 찾지 못하면 그 주장을 철회하게 한다
사고 과정 검증thinking을 display: "summarized"로 받아, 답이 이상할 때 요약된 추론을 검토한다
Best-of-N 검증같은 프롬프트를 여러 번 돌려 비교한다. 출력 간 불일치는 환각의 신호일 수 있다
반복 개선출력을 후속 프롬프트의 입력으로 써서 앞선 진술을 검증·보완하게 한다
외부 지식 제한제공된 문서의 정보만 쓰고 일반 지식은 쓰지 말라고 지시한다

시험 함정 · 흔한 오해

오해명확한 프롬프트와 예시가 있으면 JSON을 방어 코드 없이 파싱해도 된다.
사실프롬프트는 확률을 높일 뿐이다. 깨진 JSON·필드 누락·타입 오류를 배제하는 것은 제약 디코딩(Structured Outputs)뿐이다.
오해안전하게 하려면 tools의 모든 항목에 strict: true를 붙인다.
사실컴퓨터 사용·브라우저 사용 툴셋 항목은 strict: true를 받지 않으며, 붙이면 요청이 거부된다.
오해모든 max_tokens 중단은 "계속해 주세요"로 이어 쓰게 하면 된다.
사실마지막 블록이 잘린 tool_use라면 이어 쓸 수 없다. 더 높은 max_tokens로 재요청한다.
오해거절은 API 오류이므로 try/except로 잡힌다.
사실거절은 HTTP 200, stop_reason: "refusal"인 정상 응답이다. stop_reason을 직접 확인해야 한다.
오해빈 응답은 같은 요청을 다시 보내면 해결된다.
