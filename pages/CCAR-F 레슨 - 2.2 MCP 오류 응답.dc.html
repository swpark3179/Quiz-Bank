01

MCP의 두 오류 채널

Protocol errors vs tool execution errors

MCP 명세(현재 latest인 2026-07-28 개정판, 2025-11-25판도 같은 구분)는 도구 오류를 두 갈래로 보고한다.

프로토콜 오류 · JSON-RPC error
{"jsonrpc": "2.0", "id": 7, "error": {"code": -32602, "message": "Unknown tool: book_flihgt"}}

알 수 없는 도구, CallToolRequest 스키마를 어긴 요청, 서버 오류. 요청 구조 자체의 문제라 모델이 고쳐 내기 어렵다. 클라이언트는 이를 모델에 전달해도 된다(MAY).

도구 실행 오류 · isError: true
{"jsonrpc": "2.0", "id": 8, "result": {"resultType": "complete", "content": [{"type": "text", "text": "체크아웃은 체크인 이후여야 합니다 (받은 값: 11-03 → 11-01)"}], "isError": true}}

API 실패, 입력 검증 오류, 비즈니스 로직 오류. 모델이 읽고 인자를 고쳐 다시 시도할 수 있는 피드백이다. 클라이언트는 이를 모델에 전달해야 한다(SHOULD).

계층마다 다른 필드 이름
계층실패 표시
MCP 서버의 tools/call 결과isError: true
Claude API의 tool_result 블록is_error: true
Agent SDK 커스텀 도구 핸들러TypeScript isError: true / Python 반환 dict의 "is_error": True
시험 가이드 표현 vs 현재 문서

시험 가이드의 errorCategory, isRetryable(또는 retriable)은 MCP 명세가 정한 필드가 아니다. 명세가 정하는 것은 isError 플래그와 결과 내용(content, 선택적 structuredContent)까지이고, 분류 필드는 서버 설계자가 결과 내용 안에 넣는 자체 규약이다. 또 최신 명세의 결과에는 resultType이 붙는다. 사용자에게 추가 입력을 받아야 하는 경우는 오류가 아니라 "input_required" 결과(elicitation 요청 포함)로 표현할 수 있다.

02

"작업 실패"가 에이전트를 눈멀게 한다

Why generic errors break recovery

모든 실패를 "Operation failed"로 돌려주면 에이전트가 아는 것은 "안 됐다" 하나뿐이다. 재시도할지, 인자를 고칠지, 사용자에게 뭐라고 할지 추측해야 하고, 그 추측은 흔히 같은 호출의 반복으로 끝난다. Handle tool calls 문서는 "failed" 같은 일반 오류 대신 무엇이 잘못됐고 Claude가 다음에 무엇을 시도해야 하는지 적으라고 권한다(예: "Rate limit exceeded. Retry after 60 seconds."). 또 요청이 잘못됐거나 파라미터가 빠진 경우 Claude는 보통 2~3회 고쳐서 다시 시도한 뒤에야 사용자에게 사과한다고 설명한다.

BAD · 단서 없는 실패
{"isError": true, "content": [{"type": "text", "text": "Operation failed"}]}

다시 해도 되는지, 무엇을 고칠지, 고객에게 뭐라고 할지 알 수 없다.

GOOD · 회의실 예약 도구의 검증 오류
{"isError": true, "content": [{"type": "text", "text": "<아래 JSON 문자열>"}]} {"errorCategory": "validation", "isRetryable": false, "message": "start_time은 15분 단위여야 합니다 (받은 값 10:07)", "fix": "10:00 또는 10:15로 다시 요청"}

에이전트는 사용자에게 되묻지 않고 시각을 고쳐 다시 호출한다.

무엇을 빼야 하나

Writing tools for agents는 불투명한 오류 코드나 트레이스백 대신 구체적이고 실행 가능한 개선점을 전하도록 오류 응답을 프롬프트처럼 설계하라고 한다. 내부 스택 트레이스·호스트명은 빼고, 다음 행동을 고를 만큼만 담는다.

03

네 가지 오류와 재시도 판단

Classify, then decide
분류예isRetryable에이전트의 다음 행동페이로드에 넣을 것
transient
일시적		타임아웃, 503, 속도 제한true같은 입력으로 잠시 뒤 재시도 (횟수 상한·백오프)retryAfterSeconds, 지금까지 시도 횟수

검증		날짜 형식 오류, 범위 밖 값false (그대로는)입력을 고쳐 새로 호출. 고칠 정보가 없으면 사용자에게 질문어느 필드가 왜 틀렸는지, 허용 형식

비즈니스 규칙		1회 한정 쿠폰 재사용, 한도 초과false재시도·우회 금지. 사용자에게 사유를 설명하고 대안 제시고객에게 보여 줄 설명, 가능한 대안

권한		토큰 만료, 역할 부족false재시도 금지. 인증 갱신 요청이나 사람에게 이관필요한 권한, 이관 경로
# 비즈니스 규칙 위반: 재시도하지 말고 설명하라는 신호 {"errorCategory": "business", "isRetryable": false, "message": "쿠폰 WELCOME10은 계정당 1회 한정이며 2026-08-14에 이미 사용됨", "customerMessage": "이 쿠폰은 계정당 한 번만 쓸 수 있어 이미 사용 처리되었습니다. 지금 쓸 수 있는 다른 쿠폰을 찾아 드릴까요?", "alternatives": ["list_available_coupons"]}

isRetryable: false가 있으면 에이전트는 같은 호출을 반복하는 대신 customerMessage를 바탕으로 사정을 설명하고 대안을 제시한다. 이 신호가 없으면 "다시 시도해 보겠습니다"가 루프가 된다.

실제 사례 — Claude Code의 MCP 클라이언트

Claude Code 자신도 이 구분대로 움직인다. HTTP·SSE 서버의 첫 연결이 5xx·연결 거부·타임아웃 같은 일시적 오류로 실패하면 최대 세 번 재시도하지만, 인증 오류나 not-found는 설정을 바꿔야 풀리므로 재시도하지 않는다. 연결 뒤 tools/list 같은 탐색 요청도 일시적 오류는 짧은 백오프로 세 번까지 재시도하고, 인증 오류·4xx·요청 타임아웃은 재시도하지 않는다.

04

빈 결과는 실패가 아니다

Empty is a valid answer

"조건에 맞는 고객 없음"은 질의가 성공했고 답이 0건이라는 뜻이다. "고객 DB에 접속하지 못함"은 질의 자체가 실패했다는 뜻이다. 둘을 섞으면 양쪽으로 틀린다. 접근 실패를 빈 결과처럼 돌려주면 에이전트는 "그런 고객은 없다"고 단정하고, 빈 결과를 오류로 돌려주면 있지도 않은 장애를 풀려고 재시도를 거듭한다.

정상 응답 · 결과 0건
isError: false {"query": {"email": "kim@example.com"}, "matches": [], "total": 0}

어떤 조건으로 찾았는지 함께 돌려주면, 에이전트가 조건을 바꿔(예: 이메일 대신 전화번호) 다시 찾을지 스스로 판단한다.

접근 실패
isError: true {"errorCategory": "transient", "isRetryable": true, "message": "고객 DB 응답 없음 (5초 타임아웃)", "retryAfterSeconds": 10}

실패를 실패로 알려야 에이전트가 "없음"이라는 잘못된 결론을 내리지 않는다.

05

서브에이전트의 로컬 복구와 전파

Recover locally, escalate with context

멀티에이전트 시스템에서 모든 오류를 코디네이터로 올리면 코디네이터의 컨텍스트가 잡음으로 차고, 서브에이전트가 오류를 삼키면 코디네이터는 결과가 불완전하다는 사실을 모른다. 원칙은 이렇다. 서브에이전트가 풀 수 있는 일시적 오류는 그 안에서 상한을 두고 재시도하고, 풀지 못한 오류만 무엇을 시도했고 무엇을 얻었는지와 함께 올린다.

  1. transient → 서브에이전트 안에서 백오프 재시도 (예: 최대 3회)
  2. validation → 서브에이전트가 입력을 고쳐 다시 호출
  3. business · permission, 또는 재시도 소진 → 코디네이터에 보고
  4. 코디네이터 → 다른 출처로 재위임, 범위 축소, 사람에게 이관 중에서 결정
# 서브에이전트의 최종 보고 예시 {"status": "partial", "completed": ["2024·2025 연간 보고서에서 매출 수치 추출"], "failed": [{"source": "IR 포털 2026 분기 보고서", "errorCategory": "permission", "isRetryable": false, "attempted": ["공개 URL 조회", "검색 캐시 조회"]}], "partialResults": {"revenue_2024": "…", "revenue_2025": "…"}, "suggestion": "2026 수치는 담당자에게 자료 요청이 필요"}

Anthropic의 멀티에이전트 리서치 시스템 글은 도구가 실패하고 있다는 사실을 에이전트에게 알리고 적응하게 하는 방식이 의외로 잘 통했다고 하며, 이를 재시도 로직·정기 체크포인트 같은 결정론적 안전장치와 함께 쓴다고 설명한다.

Agent SDK 커스텀 도구에서

핸들러가 예외를 잡지 않으면 SDK의 in-process MCP 서버가 원래 예외 메시지를 담은 오류 결과로 바꾸고, 에이전트 루프는 계속된다. 예외를 직접 잡아 isError와 함께 메시지를 만들면 어느 요청이 왜 실패했고 무엇을 대신 해 볼지를 덧붙일 수 있다. Python @tool 데코레이터는 반환 dict에서 content와 is_error만 전달하므로, 분류 필드는 텍스트 content 안의 JSON으로 넣는다.

시험 함정 · 흔한 오해

오해도구 안에서 난 오류는 JSON-RPC error로 던지는 것이 정석이다.
사실API 실패·입력 검증·비즈니스 규칙 오류는 isError: true 결과로 돌려줘야 모델이 읽고 고칠 수 있다. 프로토콜 오류는 알 수 없는 도구나 잘못된 요청 구조용이다.
오해errorCategory와 isRetryable은 MCP 표준 필드다.
사실명세는 isError와 결과 내용까지 정한다. 분류 필드는 결과 내용에 넣는 자체 규약이다.
오해검색 결과가 하나도 없으면 isError: true로 알린다.
사실0건은 성공한 질의다. 빈 목록과 사용한 조건을 정상 결과로 돌려주고, 접근 실패만 오류로 보고한다.
오해원인을 자세히 알리려면 스택 트레이스를 그대로 넘기는 게 낫다.
사실필요한 것은 실행 가능한 설명이다. 트레이스는 판단에 도움이 적고 내부 정보를 노출한다.
오해투명성을 위해 서브에이전트는 모든 오류를 즉시 코디네이터로 올린다.
사실일시적 오류는 로컬에서 복구하고, 풀지 못한 오류만 시도 내역·부분 결과와 함께 올린다.
