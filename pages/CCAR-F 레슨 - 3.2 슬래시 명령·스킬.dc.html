커스텀 슬래시 명령과 스킬

.claude/commands · .claude/skills/SKILL.md · 프로젝트 vs 개인 · context: fork · allowed-tools · argument-hint

참고 레슨 · CertSafari 3.2  |  출제 도메인: 도메인 3 · Claude Code Configuration & Workflows (20%)

3.1 CLAUDE.md3.2 명령·스킬3.3 경로별 규칙3.4 플랜 모드3.5 반복 개선3.6 CI/CD

같은 절차나 체크리스트를 채팅에 반복해서 붙여 넣고 있다면 스킬(skill)로 만들 때다. 현재 Claude Code에서 커스텀 슬래시 명령은 스킬에 통합되어, .claude/commands/x.md와 .claude/skills/x/SKILL.md가 똑같이 /x를 만든다. 시험은 공유 범위, frontmatter 옵션이 실제로 하는 일, CLAUDE.md와의 역할 분담을 묻는다. 매 세션 필요한 사실은 CLAUDE.md, 필요할 때만 불러오는 절차와 참고 자료는 스킬에 둔다.

습득 포인트
  • 프로젝트 .claude/commands/·.claude/skills/(커밋해 공유) vs 개인 ~/.claude/commands/·~/.claude/skills/
  • SKILL.md frontmatter: context: fork, allowed-tools, argument-hint 등이 실행 시 하는 일
  • 장황한 분석·탐색 출력을 context: fork로 메인 대화에서 격리하기
  • 개인 변형 스킬은 다른 이름으로 — 같은 이름이면 내 세션에서 팀 스킬을 가린다
  • 스킬(필요할 때 호출)과 CLAUDE.md(항상 로드) 중 어디에 둘지 판단
01

명령 파일과 스킬 디렉터리: 하나의 메커니즘

Commands merged into skills
항목.claude/commands/seed-db.md.claude/skills/seed-db/SKILL.md
만드는 명령/seed-db/seed-db (frontmatter name으로 바꿀 수 있음)
하위 폴더commands/db/seed.md → /db:seed스킬마다 자기 폴더
보조 파일없음 (단일 파일)스크립트·템플릿·참고 문서를 같은 폴더에
frontmatter스킬 필드 중 name·paths 제외 전부전체 필드
이름이 겹치면스킬이 이긴다
시험 가이드 표현 vs 현재 문서

가이드는 "커스텀 슬래시 명령(.claude/commands/)"과 "스킬(.claude/skills/)"을 나란히 다룬다. 현재 문서는 커스텀 명령이 스킬로 통합되었다고 명시한다. 기존 .claude/commands/ 파일은 계속 동작하는 이전 형식이고, 새 작업에는 보조 파일을 둘 수 있는 스킬을 권장한다. 시험의 "프로젝트 vs 개인" 판단은 두 형식에 똑같이 적용된다.

02

누가 받는가: 프로젝트 · 개인 · 그 밖

Where a skill is saved decides its audience
위치경로로드 범위
Project.claude/skills/<name>/SKILL.md (명령 파일은 .claude/commands/)이 저장소 세션. 커밋하면 팀 전체
Personal~/.claude/skills/<name>/SKILL.md (명령 파일은 ~/.claude/commands/)이 머신의 내 모든 프로젝트
Nestedapps/web/.claude/skills/...그 디렉터리에서 시작했거나, Claude가 그 아래 파일을 다룬 뒤
Enterprise · Pluginmanaged 설정 디렉터리 · <plugin>/skills/조직 배포 · 플러그인 활성화된 곳(/plugin-name:skill)

이름이 겹치면 누가 이기나

enterprise, personal, project에 같은 이름이 있으면 enterprise → personal → project 순으로 이긴다. 예를 들어 팀이 커밋한 버그 분류 스킬 /triage-bug에 내 습관을 더하고 싶어 ~/.claude/skills/triage-bug/를 만들면, 팀원에게는 영향이 없지만 내 세션에서는 팀 버전이 가려진다. 팀 스킬이 갱신돼도 나는 받지 못한다. 개인 변형은 triage-bug-deep처럼 다른 이름으로 만든다. 플러그인 스킬은 /plugin-name:skill로 네임스페이스가 붙어 충돌하지 않는다.

시험 가이드의 "팀원에게 영향을 주지 않도록 다른 이름으로" 표현은 위 우선순위와 함께 이해하면 정확하다: 개인 폴더는 원래 내 머신에만 있고, 같은 이름이 문제 되는 쪽은 나 자신의 세션이다.

03

frontmatter로 실행 방식 정하기

What each field actually does
--- name: changelog-draft description: 지정한 태그 이후 병합된 PR을 모아 CHANGELOG 초안을 화면에 출력한다. 버전 업 직전에 사용. argument-hint: "[since-tag] [audience]" arguments: [since, audience] disable-model-invocation: true allowed-tools: Bash(git log *) Bash(git tag *) Bash(gh pr list *) disallowed-tools: Edit --- $since 태그 이후 병합된 PR을 모아 $audience 독자용 CHANGELOG 초안을 출력한다. 파일은 고치지 않는다. 1. git tag로 $since가 있는지 확인하고, 없으면 멈추고 묻는다 2. 사용자에게 보이는 변경만 한 줄씩 요약한다
필드실행 시 하는 일
description (+ when_to_use)Claude가 언제 이 스킬을 쓸지 판단하는 근거. 합쳐서 목록에서 1,536자에서 잘리므로 핵심 용도를 앞에
argument-hint자동완성 중 명령 뒤에 보이는 인자 힌트(예: [since-tag] [audience])
arguments · $ARGUMENTS · $0인자 치환. $ARGUMENTS는 입력 전체, $0·$1은 위치, arguments에 선언한 이름은 $since처럼 쓴다
disable-model-invocation: trueClaude가 스스로 호출하지 못한다. 사용자가 /name으로만 실행. 설명도 컨텍스트에서 빠진다
user-invocable: false반대로 Claude만 호출. / 메뉴에서 숨겨지는 배경 지식용
allowed-tools스킬을 호출한 그 턴 동안 나열한 도구를 승인 없이 쓰게 허용. 다음 메시지를 보내면 해제
disallowed-tools스킬이 활성인 동안 나열한 도구를 사용 가능 목록에서 제거
context: fork (+ agent)서브에이전트에서 격리 실행(04 단원)
시험 가이드 표현 vs 현재 문서

① 가이드는 allowed-tools를 "스킬 실행 중 도구 접근을 제한"하는 설정으로 설명한다. 현재 문서에서 allowed-tools는 사전 승인이며 다른 도구도 그대로 호출 가능하다고 명시한다. 도구를 실제로 빼려면 disallowed-tools, 권한 deny 규칙, 또는 context: fork + 도구가 한정된 서브에이전트(agent)를 쓴다. ② 가이드는 argument-hint가 인자 없이 호출할 때 "입력을 요청"한다고 적지만, 문서는 자동완성 중 보이는 힌트로만 설명한다. 인자 없이 실행하면 $1 같은 위치 자리표시자는 그대로 남고, arguments로 선언한 이름은 빈 문자열이 된다.

04

context: fork로 메인 대화 지키기

Run a skill in an isolated subagent

context: fork를 주면 Claude Code는 agent 필드의 서브에이전트(생략 시 general-purpose, 그 밖에 Explore·Plan이나 .claude/agents/의 커스텀 에이전트)를 새로 띄우고 SKILL.md 내용을 그 프롬프트로 준다. 서브에이전트는 지금까지의 대화를 보지 못하며, 작업 결과만 메인 대화로 돌아온다. 기본은 백그라운드 실행이고, background: false면 호출한 턴에서 결과를 기다린다.

인라인 스킬 (기본)
/dep-audit → 패키지 180개 조사 로그가 메인 대화에 그대로 쌓임

이후 작업의 컨텍스트를 잠식한다.

context: fork + agent: Explore
/dep-audit → 조사는 별도 컨텍스트에서 → "위험 패키지 4개 + 근거" 요약만 반환

메인 대화에는 결론만 남는다.

fork를 쓸 때 / 쓰지 말 때
  • 쓴다: 코드베이스 전체 분석처럼 출력이 장황한 작업, 대안 브레인스토밍처럼 탐색 흔적을 메인에 남기고 싶지 않은 작업
  • 쓰지 않는다: "이 API 규칙을 따르라" 같은 참고용 지침만 있는 스킬 — 할 일이 없어 의미 있는 결과 없이 돌아온다
  • 쓰지 않는다: 지금까지의 대화 내용이 필요한 작업 — 이름과 달리 대화 포크가 아니므로, 그럴 때는 대화 자체를 포크한다
  • Explore·Plan 에이전트는 CLAUDE.md 없이 시작하므로 필요한 맥락은 SKILL.md에 다 적는다
  • 백그라운드 fork가 만든 파일 편집은 체크포인트 밖이라 /rewind로 되돌려지지 않는다 — git으로 되돌린다
05

스킬인가, CLAUDE.md인가

On-demand vs always loaded
방식로드 시점어울리는 내용 (예)
CLAUDE.md매 세션, 매 요청에 포함"커밋 제목은 Conventional Commits 형식", 단일 테스트 실행 명령, 헷갈리는 디렉터리 경고
스킬시작 시 이름·설명만, 본문은 호출될 때분기 보안 점검 절차 15단계, 사내 API 문서 작성 가이드
스킬 + disable-model-invocation사용자가 /name을 칠 때만프로덕션 배포, 릴리스 태그 푸시처럼 부작용이 있는 작업
Hook정해진 이벤트마다 결정적으로 실행"비밀값 파일 편집 차단"처럼 예외 없이 지켜야 하는 규칙

문서는 CLAUDE.md 일부가 "사실"이 아니라 여러 단계 "절차"로 자라났다면 스킬로 옮기라고 권한다. 스킬 본문은 쓰일 때만 로드되므로 긴 절차가 상관없는 버그 수정의 컨텍스트를 차지하지 않는다. 다만 호출된 스킬 본문은 이후 턴에도 대화에 남으므로 짧게 쓴다.

시험 함정 · 흔한 오해

오해allowed-tools: Read Grep이면 스킬 실행 중 Bash나 Edit는 쓸 수 없다.
사실allowed-tools는 나열한 도구를 승인 없이 쓰게 할 뿐 다른 도구를 막지 않는다. 제거는 disallowed-tools나 deny 규칙으로 한다.
오해context: fork 스킬은 지금까지의 대화를 이어받아 작업한다.
사실새 서브에이전트가 SKILL.md 내용만 프롬프트로 받는다. 대화 기록은 보지 못한다.
오해스킬 도입으로 .claude/commands/는 더 이상 동작하지 않는다.
사실계속 동작한다. 같은 메커니즘의 이전 형식이며, 같은 이름의 스킬이 있으면 스킬이 우선한다.
오해팀 스킬과 같은 이름으로 개인 스킬을 만들면 팀원들의 /triage-bug가 바뀐다.
사실개인 스킬은 내 머신에만 있다. 대신 personal이 project보다 우선하므로 내 세션에서 팀 버전이 가려진다.

자가 점검 퀴즈

점수 0 / 6
Q1팀 공유
QA 리드가 회귀 테스트 데이터 초기화 절차를 /reset-fixtures로 만들어, 저장소를 쓰는 모든 개발자가 같은 명령을 쓰게 하려 한다.어디에 두어야 하는가?
정답 (A)

프로젝트 스킬(또는 .claude/commands/ 파일)을 커밋하면 버전 관리로 팀 전체가 받는다. B는 리드 혼자만 쓰고, C는 매 세션 로드되어 절차가 컨텍스트를 상시 차지하며 /reset-fixtures 명령도 생기지 않는다.

Q2context: fork
/dep-audit 스킬을 실행할 때마다 수백 줄의 조사 출력이 메인 대화에 쌓여, 이어지는 구현 작업에서 Claude가 앞선 지시를 놓친다.가장 알맞은 변경은?
정답 (C)

장황한 출력을 격리하는 것이 context: fork의 용도다. A는 누가 호출하느냐만 바꾸고, B는 오히려 매 세션 로드량을 늘린다. D는 사전 승인을 뺄 뿐 출력량과 무관하다.

Q3allowed-tools
SKILL.md에 allowed-tools: Bash(git status *) Bash(git diff *)를 적었다. 이 스킬을 호출한 턴의 동작으로 옳은 것은?
정답 (B)

allowed-tools는 호출한 턴 동안의 사전 승인이며 다음 메시지를 보내면 해제된다(C 오답). 도구를 막지 않으므로 A도 틀리고, 목록에서 제거하는 것은 disallowed-tools다(D).

Q4개인 변형
팀이 .claude/skills/triage-bug/를 커밋해 쓰고 있다. 한 개발자가 로그를 더 많이 모으는 버전을 원해 ~/.claude/skills/triage-bug/를 만들었다.무슨 일이 생기는가?
정답 (D)

같은 이름이면 personal이 project보다 우선한다. 개인 폴더는 그 사람 머신에만 있으므로 팀원에게는 영향이 없다(A 오답). 팀 버전 갱신을 계속 받으려면 triage-bug-deep처럼 이름을 달리한다.

Q5호출 제어
스테이징 DB를 초기화하는 /wipe-staging 스킬이 있다. 대화 중 "스테이징 데이터가 꼬였네"라는 말만으로 Claude가 이 스킬을 실행할까 걱정된다.알맞은 설정은?
정답 (C)

Claude의 자동 호출을 막고 사용자가 /wipe-staging을 칠 때만 실행되게 한다. A는 정반대로 사용자 호출을 막는다. B는 실행 위치만 바꾸고, D는 자동완성 힌트일 뿐이다.

Q6스킬 vs CLAUDE.md
다음 중 CLAUDE.md보다 스킬에 두는 것이 알맞은 것은?
정답 (B)

가끔 필요한 여러 단계 절차는 스킬이 맞다. 평소에는 이름·설명만 로드되어 컨텍스트를 아낀다. A·C·D는 모든 작업에 적용되는 짧은 사실이라 CLAUDE.md에 어울린다.
