지시문을 아무리 다듬어도 출력 형식이 실행마다 조금씩 달라지고, 애매한 입력에서 판단이 흔들리는 시점이 온다. 이때 지시를 더 늘리기보다 잘 고른 예시 몇 개를 넣는 것이 퓨샷(few-shot, multishot) 프롬프팅이다. 시험은 퓨샷이 정답인 상황과, 예시를 어떻게 골라야 하는지를 묻는다. 예시는 형식을 복사시키는 도구이자, 경계 사례에서 왜 그렇게 판단하는지를 보여 줘 새로운 사례로 판단을 일반화시키는 도구다.

습득 포인트
  • 자세한 지시만으로 형식이 흔들릴 때 퓨샷 예시가 가장 효과적인 수단이라는 점
  • 모호한 사례(도구 선택, 분기 단위 테스트 커버리지 공백 등)에서 "왜 다른 그럴듯한 선택이 아닌가"까지 보여 주는 2~4개의 표적 예시
  • 원하는 출력 형식(위치·문제·심각도·수정 제안)을 예시로 고정하기
  • 허용되는 코드 패턴과 진짜 문제를 대비시켜 오탐을 줄이면서 일반화하기
  • 문서 구조가 다양한 추출 작업에서 예시로 빈 값·환각을 줄이기 (비공식 단위, 인라인 인용 vs 참고문헌)
01

예시가 지시보다 강한 지점

When instructions plateau

플랫폼 Prompting best practices 문서는 예시를 Claude의 출력 형식·어조·구조를 잡는 가장 신뢰할 만한 방법 중 하나로 꼽는다. Increase output consistency 문서도 원하는 출력의 예시를 주는 것이 추상적인 지시보다 효과적이라고 적는다. 문서가 말하는 좋은 예시의 조건은 세 가지다.

관련성 (Relevant)
실제 사용 사례와 가깝게. 장난감 예시는 실제 입력의 난점을 보여 주지 못한다
다양성 (Diverse)
엣지 케이스를 포함하고, 의도하지 않은 패턴을 배우지 않을 만큼 서로 다르게
구조 (Structured)
<example> 태그로 감싸고 여러 개는 <examples>로 묶어 지시와 구분

퓨샷이 무엇을 보장하지 않는지도 구분해야 한다. 응답이 특정 JSON 스키마를 반드시 따라야 한다면 Increase output consistency 문서는 프롬프트 기법 대신 structured outputs를 쓰라고 안내한다. 예시는 스키마가 표현하지 못하는 것, 즉 각 필드에 무엇을 어떤 판단으로 채우는지를 가르치는 데 쓴다. 또 예전에 쓰던 응답 prefill은 Claude 4.6 이후 모델에서 지원되지 않으므로, 형식 고정은 예시·지시·structured outputs로 한다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 2~4개의 표적 예시를 말한다. Prompting best practices 문서의 일반 권고는 "3–5개 예시가 가장 좋은 결과"이고, 도구 정의에 예시를 넣는 경우를 다룬 Anthropic 엔지니어링 글(Advanced tool use)은 도구당 1~5개를 권한다. 시험 문항은 가이드 기준(모호한 사례를 겨냥한 소수의 예시)으로 판단하되, 핵심은 개수보다 표적성과 다양성이라는 점이 모든 문서에서 공통이다.

02

모호한 사례: 결론과 함께 "왜"를 보여 준다

Show the reasoning behind the choice

예시가 가장 큰 차이를 만드는 곳은 지시만으로는 판단이 갈리는 경계 사례다. 이때 예시는 입력과 정답만이 아니라, 그럴듯한 다른 선택지를 왜 고르지 않았는지를 담아야 한다. 그래야 모델이 표면적인 단어가 아니라 판단 기준을 배운다. 프롬프팅 문서도 thinking과 함께 쓸 때 예시를 "문제, 적용할 방법, 기대 답" 형태로 제시하라고 권한다. 아래는 사내 IT 헬프데스크 에이전트의 도구 선택 예시다.

# 이 가이드의 예시: 비슷한 도구 사이의 선택 <examples> <example> 요청: "비밀번호를 다섯 번 틀려서 로그인이 안 돼요" 선택: unlock_account 이유: 사용자는 비밀번호를 알고 있고 잠금만 풀면 된다. reset_password는 기존 비밀번호를 무효화하므로 과한 조치다. </example> <example> 요청: "비밀번호가 기억이 안 나요. 계정도 잠긴 것 같아요" 선택: reset_password 이유: 잠금만 풀어도 다시 로그인할 수 없다. 재설정이 잠금 해제를 포함한다. </example> <example> 요청: "다른 사람이 제 계정으로 로그인한 기록이 있어요" 선택: create_security_ticket 이유: 계정 탈취 의심은 셀프서비스 조치 대상이 아니다. 잠금 해제나 재설정을 먼저 하면 조사 증거가 사라질 수 있다. </example> </examples>

도구의 인자 사용법이 모호하다면 도구 정의 자체에 예시를 넣을 수 있다. Define tools 문서의 input_examples 필드는 예시 입력 객체 배열을 받으며, 각 예시는 도구의 input_schema를 통과해야 한다(아니면 400 오류). 중첩 객체·선택 인자·형식에 민감한 인자가 많은 도구에 유용하고, 예시마다 프롬프트 토큰이 추가된다(단순한 예시 약 20~50, 복잡한 중첩 객체 약 100~200 토큰).

코드 리뷰의 "분기 단위 테스트 커버리지 공백"도 대표적인 모호 사례다. 함수에 테스트가 있다는 사실만으로는 충분하지 않다. 예시 하나가 "if (stock < requested)의 재고 부족 분기는 테스트되지만 재고가 정확히 같은 경우(stock == requested)를 지나는 경로는 검증되지 않음 → 커버리지 공백으로 보고"를 보여 주면, 모델은 함수 단위가 아니라 분기 단위로 보는 법을 배운다.

03

허용 패턴과 진짜 문제를 나란히

Contrast pairs for generalization

리뷰 오탐을 줄이는 데에는 "이건 수상해 보여도 괜찮다"는 예시가 "이건 문제다"라는 예시만큼 중요하다. 비슷해 보이는 두 코드를 짝지어 경계를 보여 주면, 목록에 없던 새 패턴에도 같은 판단을 적용한다. 아래 예시는 출력 형식(위치·문제·심각도·수정 제안)까지 함께 고정한다.

허용 · 보고하지 않음
// 데모 화면의 카드 순서 섞기 const order = cards .map(c => [Math.random(), c]) .sort((a, b) => a[0] - b[0]) .map(([, c]) => c)

판단: 예측 가능해도 아무 피해가 없는 표시용 무작위성이다 → 지적 없음.

진짜 문제 · 보고
// 비밀번호 재설정 토큰 생성 const token = Math.random() .toString(36).slice(2)

위치: auth/reset.ts:41 · 문제: 보안 토큰을 암호학적으로 안전하지 않은 난수로 생성 · 심각도: blocker · 수정: crypto.randomBytes() 같은 CSPRNG를 쓴다.

두 코드는 같은 API를 쓰지만 판단을 가르는 것은 용도다. 이유가 담긴 짝을 보면, 모델은 "Math.random을 보면 지적"이라는 표면 규칙 대신 "예측 가능성이 피해로 이어지는가"라는 기준을 배워 쿠폰 코드·초대 링크 같은 새 사례에도 적용한다.

Anthropic의 컨텍스트 엔지니어링 글은 모든 엣지 케이스를 규칙 목록으로 프롬프트에 욱여넣는 방식을 권하지 않는다. 대신 기대 동작을 잘 보여 주는 다양하고 대표적인(canonical) 예시 세트를 고르라고 한다. 대비 쌍은 그 원칙을 리뷰에 적용한 형태다. 규칙을 하나 더 쓰는 대신, 경계 양쪽에 놓인 사례를 하나씩 보여 준다.

04

다양성: 예시가 엉뚱한 규칙을 가르치지 않게

Avoid unintended patterns

모델은 예시의 의도한 특징뿐 아니라 우연한 공통점도 배운다. 문서가 예시를 "의도하지 않은 패턴을 배우지 않을 만큼 다양하게" 만들라고 하는 이유다.

예시 세트의 우연한 공통점모델이 배울 수 있는 잘못된 규칙 → 처방
"긴급" 티켓 예시가 모두 모바일 앱 채널에서 왔다앱 채널 = 긴급 → 채널을 섞는다
모든 예시가 결제 모듈에서 나왔다결제 외 모듈은 덜 엄격 → 모듈을 섞는다
정답 도구가 항상 첫 번째로 나열된 도구다순서 = 선호 → 정답 위치를 바꾼다
추출 예시 문서에 필드가 항상 다 있다필드는 언제나 존재 → 값이 없는 예시를 넣는다 (05 단원)
예시 점검을 Claude에게

Prompting best practices 문서는 Claude에게 예시 세트의 관련성과 다양성을 평가하게 하거나, 처음 만든 예시를 바탕으로 추가 예시를 생성하게 할 수 있다고 안내한다. 사람이 만든 예시 세트의 편향을 찾는 데 쓸 만하다.

05

추출: 다양한 문서 구조와 비어 있는 값

Extraction across varied formats

문서에서 필드를 뽑는 작업은 두 방향으로 실패한다. 값이 있는데 형식이 예상과 달라 빈 값으로 두거나, 값이 없는데 그럴듯한 값을 지어내는 것이다. 두 실패 모두 지시보다 예시로 더 잘 고쳐진다. 부동산 매물 설명에서 전용면적(area_m2)을 뽑는 예를 보자.

# 이 가이드의 예시: 구조가 다른 세 매물 설명 <example> # 사양 표에 명시된 경우 문서: "| 전용면적 | 84.97㎡ | 방/욕실 | 3/2 |" 출력: {"area_m2": 84.97, "evidence": "전용면적 | 84.97㎡"} </example> <example> # 본문에 비공식 단위로 묻혀 있는 경우 문서: "... 남향, 전용 약 25평이라 거실이 넓고 ..." 출력: {"area_m2": 82.6, "evidence": "전용 약 25평", "converted_from": "평"} </example> <example> # 정보가 없는 경우 문서: "... 역세권, 리모델링 완료, 즉시 입주 가능 ..." 출력: {"area_m2": null, "evidence": null} </example>

세 예시는 각각 다른 것을 가르친다. 첫째는 표 형식, 둘째는 본문 속 비공식 단위의 환산(1평 ≈ 3.3058㎡)과 원래 표현의 보존, 셋째는 없는 값은 null이라는 규칙이다. 셋째가 빠지면 모델은 "면적은 항상 있다"를 배워 비슷한 매물의 값을 지어낼 수 있다. 시험 가이드가 드는 인라인 인용 vs 참고문헌 목록, 방법론 섹션 vs 본문 속 세부처럼 구조가 갈리는 경우도 같은 방식으로 구조별 예시를 하나씩 둔다.

Reduce hallucinations 문서의 기법이 이 설계를 받친다. Claude가 "모른다"고 말해도 된다고 명시적으로 허용하기, 긴 문서에서는 작업 전에 원문 그대로의 인용을 먼저 뽑게 하기, 주장마다 근거 인용을 찾게 하고 찾지 못하면 철회하게 하기, 제공한 문서 밖의 일반 지식을 쓰지 말라고 제한하기다. 위 예시의 evidence 필드는 값과 원문 근거를 함께 받아, 근거 없는 값은 사람이 바로 의심할 수 있게 한다.

시험 판단 축
  • 형식이 실행마다 흔들린다 → 원하는 형식을 그대로 보여 주는 예시 (엄격한 스키마 보장이 필요하면 structured outputs)
  • 경계 사례에서 판단이 갈린다 → 대안을 왜 버렸는지 담은 표적 예시 2~4개
  • 정상 패턴까지 지적한다 → 허용 vs 문제 대비 쌍
  • 필수 필드가 비거나 값이 지어진다 → 문서 구조별 예시 + 값이 없는 경우의 null 예시 + 근거 인용

시험 함정 · 흔한 오해

오해형식이 흔들리면 형식 설명 문단을 더 길고 자세하게 쓰는 것이 최선이다.
사실문서는 원하는 출력의 예시가 추상적 지시보다 효과적이라고 설명한다. 자세한 지시가 이미 있는데도 흔들린다면 예시를 넣는다.
오해예시에는 정답만 보여 주면 된다.
사실모호한 사례에서는 그럴듯한 대안을 왜 고르지 않았는지까지 보여 줘야 판단 기준이 일반화된다.
오해엣지 케이스를 빠짐없이 규칙으로 나열하는 것이 예시보다 안전하다.
사실Anthropic은 규칙 목록을 욱여넣기보다 다양하고 대표적인 예시 세트를 고르라고 권한다.
오해퓨샷 예시를 충분히 넣으면 JSON 스키마 준수가 보장된다.
사실예시는 일관성을 높일 뿐 보장하지 않는다. 스키마 보장이 필요하면 structured outputs(또는 strict 도구 사용)를 쓴다.
