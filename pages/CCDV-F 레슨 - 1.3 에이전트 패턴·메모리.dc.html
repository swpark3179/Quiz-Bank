  • 내 코드·tool runner·서버 측 루프·Agent SDK 중 누가 도구를 실행하고 tool_result를 만드는지 구분한다
  • 서브에이전트가 부모 컨텍스트에 무엇을 남기고 무엇을 남기지 않는지 말하고, 이전 서브에이전트를 재개하는 절차를 안다
  • 메모리 도구가 클라이언트 측 도구라는 점과 압축(compaction)·컨텍스트 편집과의 역할 분담을 설명한다
01

다섯 패턴을 가르는 결정적 신호

Five workflow patterns, sharply separated

다섯 패턴은 모두 '코드가 경로를 정하는' 워크플로다. 겉모습(병렬로 돈다, 검사가 있다, 여러 언어로 나온다)이 아니라 아래 신호로 구분한다.

패턴결정적 신호대표 예혼동하는 오답
프롬프트 체이닝고정된 단계가 앞 단계 출력을 받아 순서대로 진행. 단계 사이에 코드 게이트를 둘 수 있다개요 작성 → 기준 검사 → 본문 작성게이트가 있다고 평가자-최적화자로 보는 것
라우팅입력을 미리 정한 범주로 분류해 범주별 전용 프롬프트·모델로 보낸다쉬운 질문은 작은 모델, 어려운 질문은 큰 모델분류 후 분기를 '에이전트'로 보는 것
병렬화 · 섹셔닝서로 다른 독립 하위 작업을 동시에한 호출은 응답, 다른 호출은 가드레일 검사관점이 다르면 투표가 아니다
병렬화 · 투표같은 작업을 여러 번(또는 문구만 다른 여러 프롬프트로) 돌려 집계. 표 기준(threshold)으로 오탐·미탐을 조절여러 프롬프트가 같은 코드의 취약점을 각각 찾고, 하나라도 지적하면 표시프롬프트 문구가 달라도 같은 판정을 하면 섹셔닝이 아니다
오케스트레이터-워커하위 작업을 입력을 본 뒤에 중앙 LLM이 정한다어떤 파일을 어떻게 고칠지 작업마다 다른 코딩 변경갈래가 고정된 섹셔닝
평가자-최적화자생성 LLM과 평가 LLM이 피드백 루프를 돈다문학 번역의 뉘앙스 다듬기, 더 찾을지 평가하며 반복하는 검색통과/반려만 하는 코드 검사
평가자-최적화자가 맞는 두 신호

① 사람이 피드백을 주면 응답이 눈에 띄게 나아진다. ② LLM이 그런 피드백을 스스로 줄 수 있다. 평가 기준이 분명하고 반복이 측정 가능한 가치를 더할 때만 쓴다.

투표의 기준값

콘텐츠 검토처럼 놓치면 위험한 일은 '하나라도 지적하면 표시'처럼 기준을 낮춰 미탐을 줄이고, 오탐 비용이 크면 '과반 이상'으로 올린다. 기준값은 설계자가 정하는 손잡이다.

시나리오를 읽는 질문 순서
  • 하위 작업이 실행 전에 정해져 있는가? 아니면 입력을 본 뒤 정해지는가? 뒤쪽이면 오케스트레이터-워커
  • 정해져 있다면, 순서대로 이어지는가(체이닝) 동시에 도는가(병렬화)? 입력을 범주로 나눠 한 갈래만 타는가(라우팅)?
  • 동시에 돈다면, 갈래마다 다른 일인가(섹셔닝) 같은 일인가(투표)?
  • 결과가 평가를 받고 피드백과 함께 다시 생성 단계로 돌아가는가? 그렇다면 평가자-최적화자
  • 패턴은 섞어 쓸 수 있다. 라우팅으로 범주를 나눈 뒤 범주 안에서 체이닝을 돌리는 식이다. 시험은 보통 시나리오의 주된 구조를 묻는다
02

에이전트가 맞는 때, 그리고 프레임워크라는 함정

Agents, and when frameworks get in the way

필요한 단계 수를 미리 알 수 없고 경로를 하드코딩할 수 없는 개방형 문제라면 에이전트가 후보가 된다. 그래도 Anthropic의 세 원칙은 그대로다. 설계를 단순하게 유지하고, 에이전트의 계획 단계를 드러나게 하고, 도구 문서와 테스트(에이전트-컴퓨터 인터페이스, ACI)를 공들여 만든다.

프레임워크가 숨기는 것

프레임워크는 시작을 쉽게 해 주지만 추상화 층이 실제 프롬프트와 응답을 가린다. 그러면 "모델이 정확히 무엇을 받았나"를 볼 수 없어 디버깅이 어려워지고, 필요 없는 복잡성을 덧붙이고 싶어진다. 프레임워크가 내부에서 무엇을 하는지에 대한 잘못된 가정은 흔한 오류 원인이다.

권장 대응

먼저 LLM API를 직접 호출해 만든다. 대부분의 패턴은 몇 줄이면 된다. 프레임워크를 쓰더라도 그 아래 코드를 이해하고, 이상 동작이 보이면 해당 부분을 직접 호출로 재현해 모델이 받은 입력을 눈으로 확인한다.

03

도구 루프는 누가 돌리나

Who drives the tool-use loop

모델은 스스로 아무것도 실행하지 않는다. 구조화된 요청을 낼 뿐이고, 실행은 내 코드나 Anthropic 서버가 한다. 도구는 코드가 어디서 실행되는가로 세 부류로 나뉘고, 그에 따라 내 애플리케이션의 책임이 정해진다.

부류예실행내 앱이 할 일
사용자 정의 도구내 DB 조회, 사내 API 호출내 코드tool_use를 받아 실행하고 tool_result를 만들어 다음 요청에 넣는다
Anthropic 스키마 도구memory, bash, text_editor, computer, browser내 코드위와 같다. 스키마가 학습되어 있어 Claude가 더 안정적으로 호출할 뿐이다
서버 실행 도구web_search, web_fetch, code_execution, tool_searchAnthropic요청에서 켜기만 한다. tool_result를 만들지 않는다. 응답의 server_tool_use와 결과 블록을 읽는다

클라이언트 도구는 stop_reason이 "tool_use"인 동안 '실행 → 결과 반환 → 재요청'을 반복하는 while 루프를 내가 돈다. 서버 도구는 Anthropic 안에서 자체 루프를 돈다. 요청 한 번에 검색을 여러 번 하고 답을 낼 수 있다. 이 내부 루프에는 반복 상한(기본 10회)이 있어, 상한에 걸리면 stop_reason "pause_turn"으로 돌아온다. 이때는 받은 응답을 그대로 대화에 붙여 다시 보내면 이어서 진행한다. Claude가 서버 도구와 클라이언트 도구를 한 번에 함께 부르면, 서버 도구는 내가 클라이언트 도구 결과를 돌려준 뒤에 실행된다.

while True: resp = client.messages.create(model=MODEL, max_tokens=4096, tools=TOOLS, messages=messages) messages.append({"role": "assistant", "content": resp.content}) if resp.stop_reason == "pause_turn": continue # 서버 루프가 상한에 걸림: 그대로 재요청 if resp.stop_reason != "tool_use": break # end_turn·max_tokens·refusal 등은 별도 처리 results = [run_client_tool(b) for b in resp.content if b.type == "tool_use"] # server_tool_use는 건너뛴다 messages.append({"role": "user", "content": results})

위 루프에서 tool_result를 만드는 것은 클라이언트 도구(tool_use 블록)뿐이다. 서버 도구 블록은 실행과 결과가 이미 응답 안에 있으므로 손대지 않는다. 사용자 메시지에는 tool_result 블록만 담는다. 텍스트를 결과 뒤에 덧붙이는 습관은 빈 응답의 원인이 될 수 있다(도메인 4 참고).

루프 운전자특징
내 코드 (수동 루프)가장 세밀한 제어. 오류 처리·재시도·로깅을 모두 직접
Client SDK의 tool runner (beta)함수를 도구로 등록하면 SDK가 호출·결과 포맷·반복을 대신한다
Agent SDKClaude Code의 루프와 내장 도구가 실행까지 맡는다(1.2)
서드파티 프레임워크편리하지만 프롬프트와 응답이 가려질 수 있다(02)
04

컨텍스트 전략으로서의 서브에이전트

Subagents keep the main window lean

컨텍스트 창은 세션 안에서 턴마다 초기화되지 않는다. 시스템 프롬프트, 도구 정의, 대화 기록, 도구 입력과 출력이 계속 쌓인다. 큰 파일을 읽거나 출력이 긴 명령을 돌리면 한 턴에 수천 토큰이 들어온다. 서브에이전트는 이 무게를 다른 창으로 옮기는 수단이다.

서브에이전트가 받는 것받지 않는 것
자기 시스템 프롬프트(prompt)와 Agent 도구에 담긴 위임 프롬프트부모의 대화 기록과 도구 결과
프로젝트 CLAUDE.md(settingSources로 로드. omitClaudeMd를 켜면 제외)부모의 시스템 프롬프트
도구 정의(상속 또는 tools로 지정한 부분집합)skills에 나열하지 않은 스킬의 본문

부모에게 돌아오는 것은 서브에이전트의 최종 메시지 하나다. 서브에이전트가 파일 서른 개를 읽어도 부모의 컨텍스트는 요약 한 덩어리만큼만 늘어난다. 반대로 말하면 부모는 서브에이전트가 무엇을 읽었는지 모르고, 서브에이전트도 부모가 아는 것을 모른다. 필요한 경로·오류 메시지·결정은 위임 프롬프트에 직접 적어 넘긴다. 부모는 받은 보고를 자기 말로 요약할 수 있으므로, 원문을 사용자에게 그대로 보여야 하면 메인 프롬프트에 그렇게 지시한다.

맥락 없는 위임

"아까 본 그 오류 원인을 찾아 줘." 서브에이전트는 부모 대화를 보지 못하므로 '그 오류'가 무엇인지 모른다. 같은 탐색을 처음부터 다시 하거나 엉뚱한 곳을 판다.

자급자족하는 위임

"services/billing/retry.ts에서 TimeoutError: upstream 504가 난다. 재시도 정책이 원인인지 확인하고, 관련 파일 경로와 근거 줄 번호만 다섯 줄 이내로 보고하라." 필요한 경로·오류·보고 형식을 모두 담았다.

위임을 묶어 두는 세 가지 상한
  • 중첩 깊이: CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH (기본 3단계, 1이면 서브에이전트가 또 부르지 못한다)
  • 동시 실행 수: CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS (기본 20)
  • 지출: maxBudgetUsd / max_budget_usd. 서브에이전트 지출까지 합산하며, 상한에 닿으면 새 서브에이전트 생성을 거부한다
05

이전 서브에이전트를 이어서 쓰기

Resuming a subagent across queries

query()는 호출할 때마다 기본으로 새 세션을 시작한다. 후속 질의를 보낸다고 앞선 서브에이전트가 저절로 이어지지 않는다. 재개된 서브에이전트는 이전 도구 호출·결과·추론을 포함한 전체 기록을 그대로 갖는다.

① 첫 query
서브에이전트가 작업을 마친다
→
② ID 확보
메시지에서 session_id, Agent 도구 결과 텍스트에서 agentId
→
③ 새 query
옵션에 resume=세션 ID, 같은 agents 정의
→
④ 프롬프트
"agent <id>를 재개해 …"처럼 ID를 명시
second = query( prompt=f"Resume agent {agent_id} and rank the three " "riskiest migrations you found", options=ClaudeAgentOptions( agents=AGENTS, # 첫 호출과 같은 정의 resume=session_id, # 서브에이전트 기록이 있는 세션 allowed_tools=["Read", "Grep", "Agent"], ), )
재개할 수 없는 서브에이전트

내장 Explore·Plan 에이전트는 일회성이라 agentId를 돌려주지 않는다. 재개가 필요하면 커스텀 에이전트나 general-purpose를 쓴다. maxTurns 상한에 걸려 멈춘 서브에이전트의 출력은 '부분 결과'로 표시되므로, 재개해서 마저 끝낼 수 있다. 서브에이전트 기록은 메인 대화와 별도 파일로 저장되어 메인 대화가 압축되어도 영향을 받지 않는다.

06

세션이 끝나도 남는 메모리

Memory tool, compaction, and just-in-time context

장기 기억을 위해 '지난 지식을 세션 시작 때 전부 컨텍스트에 붓는' 방식은 창을 낭비하고 품질을 떨어뜨린다. 메모리 도구는 반대로 간다. 에이전트가 배운 것을 파일로 적어 두고, 필요할 때 꺼내 읽는다(just-in-time retrieval).

① VIEW
작업 전 /memories 디렉터리 목록 확인
→
② READ
관련 있는 파일만 골라 읽기
→
③ WORK
현재 작업 수행
→
④ RECORD
진행 상황·배운 점을 create·str_replace로 기록

매 단계는 Claude의 tool_use 요청과 내 핸들러의 tool_result 응답으로 이루어진다. 컨텍스트 창이 언제든 초기화될 수 있다고 가정하고 진행 상황을 적어 두라는 것이 API가 자동으로 넣는 지시의 요지다.

항목메모리 도구의 동작
선언{"type": "memory_20250818", "name": "memory"}가 설정의 전부. 입력 스키마를 정의하지 않으며 베타 헤더도 필요 없다
실행 위치클라이언트 측. Claude는 view·create·str_replace·insert·delete·rename 작업을 요청할 뿐이고, 내 핸들러가 내 저장소(디스크, DB, 객체 저장소)에서 실행해 tool_result로 돌려준다
경로/memories는 내 핸들러가 실제 저장소에 매핑하는 접두사다. 사용자별 디렉터리나 DB 키로 바꿔 둘 수 있다
자동 지시도구가 켜져 있으면 API가 "작업 전에 메모리 디렉터리부터 보라"는 지시를 시스템 프롬프트에 자동으로 넣는다
보안 책임/memories/../../secrets.env 같은 경로 이탈을 내 코드가 막아야 한다. 경로를 정규화해 메모리 디렉터리 안인지 확인한다
데이터 보존저장을 내가 통제하므로 ZDR 적용 대상이다(일부 모델 제외)
from pathlib import Path ROOT = Path("/srv/tutor-memory").resolve() def to_real_path(user_id: str, mem_path: str) -> Path: if not mem_path.startswith("/memories"): raise ValueError("outside memory root") rel = mem_path.removeprefix("/memories").lstrip("/") real = (ROOT / user_id / rel).resolve() real.relative_to(ROOT / user_id) # 벗어나면 ValueError return real

핸들러가 /memories를 사용자별 실제 디렉터리로 바꾸고, 정규화한 경로가 그 안에 있는지 확인한다. 메모리 파일 크기 상한, 오래 쓰지 않은 파일 정리, 민감 정보 제거도 내 핸들러의 책임이다.

압축 (compaction)
오래된 턴을 서버에서 Claude가 쓴 요약으로 대체한다. 창을 작게 유지하지만 초반의 세부 지시가 사라질 수 있다.
컨텍스트 편집 (context editing)
오래된 도구 결과나 thinking 블록을 규칙에 따라 지운다. 요약하지 않고 덜어 낸다.
메모리 (memory)
요약에서 살아남아야 하는 정보를 창 밖에 저장한다. 긴 작업에는 압축과 함께 쓰라고 공식 문서가 권한다.
여러 세션에 걸친 개발 작업

공식 문서의 권장 패턴은 첫 세션이 진행 로그·기능 체크리스트·초기화 스크립트 위치를 메모리에 먼저 마련하고, 이후 세션은 그 파일부터 읽어 상태를 복원하며, 세션을 끝내기 전에 진행 로그를 갱신하는 것이다. 기능은 한 번에 하나씩, 끝까지 검증된 뒤에만 완료로 표시한다.

시험 함정 · 흔한 오해

오해단계가 여러 개인 작업은 결국 자율 에이전트가 필요하다.
사실단계가 고정되어 있으면 아무리 많아도 체이닝 같은 워크플로가 더 단순하고 예측 가능하다. 에이전트는 경로를 미리 정할 수 없을 때의 선택이다.
오해웹 검색 같은 서버 도구도 결과를 내 앱이 tool_result로 만들어 넣어야 한다.
사실서버 도구는 Anthropic이 실행하고 결과까지 응답에 담아 준다. 내 앱은 켜고 읽기만 한다. 예외는 pause_turn과 클라이언트 도구를 함께 부른 턴이다.
오해후속 query()를 보내면 앞에서 쓰던 서브에이전트가 이어서 일한다.
사실각 호출은 새 세션이다. resume에 세션 ID를 넘기고 프롬프트에 agentId를 적어야 재개된다.
오해메모리 도구를 켜면 Anthropic이 메모리 파일을 저장해 준다.
사실클라이언트 측 도구다. 저장 위치·형식·보존 기간은 모두 내 핸들러가 정한다.
오해장기 기억은 세션 시작 때 과거 지식을 전부 넣어 주는 것이 가장 안전하다.
사실창을 채워 품질이 떨어진다. 메모리 파일에 적어 두고 필요할 때 읽는 방식이 권장된다.
