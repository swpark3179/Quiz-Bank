고객은 "빠르고, 싸고, 정확하게, 그리고 데이터는 미국 밖으로 나가지 않게"라고 말한다. 개발자는 이 문장을 측정할 수 있는 기준과 넘을 수 없는 한계로 바꿔야 한다. 모델은 능력·속도·비용·effort로 고르고, 컨텍스트 창과 최대 출력으로 후보를 걸러 낸 다음, 실제 과업으로 평가해 확정한다. 인프라 쪽에서는 고객이 이미 쓰는 클라우드, 추론이 실행되는 위치, 데이터 보존 약정, 확보할 수 있는 처리량이 선택지를 좁힌다. 시험은 각 요구사항이 어느 설정·플랫폼·약정으로 풀리는지, 그리고 그 장치가 하지 못하는 일이 무엇인지를 묻는다.

습득 포인트
  • 비즈니스 요구사항을 능력·속도·비용·effort 기준으로 옮기고, 모델 교체보다 effort 조정을 먼저 검토한다
  • 컨텍스트 창·최대 출력을 하드 리밋으로 보고, 요청 크기에서 탈락하는 후보를 골라낸다
  • 토큰 단가가 아니라 실제 과업으로 측정한 완료 과업당 비용으로 모델을 비교한다
  • 고객의 클라우드·청구 방식·데이터 처리자 요건으로 Claude API, Claude Platform on AWS, Bedrock, Google Cloud 중 하나를 고른다
  • inference_geo·워크스페이스 geo·ZDR이 각각 무엇을 보장하고 무엇을 보장하지 않는지 구분한다
  • 레이트 리밋·지출 한도·Priority Tier의 성격을 알고 용량 요구사항을 판단한다
01

요구사항을 선택 기준으로 번역하기

From business requirements to selection criteria

공식 가이드는 모델 선택의 기준으로 능력(capabilities), 속도(speed), 비용(cost), 그리고 effort를 든다. effort는 한 모델 안에서 지능과 지연·비용을 맞바꾸는 파라미터(output_config.effort)이고, 문서는 "effort 조정이 모델 교체보다 나은 레버인 경우가 많다"고 적는다. 응답이 느리고 비싸다는 불만이 나오면 모델을 바꾸기 전에 effort부터 낮춰 평가해 보는 것이 순서다.

고객이 하는 말기준먼저 검토할 레버
"상담 화면에서 답이 1~2초 안에 떠야 한다"속도빠른 모델(Haiku 5.5), 낮은 effort. 출력 속도가 더 필요하면 지원 모델의 fast mode(최대 2.5배, 할증 가격)
"하루 200만 건의 반품 사유를 분류한다"비용저비용 모델, 프롬프트 캐싱. 당장 결과가 필요 없으면 Batch API(50% 할인)
"여러 시간 걸리는 리팩터링을 에이전트가 끝까지 해야 한다"능력Opus 5.5부터 시작. 높은 effort에서도 평가가 부족하면 Fable 5.1
"지금 쓰는 모델이 품질은 괜찮은데 비싸다"effort같은 모델에서 effort를 한 단계씩 낮추며 평가 점수를 확인
효율 우선으로 시작

Haiku 5.5로 구현하고 충분히 테스트한 뒤, 능력이 부족한 지점이 확인될 때만 올린다. 프로토타입, 지연 요건이 빡빡한 앱, 대량의 단순 작업에 맞다.

능력 우선으로 시작

Opus 5.5로 구현하고 프롬프트를 다듬은 뒤, effort를 낮추거나 하위 모델로 내려 효율을 찾는다. xhigh·max에서도 부족한 장기 에이전트 작업이면 Fable 5.1로 간다.

기본 출발점

모델 비교표 문서는 "어떤 모델을 쓸지 모르겠으면 대부분의 워크로드는 Claude Opus 5.5에서 시작하라"고 권한다. Opus 5.5와 Haiku 5.5의 기본 effort는 medium, Fable 5.1과 Sonnet 5.5는 high다. 같은 이름의 effort라도 모델마다 결과가 다르니, 모델을 바꾸면 effort 스윕을 다시 한다.

02

컨텍스트 창과 최대 출력은 하드 리밋이다

Context window and max output as hard limits

속도·비용은 맞바꿀 수 있지만 크기 제한은 협상이 안 된다. 요청 하나에 넣어야 하는 입력과 받아야 하는 출력이 한도를 넘는 후보는 평가하기 전에 지운다. 현재 라인업(2026년 10월 문서 기준)은 다음과 같다.

모델입력 / 출력 (USD/MTok)컨텍스트최대 출력지연·용도
Fable 5.1$10 / $501M128K느림. 까다로운 추론, 장기 에이전트 작업
Opus 5.5$4 / $201M128K보통. 장시간 에이전트 코딩·지식 작업
Sonnet 5.5$2 / $101M128K빠름. 속도와 지능의 균형
Haiku 5.5$0.10 / $0.50 (프롬프트 10만 토큰 초과 시 $0.50 / $2.50)1M128K가장 빠름. 분류·추출·라우팅 같은 대량 작업

현재 모델 넷은 모두 1M 컨텍스트라서 이들 사이에서는 크기로 탈락하는 모델이 없다. 갈리는 지점은 레거시 모델이다. Claude Sonnet 4.5(deprecated)와 Haiku 4.5를 포함한 그 밖의 모델은 컨텍스트가 200K다. 이미지·PDF 페이지는 요청당 600개까지(200K 모델은 100개)이고, 토큰 한도보다 요청 크기 한도에 먼저 걸릴 수도 있다.

상황API 동작
입력만으로 컨텍스트 창을 넘는다모든 모델에서 400 invalid_request_error("prompt is too long")
입력 + max_tokens가 창을 넘는다 (Claude 4.5 이후 모델)요청은 받아들이고, 생성이 창 끝에 닿으면 stop_reason: "model_context_window_exceeded"로 멈춘다
128K보다 긴 출력이 필요하다동기 호출로는 불가. Message Batches API에서 지원 모델에 output-300k-2026-03-24 베타 헤더를 붙이면 300K까지
토큰 수는 모델마다 다르다

Claude Opus 4.7부터 쓰는 새 토크나이저는 같은 텍스트를 약 30% 더 많은 토큰으로 센다. 크기 판단은 글자 수 어림이 아니라 대상 모델로 토큰 카운팅 API를 돌려서 한다. 각 모델의 max_input_tokens·max_tokens는 Models API로도 조회된다.

03

단가가 아니라 완료 과업당 비용으로 비교한다

Compare candidates with an eval before committing

크기 조건을 통과한 후보가 둘 이상 남으면 평가로 정한다. 공식 절차는 ① 사용 사례에 맞는 벤치마크(평가 세트)를 만들고 ② 실제 프롬프트와 데이터로 돌려 ③ 정확도·응답 품질·엣지 케이스 처리를 비교한 뒤 ④ 성능과 비용을 함께 따지는 것이다. 문서는 좋은 평가 세트를 "가장 중요한 단계"라고 부른다.

비용 비교의 단위는 완료된 과업이다. 값싼 모델이 실패한 과업도 토큰 비용은 그대로 나가고, 재시도 비용과 실패가 남긴 후처리 비용이 그 위에 붙는다. 더 유능한 모델이 적은 작업량으로 끝내 토큰 단가 차이를 상당 부분 메우기도 한다. 공식 문서가 공개한 측정 예시(SWE-bench Pro 일부)에서도 그 차이가 보인다.

모델 · effort해결률해결 과업당 비용
Sonnet 5.5 · high(기본)87.6%$0.11
Opus 5.5 · low87.4%$0.12
Opus 5.5 · medium(기본)92.8%$0.22

입력 단가는 Opus 5.5가 Sonnet 5.5의 두 배지만, effort를 낮춘 Opus 5.5의 과업당 비용은 Sonnet 5.5와 거의 같다. 비용은 usage의 토큰 항목마다 해당 단가를 곱해 과업에 속한 요청 전체를 더해서 구한다.

# 과업 하나에 속한 모든 응답의 usage를 단가별로 합산 (예: Sonnet 5.5 정가) RATE = {"in": 2.00, "w5m": 2.50, "w1h": 4.00, # USD / MTok "read": 0.10, "out": 10.00} def task_cost(usages): total = 0.0 for u in usages: cc = u.cache_creation # TTL별 캐시 쓰기 내역 w5 = cc.ephemeral_5m_input_tokens if cc else 0 w1 = cc.ephemeral_1h_input_tokens if cc else 0 total += (u.input_tokens * RATE["in"] + w5 * RATE["w5m"] + w1 * RATE["w1h"] + (u.cache_read_input_tokens or 0) * RATE["read"] + u.output_tokens * RATE["out"]) return total / 1_000_000
시험 판단 축
  • "가장 싼 모델은?"이라는 질문에 토큰 단가표만 보고 답하는 보기는 함정이다. 실제 과업으로 측정한 완료 과업당 비용이 기준이다
  • 평균이 아니라 어려운 꼬리(가장 어려운 10%)에서 비교하라는 것이 문서의 권고다
  • 평가 세트 없이 모델부터 바꾸는 순서는 틀린다. 평가 세트 구축이 첫 단계다
  • 밤사이 돌려도 되는 대량 분석이면 Batch API의 50% 할인을 먼저 떠올린다(→ 2.3)

05

데이터 레지던시: 추론 위치와 저장 위치

Inference geo vs workspace geo

데이터 레지던시(data residency) 설정은 서로 독립인 두 가지다. inference geo는 모델 추론이 실행되는 곳을 요청 단위로 정하고, workspace geo는 저장 데이터와 엔드포인트 처리(이미지 변환, 코드 실행 등)가 일어나는 곳을 워크스페이스 단위로 정한다.

resp = client.messages.create( model="claude-sonnet-5-5", max_tokens=2048, inference_geo="us", # 미국 인프라에서만 추론 (기본값 "global") messages=[{"role": "user", "content": claim_text}], ) print(resp.usage.inference_geo) # 실제로 추론이 실행된 곳
설정정하는 것알아 둘 점
inference_geo요청별 추론 위치. "us" 또는 "global"Claude 4.6 이후 모델만 지원. Haiku 4.5·Opus 4.5·Sonnet 4.5에 붙이면 400. "us"는 모든 토큰 항목에 1.1배 가격
default_inference_geo · allowed_inference_geos워크스페이스 기본값과 허용 목록허용 목록에 없는 geo를 요청하면 오류. Console 또는 Admin API에서 설정
workspace geo저장 위치와 엔드포인트 처리 위치워크스페이스를 만들 때 정하고 바꿀 수 없다. 현재 값은 "us"뿐

inference_geo는 Claude API, Claude Platform on AWS, Google Cloud(Anthropic managed)에서 쓴다. Bedrock과 Google Cloud(Google managed)에서는 엔드포인트 URL이나 추론 프로필이 리전을 정하므로 이 파라미터가 해당하지 않는다. Bedrock의 리전 엔드포인트는 전역 엔드포인트보다 10% 비싸다.

레지던시는 용량을 늘리지 않는다

레이트 리밋은 모든 geo가 공유한다. inference_geo: "us" 요청과 "global" 요청은 같은 한도 풀에서 빠져나가므로, 미국 추론으로 바꾼다고 처리량이 따로 생기지 않는다.

06

Zero Data Retention: 무엇을 덮고 무엇이 벗어나는가

What ZDR covers and what breaks it

기본 정책에서 Claude API 입력·출력은 받거나 생성한 지 30일 안에 백엔드에서 삭제된다. ZDR(Zero Data Retention) 약정이 있으면 API 응답이 반환된 뒤 프롬프트와 응답을 저장하지 않는다. ZDR은 영업팀을 통해 조직 단위로 켜고, 같은 계정의 다른 조직으로 자동 확장되지 않는다.

항목ZDR이유·비고
Messages·Token Counting API(적격 기능)적용Commercial 조직 API 키로 쓰는 Claude Code도 포함
프롬프트 캐싱적격프롬프트·출력은 저장하지 않는다. KV 캐시 표현은 TTL 동안 메모리에만 있다
웹 검색 · 웹 페치 도구적격웹 페이지·PDF 전체 내용은 웹 페치로 가져온다. 동적 필터링은 제외
Message Batches비적격비동기 처리라 저장이 필요하다. 29일 보존
Files API · 코드 실행비적격파일은 삭제하거나 만료될 때까지, 컨테이너 데이터는 최대 30일
Claude Console(플레이그라운드 포함), Managed Agents미적용Managed Agents 세션 기록은 지울 때까지 남는 상태 저장형 리소스다

API가 막아 주지 않는다

ZDR 조직이 Batch API나 Files API를 호출해도 요청은 그대로 성공한다. 비적격 기능을 쓰는 것은 그 데이터만큼 ZDR 약정 밖으로 나가는 선택이고, 데이터는 그 기능의 보존 정책을 따른다. 아키텍처 검토 단계에서 걸러야 한다.

약정과 무관한 보존

ZDR이나 HIPAA 약정이 있어도 법이 요구하거나 자동 신뢰·안전 시스템이 플래그한 경우에는 보존될 수 있다. 플래그된 채팅·세션의 입력과 출력은 최대 2년까지 남을 수 있다.

Bedrock과 Google Cloud(Google managed)에서는 클라우드 사업자가 데이터 처리자이므로, 보존·컴플라이언스 조건은 그 플랫폼 문서를 따른다. ZDR 조직에서는 CORS도 지원하지 않으니 브라우저 앱은 백엔드 프록시를 거쳐 호출한다.

07

용량 산정: 레이트 리밋·지출 한도·Priority Tier

Sizing capacity

조직에는 두 종류의 한도가 걸린다. 지출 한도(spend limit)는 한 달에 쓸 수 있는 최대 금액이고, 레이트 리밋(rate limit)은 일정 시간에 보낼 수 있는 요청·토큰의 최댓값이다. 둘 다 사용 등급(usage tier)에 따라 정해지고, 사용 이력이 쌓이면 등급이 올라간다.

한도단위·값넘었을 때
등급별 월 지출 상한Start $500 · Build $1,000 · Scale $200,000 (Custom은 별도 협의)429 rate_limit_error, error_code: enforced_spend_limit_reached. retry-after 없음, 다음 달 1일 00:00 UTC까지 재시도해도 실패
직접 정한 지출 한도조직·워크스페이스별로 등급 상한 이하400 invalid_request_error
레이트 리밋모델 클래스별 RPM·ITPM·OTPM. 토큰 버킷 방식으로 계속 채워진다429와 어떤 한도를 넘었는지 설명. retry-after가 있으면 그만큼 기다린다
  • 캐시 인지 ITPM: 대부분의 모델에서 캐시에서 읽은 입력(cache_read_input_tokens)은 ITPM에 들어가지 않는다. 반복되는 시스템 프롬프트를 캐싱하면 비용과 실효 처리량이 함께 좋아진다
  • OTPM은 실제 생성된 토큰으로 센다. max_tokens를 크게 잡아도 OTPM 불이익은 없다
  • 사용량이 갑자기 늘면 가속 한도(acceleration limit)로 429가 날 수 있다. 트래픽은 점진적으로 올린다
  • 워크스페이스별로 더 낮은 한도를 걸어 한 팀이 조직 전체 한도를 다 쓰지 못하게 할 수 있다
한도는 보장이 아니다

문서에 나온 레이트 리밋은 허용되는 최댓값이지 보장된 최솟값이 아니다. 이전에는 Priority Tier 약정(분당 입력·출력 토큰, 1·3·6·12개월, 특정 모델 버전, 99.5% 가동 목표)이 확정 용량을 주는 수단이었다. 그러나 현재 문서는 서비스 티어를 레거시로 표시하고, Priority Tier 약정은 더 이상 판매하지 않으며 기존 약정은 계약 종료일까지만 쓴다고 적는다. Fable 5.1, Opus 5.5, Sonnet 5.5, Haiku 5.5 같은 5.x 모델은 Priority Tier를 지원하지 않는다. 보장 용량이 필요하면 영업팀에 문의하라는 것이 현재 안내다. CertSafari 레슨은 "확정 처리량에는 Priority Tier 약정이 필요하다"고 설명하는데, 이 가이드는 공식 문서를 따랐다.

시험 함정 · 흔한 오해

오해입력이 아주 크면 가장 비싼 최상위 모델만 처리할 수 있다.
사실현재 모델 넷은 모두 1M 컨텍스트다. 크기로 탈락하는 것은 200K 창을 가진 레거시 모델이고, 남은 후보는 비용과 평가 결과로 고른다.
오해토큰 단가가 가장 낮은 모델이 운영비도 가장 적게 든다.
사실실패한 과업도 토큰이 청구되고 재시도 비용이 더해진다. 실제 과업으로 잰 완료 과업당 비용을 비교한다.
오해inference_geo: "us"를 쓰면 미국 리전 몫의 처리량이 추가된다.
사실레이트 리밋은 모든 geo가 공유한다. 바뀌는 것은 추론 위치와 1.1배 가격이다.
오해ZDR 조직에서는 어떤 기능을 써도 데이터가 남지 않는다.
사실Batch·Files API·코드 실행은 비적격이라 각자의 보존 정책을 따르고, 법적 요구나 안전 플래그가 걸린 데이터는 최대 2년 보존될 수 있다.
오해AWS를 쓰는 고객이면 무조건 Bedrock으로 연결한다.
사실Marketplace 청구와 Claude API 기능(Agent Skills, 코드 실행, 베타 헤더)이 필요하면 Claude Platform on AWS가 맞다. AWS가 유일한 데이터 처리자여야 할 때 Bedrock을 고른다.
오해요금 등급표의 레이트 리밋까지는 처리량이 보장된다.
사실표의 값은 최댓값일 뿐이다. 확정 용량을 주던 Priority Tier는 신규 판매가 끝났고 5.x 모델은 지원하지 않는다.
