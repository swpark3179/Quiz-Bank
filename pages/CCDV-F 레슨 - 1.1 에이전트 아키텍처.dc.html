'에이전트로 만들까, 워크플로로 만들까'는 기술 취향 문제가 아니라 다음 단계를 누가 정하느냐의 문제다. 코드가 경로를 정해 두면 워크플로, 모델이 실행 중에 스스로 다음 행동과 도구를 고르면 에이전트다. 시험은 이 구분을 바탕으로, 요구사항을 만족하는 가장 단순한 구조를 고를 수 있는지 묻는다. 자율성은 공짜가 아니다. 지연·비용·예측 불가능성이라는 값을 치르므로, 그 값을 치를 이유가 있을 때만 한 칸씩 올라간다.

습득 포인트
  • 워크플로(미리 정한 코드 경로)와 에이전트(모델이 과정을 스스로 지휘)를 제어 흐름 기준으로 구분한다
  • 단일 호출 → 워크플로 → 단일 에이전트 → 멀티에이전트 순서로, 요구사항을 채우는 가장 낮은 단계를 고른다
  • 라우팅·프롬프트 체이닝·병렬화(섹셔닝·투표)·오케스트레이터-워커를 시나리오에서 알아본다
  • 오케스트레이터-서브에이전트 계층에서 일이 어떤 순서로 흐르고, 부모가 무엇을 돌려받는지 설명한다
  • 서브에이전트가 결과를 개선하는 세 가지 경우와 토큰·시간 비용을 따져 도입 여부를 판단한다
01

제어 흐름을 누가 쥐는가

Workflows vs agents

Anthropic은 둘을 이렇게 나눈다. 워크플로는 LLM과 도구가 미리 정의된 코드 경로를 따라 움직이는 시스템이고, 에이전트는 LLM이 자신의 과정과 도구 사용을 동적으로 지휘하며 작업 방식을 스스로 통제하는 시스템이다. 둘 다 LLM을 쓰고 둘 다 도구를 부를 수 있으니, 'LLM이 들어 있느냐', '도구를 쓰느냐'는 구분 기준이 아니다.

상황분류이유
LLM이 문의를 '결제/배송/기타'로 분류하고, 코드의 if문이 분류값에 따라 담당 프롬프트를 고른다워크플로모델은 값 하나를 낼 뿐이고, 갈 수 있는 길은 코드가 모두 정해 두었다
LLM이 초안 → 검토 → 요약을 차례로 수행하는데, 순서는 코드에 고정되어 있다워크플로단계 수와 순서를 실행 전에 알 수 있다
목표와 도구만 받은 Claude가 결과를 보며 다음에 무엇을 조회할지 매 바퀴 정한다에이전트다음 단계가 실행 중의 발견에 따라 달라지고, 그 결정을 모델이 내린다
판별 질문 하나

"실행 전에 이 시스템이 거칠 수 있는 경로를 코드만 보고 전부 나열할 수 있는가?" 할 수 있으면 워크플로다. 모델 출력이 분기를 고르는 데 쓰이더라도, 분기 자체가 코드에 있으면 마찬가지다.

02

자율성 사다리: 가장 낮은 칸에서 시작한다

Climb only when the evidence says so

공식 가이드의 출발점은 "가능한 가장 단순한 해법을 찾고, 필요할 때만 복잡성을 더하라"이다. 검색과 예시를 곁들인 단일 LLM 호출로 충분한 경우가 많고, 그러면 에이전트형 시스템을 아예 만들지 않는 것이 정답이다.

단계단계를 정하는 주체이 단계로 충분한 때
① 단일 호출없음 (한 번 묻고 답)검색 결과·예시를 넣은 프롬프트 하나로 품질 목표를 채울 때
② 워크플로코드하위 작업이 고정되어 있고 미리 알 수 있을 때. 예측 가능성과 일관성이 중요할 때
③ 단일 에이전트모델필요한 단계 수를 미리 알 수 없는 개방형 문제이고, 모델의 판단을 어느 정도 믿을 수 있을 때
④ 멀티에이전트오케스트레이터 모델단일 에이전트로는 컨텍스트·병렬성·전문화의 한계가 실제로 확인될 때 (→ 05)
시험 판단 축
  • 현재 파이프라인이 품질 목표를 이미 채운다면 에이전트로 바꾸는 보기는 오답이다. 지연·비용이 늘고 예측 가능성만 잃는다
  • '더 복잡한 문제 = 에이전트'가 아니다. 단계가 고정되어 있으면 아무리 길어도 워크플로가 맞다
  • 에이전트를 고를 때는 샌드박스 테스트와 가드레일, 반복 상한 같은 정지 조건을 함께 고려한다
03

워크플로 패턴 한눈에

Routing, chaining, parallelization, orchestrator-workers

시나리오를 읽고 어떤 패턴인지 이름을 붙이는 문항이 자주 나온다. 핵심은 하위 작업이 언제 정해지는가와 같은 입력을 몇 번 처리하는가다. 패턴별 세부 설계는 1.3에서 다룬다.

패턴구조시나리오 신호
프롬프트 체이닝고정된 단계를 순서대로. 단계 사이에 코드 검사(게이트)를 둘 수 있다"초안 작성 → 규정 검사 → 번역"처럼 순서가 늘 같다
라우팅입력을 분류한 뒤 범주별 전용 경로로 보낸다범주가 미리 정해진 몇 개이고, 범주마다 처리 방식이 다르다
병렬화 · 섹셔닝서로 독립인 하위 작업을 동시에 돌려 결과를 합친다같은 입력을 서로 다른 관점(보안·성능·스타일)으로 동시에 검토
병렬화 · 투표같은 작업을 여러 번 돌려 결과를 비교·집계한다"세 번 판정해 두 번 이상 위반이면 차단"
오케스트레이터-워커중앙 LLM이 실행 중에 하위 작업을 정해 워커에 맡기고 결과를 종합한다어떤 파일·자료를 봐야 할지 입력을 보기 전에는 알 수 없다
평가자-최적화자한 LLM이 만들고 다른 LLM이 평가해 피드백하는 루프평가 기준이 분명하고, 피드백으로 측정 가능하게 나아진다
헷갈리기 쉬운 쌍 ①

섹셔닝 vs 오케스트레이터-워커. 둘 다 여러 갈래를 동시에 돌리지만, 섹셔닝은 갈래가 미리 고정되어 있고 오케스트레이터-워커는 오케스트레이터가 입력을 보고 갈래를 그때 정한다. 오케스트레이터-워커를 '모델이 하나 더 붙은 병렬화'로 보면 틀린다.

헷갈리기 쉬운 쌍 ②

섹셔닝 vs 투표. 섹셔닝은 서로 다른 일을 나눠 맡고, 투표는 같은 일을 반복해 신뢰도를 높인다. 관점이 서로 다른 검토 세 개를 동시에 돌리면 섹셔닝이다.

04

오케스트레이터와 서브에이전트

Manager / supervisor hierarchies

오케스트레이터-워커를 에이전트 수준으로 올린 것이 관리자(감독자) 계층이다. 리드 에이전트가 계획을 세우고, 하위 작업을 서브에이전트에 나눠 주고, 돌아온 결과를 종합한다. Anthropic의 리서치 기능이 이 구조다.

① PLAN
리드가 전략을 세우고 계획을 메모리에 저장
→
② DELEGATE
하위 질문별 서브에이전트 생성
→
③ EXPLORE
서브에이전트가 각자 검색·평가 후 보고
→
④ SYNTHESIZE
리드가 종합하고 추가 조사 여부 결정 (필요하면 ②로)
→
⑤ CITE
인용 담당 에이전트가 출처를 붙임

계획을 메모리에 저장하는 이유는 컨텍스트가 길어지면 앞부분이 잘릴 수 있어서다. 인용은 종합이 끝난 뒤 별도 단계로 처리된다.

Claude Agent SDK에서는 agents 옵션으로 서브에이전트를 선언하고, Claude가 Agent 도구로 호출한다. 서브에이전트마다 쓸 수 있는 도구를 tools로 좁힐 수 있다.

from claude_agent_sdk import query, ClaudeAgentOptions, AgentDefinition options = ClaudeAgentOptions( allowed_tools=["Read", "Grep", "Glob", "WebSearch", "Agent"], # 자동 승인 목록일 뿐, 제한이 아니다 agents={ "market-researcher": AgentDefinition( description="Use for one market-sizing question. Returns figures with sources.", prompt="You research a single market question and cite every figure.", tools=["WebSearch", "WebFetch"], # 이 서브에이전트의 도구는 이것뿐 model="sonnet", ), "report-reader": AgentDefinition( description="Use to summarize internal reports under ./reports. Read-only.", prompt="Summarize the requested report. Never modify files.", tools=["Read", "Grep", "Glob"], # 읽기 전용 ), }, )
필드·옵션역할헷갈리는 점
descriptionClaude가 언제 이 서브에이전트에 맡길지 판단하는 근거모호하게 쓰면 위임이 일어나지 않는다
prompt서브에이전트의 시스템 프롬프트(역할·행동)위임 여부가 아니라 실행 중 행동을 정한다
tools서브에이전트가 쓸 수 있는 도구 목록. 빠진 도구는 세션에 아예 없다생략하면 서브에이전트용 도구를 모두 물려받는다
allowedTools (query 옵션)권한 확인 없이 실행할 도구 목록목록에 없는 도구를 막지 않는다. 제거는 disallowedTools
부모가 돌려받는 것

서브에이전트는 새 컨텍스트에서 시작하고, 중간의 도구 호출과 결과는 서브에이전트 안에 남는다. 부모에게 돌아오는 것은 최종 메시지 하나다. 그래서 오케스트레이터는 서브에이전트가 어떤 파일을 몇 번 읽었는지 볼 수 없다. 서브에이전트에게 필요한 경로·오류 메시지·결정 사항은 Agent 도구의 프롬프트에 직접 담아 넘겨야 한다.

05

서브에이전트가 이득인 경우와 그 비용

When subagents help, and what they cost

멀티에이전트가 결과를 개선하는 경우는 크게 셋이다. 이 셋에 해당하지 않으면 조정 비용이 이득보다 큰 경우가 많다.

상황에이전트 하나로 하면 생기는 문제서브에이전트가 주는 것
대량의 중간 자료검색 결과·파일 내용이 메인 컨텍스트를 채워 추론이 흐려진다컨텍스트 격리: 많이 읽고 짧은 요약만 돌려준다
서로 독립인 조사 갈래갈래를 하나씩 차례로 조사해 범위가 좁아진다병렬 탐색: 더 넓은 탐색 공간을 동시에 훑는다
도구가 너무 많음도메인이 섞인 도구 수십 개 사이에서 도구 선택이 흔들린다전문화: 역할별로 좁힌 도구와 맞춤 프롬프트
토큰 비용

Anthropic 리서치 시스템 기준으로 에이전트는 일반 채팅의 약 4배, 멀티에이전트는 약 15배 토큰을 쓴다. 같은 작업을 단일 에이전트와 비교하면 보통 3~10배다. 그래서 결과의 가치가 그 비용을 정당화하는 작업에만 쓴다.

걸리는 시간

서브에이전트가 동시에 돈다고 전체가 빨라지는 것은 아니다. 총 연산량이 크게 늘어 병렬 시스템이 단일 에이전트보다 오래 걸리는 경우가 많다. 병렬화의 주된 이득은 속도가 아니라 탐색의 폭과 철저함이다.

나누는 기준
  • 일을 필요한 컨텍스트 기준으로 나눈다. 서로 독립인 조사 갈래, 인터페이스가 깔끔한 구성 요소, 결과만 보면 되는 검증이 좋은 경계다
  • '기획 → 구현 → 테스트 → 리뷰'처럼 같은 일의 순차 단계를 역할별 에이전트로 쪼개면, 넘길 때마다 맥락이 빠져 품질이 떨어진다
  • 모든 에이전트가 같은 맥락을 공유해야 하거나 서로 의존이 많은 작업(대부분의 코딩 작업)은 멀티에이전트에 맞지 않는다

시험 함정 · 흔한 오해

오해LLM이 분류 결과를 내서 분기를 고르면 에이전트다.
사실갈 수 있는 경로를 코드가 모두 정해 두었다면 워크플로(라우팅)다. 에이전트는 모델이 과정 자체를 지휘한다.
오해에이전트는 워크플로의 상위 호환이니 바꾸면 나아진다.
사실잘 정의된 작업에는 워크플로나 단일 호출이 더 예측 가능하고 싸다. 기존 구조가 목표를 채우면 바꿀 이유가 없다.
오해오케스트레이터는 서브에이전트가 한 일을 모두 본다.
사실부모는 최종 메시지만 받는다. 중간 도구 호출과 결과는 서브에이전트 컨텍스트에 남는다.
오해서브에이전트를 병렬로 돌리면 전체 작업이 빨리 끝난다.
사실총 연산량이 늘어 오히려 오래 걸리는 경우가 많다. 얻는 것은 속도보다 탐색 범위다.
오해allowedTools에 넣지 않은 도구는 서브에이전트가 쓸 수 없다.
사실allowedTools는 자동 승인 목록이다. 서브에이전트의 도구를 좁히는 것은 tools, 도구를 빼는 것은 disallowedTools다.
