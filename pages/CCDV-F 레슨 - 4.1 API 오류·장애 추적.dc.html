4.1 API 오류·장애 추적

Claude 통합이 실패할 때 첫 질문은 "다시 보내면 나아지는가"다. 요청이 잘못됐으면 몇 번을 보내도 같은 오류가 나고, 서버가 일시적으로 바쁘면 기다렸다 보내면 된다. 오류가 어디서 왔는지가 '요청을 고칠지, 재시도할지'를 정한다. 시험은 HTTP 상태와 오류 유형, 재시도 헤더 유무로 이것을 가려내는지, 그리고 아무 예외도 나지 않는 200 응답 속 실패(stop_reason, 빈 응답, 도구 오류)를 통합 계층의 문제와 모델 출력의 문제로 나눌 수 있는지 묻는다.

습득 포인트
  • 4xx(요청을 고친다)와 5xx·529(물러났다 재시도한다)를 나누고, 409·413·504의 올바른 대응을 고른다
  • SDK가 기본으로 무엇을 몇 번 재시도하는지, 지원 문의에 어떤 요청 ID를 남기는지 안다
  • 일반 rate limit, 가속 한도, 등급 월 지출 상한, 직접 정한 지출 한도를 신호로 구별한다
  • tool_use·thinking 블록 관련 400이 통합 코드의 어느 부분을 가리키는지 읽는다
  • stop_reason으로 잘림·거절·일시 정지를 판별하고, 빈 end_turn을 메시지 구조부터 고친다
01

오류 분류: 고칠 것인가, 재시도할 것인가

Sorting an error by its origin

API 오류는 항상 JSON이며 최상위 error 객체에 type과 message가 있고, 응답 본문에 request_id가 함께 온다.

상태유형의미대응
400invalid_request_error요청 형식·내용 문제. 직접 정한 지출 한도에 닿아도 400요청을 고친다(또는 한도를 올린다)
401 · 403authentication_error · permission_errorAPI 키 문제 · 리소스 권한 없음키·워크스페이스 설정 확인
402billing_error결제 정보 문제Console에서 결제 정보 확인
404not_found_error리소스 없음경로와 ID 확인
409conflict_error리소스의 현재 상태와 충돌(동시 수정, 고유 값 중복)충돌을 해소한 뒤 재시도
413request_too_large요청 바이트가 엔드포인트 최대치를 넘음본문을 줄인다. 재시도는 소용없다
429rate_limit_errorrate limit, 등급 월 지출 상한, Claude Code 워크스페이스 한도신호에 따라 다르다(04)
500api_errorAnthropic 내부의 예기치 않은 오류지수 백오프로 재시도, 계속되면 요청 ID로 지원 문의
504timeout_error처리 중 시간 초과긴 요청은 스트리밍이나 Batches로
529overloaded_errorAPI가 일시적으로 과부하(전체 사용자 트래픽)물러났다 재시도
200이라고 성공은 아니다

스트리밍(SSE) 응답에서는 API가 200을 돌려준 뒤에 오류가 날 수 있다. 이 경우 위의 표준 오류 처리 흐름을 타지 않으므로, 스트림의 오류 이벤트를 따로 처리해야 한다. 또 안전 분류기의 거절(stop_reason: "refusal")도 오류가 아닌 정상 200 응답으로 온다.

02

내 코드에 닿기 전에 SDK가 하는 일

Typed exceptions, retries, request IDs

공식 SDK는 오류를 원시 JSON이 아닌 타입 있는 예외로 올린다(Python 예: BadRequestError, RateLimitError, InternalServerError, APIConnectionError). 메시지 문자열을 비교하지 말고 가장 구체적인 클래스부터 잡는다.

SDK 기본 동작내용
자동 재시도 대상연결 오류, 408 Request Timeout, 409 Conflict, 429 Rate Limit, 500 이상(529 포함)
횟수·간격기본 2회, 짧은 지수 백오프. retry-after 헤더가 있으면 따른다
설정max_retries(TS maxRetries)로 늘리거나 0으로 끈다. 요청별로도 덮어쓸 수 있다
타임아웃기본 10분. 비스트리밍 요청이 약 10분을 넘을 것으로 예상되면 SDK가 미리 오류를 낸다
msg = client.messages.create(model=MODEL, max_tokens=1024, messages=history) log.info("claude call ok", extra={ "request_id": msg._request_id, # req_... 지원 문의용 "message_id": msg.id, # msg_... 응답 객체 ID })

모든 응답에는 request-id 헤더가 있고, 같은 값이 오류 본문의 request_id로도 온다. Python·TypeScript SDK는 이 값을 응답 객체의 _request_id 속성으로 노출한다(밑줄로 시작하지만 공개 속성이다). 지원팀이 요청을 추적할 때 필요한 것은 메시지 ID(msg_...)가 아니라 이 요청 ID다.

03

너무 큰 요청과 너무 긴 요청

413 and long-running calls
엔드포인트최대 요청 크기 (1st-party API)
Messages API · Token Counting API128 MB
Message Batches API256 MB
Files API500 MB

한도를 넘으면 413 request_too_large가 오며, 1st-party API에서는 요청이 API 서버에 닿기 전에 Cloudflare가 돌려준다. 용량이나 일시적 문제가 아니므로 재시도해도, 컨텍스트 창이 더 큰 모델로 바꿔도 소용없다. 문서·이미지를 나눠 보내는 등 요청 본문 자체를 줄인다. 컨텍스트 창(토큰)과 요청 크기(바이트)는 다른 한도다.

학습 자료의 수치 vs 현재 문서

일부 학습 자료는 Messages API 요청 한도를 32 MB로 적는다. 2026년 10월 현재 공식 오류 문서의 1st-party API 한도는 Messages API 128 MB, Batch API 256 MB, Files API 500 MB다. 다른 플랫폼(Bedrock 등)의 한도는 API 개요 문서에서 따로 확인한다. 시험에서는 수치보다 '413은 본문을 줄여야 풀린다'는 판단이 핵심이다.

긴 요청은 스트리밍으로

504 timeout_error나 큰 max_tokens가 걸린 요청은 스트리밍 Messages API나 Message Batches API를 쓴다. 일부 네트워크는 유휴 연결을 끊기 때문이다. 이벤트를 하나씩 처리할 필요가 없으면 SDK가 스트림을 대신 소비해 완성된 Message를 돌려주게 할 수 있다(Python stream.get_final_message()).

04

429를 구별하고, 429처럼 보이는 400도 구별한다

Rate limits, acceleration, spend caps, spend limits

Messages API의 rate limit은 모델 등급별 RPM·ITPM·OTPM으로 측정되고, 토큰 버킷 방식이라 고정 주기로 초기화되지 않고 계속 채워진다. 60 RPM이 초당 1건처럼 짧은 간격으로 적용될 수도 있어 짧은 폭주만으로도 걸린다. 한도는 조직 단위로 걸린다.

상황신호대응
일반 rate limit429 rate_limit_error + retry-after 헤더헤더의 초만큼 기다린 뒤 재시도. 반복되면 더 물러난다. 그 전의 재시도는 실패한다
가속 한도 (acceleration limit)공개된 한도보다 한참 아래인데 트래픽을 급격히 늘린 직후 429트래픽을 점진적으로 늘리고 사용 패턴을 일정하게 유지
등급 월 지출 상한429 rate_limit_error, retry-after 없음, error.details.error_code = enforced_spend_limit_reached, 몇 시간이고 계속 실패재시도를 멈추고 알린다. 등급 상향을 요청하거나 다음 달 1일 00:00 UTC까지 기다린다
직접 정한 지출 한도400 invalid_request_error, 메시지가 "You have reached your specified (workspace) API usage limits"로 시작Console의 Billing에서 한도를 올리거나 없앤다
사용 등급월 지출 상한
Start · Build · Scale$500 · $1,000 · $200,000 (Custom 등급은 상한 없음, 계정 팀과 협의)
시험 판단 축
  • 재시도가 답인 429는 retry-after가 있는 것뿐이다. 헤더가 없고 enforced_spend_limit_reached면 SDK 자동 재시도까지 포함해 모두 실패한다
  • 'usage limits'라는 말이 있어도 400이면 내가 정한 한도다. 요청 형식을 고치는 400과 헷갈리지 않는다
  • 같은 조직의 API 키를 여러 개 돌려 써도 조직 단위 한도는 그대로다
  • 프롬프트 캐시에서 읽은 토큰은 대부분의 모델에서 ITPM에 세지 않으므로, 캐싱은 처리량을 늘리는 정공법이다
05

400이 내 메시지 기록을 가리킬 때

When the bug is in your history-building code

400의 메시지는 종종 고쳐야 할 블록의 위치(예: messages.1.content.0)까지 알려 준다. 도구와 사고(thinking)를 쓰는 통합에서 자주 나는 것은 다음과 같다.

오류 메시지의 핵심원인과 수정
tool_use ids were found without tool_result blocks immediately after일부 tool_use에 결과가 없거나, tool_result가 사용자 메시지의 첫 블록이 아니다. 모든 tool_use에 결과를 하나씩 돌려주고 결과 블록을 텍스트보다 앞에 둔다
thinking or redacted_thinking blocks … cannot be modified통합 코드가 블록을 타입으로 걸러 redacted_thinking을 빠뜨렸거나, 어시스턴트 메시지를 다시 조립했다. 어시스턴트 턴을 받은 그대로 돌려보내고 그 뒤에 tool_result를 붙인다
assistant message prefill 미지원최신 모델은 마지막 어시스턴트 메시지 미리 채우기를 받지 않는다. 구조화 출력이나 시스템 프롬프트 지시로 바꾼다
400을 부르는 재조립

[b for b in resp.content if b.type in ("text", "tool_use")]로 어시스턴트 메시지를 다시 만든 뒤 도구 결과를 붙인다. thinking 블록이 사라져 다음 요청이 거부된다.

그대로 돌려보내기

messages.append({"role": "assistant", "content": resp.content})로 받은 턴을 손대지 않고 넣고, 이어서 tool_result만 담은 사용자 메시지를 붙인다.

end_turn자연스럽게 응답 완료정상. 단 내용이 비었으면 07

pause_turn서버 도구 루프가 반복 상한(기본 10회)에 닿음응답을 그대로 대화에 붙여 다시 보내면 이어서 진행

도구가 실패할 때의 흐름도 통합 계층의 몫이다. 도구 실행기가 백엔드 연결 오류를 만나면 앱은 그 내용을 is_error: true인 tool_result로 돌려주고, Claude는 그 오류를 응답에 반영해 사용자에게 사과하거나 설명한다. 이때 Claude의 사과는 모델 결함이 아니라 도구 백엔드가 실패했다는 증상이다. 도구를 다시 시도할지, 얼마나 기다릴지는 앱이 정한다. 오류 메시지에 무엇이 잘못됐고 다음에 무엇을 하면 되는지를 적으면 Claude가 더 잘 대처한다.

도구 결과 안의 내 지시

Claude가 도구 결과를 근거로 움직이지 않거나, 결과에 담긴 지시를 사용자에게 확인받으려 한다면 앱이 자기 지시를 tool_result 안에 넣고 있는지 본다. Claude는 도구 결과 속 지시를 신뢰할 수 없는 제3자 콘텐츠로 다루도록 학습되어 있다. 지시는 도구 결과 밖으로 옮기고(지원 모델의 mid-conversation system message 등), 도구 결과에는 데이터만 남긴다. 반대로 웹 페이지·메일처럼 외부에서 온 신뢰할 수 없는 내용은 시스템 프롬프트가 아니라 tool_result 안에 둔다.

07

빈 end_turn 응답 고치기

Empty responses after tool results

가끔 Claude가 내용 없이 2~3토큰짜리 응답을 stop_reason: "end_turn"으로 돌려준다. 주로 도구 결과 직후에, Claude가 어시스턴트 턴이 끝났다고 판단할 때 생긴다. 원인은 두 가지다.

  • 도구 결과 바로 뒤에 텍스트 블록을 붙인다. 기록에 '도구 결과 뒤엔 사용자 텍스트'라는 패턴이 쌓여 Claude가 그 패턴대로 턴을 끝낸다
  • 이미 완료된 Claude의 응답을 아무것도 더하지 않고 다시 보낸다. Claude는 이미 끝났다고 판단했으므로 계속 끝난 상태로 남는다

시험 판단 축
  • 빈 응답을 그대로 다시 보내면 같은 결과가 나온다. 일회성 오류로 보고 단순 재전송하는 보기는 오답이다
  • 계속 진행을 요청하는 프롬프트는 구조를 고친 뒤에도 비어 있을 때만, 빈 응답을 재시도하는 대신 새 사용자 메시지로 넣는다
  • 서버 도구가 결과 없이 남은 턴에서는 사용자 메시지에 tool_result만 담아야 한다. 뒤에 텍스트를 붙이면 400이 날 수 있다

요청마다 _request_id, 모델, stop_reason, 사용량, 도구 호출 이름과 is_error 여부를 함께 남기면 위 표의 어느 칸인지 재현 없이도 대부분 가릴 수 있다. 스트리밍이라면 200 뒤에 온 오류 이벤트도 같은 요청 ID 아래에 기록한다.

시험 함정 · 흔한 오해

오해200을 받았으면 요청은 성공했다.
사실스트리밍은 200 뒤에 오류 이벤트를 보낼 수 있고, 거절·잘림·빈 응답도 200으로 온다. 스트림 오류와 stop_reason을 확인한다.
오해413은 용량 문제라 재시도하거나 컨텍스트 창이 큰 모델로 바꾸면 된다.
사실요청 바이트 크기 한도다. 본문을 줄이는 것 말고는 해결책이 없다.
오해400 invalid_request_error는 늘 요청 본문이 잘못됐다는 뜻이다.
사실직접 정한 조직·워크스페이스 지출 한도에 닿아도 400이다. 메시지를 읽고 한도를 조정한다.
오해429 rate_limit_error는 언젠가 재시도로 풀린다.
사실등급 지출 상한의 429는 retry-after가 없고 접근이 재개될 때까지 계속 실패한다.
오해refusal이 오면 요청 형식이 깨진 것이다.
사실모델이 응답을 거절한 정상 응답이다. 요청 구조를 뜯어고칠 문제가 아니다.
오해빈 end_turn은 일시적 오류라 다시 보내면 된다.
사실그대로 다시 보내면 계속 비어 있다. 도구 결과 뒤 텍스트 같은 메시지 구조부터 고친다.
