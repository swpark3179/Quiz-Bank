Claude는 도구의 구현 코드를 보지 못한다. 판단 재료는 이름, 설명, 입력 스키마, 그리고 넣었다면 입력 예시뿐이다. 그래서 Define tools 문서는 아주 자세한 설명이 도구 성능을 좌우하는 단연 가장 중요한 요소라고 적는다. 이 단원은 선택되는 설명을 쓰는 법, 겹치는 도구를 정리하는 법, 그리고 시스템 프롬프트의 한 줄이 잘 쓴 설명을 무력하게 만드는 경우를 다룬다.

습득 포인트
  • 도구 선택의 근거가 되는 정의 요소: name · description · input_schema · input_examples
  • 설명에 넣을 것: 기능, 쓸 때와 쓰지 말 때, 파라미터 의미, 한계와 경계
  • 설명이 겹치는 도구의 오라우팅을 진단하고 이름·설명을 다시 정하기
  • 범용 도구를 목적별 계약으로 나누기, 늘 이어 불리는 도구는 합치기
  • 시스템 프롬프트의 키워드성 지시가 도구 선택을 왜곡하는지 점검하기
01

Claude가 실제로 보는 것

What the model sees

tools 파라미터로 도구를 넘기면 API는 도구 정의, 도구 설정, 사용자 시스템 프롬프트를 묶어 별도의 시스템 프롬프트를 구성한다. 기본값 tool_choice: auto에서 Claude는 턴마다 요청이 어떤 도구의 설명된 능력에 들어맞고 답이 아직 컨텍스트에 없을 때 도구를 부른다. 요컨대 고를 때 쓰는 것은 정의에 적힌 글이 전부다.

필드역할선택에 미치는 영향
name^[a-zA-Z0-9_-]{1,128}$ 형식의 식별자첫 신호. 서비스 접두사(github_, slack_)로 경계를 드러낸다
description무엇을, 언제, 어떻게 하는지가장 큰 영향. 도구당 최소 3~4문장, 복잡하면 더 길게
input_schemaJSON Schema 파라미터 정의파라미터 이름·설명·enum이 올바른 인자를 만들게 돕는다
input_examples스키마를 통과하는 입력 예시 배열 (선택)중첩 객체, 형식이 까다로운 파라미터에 효과
strict입력의 스키마 준수 보장 (선택)어느 도구를 고를지가 아니라 인자 형식을 보장한다
02

선택되는 설명의 구성

Anatomy of a selectable description

Define tools의 권고 목록: 도구가 하는 일, 언제 써야 하고 언제 쓰지 말아야 하는지, 각 파라미터의 의미와 동작에 미치는 영향, 반환하지 않는 정보 같은 한계와 주의점. Writing tools for agents 글은 팀에 새로 온 사람에게 설명하듯 쓰라고 하며, 특수한 질의 형식이나 사내 용어, 자원 사이의 관계처럼 머릿속에만 있는 맥락을 글로 드러내라고 한다. 파라미터 이름도 모호하지 않게 짓는다 — user보다 user_id.

BAD · 판단 재료 없음
{"name": "search", "description": "청구서를 검색한다.", "input_schema": {"type": "object", "properties": {"q": {"type": "string"}}}}

무엇으로 찾는지, 몇 건이 오는지, 입금 내역도 나오는지 알 수 없다.

GOOD · 기능·시점·한계·형식
{"name": "billing_search_invoices", "description": "회계 시스템에서 발행된 청구서를 고객 ID·기간·상태로 찾는다. 특정 고객의 청구서 목록, 미납 건, 특정 달의 발행 건을 물을 때 쓴다. 입금 내역은 반환하지 않으므로 입금 여부는 billing_get_payments를 쓴다. 결과는 최신순 최대 50건이며 더 있으면 next_cursor를 준다.", "input_schema": {"type": "object", "properties": { "customer_id": {"type": "string", "description": "CUST-로 시작하는 고객 ID"}, "period": {"type": "string", "description": "YYYY-MM, 최대 12개월 범위"}, "status": {"type": "string", "enum": ["open", "paid", "void"]}}, "required": ["customer_id"]}}
input_examples를 붙일 때

형식이 까다로운 파라미터에는 input_examples로 구체적인 입력을 보여 준다. 각 예시는 input_schema를 통과해야 하고(아니면 400), 단순 예시는 약 20~50토큰, 복잡한 중첩 객체는 약 100~200토큰을 더 쓴다. web search·code execution 같은 server tool에는 쓸 수 없다. Advanced tool use 글은 내부 테스트에서 복잡한 파라미터 처리 정확도가 72%에서 90%로 올랐다고 보고한다.

03

겹치는 도구가 오라우팅을 만든다

Overlap causes misrouting

두 도구의 설명이 거의 같으면 Claude에게는 둘을 가를 근거가 없다. Troubleshooting tool use 문서는 증상별로 처방을 정리한다.

증상흔한 원인처방
B를 원했는데 A를 부른다설명이 모호함무엇을 하는지만이 아니라 언제 쓰는지로 구분해 설명을 다듬는다
만든 도구를 아예 안 부른다이름 충돌, 지나치게 일반적인 스키마도구 목록의 중복 이름 확인, input_examples로 의도한 쓰임을 구체화
파라미터 타입이 틀린다스키마가 모호함strict: true(지원 범위의 스키마일 때) 또는 input_examples

예: 사내 지원 에이전트에 search_kb("지식 베이스를 검색한다")와 search_docs("문서를 검색한다")가 있다. 실제로 하나는 엔지니어용 장애 대응 런북이고 다른 하나는 고객에게 공개된 제품 설명서다. 고객 답변에 내부 런북 내용이 섞여 나가는 사고가 난다.

BAD · 이름도 설명도 겹침
search_kb "지식 베이스를 검색한다" search_docs "문서를 검색한다"

어느 쪽이 내부용인지, 어떤 질문에 쓰는지 드러나지 않는다.

GOOD · 범위를 이름과 설명에
runbook_search_internal "엔지니어용 장애 대응 런북을 검색한다. 온콜 담당자의 진단·복구 절차 질문에만 쓴다. 내부 호스트명이 들어 있어 고객 답변 작성에는 쓰지 않는다." productdocs_search_public "고객에게 공개된 제품 설명서를 검색한다. 고객 문의에 답할 때 쓴다. 장애 원인이나 내부 절차는 들어 있지 않다."
네임스페이스에 대해

Writing tools for agents는 서비스·자원 단위로 접두사를 붙이는 namespacing이 많은 도구 사이의 경계를 긋는 데 도움이 된다고 하면서, 접두사형과 접미사형 중 무엇이 나은지는 모델마다 평가 결과가 달랐으니 자기 평가로 고르라고 한다. 같은 글은 웹 검색 도구의 설명을 고쳐 Claude가 쿼리에 불필요하게 연도를 붙이던 습관을 바로잡은 사례도 소개한다.

04

쪼갤 것인가, 합칠 것인가

Split vague tools, merge chained ones

범용 도구 하나가 mode 문자열에 따라 전혀 다른 일을 하고 모양이 다른 결과를 돌려주면, 진짜 선택이 도구 안쪽의 파라미터 값으로 숨는다. 설명에는 "파일을 처리한다" 정도밖에 쓸 수 없고, Claude는 mode를 잘못 고르거나 결과를 잘못 해석한다. 이럴 때는 목적별 도구로 나누고 각자 입력·출력 계약을 정한다.

전후 (도구별 계약)
process_file(file_id, mode)
mode: ocr · summary · pii …		extract_text_from_scan(file_id) → {pages: [{n, text}]}
summarize_document(file_id, max_words) → {summary, key_points[]}
detect_pii(file_id) → {findings: [{type, page, span}]}

반대 방향도 있다. 늘 함께 이어 불리는 작은 도구들은 하나로 합치는 편이 낫다. 빌드 로그를 통째로 가져오는 fetch_build_log 뒤에 매번 grep_build_log를 부른다면, search_build_log(build_id, pattern, context_lines) 하나가 컨텍스트도 아끼고 선택지도 줄인다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 범용 도구를 목적별 도구로 쪼개는 방향(analyze_document → 세 도구)을 강조한다. 현재 Define tools의 모범 사례에는 반대로 보이는 항목, "관련 작업을 더 적은 도구로 합쳐라"(create_pr·review_pr·merge_pr → action 파라미터를 가진 도구 하나)가 있다. 둘은 충돌하지 않는다. 기준은 각 도구가 뚜렷이 구별되는 목적과 명확한 계약을 갖는가(Writing tools for agents)다. 입력·출력 모양이 서로 다른 일을 하나에 숨겼으면 쪼개고, 같은 자원에 대한 비슷한 동작들이 선택만 헷갈리게 하면 합친다.

05

시스템 프롬프트가 설명을 덮어쓸 때

Prompt wording vs tool descriptions

Tool use overview는 시스템 프롬프트로 도구 사용의 경계를 움직일 수 있다고 설명한다. "응답 전에 도구로 조사하라"는 도구 호출을 늘리고, "항상 먼저 도구를 호출하라"는 더 강하게 민다. 위험한 것은 특정 단어에 도구를 묶는 지시다. 설명에 적어 둔 사용 조건보다 그 단어가 먼저 작동한다.

BAD · 키워드에 묶인 지시
메시지에 '주문'이 있으면 반드시 먼저 orders_lookup을 호출하라. CRITICAL: 숫자가 보이면 무조건 주문 번호다.

"주문 취소 규정이 뭐예요?" 같은 정책 질문이나 전화번호에도 주문 조회가 일어난다.

GOOD · 의도 단위의 지시
주문의 현재 상태나 배송 위치를 물으면 orders_lookup을 쓴다. 규정·절차 질문은 productdocs_search_public으로 답한다.

지시는 의도 단위로 쓰고, 세부 사용 조건은 도구 설명에 둔다.

최신 모델과 강한 어조

Prompting best practices는 최신 모델이 시스템 프롬프트에 더 민감해서, 예전 모델의 호출 부족을 막으려고 쓴 "CRITICAL: You MUST use this tool when…" 같은 공격적 표현이 이제는 과호출(overtriggering)을 일으킨다고 경고한다. "If in doubt, use [tool]" 같은 문장도 과호출 원인으로 꼽는다. 해법은 "Use this tool when…" 정도의 평범한 어조다.

점검 순서
  • 시스템 프롬프트에서 도구 이름과 특정 단어가 함께 나오는 문장을 찾는다
  • 그 문장이 도구 설명의 "언제 쓰지 않는지"와 모순되는지 본다
  • 평가 대화의 전사(transcript)에서 잘못된 호출 직전에 어떤 지시가 작동했는지 확인한다. interleaved thinking을 켜면 왜 그 도구를 불렀는지 살피기 쉽다
  • 고친 뒤 같은 평가 세트로 다시 측정한다

시험 함정 · 흔한 오해

오해이름만 명확하면 설명은 한 줄이면 충분하다.
사실문서는 자세한 설명을 도구 성능의 가장 중요한 요소로 꼽고, 도구당 최소 3~4문장을 권한다.
오해비슷한 두 도구는 시스템 프롬프트에 "A를 우선하라"고 쓰면 해결된다.
사실원인은 설명의 중복이다. 이름과 설명을 언제 쓰는지 기준으로 갈라야 하며, 키워드성 우선 규칙은 새로운 오라우팅을 만든다.
오해CRITICAL·MUST 같은 강한 어조가 도구 호출의 신뢰도를 높인다.
사실최신 모델에서는 과호출을 부른다. 평범한 조건문으로 쓴다.
오해strict: true를 켜면 Claude가 올바른 도구를 고른다.
사실strict는 입력이 스키마를 따르도록 보장할 뿐이다. 어느 도구를 고를지는 여전히 이름과 설명이 정한다.
