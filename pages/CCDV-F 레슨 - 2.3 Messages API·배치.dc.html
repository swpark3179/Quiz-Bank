Messages API 동작과 Message Batches

Messages API는 단순해 보이지만, 실제 서비스에서 터지는 버그는 대부분 몇 가지 규칙을 놓친 데서 나온다. 가장 중요한 규칙은 API가 아무것도 기억하지 않는다는 것이다. 대화 이력, 앞 턴의 이미지, 도구 호출 중의 thinking 블록까지 매 요청에 애플리케이션이 다시 담아 보내야 한다. 시험은 응답 필드를 읽는 법, 캐시가 왜 안 맞는지, 스트림 조각을 언제 파싱하는지, 그리고 누가 응답을 기다리고 있지 않은 작업을 Message Batches로 넘기는 판단을 묻는다.

습득 포인트
  • 요청 필수 필드와 응답의 콘텐츠 블록·stop_reason·usage를 읽고, 거절 사유는 stop_details에서 찾는다
  • 무상태 API에서 이력을 다시 보내는 방식과, 캐시 중단점·TTL을 바꾸지 않는 접두사로 설계하는 법을 설명한다
  • 클라이언트 도구 루프에서 tool_result와 thinking 블록을 돌려보내는 규칙, pause_turn 처리법을 안다
  • SSE 이벤트 순서와 input_json_delta 누적, 스트림 중간 오류를 다룬다
  • 이미지 소스 세 가지와 요청당 한도, Files API, 클라우드 플랫폼별 요청 차이를 구분한다
  • 배치의 생성·폴링·결과 회수 흐름과 한도·과금·미지원 파라미터를 알고, 배치와 실시간 중 하나를 고른다
01

요청과 응답의 모양

Request fields, content blocks, stop reasons

POST /v1/messages 요청에는 model, max_tokens, messages가 반드시 들어간다. 시스템 지시는 최상위 system 필드에 둔다. 응답은 type: "message"인 객체이고, 본문은 문자열이 아니라 타입이 붙은 콘텐츠 블록의 배열(content)이다. 텍스트만 오는 것이 아니라 tool_use, thinking 같은 블록이 섞여 오므로, content[0].text를 바로 꺼내는 코드는 언젠가 깨진다. 블록의 type을 보고 고른다.

stop_reason뜻애플리케이션이 할 일
end_turn자연스럽게 답을 마침응답을 쓴다
max_tokens요청한 max_tokens에 닿아 잘림한도를 올리거나 이어 쓰게 한다. 마지막 블록이 미완성 tool_use면 더 큰 한도로 재시도
stop_sequence지정한 정지 문자열이 나옴stop_sequence 필드로 어느 것인지 확인
tool_use도구 호출을 요청함도구를 실행해 tool_result로 돌려준다 (→ 04)
pause_turn서버 도구 루프가 반복 한도에 닿아 멈춤어시스턴트 콘텐츠를 그대로 다시 보내 이어 가게 한다
refusal응답을 거절함. 오류가 아니라 HTTP 200으로 온다stop_details로 정책 범주를 기록하고 필요하면 대체 모델로 재시도
model_context_window_exceeded응답이 컨텍스트 창을 채움잘린 응답으로 취급

stop_details는 refusal일 때만 채워지고 나머지 정지 사유에서는 null이다. 거절 사유를 로그로 남기려면 응답 텍스트를 파싱할 것이 아니라 이 필드를 읽는다. 토큰 사용량은 usage.input_tokens·output_tokens에 오고, 캐시를 쓰면 캐시 관련 필드가 더해진다(→ 03).

02

대화 상태는 애플리케이션이 들고 있다

The API is stateless

Messages API는 무상태(stateless)다. 두 번째 질문을 보낼 때는 첫 질문과 첫 답을 포함한 전체 이력을 messages에 다시 넣어야 한다. 이력 속 assistant 메시지는 실제로 Claude가 만든 것이 아니어도 된다(합성 메시지 가능). 서버 쪽 세션 ID 같은 것은 없으므로, 대화별 이력을 DB나 세션 저장소에 두고 요청할 때마다 조립하는 것이 애플리케이션의 책임이다.

프리필은 최신 모델에서 막혔다

마지막 assistant 메시지에 답의 첫머리를 미리 채우는 프리필(prefill)은 Claude 4.6 이후 모델과 Mythos Preview에서 지원되지 않고 400 오류가 난다. 출력 형식을 고정하려면 구조화 출력(output_config.format)이나 시스템 프롬프트 지시를 쓴다.

대화 중간의 system 메시지

Opus 5.5, Sonnet 5.5, Haiku 5.5 등 최신 모델은 사용자 턴 뒤에 "role": "system" 메시지를 넣어 지시를 추가할 수 있다. 이력 끝에 붙으므로 앞쪽의 캐시 접두사를 무효화하지 않는다. 처음부터 적용할 지시는 여전히 최상위 system에 둔다.

03

프롬프트 캐싱: 바뀌지 않는 접두사에 중단점

Breakpoints, TTL, and why reads stay at zero

이력을 매번 다시 보내는 비용을 줄이는 장치가 프롬프트 캐싱(prompt caching)이다. 캐시는 tools → system → messages 순서의 접두사를 기준으로, cache_control이 붙은 블록까지를 저장한다. 맞추기는 완전 일치라서, 중단점 앞 어딘가가 한 글자라도 바뀌면 그 요청은 새로 쓴다.

{ "model": "claude-opus-5-5", "max_tokens": 2048, "system": [ {"type": "text", "text": "<보험 약관 전문, 약 4만 토큰>", "cache_control": {"type": "ephemeral", "ttl": "1h"}}, {"type": "text", "text": "상담 시각: 2026-10-30 14:05"} ], # 매번 바뀌는 값은 중단점 '뒤'에 "messages": [ ... ] }
항목규칙 (문서 기준)
켜는 법블록마다 cache_control을 붙이는 명시적 중단점, 또는 요청 최상위에 cache_control 하나를 두는 자동 캐싱. 명시적 중단점은 요청당 최대 4개
수명(TTL)기본 5분이고 읽힐 때마다 추가 비용 없이 갱신. "ttl": "1h"로 1시간. 둘을 섞으면 1시간 항목이 5분 항목보다 앞에 와야 한다
요금 배수5분 쓰기 1.25배, 1시간 쓰기 2배, 읽기 0.1배(Opus 5.5·Sonnet 5.5는 0.05배). 배치 할인과 곱해진다
최소 길이모델별 512~4,096토큰. 이보다 짧으면 오류 없이 캐시만 안 된다
되돌아보기중단점 하나당 최대 20개 위치까지 거슬러 이전 쓰기를 찾는다. 대화가 길게 자라면 중단점을 하나 더 둔다
확인 필드cache_creation_input_tokens(쓰기), cache_read_input_tokens(읽기). 둘 다 0이면 캐시가 아예 안 된 것(보통 최소 길이 미달)
격리조직 간에는 절대 공유되지 않고, Claude API·Claude Platform on AWS·Microsoft Foundry에서는 워크스페이스 단위로 격리된다
읽기가 계속 0일 때

타임스탬프·요청 ID·사용자 이름처럼 매번 바뀌는 값이 중단점 앞에 들어가 있는지부터 본다. 그러면 요청마다 해시가 달라져 매번 쓰기 비용(1.25배)만 낸다. 중단점을 바뀌지 않는 마지막 블록으로 옮기거나, 바뀌는 값을 중단점 뒤로 보낸다. 도구 정의를 바꾸면 tools·system·messages 캐시가 모두 무효화되고, thinking 설정이나 effort를 바꾸면 messages 캐시가 무효화된다는 점도 기억한다.

04

도구 루프와 thinking 블록

tool_use, tool_result, pause_turn, thinking signatures

클라이언트에서 실행하는 도구는 애플리케이션이 루프를 돌린다. stop_reason이 tool_use인 동안 도구를 실행하고, 이전 메시지 + 방금 받은 어시스턴트 응답 + tool_result를 담은 사용자 메시지를 붙여 다시 요청한다. 그 밖의 정지 사유가 오면 루프를 끝낸다.

  • 후속 사용자 메시지에는 tool_use 블록마다 하나씩 tool_result만 넣는다. 결과 뒤에 텍스트를 덧붙이면 턴이 끝난 것으로 처리되고, 빈 응답(end_turn)이 돌아오는 원인이 된다
  • 같은 tools 배열을 그대로 보낸다. 바꾸면 400 오류가 난다
  • 웹 검색·코드 실행 같은 서버 도구는 Anthropic 쪽 루프에서 돌고, 결과 블록도 서버가 채운다. 반복 한도에 닿으면 pause_turn이 오므로 받은 어시스턴트 콘텐츠를 그대로 이력에 넣어 다시 보낸다

thinking이 켜진 상태에서 도구를 쓰면 규칙이 하나 더 붙는다. 도구 호출을 낸 어시스턴트 메시지의 thinking·redacted_thinking 블록을 받은 그대로 돌려보내야 한다. 각 블록의 signature에는 전체 추론이 암호화되어 있어, 서버가 이것으로 이어지는 추론을 복원한다. 최신 어시스턴트 메시지의 thinking 블록을 수정·재배열·필터링·재구성하면 400 invalid_request_error가 난다. 화면에 안 보여 줄 거라며 블록 타입으로 걸러 내는 코드가 전형적인 원인이다.

설정해당 모델알아 둘 점
thinking: {type: "adaptive"} + output_config.effortClaude 4.6 이후 모델. Claude 5 계열은 기본으로 켜져 있음얼마나 생각할지 모델이 정하고, 깊이는 effort로 조절. Opus 5.5·Haiku 5.5의 기본 effort는 medium
thinking: {type: "enabled", budget_tokens: N}Haiku 4.5·Opus 4.5 등 수동 모드 전용 모델. 4.6에서는 폐기 예정budget_tokens는 1,024 이상이고 max_tokens보다 작아야 한다(인터리브 thinking 예외). 4.7 이후 모델은 이 형식을 400으로 거부
출력 상한은 effort가 아니다

effort는 응답 전체에 드는 노력을 조절하는 부드러운 지침이고, 지출의 확실한 상한은 max_tokens다. 최신 모델은 thinking 표시 기본값이 "omitted"라서 블록의 thinking 필드가 비어 오지만, 서명은 그대로 있으므로 다중 턴에서 똑같이 돌려보낸다.

05

스트리밍: 서버 전송 이벤트 읽기

SSE event flow and partial JSON

"stream": true를 주면 응답이 서버 전송 이벤트(SSE, server-sent events)로 조금씩 온다. 이벤트 순서는 항상 같다.

① message_start
빈 content를 가진 Message
→
② 블록마다
content_block_start → content_block_delta 여러 번 → content_block_stop
→
③ message_delta
stop_reason 등 최상위 변경. usage는 누적값
→
④ message_stop
스트림 끝. 중간중간 ping이 끼어들 수 있다

델타 타입은 text_delta, input_json_delta, thinking_delta, signature_delta(thinking 블록이 닫히기 직전에 한 번)다. 도구 입력은 partial_json 문자열 조각으로 오고, 최종 tool_use.input만 객체다. 조각 하나하나는 올바른 JSON이 아니므로 content_block_stop까지 이어 붙인 뒤 파싱하거나 SDK 도우미를 쓴다. 문서는 버전 정책상 새 이벤트 타입이 추가될 수 있으니 모르는 이벤트는 무시하고 넘어가도록 짜라고 한다.

with client.messages.stream( model="claude-sonnet-5-5", max_tokens=32000, tools=TOOLS, messages=history, ) as stream: for text in stream.text_stream: chat_ui.append(text) # 화면엔 조각을 바로 그린다 final = stream.get_final_message() # 블록·서명이 다 조립된 Message history.append({"role": "assistant", "content": final.content})
시험 판단 축
  • 스트림은 200 응답 뒤에도 실패할 수 있다. 과부하 때는 event: error에 overloaded_error가 실려 오는데, 비스트리밍이었다면 HTTP 529였을 오류다. 상태 코드만 보는 재시도 로직은 이것을 못 잡는다
  • 끊긴 스트림을 이어 받을 때, Claude 4.6 이후 모델은 받은 부분을 어시스턴트 프리필이 아니라 "이어서 써 달라"는 사용자 메시지에 담아 다시 요청한다. tool_use·thinking 블록은 부분 복구가 안 되고 마지막 텍스트 블록부터 이어 갈 수 있다
  • 이벤트를 직접 다룰 필요가 없으면 SDK의 누적 도우미(Python get_final_message(), TypeScript finalMessage())로 완성된 Message만 받는다
06

이미지와 파일: 인라인, URL, file_id

Vision inputs and the Files API

이미지 블록의 source는 base64, url, file 세 가지다. 형식은 JPEG·PNG·GIF·WebP이고, 애니메이션은 첫 프레임만 쓴다. 이력을 매 요청 다시 보내므로 base64 이미지는 턴마다 바이트 전체가 다시 실린다. 대화가 길어질수록 요청이 커지고 느려진다.

한도 (Claude API 기준)값
요청당 이미지 수컨텍스트 창이 200k인 모델(예: Haiku 4.5)은 100장, 그 밖의 모델은 600장
이미지 크기최대 8000×8000px. 한 요청에 이미지가 20장을 넘으면 더 엄격한 픽셀 한도가 모든 이미지에 걸린다(긴 변 3,000px 이하로 줄이면 안전)
이미지 한 장 용량base64 기준 10MB. Amazon Bedrock은 5MB
요청 전체 크기Messages 128MB. 이미지 수보다 이 한도에 먼저 닿을 수 있다

예를 들어 중고차 검수 앱이 차량 한 대당 사진 140장을 한 요청에 넣어야 한다면, 200k 컨텍스트 모델로는 100장 한도에 걸리므로 600장 한도의 모델을 고르거나 요청을 나눈다. 같은 사진을 여러 턴에 걸쳐 다룬다면 Files API로 한 번 올리고 file_id로 참조해 요청 크기를 작게 유지한다.

file_id가 해 주지 않는 것

file_id를 써도 이력에서 그 블록을 빼면 Claude는 이미지를 볼 수 없다. 참조 블록 자체는 매 요청 이력에 남아 있어야 하고, 파일 내용은 매번 입력 토큰으로 과금된다. 줄어드는 것은 전송 바이트이지 토큰 비용이 아니다.

Files API에서 알아 둘 것

Files API는 정식(GA) 기능이라 베타 헤더가 필요 없다. 파일은 워크스페이스 단위로 공유되므로 최종 사용자가 보낸 file_id를 받아 쓰면 안 되고, 테넌트별로 워크스페이스를 나눈다. 파일당 500MB, 조직당 1TB. Bedrock과 Google 관리형 Google Cloud에서는 Files API와 URL 소스를 쓸 수 없다.

07

클라우드 플랫폼으로 부를 때 달라지는 것

Model addressing, versions, clients

요청 본문의 모양은 거의 같지만, 모델을 어디에 적는지, API 버전을 헤더로 보내는지 본문으로 보내는지, 어떤 SDK 클라이언트를 쓰는지가 다르다.

플랫폼모델 지정·버전클라이언트·특이점

파트너 운영 플랫폼의 공통점

Bedrock과 Google 관리형 Google Cloud는 Message Batches, Files API, URL 소스, 일부 서버 도구, Claude Managed Agents를 지원하지 않는다. 캐시는 조직 단위로만 격리되고, 요청 크기 한도도 더 작다(Bedrock 20MB, Google 관리형 30MB). 리전 고정 엔드포인트는 글로벌보다 10% 비싸다. 모델 폐기 일정도 각 클라우드가 따로 정하므로, 수명주기 날짜는 그 플랫폼 문서에서 확인한다.

Message Batches: 제출, 폴링, 결과 회수

Batch lifecycle, limits, billing

Message Batches API는 Messages 요청 여러 개를 묶어 비동기로 처리하고, 모든 사용량을 표준 가격의 50%로 청구한다(Opus 5.5 기준 입력 $4→$2, 출력 $20→$10 / MTok). 대부분 1시간 안에 끝난다. 요청마다 custom_id와 일반 Messages 파라미터인 params를 넣는다.

① CREATE
batches.create. 배치 id를 저장
→
② IN_PROGRESS
processing_status가 in_progress로 시작
→
③ POLL
batches.retrieve를 주기적으로 호출
→
④ ENDED
모든 요청이 끝나 결과가 준비됨
→
⑤ RESULTS
results_url의 .jsonl을 스트리밍으로 읽음
batch = client.messages.batches.create(requests=[ {"custom_id": f"rv-{r.id}", # 1~64자, 영숫자·-·_ "params": {"model": "claude-haiku-5-5", "max_tokens": 300, "system": LABEL_RULES, "messages": [{"role": "user", "content": r.text}]}} for r in pending_reviews ]) store.save("review_batch", batch.id) # 재시작해도 이어서 폴링 while client.messages.batches.retrieve(batch.id) \ .processing_status != "ended": time.sleep(60) for e in client.messages.batches.results(batch.id): if e.result.type == "succeeded": save_label(e.custom_id, e.result.message) else: # errored·canceled·expired retry_queue.add(e.custom_id) # 이 셋은 과금 없음
항목문서 기준 값
크기 한도요청 100,000개 또는 256MB 중 먼저 닿는 쪽
만료24시간 안에 처리되지 못한 요청은 expired. 수요가 많으면 만료가 늘 수 있다
결과 보관배치 생성 시각(created_at)부터 29일. 그 뒤에도 배치는 보이지만 결과는 못 받는다
결과 순서보장되지 않는다. 반드시 custom_id로 짝을 맞춘다
결과 타입·과금succeeded만 과금. errored·canceled·expired는 과금되지 않는다
취소취소 직후 canceling, 끝나면 ended이고 이미 처리된 부분 결과가 남을 수 있다. 제출한 배치는 수정할 수 없다
범위워크스페이스 단위로 격리. 같은 워크스페이스의 요청과 권한 있는 사용자만 조회
거부되는 파라미터stream: true(결과가 파일로 옴), speed(fast mode), fallbacks, max_tokens: 0. 도구·서버 도구·시스템 메시지·다중 턴·thinking·이미지는 배치 가능

배치에서 pause_turn이 오면 그 턴은 끝나지 않은 것이다. 멈춘 어시스턴트 콘텐츠를 담아 후속 요청(배치든 동기든)으로 이어 간다. 배치는 Claude API, Claude Platform on AWS, Anthropic 관리형 Google Cloud에서 쓸 수 있다.

배치냐 실시간이냐, 그리고 배치 안의 캐싱

Is anyone waiting for the reply?

판단 질문은 하나다. 그 응답을 지금 누가 기다리고 있는가. 사람이 화면 앞에 있거나 다음 단계가 응답에 막혀 있으면 실시간 Messages API, 결과가 몇 시간 뒤에 와도 되면 배치다.

기준실시간 Messages APIMessage Batches
지연즉시 응답, 스트리밍 가능대부분 1시간 안, 최대 24시간
가격표준 가격50% (캐시 할인과 중첩)
맞는 일채팅, 대화형 에이전트, 사용자 요청 처리대량 평가, 콘텐츠 분류·모더레이션, 상품 설명 대량 생성, 야간 요약

배치에서도 프롬프트 캐싱을 쓸 수 있지만, 요청이 동시에 순서 없이 처리되므로 캐시 적중은 최선 노력(best-effort)이다. 문서는 트래픽 패턴에 따라 30~98% 적중을 보인다고 한다. 적중률을 올리는 방법도 문서에 있다.

  • 모든 요청에 똑같은 cache_control 블록을 넣고, 공유 내용을 최대한 접두사에 모은다
  • 배치는 5분을 넘기기 쉬우므로 1시간 캐시를 쓴다
  • 공유 접두사와 1시간 캐시 블록을 가진 요청 하나짜리 배치를 먼저 보내 캐시를 써 두고, 그것이 끝나면 나머지를 제출한다. 배치 안에서 max_tokens: 0으로 미리 데우는 방식은 거부된다
지출 한도

배치는 처리량이 높고 동시에 돌기 때문에 워크스페이스에 설정한 지출 한도를 약간 넘을 수 있다고 문서에 적혀 있다. 대량 배치를 계획할 때 한도에 여유를 둔다.

시험 함정 · 흔한 오해

오해세 번째 턴에서 "아까 보낸 사진"이라고 하면 Claude가 첫 턴의 이미지를 기억해 답한다.
사실API는 무상태다. 이미지 블록(또는 file_id 참조)이 이번 요청의 이력 안에 다시 들어 있어야 보인다.
오해thinking 블록은 표시용이니 도구 결과를 돌려보낼 때 걸러 내도 된다.
사실최신 어시스턴트 메시지의 thinking 블록은 받은 그대로 돌려보내야 한다. 수정·재배열·필터링하면 400 오류가 난다.
오해input_json_delta가 올 때마다 json.loads로 도구 인자를 꺼낼 수 있다.
사실조각은 부분 JSON 문자열이다. content_block_stop까지 이어 붙인 뒤 파싱하거나 SDK 누적 도우미를 쓴다.
오해배치에서 실패하거나 만료된 요청도 할인된 배치 요금이 청구된다.
사실succeeded만 과금된다. errored·canceled·expired는 청구되지 않는다.
오해배치의 모든 요청이 같은 캐시 시스템 프롬프트를 쓰면 거의 매번 캐시가 맞는다.
사실동시·무순서 처리라 적중은 최선 노력이다. 1시간 캐시와, 캐시를 먼저 써 두는 요청 하나짜리 배치로 적중률을 끌어올린다.
오해HTTP 200이 왔으면 정상 응답이다.
사실거절(stop_reason: "refusal")도 200으로 오고, 스트림은 200 뒤에 error 이벤트로 실패할 수 있다. 정지 사유와 이벤트 타입을 확인한다.
