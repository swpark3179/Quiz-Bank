도구를 많이 줄수록 에이전트가 유능해질 것 같지만, 실제로는 턴마다 비교할 후보가 늘어 선택이 흔들리고 자기 역할 밖의 도구를 집어 드는 일이 생긴다. 각 에이전트에는 역할에 필요한 도구만 주고, 다른 역할의 일이 자주 필요하면 좁게 잘린 도구 하나로만 연다. 뒷부분은 호출 자체를 제어하는 tool_choice와, 2026년 10월 현재 일부 모델에서 강제 호출이 막혀 있다는 점을 다룬다.

습득 포인트
  • 도구 수가 늘 때 선택 신뢰도가 떨어지는 이유와 역할 밖 도구의 오용
  • Agent SDK·Claude Code의 서브에이전트 도구 범위(tools, disallowedTools)와 allowedTools의 차이
  • 범용 도구를 제약형 도구로 바꾸기, 좁은 교차 역할 도구 제공
  • tool_choice의 auto · any · tool · none과 disable_parallel_tool_use
  • 첫 호출을 강제한 뒤 후속 턴에서 풀어 주는 패턴과 현재 모델 제약
01

도구가 많을수록 선택이 흔들린다

More tools, worse choices

Claude는 턴마다 등록된 도구 정의를 읽고 고른다. 후보가 늘면 비슷한 도구끼리 구분하기 어려워지고, 정의 자체가 컨텍스트를 차지한다. Agent SDK의 tool search 문서는 도구 50개의 정의가 10~20K 토큰을 쓰고, 한 번에 30~50개를 넘게 실으면 선택 정확도가 떨어진다고 적는다. Advanced tool use 글도 큰 도구 라이브러리에서 가장 흔한 실패로 잘못된 도구 선택과 틀린 파라미터를 꼽는다.

역할 밖의 도구는 오용을 부른다. 넘겨받은 자료로 보고서를 써야 할 종합(synthesis) 에이전트에게 웹 검색을 주면, 직접 검색을 시작해 범위를 넓히고 출처 관리가 흐트러진다. 프롬프트로 "검색은 자제하라"고 해도 도구가 손에 있는 한 확률적으로 쓰인다.

시험 가이드 표현 vs 현재 문서

시험 가이드는 "18개 대신 4~5개"를 예로 든다. 현재 문서의 수치는 "30~50개를 넘으면 정확도 저하"(Agent SDK tool search)이고, 도구가 매우 많을 때 정의를 미리 다 싣지 않고 필요할 때 검색해 불러오는 tool search가 Agent SDK에서 기본으로 켜져 있다. 숫자는 다르지만 결론은 같다. 한 에이전트가 한 번에 비교하는 도구를 줄이는 것이다. tool search는 컨텍스트와 대규모 카탈로그 문제를 덜어 줄 뿐이므로 역할에 맞는 범위는 여전히 설계자가 정한다.

02

역할별로 도구 범위 정하기

Scope tools per role

예: 시장 조사 시스템을 코디네이터와 세 서브에이전트로 나눈다.

에이전트줄 도구주지 않을 도구이유
코디네이터Agent(서브에이전트 호출)웹 검색, 파일 편집직접 일하지 않고 분해·위임·통합
searcherweb_search, fetch_source파일 쓰기출처 수집과 발췌만
analystRead, Grep, parse_pdf웹 검색, 편집넘겨받은 문서 분석
writerWrite, verify_claim웹 검색, fetch_source받은 자료로만 작성, 사실 확인은 좁은 도구로
agents = { "searcher": AgentDefinition( description="외부 공개 자료를 찾아 출처 URL과 발췌를 돌려준다", prompt="...", tools=["mcp__web__search", "mcp__web__fetch_source"]), # 허용 목록 "analyst": AgentDefinition( description="수집된 PDF·문서를 분석한다", prompt="...", disallowedTools=["mcp__web", "Write", "Edit"]), # 거부 목록 (서버 단위 가능) "writer": AgentDefinition( description="코디네이터가 준 자료만으로 보고서 초안을 쓴다", prompt="...", tools=["Write", "mcp__factcheck__verify_claim"]), } options = ClaudeAgentOptions(agents=agents, allowed_tools=["Agent"]) # 자동 승인일 뿐
가용성(availability)과 권한(permission)은 다른 층이다 — Agent SDK custom tools 문서
옵션층효과
AgentDefinition tools가용성나열한 도구만 서브에이전트 세션에 존재. 빠진 도구는 아예 없어 시도도, 권한 프롬프트도 없다. 생략하면 서브에이전트가 쓸 수 있는 도구를 모두 물려받는다
disallowedTools (맨 이름, mcp__server)가용성해당 도구나 서버의 도구 전체를 컨텍스트에서 뺀다
allowedTools권한나열한 도구를 묻지 않고 실행한다. 다른 도구를 막지 않는다
범위 규칙 Bash(rm *) 등권한도구는 보이고 일치하는 호출만 거부. 시도하느라 턴을 낭비할 수 있다
이름 변경과 생성 제한

Claude Code 2.1.63에서 Task 도구가 Agent로 바뀌었다. 기존 Task(...) 표기는 별칭으로 계속 동작하고, SDK의 system:init 도구 목록에는 여전히 "Task"로 나오므로 감지 코드는 두 이름을 모두 확인하라는 것이 문서 안내다. claude --agent로 메인 스레드에서 도는 에이전트는 tools: Agent(worker, researcher)처럼 생성할 수 있는 서브에이전트 종류를 허용 목록으로 제한할 수 있다.

03

제약형 도구와 좁은 교차 역할 도구

Constrained and cross-role tools

fetch_url(url), run_sql(query), http_request(method, url, body) 같은 범용 도구는 무엇이든 할 수 있다는 점이 문제다. 에이전트가 의도 밖의 대상에 접근할 수 있고, 설명만으로는 언제 써야 하는지 경계를 긋기 어렵다. 역할에 필요한 동작만 하는 도구로 바꾼다. Writing tools for agents도 API를 그대로 감싼 도구보다 영향이 큰 특정 워크플로를 겨냥한 소수의 도구를 권하고, 멀티에이전트 리서치 글은 에이전트에게 "범용 도구보다 전문 도구를 우선하라"는 휴리스틱을 줬다고 한다.

BAD · 무엇이든 되는 범용 도구
http_request(method, url, body)

배송 조회 에이전트가 사내 관리 API까지 부를 수 있다. 설명에 쓸 "언제"가 없다.

GOOD · 역할에 맞춘 제약형 도구
shipping_get_status(tracking_no) - 형식 검사: ^[A-Z]{2}\d{9}KR$ - 내부에서 배송사 API 한 곳만 호출 - 반환: {status, last_scan_at, location}

입력 검증과 접근 대상이 도구 안에 고정된다.

교차 역할 도구는 반대 방향의 문제를 푼다. writer가 문장 하나의 근거를 확인하려고 매번 코디네이터를 거치면 왕복이 많아진다. 이런 잦고 단순한 필요에는 이미 수집된 출처 안에서만 확인해 supported / unsupported / unclear만 돌려주는 verify_claim(claim, source_id) 같은 좁은 도구를 준다. 새 자료가 필요하거나 출처끼리 충돌하는 복잡한 경우는 writer가 직접 풀지 않고 코디네이터에 돌려보내 searcher에게 재위임하게 한다.

필요처리
이미 모은 출처로 문장 하나 확인 (잦음 · 단순)writer의 verify_claim
새 출처 탐색, 출처 간 충돌 해결 (드묾 · 복잡)코디네이터 → searcher 재위임
04

tool_choice: 맡길지, 요구할지, 막을지

auto · any · tool · none
값의미기본값일 때쓰는 때
{"type": "auto"}도구를 부를지 말지 Claude가 판단tools가 있을 때대부분의 에이전트 턴
{"type": "any"}도구 하나는 반드시 부르되, 어느 것인지는 Claude가 선택—텍스트 답이 허용되지 않는 턴 (예: 모든 응답이 라우팅 도구 중 하나여야 할 때)
{"type": "tool", "name": "…"}지정한 도구를 반드시 호출—특정 단계를 먼저 실행해야 할 때
{"type": "none"}도구 호출 금지tools가 없을 때도구 정의는 둔 채 이번 턴은 텍스트로만

any나 tool이면 API가 assistant 메시지를 미리 채워 도구 호출을 강제한다. 그래서 요청해도 tool_use 블록 앞에 설명 텍스트가 나오지 않고, 강제를 받아들이는 모델에서도 thinking을 건너뛴다. 설명이나 사고 과정이 필요하면 auto에 "get_x 도구를 써서 답해" 같은 지시를 사용자 메시지로 넣는다.

병렬 호출은 tool_choice 안의 disable_parallel_tool_use: true로 끈다(최상위 파라미터가 아니다). auto와 함께면 응답당 도구 호출이 최대 하나, any·tool과 함께면 정확히 하나다. 또 tool_choice를 바꾸면 프롬프트 캐시의 메시지 블록이 무효화된다(도구 정의와 시스템 프롬프트 캐시는 유지).

05

첫 호출을 강제하고, 다음 턴에 풀어 준다

Force first, then release

계약서 처리 에이전트가 어떤 보강(enrichment) 도구보다 먼저 extract_metadata를 실행해야 한다고 하자. 강제 호출을 지원하는 모델이라면 첫 요청에만 그 도구를 지정하고, 결과를 돌려준 뒤 이어지는 요청은 auto로 되돌린다. 매 턴 강제하면 에이전트는 같은 도구만 계속 불러야 해서 보강 도구로 넘어가지도, 텍스트로 끝내지도 못한다.

# 1턴: 메타데이터 추출을 강제 (강제 호출을 지원하는 모델에서) r1 = client.messages.create(model=MODEL, max_tokens=1024, tools=TOOLS, messages=msgs, tool_choice={"type": "tool", "name": "extract_metadata"}) msgs += [{"role": "assistant", "content": r1.content}, {"role": "user", "content": run_tools(r1)}] # tool_result 블록들 # 2턴부터: 어떤 보강 도구를 쓸지는 Claude에게 r2 = client.messages.create(model=MODEL, max_tokens=1024, tools=TOOLS, messages=msgs, tool_choice={"type": "auto"})
시험 가이드 표현 vs 현재 문서

시험 가이드는 강제 선택({"type": "tool", …})과 "any"를 도구 호출 보장 수단으로 다룬다. 2026년 10월 현재 문서 기준으로 Claude Opus 5.5, Claude Sonnet 5.5, Claude Fable 5.1, Claude Mythos 5.1은 any와 tool을 지원하지 않으며, 보내면 토큰 카운팅 요청까지 포함해 400 invalid_request_error가 난다. 수동 extended thinking(thinking: {type: "enabled"})을 켠 요청도 any·tool을 받지 않는다. 이런 경우 문서는 auto + strict tool use(입력의 스키마 준수 보장)로 쓰고 프롬프트로 원하는 도구를 유도하거나, 응답 자체가 고정 JSON이어야 하면 structured outputs를 쓰라고 안내한다. thinking이 기본으로 켜진 Claude Opus 5 같은 모델은 강제 호출을 받아들이되, 그때는 thinking 없이 도구 호출로 바로 시작한다.

시험 판단 기준
  • "어떤 도구든 반드시 하나" → any · "반드시 이 도구" → tool · "이번 턴은 도구 금지" → none
  • 순서 보장이 필요하면 첫 턴만 강제하고 이후는 auto
  • 강제 호출을 받지 않는 모델이면 auto + strict + 명시적 지시. 반드시 지켜야 하는 순서라면 첫 호출이 기대한 도구인지 코드에서 검사해 다시 요청하는 애플리케이션 측 게이트를 더한다(설계 선택)
  • 역할 밖 도구 오용은 tool_choice가 아니라 도구 범위로 푼다

시험 함정 · 흔한 오해

오해모든 에이전트에게 같은 전체 도구 세트를 주는 편이 유연하고 안전하다.
사실후보가 늘수록 선택 정확도가 떨어지고, 역할 밖 도구를 오용한다. 역할별로 범위를 좁힌다.
오해allowedTools에 넣지 않은 도구는 에이전트가 쓸 수 없다.
사실allowedTools는 자동 승인 목록(권한 층)이다. 도구를 컨텍스트에서 빼려면 tools나 맨 이름의 disallowedTools를 쓴다.
오해tool_choice: any는 특정 도구를 강제한다.
사실any는 "어떤 도구든 하나"다. 특정 도구는 {"type": "tool", "name": …}로 지정한다.
오해강제 호출은 모든 모델과 설정에서 동작한다.
사실현재 Opus 5.5·Sonnet 5.5·Fable 5.1·Mythos 5.1과 수동 extended thinking 요청은 any·tool에 400 오류를 낸다.
오해강제 호출을 해도 Claude가 먼저 이유를 설명한 뒤 도구를 부른다.
사실API가 응답을 미리 채워 텍스트 없이 tool_use부터 시작하고 thinking도 건너뛴다.

Q1역할 밖 도구
고객 상담 시스템에서 상담 기록을 요약해 CRM에 남기는 요약 에이전트가 모든 에이전트와 같은 도구 세트를 받았다. 어느 날 요약 도중 이 에이전트가 cancel_order를 실행했다. 다만 요약 중에 주문 상태를 확인할 일은 자주 있다.가장 알맞은 설계 변경은?
정답 (C)

역할 밖 도구는 범위에서 빼고, 잦은 단순 필요만 좁은 교차 역할 도구로 연다. 실제 처리는 코디네이터를 거친다. A는 확률적 억제일 뿐 도구는 여전히 손에 있고, B는 오용 가능성을 그대로 둔다. D는 상태 확인과 CRM 기록 도구까지 막는다.

Q2tool_choice 의미
tool_choice: {"type": "any"}의 의미는?
정답 (A)

any는 "반드시 도구를 쓰되 선택은 자유"다. B는 tool, C는 auto, D는 none의 설명이다.

Q3첫 호출 강제
의료비 영수증 처리 에이전트는 먼저 detect_document_type으로 문서 종류를 판별하고, 그 결과에 따라 parse_pharmacy_receipt나 parse_hospital_bill 중 하나를 써야 한다. 사용하는 모델은 강제 호출을 지원한다.가장 알맞은 방법은?
정답 (D)

첫 단계만 강제하고 이후 선택은 Claude에게 맡긴다. A는 매 턴 같은 도구만 불러 파싱 단계로 넘어가지 못하고, B는 순서를 보장하지 않는다. C는 어떤 도구든 부르게 할 뿐 판별을 먼저 하도록 정하지 못한다.

Q4강제 호출 제약
팀이 분류 파이프라인의 모델을 Claude Sonnet 5.5로 바꾼 뒤, tool_choice: {"type": "any"}를 쓰던 요청이 모두 400 오류를 낸다.올바른 진단과 대응은?
정답 (B)

현재 문서상 Sonnet 5.5는 강제 도구 호출을 받지 않으며, 문서가 제시하는 대안은 auto + strict + 지시, 또는 structured outputs다. A와 C는 원인과 무관하고, D의 tool도 같은 이유로 거부된다.

Q5가용성 vs 권한
