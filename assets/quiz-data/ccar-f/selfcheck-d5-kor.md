## 문제 1
### **상담 봇은 대화가 20턴을 넘으면 앞부분을 요약으로 바꾼다. 30턴째 고객이 "아까 말한 48,200원 환급은 언제 돼요?"라고 묻자, 요약에 "일부 환급 약속"만 남아 있어 봇이 금액과 날짜를 답하지 못했다. 가장 적절한 개선은?**

| 보기 | 설명 |
|------|------|
| 1. 요약 시작 시점을 40턴으로 늦춘다 | |
| **2. 금액·날짜·약속·주문번호를 case facts 블록으로 뽑아 요약과 별도로 매 요청에 넣는다** | |
| 3. 요약 프롬프트에 "더 간결하게"를 추가한다 | |
| 4. 더 큰 컨텍스트 창을 가진 모델로 바꾼다 | |

**정답: 2.**

**해설:**

> 📘 레슨 5.1 · 핵심 정보 보존 — case facts

> **핵심:** 금액·날짜·약속 같은 거래성 사실은 요약하지 말고, 요약과 분리된 구조화 블록으로 매 요청에 넣습니다.

1. **오답** - 요약 시작을 40턴으로 늦춰도 요약이 도는 순간 같은 손실이 생깁니다. 그동안 컨텍스트가 길어지며 recall이 떨어지는 context rot도 겪습니다.
2. **정답** - case facts 블록은 앱이 도구 결과와 확정된 발언에서 값을 뽑아 관리하고, 요약되는 이력과 섞지 않은 채 system 프롬프트나 매 요청의 고정 위치에 넣습니다. 이력이 몇 번 요약되든 "48,200원"과 환급 날짜는 원래 값 그대로 남습니다. 이슈가 여럿이면 이슈마다 항목을 나눠 서로 섞이지 않게 합니다.
3. **오답** - "더 간결하게"는 요약이 구체적인 값을 더 많이 일반화하게 만듭니다. 문제를 악화시키는 방향입니다.
4. **오답** - 창이 커도 앱이 이력을 요약으로 바꾸는 한 값은 사라집니다. 손실 시점을 늦출 뿐입니다.

## 문제 2
### **반품 에이전트가 턴마다 주문 조회 도구를 부르는데, 응답이 45개 필드의 JSON이다. 대화가 길어질수록 비용이 급증하고, 답변에 반품과 무관한 필드가 섞여 나온다. 가장 적절한 조치는?**

| 보기 | 설명 |
|------|------|
| 1. 주문 조회 도구를 없앤다 | |
| 2. `max_tokens`를 줄인다 | |
| 3. system 프롬프트에 "관련 필드만 참고하라"를 추가한다 | |
| **4. 도구 결과를 이력에 넣기 전에 반품 판단에 필요한 필드만 남긴다** | |

**정답: 4.**

**해설:**

> 📘 레슨 5.1 · 핵심 정보 보존 — 도구 결과

> **핵심:** 도구 결과는 이력에 들어가는 순간부터 이후 모든 요청에 다시 실리므로, 넣기 전에 필요한 필드만 남깁니다.

1. **오답** - 주문 조회는 반품 판단에 필요한 정보의 출처입니다. 도구를 없애면 판단 근거 자체가 사라집니다.
2. **오답** - `max_tokens` 는 응답 출력의 상한입니다. 입력에 쌓이는 도구 결과의 크기와는 무관합니다.
3. **오답** - 지시를 넣어도 45개 필드는 그대로 컨텍스트에 쌓이므로 비용이 줄지 않고, 모델이 무관한 필드에 주의를 빼앗기는 문제도 남습니다.
4. **정답** - 앱 코드에서 응답을 파싱해 주문번호·금액·반품 기한처럼 반품 판단에 필요한 필드만 `tool_result` 로 넣으면, 이후 모든 요청의 입력이 작아지고 답변에 무관한 필드가 섞일 여지도 줄어듭니다. 이미 처리한 오래된 결과는 context editing의 tool result clearing으로 정리하는 방법을 함께 쓸 수 있습니다.

## 문제 3
### **Messages API로 만든 챗봇이 두 번째 요청에서 첫 질문의 맥락을 전혀 모른다. 가장 가능성 높은 원인은?**

| 보기 | 설명 |
|------|------|
| **1. 두 번째 요청의 `messages`에 이전 user·assistant 메시지를 넣지 않았다** | |
| 2. 서버 쪽 대화 세션이 만료됐다 | |
| 3. system 프롬프트가 너무 짧다 | |
| 4. 첫 응답의 `stop_reason`이 `end_turn`이었다 | |

**정답: 1.**

**해설:**

> 📘 레슨 5.1 · 핵심 정보 보존 — stateless

> **핵심:** Messages API는 상태를 저장하지 않으므로, 이전 대화는 앱이 매 요청의 `messages` 에 다시 넣어야 합니다.

1. **정답** - 공식 문서는 Messages API가 stateless라서 항상 전체 대화 이력을 보낸다고 설명합니다. 이전 user·assistant 메시지가 두 번째 요청에 없으면 모델은 첫 질문을 본 적이 없는 것과 같습니다. 이전 턴이 꼭 Claude가 만든 것일 필요도 없어서, 합성 assistant 메시지를 넣을 수도 있습니다.
2. **오답** - Messages API에는 대화를 보관하는 서버 측 세션이 없으므로 만료될 세션도 없습니다.
3. **오답** - system 프롬프트 길이는 이전 대화 내용이 모델에 전달되는지와 무관합니다.
4. **오답** - `end_turn` 은 모델이 응답을 자연스럽게 마쳤다는 정상 종료 신호일 뿐, 다음 요청의 맥락에는 영향을 주지 않습니다.

## 문제 4
### **리서치 코디네이터가 서브에이전트 10개의 보고서를 순서대로 이어 붙여 종합한다. 중간에 놓인 보고서들의 발견이 최종 보고서에서 자주 빠진다. 가장 적절한 개선은?**

| 보기 | 설명 |
|------|------|
| 1. 실행할 때마다 보고서 순서를 무작위로 섞는다 | |
| 2. 보고서 10개를 한 문단으로 압축해 합친다 | |
| **3. 입력 맨 앞에 보고서별 핵심 발견 요약을 두고, 각 보고서를 출처가 붙은 명시적 섹션으로 나누며, 지시는 끝에 둔다** | |
| 4. 컨텍스트 창이 더 큰 모델로 바꾼다 | |

**정답: 3.**

**해설:**

> 📘 레슨 5.1 · 핵심 정보 보존 — 위치 효과

> **핵심:** 긴 집계 입력에서는 중간 내용이 빠지기 쉬우므로, 핵심 요약을 앞에 두고 섹션을 명시적으로 나누며 지시는 끝에 둡니다.

1. **오답** - 순서를 섞으면 누락이 매번 다른 보고서로 옮겨 갈 뿐, 중간에 놓이는 보고서는 계속 생깁니다.
2. **오답** - 보고서 열 개를 한 문단으로 압축하면 수치·출처 같은 세부가 사라져 종합의 품질이 떨어집니다.
3. **정답** - 앞쪽의 핵심 발견 요약은 중간 보고서의 결론을 입력 앞부분에 한 번 더 놓습니다. 공식 프롬프팅 가이드도 긴 문서는 프롬프트 위쪽에, 질문·지시는 끝에 두고, 문서마다 `<document>` 태그와 `<source>` 같은 메타데이터 하위 태그로 감싸라고 권합니다.
4. **오답** - 창이 커져도 토큰이 늘수록 recall이 떨어지는 context rot은 그대로이며, 중간 위치가 약하다는 문제를 해결하지 않습니다.

## 문제 5
### **하위 에이전트들이 추론 과정을 포함한 3,000단어 서술을 반환한다. 종합 에이전트는 컨텍스트 예산이 빠듯하고, 최종 보고서에 기준일이 불분명한 오래된 통계가 최신처럼 인용됐다. 어디를 어떻게 바꾸는 것이 가장 적절한가?**

| 보기 | 설명 |
|------|------|
| 1. 종합 에이전트가 받은 서술을 다시 요약하게 한다 | |
| 2. 하위 에이전트에게 더 자세히, 더 길게 쓰라고 지시한다 | |
| 3. 종합 단계를 없애고 서술을 그대로 이어 붙여 낸다 | |
| **4. 하위 에이전트가 핵심 사실·수치·기준일·출처 위치·관련도를 구조화해 반환하도록 출력 형식을 바꾼다** | |

**정답: 4.**

**해설:**

> 📘 레슨 5.1 · 핵심 정보 보존 — 핸드오프 형식

> **핵심:** 하류 에이전트의 컨텍스트 예산이 빠듯하면, 상류 에이전트의 출력 형식을 구조화된 사실과 메타데이터로 바꿉니다.

1. **오답** - 받은 서술을 다시 요약하면 압축 단계가 하나 더 생겨 기준일·출처 같은 정보가 더 사라집니다.
2. **오답** - 더 길게 쓰게 하면 종합 에이전트의 빠듯한 예산을 더 압박합니다. 문제는 양이 아니라 형식입니다.
3. **오답** - 종합 없이 서술을 이어 붙이면 3,000단어짜리 서술이 그대로 나가 독자가 직접 종합해야 하고, 기준일 문제도 해결되지 않습니다.
4. **정답** - Anthropic이 설명하는 sub-agent 구조에서는 하위 에이전트가 수만 토큰을 써서 조사하더라도 1,000~2,000 토큰 정도로 압축한 결과만 돌려줍니다. 사실·수치에 기준일·출처 위치·관련도를 붙여 넘기면 종합 단계가 적은 토큰으로 시점과 출처를 보존하므로, 오래된 통계를 최신처럼 인용하는 일이 사라집니다.

## 문제 6
### **context editing의 tool result clearing(`clear_tool_uses_20250919`)에 대한 설명으로 옳은 것은?**

| 보기 | 설명 |
|------|------|
| 1. 앱이 보관한 원본 대화 이력에서도 해당 결과가 삭제된다 | |
| **2. 임계값을 넘으면 오래된 도구 결과부터 자리표시 텍스트로 바뀌므로, 나중에 필요한 값은 미리 옮겨 두거나 `exclude_tools`로 보호해야 한다** | |
| 3. 가장 최근 도구 결과부터 지운다 | |
| 4. prompt cache에는 전혀 영향을 주지 않는다 | |

**정답: 2.**

**해설:**

> 📘 레슨 5.1 · 핵심 정보 보존 — context editing

> **핵심:** tool result clearing은 서버 측에서 오래된 도구 결과부터 자리표시 텍스트로 바꾸므로, 나중에 필요한 값은 미리 옮기거나 보호해야 합니다.

1. **오답** - context editing은 프롬프트가 Claude에 도달하기 전에 서버 측에서 적용되며, 앱은 수정되지 않은 전체 대화 이력을 그대로 가집니다.
2. **정답** - 기본 설정에서는 입력이 100,000 토큰을 넘으면 작동하고(`trigger`), 최근 3개의 도구 사용·결과 쌍을 남긴 채(`keep`) 오래된 결과부터 지웁니다. 지운 자리는 자리표시 텍스트가 되므로, 나중에 필요한 값은 case facts로 옮겨 두거나 해당 도구 이름을 `exclude_tools` 에 넣어 보호합니다.
3. **오답** - 문서상 API는 가장 오래된 도구 상호작용부터 지우고 가장 최근 것을 보존합니다. 방향이 반대입니다.
4. **오답** - 내용을 지우면 캐시된 프롬프트 접두부가 무효화됩니다. 그래서 `clear_at_least` 로 한 번에 지울 최소 토큰 수를 정해, 캐시를 깨는 비용만큼 충분히 지우게 합니다.

## 문제 7
### **고객이 단말 할부 잔액 일시불 정산, 요금제 변경, 변경 후 위약금 안내를 한 번에 요청했다. 세 작업 모두 정책 문서에 절차가 있다. 에이전트의 바람직한 처리는?**

| 보기 | 설명 |
|------|------|
| 1. 단계가 많아 실수 위험이 크므로 상담원에게 이관한다 | |
| 2. 첫 번째 작업만 처리하고 나머지는 상담원에게 넘긴다 | |
| **3. 정책이 모든 단계를 다루므로 직접 순서대로 처리한다** | |
| 4. 모델이 확신도를 출력하게 해 0.8 미만이면 이관한다 | |

**정답: 3.**

**해설:**

> 📘 레슨 5.2 · 에스컬레이션 — 트리거 판단

> **핵심:** 복잡도는 이관 트리거가 아니며, 정책이 모든 단계를 다루면 에이전트가 처리합니다.

1. **오답** - 단계가 많다는 것은 정책 공백이 아닙니다. 복잡도를 기준으로 넘기면 과다 이관이 되고, 공식 고객지원 가이드가 함께 재라고 하는 자동 처리율(deflection rate)이 떨어집니다.
2. **오답** - 첫 작업만 처리하고 넘기는 것도 근거 없는 과다 이관입니다. 나머지 두 작업 역시 정책 문서에 절차가 있습니다.
3. **정답** - 할부 정산, 요금제 변경, 위약금 안내 모두 정책 문서에 절차가 있으므로 에이전트가 순서대로 처리할 범위입니다. 이관 근거는 명시적 요청, 정책의 공백·모호, 진전 불가 세 가지입니다.
4. **오답** - 모델이 스스로 보고한 확신도는 실제 정확도와 대조해 보정하지 않은 숫자라, 케이스 복잡도의 대리지표로 믿을 수 없습니다.

| **3. 백오프를 두고 제한된 횟수만 재시도하고, 그래도 실패하면 시도 내역과 부분 결과를 붙여 보고한다** | |

**해설:**

> 📘 레슨 5.3 · 오류 전파 — 로컬 복구

> **핵심:** 일시적 실패는 실패가 난 서브에이전트 안에서 제한적으로 재시도하고, 해결하지 못한 것만 맥락과 함께 올립니다.

1. **오답** - 몇 초 뒤면 풀리는 429까지 즉시 올리면 코디네이터에게 불필요한 결정을 떠넘기고 그 컨텍스트를 채웁니다.

3. **정답** - 429(rate limit)는 잠시 기다리면 풀리는 경우가 많으므로 백오프를 두고 횟수를 제한해 재시도합니다. 상한에 닿으면 시도 내역과 부분 결과를 붙여 보고해, 코디네이터가 재시도·대체 소스·공백 표시 중에서 고르게 합니다.

4. **오답** - 인증 실패는 `authentication_failed` 라는 별도 값입니다. 재시도로 풀리지 않으므로 바로 상위로 보고할 실패입니다.

## 문제 29
### **`confidence` 필드에 `"minimum": 0, "maximum": 1`을 넣은 원시 JSON 스키마를 `output_config.format`으로 보냈다. 현재 문서 기준으로 옳은 설명은?**

| 보기 | 설명 |
|------|------|
| **1. 숫자 범위 제약은 지원되지 않아 원시 스키마면 400 오류가 난다. SDK 헬퍼는 제약을 설명으로 옮기고 응답을 검증하므로 범위는 코드에서 확인한다** | |
| 2. constrained decoding이 범위를 완벽하게 강제한다 | |
| 3. 제약은 경고 없이 조용히 무시된다 | |
| 4. structured outputs는 number 타입을 지원하지 않는다 | |

**정답: 1.**

**해설:**

> 📘 레슨 5.5 · 사람 검토·신뢰도 — 스키마 제약

> **핵심:** structured outputs는 `minimum`·`maximum` 같은 숫자 범위 제약을 지원하지 않으므로, 범위 검증은 SDK 헬퍼나 앱 코드가 맡습니다.

1. **정답** - 문서의 JSON Schema 한계 목록은 숫자 제약(`minimum`, `maximum`, `multipleOf`)을 지원하지 않는 기능으로 두고, 지원하지 않는 기능을 쓰면 400 오류가 난다고 합니다. 대부분의 SDK 헬퍼는 이런 제약을 보낼 스키마에서 빼서 필드 설명에 덧붙이고, 응답을 원래 제약으로 검증합니다.
