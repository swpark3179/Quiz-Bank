## 문제 1
### **"주석이 정확한지 확인하라"는 리뷰 지시가 맞춤법, 오래된 작성자 이름, 짧은 주석까지 지적해 개발자들이 무시하기 시작했다. 가장 알맞은 수정은?**

| 보기 | 설명 |
|------|------|
| 1. "정말 중요한 것만 신중하게 지적하라"를 추가한다 | |
| **2. "주석이 말하는 동작(반환값·부수 효과·오류 조건)이 실제 코드와 모순될 때만 지적하고, 문체·맞춤법·작성자 정보는 건너뛴다"로 바꾼다** | |
| 3. 지적 개수를 PR당 3개로 제한한다 | |
| 4. 주석 리뷰를 영구히 없앤다 | |

**정답: 2.**

**해설:**

> 📘 레슨 4.1 · 명시적 기준 — 명시적 기준

> **핵심:** 정밀도는 태도 지시가 아니라 **보고할 범주·건너뛸 범주·그 경계 조건을 적은 명시적 기준** 에서 나옵니다.

1. **오답** - "정말 중요한 것만 신중하게"는 무엇이 문제인지에 대한 모델의 정의를 바꾸지 않는 태도 지시입니다. 맞춤법이나 작성자 이름을 문제로 보는 판단은 그대로 남고, 확신 문턱만 올라가 진짜 문제까지 덜 보고될 수 있습니다.
2. **정답** - 보고 범주(반환값·부수 효과·오류 조건이 코드와 모순)와 건너뛸 범주(문체·맞춤법·작성자 정보)를 명시해 "주석이 정확한가"라는 모호한 지시를 확인 가능한 기준으로 바꿉니다. Opus 4.8 가이드가 권하듯 "중요한" 같은 질적 표현 대신 기준선을 구체적으로 적은 형태입니다.
3. **오답** - 개수 제한은 어떤 지적이 남을지 통제하지 못합니다. 맞춤법 지적 3개가 남고 진짜 동작 불일치가 잘려 나갈 수도 있습니다.
4. **오답** - 주석 리뷰를 없애면 "읽기 전용"이라고 적힌 함수가 실제로는 DB에 기록하는 것 같은 가치 있는 범주까지 버리게 됩니다. 문제는 범주 자체가 아니라 기준의 모호함입니다.

## 문제 2
### **오탐을 줄이려고 리뷰 프롬프트에 "be conservative, only report high-confidence findings"를 넣었다. 오탐은 조금 줄었지만, 나중에 장애로 이어진 off-by-one 버그를 리뷰가 놓쳤다. 현재 문서 기준으로 가장 그럴듯한 설명과 대응은?**

| 보기 | 설명 |
|------|------|
| 1. 모델의 버그 탐지 능력이 떨어졌다 → 더 큰 모델로 바꾼다 | |
| 2. 지시가 너무 약했다 → "extremely conservative"로 강화한다 | |
| 3. 프롬프트가 너무 길다 → 기준을 모두 지운다 | |
| **4. 모델이 지시를 충실히 따라 문턱 아래 발견을 보고하지 않았다 → 구체적 보고 조건을 쓰거나, 찾기 단계는 모두 보고하고 거르기를 분리한다** | |

**정답: 4.**

**해설:**

> 📘 레슨 4.1 · 명시적 기준 — 태도 지시의 효과

> **핵심:** 최신 모델은 "보수적으로", "확신 높은 것만" 같은 지시를 **충실히 따라 문턱 아래 발견을 보고하지 않으므로**, 정밀도는 대체로 오르지만 재현율이 떨어질 수 있습니다.

1. **오답** - 모델 가이드는 이 현상을 능력 저하가 아닌 하네스 효과로 설명합니다. 모델은 같은 깊이로 조사하고 버그를 찾은 뒤, 지시받은 문턱 아래라고 판단한 것을 보고하지 않을 뿐입니다. 더 큰 모델도 같은 지시를 똑같이 따릅니다.
2. **오답** - "extremely conservative"로 강화하면 문턱이 더 올라가 놓치는 버그가 더 늘어납니다. 같은 문제를 키우는 처방입니다.
3. **오답** - 기준을 모두 지우면 원래의 오탐 문제로 돌아갑니다. 문제는 프롬프트 길이가 아니라 질적 문턱 표현입니다.
4. **정답** - Opus 4.8·Sonnet 5 프롬프팅 가이드가 설명하는 바로 그 현상입니다. 대응은 "잘못된 동작·테스트 실패·오해를 부르는 결과를 낳는 버그는 모두 보고"처럼 구체적 보고 조건을 쓰거나, 찾기 단계는 커버리지 위주로 모두 보고하게 하고 거르기는 별도 단계로 분리하는 것입니다.

## 문제 3
### **같은 종류의 문제(예외를 삼키는 빈 catch 블록)가 어떤 실행에서는 major, 다른 실행에서는 minor로 분류된다. 가장 효과적인 개선은?**

| 보기 | 설명 |
|------|------|
| **1. 등급마다 정의와 대표 코드 예시를 붙여, 빈 catch가 어느 등급의 앵커와 비슷한지 판단하게 한다** | |
| 2. 등급 이름을 critical/high/medium/low로 늘린다 | |
| 3. 같은 프롬프트로 세 번 돌려 다수결로 등급을 정한다 | |
| 4. 심각도 필드를 출력에서 빼 버린다 | |

**정답: 1.**

**해설:**

> 📘 레슨 4.1 · 명시적 기준 — 심각도 일관성

> **핵심:** critical·major·minor 같은 질적 이름은 해석 폭이 넓습니다. **등급마다 정의와 대표 코드 예시(앵커)** 를 붙여야 분류가 일관됩니다.

1. **정답** - 등급별 정의 한 줄과 대표 코드 예시가 비교 기준이 됩니다. 모델은 빈 catch를 각 등급의 앵커와 비교해 분류하므로 실행마다 같은 판단을 내립니다. Code Review 문서도 REVIEW.md에서 Important의 의미를 "동작을 깨거나 데이터를 유출하거나 롤백을 막는 경우"처럼 구체적으로 재정의하라고 안내합니다.
2. **오답** - 등급 이름만 늘리면 경계가 늘어날 뿐, 각 경계가 어디인지는 여전히 정의되지 않습니다. 흔들림이 오히려 커질 수 있습니다.
3. **오답** - 다수결은 흔들림을 평균낼 뿐 판단 기준을 주지 않습니다. 실행 비용도 세 배가 됩니다.
4. **오답** - 심각도를 빼면 분류 자체를 포기하는 것입니다. 리뷰어가 무엇부터 고쳐야 할지 알 수 없게 됩니다.

## 문제 4
### **리뷰 봇의 "성능 개선 제안" 범주는 지적 대부분이 무시되고, 최근에는 정확도가 높은 "권한 검사 누락" 지적까지 그냥 닫히고 있다. 가장 알맞은 단기 조치는?**

| 보기 | 설명 |
|------|------|
| 1. 봇 전체를 끄고 사람 리뷰로 돌아간다 | |
| 2. 모든 범주에 "확실한 것만"을 추가한다 | |
| **3. 성능 범주를 일시 중지하고 그 범주의 기준을 다시 쓴 뒤 평가 사례로 확인하고 재개한다. 나머지 범주는 유지한다** | |
| 4. 권한 검사 범주의 지적을 더 길게 설명하게 한다 | |

**정답: 3.**

**해설:**

> 📘 레슨 4.1 · 명시적 기준 — 신뢰 회복

> **핵심:** 오탐이 높은 범주 하나가 **정확한 범주의 신뢰까지 깎습니다.** 문제 범주만 일시 중지하고, 기준을 고쳐 평가로 확인한 뒤 재개합니다.

1. **오답** - 봇 전체를 끄면 정확도가 높은 "권한 검사 누락" 같은 가치 있는 범주까지 버리게 됩니다. 문제는 한 범주에 몰려 있습니다.
2. **오답** - "확실한 것만"을 모든 범주에 넣으면 문턱이 모든 범주에 똑같이 올라가, 정확한 범주의 재현율까지 떨어질 수 있습니다. 성능 범주의 기준 정의는 그대로입니다.
3. **정답** - 성능 범주를 잠시 꺼서 남은 코멘트가 모두 신뢰할 만한 범주에서 나오게 하면 신뢰가 회복됩니다. 그동안 보고·제외 조건을 구체적으로 다시 쓰고, 정답이 있는 평가 사례로 재현율·F1을 확인한 뒤 되돌립니다. 끄는 방법은 프롬프트에서 빼거나 REVIEW.md의 "Do not report" 목록에 넣는 것입니다.
4. **오답** - 권한 검사 지적은 이미 정확합니다. 설명을 길게 해도 개발자가 무시하는 원인(성능 범주의 소음)은 그대로 남습니다.

## 문제 5
### **리뷰 파이프라인에 이미 별도의 검증·중복 제거 단계가 있다. 그런데 앞단의 찾기 프롬프트에도 "중요한 것만 보고"가 들어 있어 검증 단계로 넘어오는 후보 자체가 적다. 찾기 프롬프트를 어떻게 바꾸는가?**

| 보기 | 설명 |
|------|------|
| 1. 찾기 단계에도 검증 단계와 같은 엄격한 기준을 복사해 넣는다 | |
| **2. 불확실하거나 사소해 보이는 것까지 모두 보고하되 지적마다 확신 수준과 추정 심각도를 붙이게 하고, 이 단계의 목표가 커버리지라고 명시한다** | |
| 3. 찾기 단계를 없애고 검증 단계만 둔다 | |
| 4. 찾기 단계에서 지적 수를 5개로 제한한다 | |

**정답: 2.**

**해설:**

> 📘 레슨 4.1 · 명시적 기준 — 찾기/거르기 분리

> **핵심:** 뒷단에 별도 검증 단계가 있다면, 찾기 단계의 목표는 **필터링이 아니라 커버리지** 입니다. 확신 기반 필터링은 찾기 단계에서 뺍니다.

1. **오답** - 찾기 단계에 검증 단계의 엄격한 기준을 복사하면, 뒷단 검증이 할 일을 앞에서 미리 버리게 됩니다. 검증 단계로 넘어오는 후보가 더 줄어듭니다.
2. **정답** - Opus 4.8 가이드가 권하는 구성입니다. 찾기 단계에서는 불확실하거나 사소해 보이는 것까지 모두 보고하되 지적마다 확신 수준과 추정 심각도를 붙이게 하고, 이 단계의 목표가 커버리지라고 명시합니다. 거르기·순위 매기기는 별도 단계가 맡습니다.
3. **오답** - 찾기 단계를 없애면 검증 단계가 검증할 후보 자체가 없습니다. 관리형 Code Review도 Find → Verify → Rank → Post 네 단계로 찾기와 검증을 분리합니다.
4. **오답** - 개수 제한은 후보를 임의로 줄여, 6번째 이후의 진짜 버그를 검증 단계가 볼 기회조차 없게 만듭니다.

## 문제 6
### **관리형 Code Review가 lockfile, `src/gen/`의 생성 코드, 이미 CI 린터가 잡는 포맷 문제까지 지적해 소음이 크다. 가장 알맞은 조치는?**

| 보기 | 설명 |
|------|------|
| 1. 리뷰 수준(review level)을 Deep으로 올린다 | |
| 2. PR 본문에 "사소한 것은 무시해 주세요"라고 쓴다 | |
| 3. 로컬 `/code-review`용 설정만 바꾼다 | |
| **4. 저장소 루트 `REVIEW.md`의 "보고하지 말 것"에 해당 경로와 CI가 강제하는 범주를 적는다** | |

**정답: 4.**

**해설:**

> 📘 레슨 4.1 · 명시적 기준 — 제외 범주

> **핵심:** 관리형 Code Review에서 건너뛸 경로와 범주는 저장소 루트의 **`REVIEW.md`(리뷰 전용 지침)** 에 적습니다. 문서의 예시도 CI가 강제하는 것, `src/gen/` 같은 생성 파일, lock 파일을 "Do not report"에 둡니다.

1. **오답** - 리뷰 수준(Quick·Standard·Deep)은 리뷰를 얼마나 철저하게 볼지를 정할 뿐이고, Deep은 가장 오래 걸리고 가장 비쌉니다. 무엇을 보고하지 않을지라는 범주는 바뀌지 않으므로 소음은 그대로이거나 늘어납니다.
2. **오답** - 관리형 Code Review는 리뷰 지침을 PR 본문이 아니라 base 또는 기본 브랜치의 `REVIEW.md`에서 읽습니다. PR마다 부탁하는 문장은 저장소 수준의 제외 규칙이 되지 못합니다.
3. **오답** - 로컬 `/code-review`는 관리형 서비스와 별개 도구입니다. 문서에 따르면 로컬 명령은 `CLAUDE.md`는 따르지만 `REVIEW.md`는 읽지 않으므로, 로컬 설정을 바꿔도 GitHub PR에 달리는 관리형 리뷰는 달라지지 않습니다.
4. **정답** - `REVIEW.md`는 팀이 무엇을 어떤 심각도로 지적받고 무엇을 건너뛸지 적는 리뷰 전용 파일입니다. "Do not report"에 lockfile, `src/gen/`, CI 린터가 잡는 포맷 범주를 적으면 해당 지적이 사라집니다. 제외 규칙은 보호된 기본 브랜치의 루트 `REVIEW.md`에 둬야 적용됩니다.

## 문제 7
### **리뷰 결과의 형식을 열 줄짜리 지시로 정의했는데도 어떤 실행은 심각도를 맨 앞에, 어떤 실행은 파일 위치를 맨 앞에 두고, 수정 제안을 빼먹기도 한다. 가장 효과적인 다음 조치는?**

| 보기 | 설명 |
|------|------|
| 1. 지시를 스무 줄로 늘려 각 필드의 순서를 더 자세히 설명한다 | |
| 2. "형식을 반드시 지켜라"를 대문자로 추가한다 | |

> 📘 레슨 4.2 · 퓨샷 프롬프팅 — 대비 예시

2. **오답** - 송장 도구를 지정하면 B/L이나 포장명세서까지 송장 스키마로 억지로 추출하게 됩니다. 이름 지정 강제는 특정 추출이 반드시 먼저 끝나야 할 때 씁니다.
3. **오답** - `none`은 도구 호출을 금지하므로 문제를 더 악화시킵니다.
4. **오답** - `auto`에서는 Claude가 도구를 부를지 스스로 정하므로, 프롬프트 지시를 더해도 호출이 보장되지 않습니다. 지금 겪는 텍스트 응답이 그대로 남을 수 있습니다.

### **Q1의 파이프라인을 Claude Sonnet 5.5로 옮기자 `tool_choice: {"type": "any"}` 요청이 400 `invalid_request_error`로 실패한다. 가장 적절한 대응은?**

### **계약서 추출 스키마에 `renewal_notice_days`(integer, required)를 넣었다. 갱신 통지 조항이 없는 계약서에서도 30이나 60 같은 값이 채워져 나온다. 가장 좋은 수정은?**

### **서류 도착 후 40시간 안에 결과를 내야 한다. 배치 처리는 최대 24시간, 결과 검증과 적재에 4시간이 걸린다. 서류는 모아 두었다가 정해진 간격으로 배치를 제출한다(안전 여유는 따로 두지 않는다). SLA를 보장하는 최대 제출 간격은?**

## 문제 27
### **2만 건 배치 결과 중 1.2%가 `errored`이고 오류 유형은 `invalid_request_error`, 메시지는 "prompt is too long"이다. 가장 적절한 대응은?**

| 보기 | 설명 |
|------|------|
| 1. 배치 전체를 다시 제출한다 | |
| 2. 실패한 요청을 그대로 다시 제출한다 | |
| 3. `max_tokens`를 늘려 다시 제출한다 | |
| **4. 해당 `custom_id`의 문서만 나누고 ID에 조각 번호를 붙여 새 배치로 제출한다** | |

**정답: 4.**

**해설:**

> 📘 레슨 4.5 · 배치 처리 — 실패 처리

> **핵심:** `invalid_request_error`는 **요청 본문을 고쳐야 하는 오류** 입니다. "prompt is too long"이면 입력이 컨텍스트 창을 넘은 것이므로 문서를 나눠 실패한 `custom_id`만 재제출합니다.

1. **오답** - "더 보수적으로"는 문턱을 더 올려 놓치는 버그를 더 늘립니다. 같은 문제를 키우는 처방입니다.
2. **오답** - 신뢰도 필드를 없애면 검증 단계가 지적을 순위 매기고 라우팅할 신호가 사라집니다. 찾기 단계는 오히려 지적마다 신뢰도와 심각도를 붙여야 합니다.
3. **정답** - Opus 4.8 가이드는 이런 지시가 있으면 모델이 같은 깊이로 조사하고도 기준 아래로 판단한 지적을 보고하지 않아, 정밀도는 오르지만 측정된 재현율이 떨어질 수 있다고 설명합니다. 권장 구성은 찾기 단계에서 불확실하거나 심각도가 낮은 것까지 모두 신뢰도·심각도와 함께 보고하고, 필터링은 별도 검증 단계로 옮기는 것입니다.
4. **오답** - 이전 모델로 되돌리는 것은 하네스 문제를 모델 문제로 오인한 것입니다. 문서는 이 현상을 능력 저하가 아니라 지시를 더 충실히 따르는 결과로 설명합니다.

## 문제 35
### **Claude Code에서 코드를 읽기만 하고 절대 수정하지 못하는 리뷰어가 필요하다. "수정하지 마"라는 부탁이 아니라 도구 수준에서 강제되기를 원한다. 가장 적절한 방법은?**

| 보기 | 설명 |
|------|------|
| **1. `.claude/agents/reviewer.md`에 `tools: Read, Grep, Glob`만 지정한 리뷰어 subagent를 만든다** | |
| 2. `CLAUDE.md`에 "리뷰할 때는 파일을 수정하지 않는다"를 적는다 | |
| 3. 같은 세션에서 `/clear` 후 리뷰를 요청한다 | |
| 4. 리뷰 프롬프트에 "절대 수정 금지"를 대문자로 강조한다 | |

**정답: 1.**

**해설:**

> 📘 레슨 4.6 · 다중 패스 리뷰 — 읽기 전용 리뷰어

> **핵심:** 도구 수준의 강제는 프롬프트가 아니라 **subagent 정의의 `tools` 허용 목록** 으로 합니다. 목록에 없는 도구는 그 subagent가 아예 쓸 수 없습니다.

1. **정답** - `.claude/agents/reviewer.md`의 frontmatter에 `tools: Read, Grep, Glob`만 지정하면 Write·Edit 같은 편집 도구가 없어 수정이 불가능해집니다. Claude Code 문서의 code-reviewer 예시도 `tools: Read, Glob, Grep`을 씁니다. Bash를 넣으면 셸로 파일을 바꿀 수 있으므로 엄격한 읽기 전용이라면 빼야 합니다.
2. **오답** - `CLAUDE.md`의 문장은 모델에게 하는 부탁일 뿐 도구 권한을 바꾸지 않습니다.
3. **오답** - `/clear`는 컨텍스트를 비울 뿐 도구 권한은 그대로입니다. 리뷰어는 여전히 편집 도구를 쓸 수 있습니다.
4. **오답** - 대문자 강조도 프롬프트 수준의 요청입니다. 모델이 따를 가능성은 높아도 도구 수준의 강제는 아닙니다.

## 문제 36
### **리뷰 지적의 자기 보고 신뢰도를 활용하는 방식으로 가장 적절한 것은?**

| 보기 | 설명 |
|------|------|
| 1. 모델이 쓴 신뢰도를 확률로 보고 0.5 이상만 그대로 게시한다 | |
| 2. 신뢰도가 낮은 지적은 기록 없이 즉시 버린다 | |
| 3. 신뢰도를 받았으니 별도 검증 패스는 필요 없다 | |
| **4. 지적마다 신뢰도와 근거를 받아, 높은 구간은 게시하고 중간 구간은 독립 검증 패스로 재확인하며, 구간 임계값은 과거 지적의 실제 정답률로 보정한다** | |

**정답: 4.**

**해설:**

> 📘 레슨 4.6 · 다중 패스 리뷰 — 신뢰도 라우팅

> **핵심:** 모델이 적어 낸 신뢰도는 **보정 없이 확률로 쓸 수 없습니다.** 라우팅 신호로 쓰고, 구간 임계값은 과거 지적의 실제 정답률로 맞춥니다.

1. **오답** - 자기 보고 신뢰도 0.5가 실제로 맞을 확률 50%라는 보장이 없습니다. 보정 없이 임계값을 정하면 게시되는 오탐 비율을 예측할 수 없습니다.
2. **오답** - 낮은 신뢰도 지적도 기록해 두면 어떤 패턴이 오탐을 부르는지 분석하는 데 씁니다(4.4의 `detected_pattern` 집계). 즉시 버리면 그 기록까지 사라집니다.
3. **오답** - 신뢰도는 검증 패스를 대신하지 않고, 어떤 지적을 검증으로 보낼지 정하는 입력입니다. 관리형 Code Review도 찾기 뒤에 별도 검증 단계를 두어 후보를 실제 코드와 대조해 오탐을 거릅니다.
4. **정답** - 지적마다 신뢰도와 근거를 받아 높은 구간은 바로 게시하고, 중간 구간은 다른 인스턴스가 근거를 따라가 재확인한 것만 게시하며, 낮은 구간은 기록만 남깁니다. 임계값은 과거 지적이 실제로 맞았는지를 구간별로 대조해 보정합니다.
