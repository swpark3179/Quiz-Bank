## 문제 1
### **회의실 예약 에이전트가 "빈 회의실을 찾아볼게요."라는 텍스트 블록과 함께 `tool_use` 블록을 돌려줬다. 그런데 루프 코드는 텍스트 블록이 있으면 사용자에게 출력하고 끝내도록 되어 있어 예약이 진행되지 않는다. 가장 알맞은 수정은?**

| 보기 | 설명 |
|------|------|
| 1. 시스템 프롬프트에 "도구를 쓸 때는 텍스트를 쓰지 마라"를 추가한다 | |
| 2. 텍스트가 일정 길이 이하이면 루프를 계속하도록 바꾼다 | |
| **3. `stop_reason`이 `"tool_use"`이면 텍스트 유무와 관계없이 도구를 실행하고 루프를 이어 간다** | |
| 4. 반복 상한을 늘린다 | |

**정답: 3.**

**해설:**

> 📘 레슨 1.1 · 에이전트 루프 — 종료 판정

> **핵심:** 한 응답에 텍스트 블록과 `tool_use` 블록이 함께 오는 것은 정상입니다. 루프를 계속할지는 `stop_reason` 하나로만 판단합니다.

1. **오답** - 증상을 프롬프트로 덮을 뿐입니다. 공식 문서는 Claude가 텍스트, 도구 호출, 또는 둘 다를 낼 수 있다고 명시하므로, 텍스트가 섞이는 응답은 언제든 다시 나오고 루프는 또 깨집니다.
2. **오답** - 텍스트 길이 같은 응답의 '모양'으로 완료를 추측하는 것도 종료 안티패턴입니다. 짧은 텍스트와 함께 끝나는 정상 `end_turn` 도 있고, 긴 설명과 함께 오는 `tool_use` 응답도 있습니다.
3. **정답** - `stop_reason` 이 `"tool_use"` 이면 텍스트 유무와 관계없이 `tool_use` 블록을 실행하고, 결과를 `tool_result` 로 붙여 다음 요청을 보냅니다. "빈 회의실을 찾아볼게요." 같은 문장은 도구 호출 직전에 Claude가 흔히 쓰는 설명일 뿐 완료 신호가 아닙니다.
4. **오답** - 루프는 상한에 걸려서가 아니라 텍스트를 보고 스스로 끝나고 있습니다. 원인은 잘못된 종료 신호이므로 상한을 늘려도 아무것도 바뀌지 않습니다.

📚 근거: [How the agent loop works (Agent SDK)](https://code.claude.com/docs/en/agent-sdk/agent-loop) · [Stop reasons and fallback](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

## 문제 2
### **응답의 `stop_reason`이 `"max_tokens"`이고, `content`의 마지막 블록은 입력이 덜 채워진 `tool_use`다. 올바른 처리는?**

| 보기 | 설명 |
|------|------|
| **1. `max_tokens`를 높여 같은 요청을 다시 보낸다** | |
| 2. 채워진 인자만으로 도구를 실행한다 | |
| 3. `end_turn`과 같다고 보고 텍스트를 사용자에게 보여 준다 | |
| 4. 빈 `tool_result`를 돌려주고 계속한다 | |

**정답: 1.**

**해설:**

> 📘 레슨 1.1 · 에이전트 루프 — max_tokens

> **핵심:** `max_tokens` 로 잘린 응답의 마지막 블록이 미완성 `tool_use` 라면, 더 큰 `max_tokens` 로 다시 요청해 완전한 호출을 받아야 합니다.

1. **정답** - Stop reasons 문서는 "잘린 응답에 미완성 도구 사용 블록이 있으면 더 큰 `max_tokens` 값으로 요청을 다시 보내 전체 도구 호출을 받아야 한다"고 안내합니다. `max_tokens` 는 정상 완료도 도구 호출 요청도 아닌 '잘린 응답'이므로 그에 맞게 처리합니다.
2. **오답** - 덜 채워진 `input` 으로 도구를 실행하면 의도와 다른 인자로 부작용(예: 잘못된 회의실 예약)을 낼 수 있습니다. 미완성 호출은 실행 대상이 아닙니다.
3. **오답** - `end_turn` 은 Claude가 응답을 자연스럽게 끝냈다는 뜻이고 `max_tokens` 는 한도에서 잘렸다는 뜻입니다. 둘을 같게 보면 미완성 작업을 완료로 착각해 사용자에게 내보냅니다.
4. **오답** - 완성되지 않은 호출에 빈 결과를 붙이는 셈입니다. Claude는 도구가 실제로 실행된 것으로 받아들여 엉뚱한 추론을 이어 갈 수 있고, 원래 하려던 호출은 끝내 실행되지 않습니다.

📚 근거: [Stop reasons and fallback](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons)

> "you'll need to retry the request with a higher `max_tokens` value to get the full tool use."

## 문제 3
### **운영용 에이전트 루프의 종료 설계로 가장 알맞은 것은?**

| 보기 | 설명 |
|------|------|
| 1. 응답에 "작업 완료"가 들어 있으면 종료한다 | |
| 2. 10회 반복하면 무조건 종료하고 마지막 응답을 결과로 쓴다 | |
| 3. `tool_use` 블록이 없고 텍스트가 50자 이상이면 종료한다 | |
| **4. `stop_reason`이 `"tool_use"`가 아니면 빠져나와 값별로 처리하고, 반복 상한·예산은 폭주를 막는 안전망으로 둔다** | |

**정답: 4.**

**해설:**

> 📘 레슨 1.1 · 에이전트 루프 — 종료 설계

> **핵심:** 1차 종료 신호는 `stop_reason` 이고, 반복 상한과 예산은 폭주를 막는 2차 방어선입니다.

1. **오답** - "작업 완료" 같은 자연어 신호 파싱은 표현이 언어·맥락마다 달라 깨지기 쉽고, "작업 완료를 위해 먼저…" 같은 문장에서 오탐이 납니다. 모델 출력에서 문자열로 결정을 뽑고 있다면 그 결정은 구조화된 신호로 설계했어야 합니다.
2. **오답** - 상한을 주 종료 장치로 쓰면 정상 작업이 10회에서 잘려 미완료 결과가 완료처럼 나갑니다. Agent SDK도 `max_turns` 도달을 성공이 아닌 `error_max_turns` subtype으로 보고하고, 이때 `result` 필드는 없습니다.
3. **오답** - `tool_use` 블록 유무와 텍스트 길이라는 응답의 모양으로 완료를 짐작하는 방식입니다. 정상 `end_turn` 이 짧은 텍스트로 끝날 수도 있고, 이 규칙은 `max_tokens`·`refusal` 같은 비정상 종료도 구분하지 못합니다.
4. **정답** - `stop_reason` 이 `"tool_use"` 가 아니면 루프를 빠져나오되 `end_turn`, `max_tokens`, `pause_turn`, `refusal` 등 값마다 다르게 처리합니다. 반복 상한·예산(`max_turns`, `max_budget_usd` 등)은 폭주를 막는 안전망으로 두고, 여기에 걸리면 미완료로 다룹니다.

📚 근거: [Stop reasons and fallback](https://platform.claude.com/docs/en/build-with-claude/handling-stop-reasons) · [How the agent loop works (Agent SDK)](https://code.claude.com/docs/en/agent-sdk/agent-loop)

## 문제 4
### **Claude가 한 응답에서 회의실 조회와 참석자 일정 조회를 동시에 요청했다. 개발자는 결과가 도착하는 대로 각각 별도 user 메시지로 보냈고, 이후 Claude가 병렬 호출을 거의 하지 않게 됐다. 올바른 반환 방식은?**

| 보기 | 설명 |
|------|------|
| 1. 두 결과를 하나의 문자열로 합쳐 시스템 프롬프트에 넣는다 | |
| **2. 두 `tool_result` 블록을 하나의 user 메시지 맨 앞에 함께 담고, 각각 `tool_use_id`로 짝을 맞춘다** | |
| 3. 먼저 끝난 결과만 보내고 나머지는 다음 요청에 보낸다 | |
| 4. 결과를 assistant 메시지로 보낸다 | |

**정답: 2.**

**해설:**

> 📘 레슨 1.1 · 에이전트 루프 — 병렬 결과 반환

> **핵심:** 병렬 호출의 결과는 하나의 user 메시지에 모두 담고, 각 `tool_result` 를 `tool_use_id` 로 짝지으며 텍스트보다 앞에 둡니다.

1. **오답** - 시스템 프롬프트에 결과를 넣으면 `tool_use` 에 대응하는 `tool_result` 가 없어 요청이 실패합니다. 도구 결과는 직전 `tool_use` 에 답하는 `tool_result` 자리에 들어가야 합니다.
2. **정답** - Parallel tool use 문서는 각 `tool_use` 에 대해 `tool_result` 하나씩을 모두 다음 user 메시지에 함께 돌려주고, `tool_use_id` 로 짝을 맞추며, 모든 `tool_result` 를 텍스트보다 앞에 두라고 안내합니다. 결과를 메시지마다 따로 보내는 것은 가장 흔한 실수로, Claude에게 병렬 호출을 피하도록 '가르치는' 효과가 있다고 문서가 경고합니다.
3. **오답** - 다음 요청에 결과가 없는 `tool_use` 가 남으면 API가 "`tool_use` ids were found without `tool_result` blocks immediately after" 같은 오류로 요청을 거부합니다. 응답의 모든 `tool_use` 에는 바로 다음 user 메시지에서 결과를 돌려줘야 합니다.
4. **오답** - `tool_result` 는 user 메시지에 들어갑니다. assistant 메시지로 보내면 role이 틀려 Claude에게 도구 결과로 전달되지 않습니다.

📚 근거: [Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use) · [Handle tool calls](https://platform.claude.com/docs/en/agents-and-tools/tool-use/handle-tool-calls)

> "Wrong: a separate user message for each tool result / Correct: all tool results together in a single user message"

## 문제 5
### **서비스 장애 원인을 찾는 에이전트를 만든다. 로그, 배포 이력, 지표 조회 도구가 있고, 무엇을 어떤 순서로 봐야 할지는 장애마다 다르다. 가장 알맞은 설계는?**

| 보기 | 설명 |
|------|------|
| **1. 도구와 목표를 주고, Claude가 매 바퀴 누적된 결과를 보고 다음 도구를 고르게 한다** | |
| 2. 로그 → 배포 이력 → 지표 순서를 코드로 고정하고 단계별 결과만 요약시킨다 | |
| 3. 모든 도구를 한 번씩 호출한 결과를 한꺼번에 넣고 한 번에 결론을 내게 한다 | |
| 4. 장애 유형별 if-else 트리를 코드로 만들어 도구 순서를 정한다 | |

**정답: 1.**

**해설:**

> 📘 레슨 1.1 · 에이전트 루프 — 모델 주도 결정

> **핵심:** 다음 행동이 중간 결과에 따라 달라지는 개방형 문제에는 Claude가 매 바퀴 누적된 결과를 보고 다음 도구를 고르는 모델 주도 루프가 맞습니다.

1. **정답** - Anthropic은 LLM이 스스로 다음 단계와 도구 사용을 정하는 시스템을 에이전트로 정의합니다. 장애마다 볼 순서가 다르다면 도구와 목표만 주고, Claude가 로그에서 본 단서에 따라 배포 이력이나 지표를 고르게 하는 것이 적합합니다. 비용·지연이 늘 수 있으므로 반복 상한 같은 가드레일은 함께 둡니다.
2. **오답** - 순서를 코드로 고정한 워크플로입니다. 단계와 순서가 매번 같은 작업에는 예측 가능해서 좋지만, 이 문제처럼 장애마다 경로가 다르면 예상 밖의 장애에서 막힙니다.
3. **오답** - 필요 없는 조회까지 전부 하면서도, 결과를 보고 추가로 조사하는 반복이 없습니다. 첫 결과에서 새 단서가 나와도 그것을 따라갈 수 없습니다.
4. **오답** - 장애 유형별 if-else 트리도 미리 정한 결정 트리라, 트리에 없는 유형의 장애에서는 대응하지 못합니다. 모델 주도 결정의 장점을 버리는 설계입니다.

📚 근거: [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents) · [How the agent loop works (Agent SDK)](https://code.claude.com/docs/en/agent-sdk/agent-loop)

## 문제 6
### **Agent SDK로 돌린 작업이 `ResultMessage` subtype `"error_max_turns"`로 끝났다. 가장 알맞은 후속 처리는?**

| 보기 | 설명 |
|------|------|
| 1. `result` 필드를 최종 답으로 사용자에게 보여 준다 | |
| 2. 같은 프롬프트로 새 세션을 처음부터 다시 시작한다 | |
| **3. 미완료로 처리하고, 결과에 담긴 `session_id`로 세션을 재개하면서 상한을 높인다** | |
| 4. `stop_reason`이 `end_turn`인지 확인해 그렇다면 성공으로 기록한다 | |

**정답: 3.**

**해설:**

> 📘 레슨 1.1 · 에이전트 루프 — Agent SDK 결과

> **핵심:** `error_max_turns` 는 성공이 아니라 미완료입니다. `result` 필드는 없지만 `session_id` 가 있으므로 상한을 높여 이어서 재개할 수 있습니다.

1. **오답** - `result` 필드는 `success` subtype에만 있습니다. `error_max_turns` 결과에는 `result` 가 없으므로 최종 답으로 보여 줄 수 있는 것이 없고, 문서도 결과를 읽기 전에 `subtype` 부터 확인하라고 안내합니다.
2. **오답** - 처음부터 다시 시작하면 지금까지 읽은 파일, 분석, 수행한 작업을 모두 버리고 비용을 다시 씁니다. 세션을 재개하면 이전 턴의 전체 컨텍스트가 복원됩니다.
3. **정답** - 모든 result subtype에는 `total_cost_usd`, `usage`, `num_turns`, `session_id` 가 들어 있어 오류 뒤에도 비용을 추적하고 재개할 수 있습니다. 공식 예제도 `error_max_turns` 분기에서 "더 높은 상한으로 재개하라(Resume with a higher limit)"고 처리합니다.
4. **오답** - `ResultMessage` 의 `stop_reason` 은 마지막 턴에서 모델이 생성을 멈춘 이유일 뿐입니다. 루프가 상한에 걸린 경우에도 마지막 응답의 값이 그대로 담기므로, 작업 완료 여부는 `subtype` 으로 판단해야 합니다.

📚 근거: [How the agent loop works (Agent SDK)](https://code.claude.com/docs/en/agent-sdk/agent-loop) · [Session management (Agent SDK)](https://code.claude.com/docs/en/agent-sdk/sessions)

> "All result subtypes carry `total_cost_usd`, `usage`, `num_turns`, and `session_id` so you can track cost and resume even after errors."

## 문제 7
### **사내 리서치 시스템이 "회사 창립 연도가 언제야?" 같은 단순한 질문에도 검색·분석·종합·검증 서브에이전트 네 개를 매번 모두 돌려 비용과 지연이 크다. 가장 알맞은 개선은?**

| 보기 | 설명 |
|------|------|
| 1. 네 서브에이전트를 더 작은 모델로 바꾼다 | |
| **2. 코디네이터가 질의의 요구와 복잡도를 먼저 분석해 필요한 서브에이전트만 호출하게 한다** | |
| 3. 네 단계를 서브에이전트 하나로 합친다 | |
| 4. 검증 단계만 빼고 나머지는 항상 실행한다 | |

**정답: 2.**

**해설:**

> 📘 레슨 1.2 · 코디네이터·서브에이전트 — 동적 선택

1. **정답** - 시험 가이드는 코디네이터의 `allowedTools` 에 Task 도구를 넣고 `agents` 에 서브에이전트 유형을 정의하는 구성을 기대합니다. 현재 SDK는 같은 도구를 `Agent` 라는 이름으로 내보내므로 공식 예제도 `allowed_tools=["Read", "Grep", "Glob", "Agent"]` 처럼 씁니다. 현재 문서에서 `allowedTools` 는 '나열한 도구를 자동 승인하는 목록'이라는 의미 차이가 있지만, 시험에서는 '도구 설정에 포함'을 정답으로 봅니다.
2. **오답** - session ID는 세션을 재개하거나 포크할 때 쓰는 식별자일 뿐, 서브에이전트 생성을 가능하게 하지 않고 부모의 맥락을 전달하지도 않습니다. 서브에이전트에 맥락을 넘기는 통로는 Agent 도구의 프롬프트 문자열입니다.
3. **오답** - 시스템 프롬프트 문구만으로는 서브에이전트 정의도 생성 도구도 생기지 않습니다. Claude가 위임 대상을 고르는 근거는 각 정의의 `description` 이므로, 정의 없이 "필요하면 써라"만 더해서는 의도한 전문 서브에이전트가 호출되지 않습니다.
4. **오답** - 앱 코드에서 `query()` 를 따로 돌리는 것은 코디네이터 에이전트가 아니라 애플리케이션 코드가 오케스트레이션하는 별개 구조입니다. 코디네이터가 질의를 보고 서브에이전트를 고르는 동적 위임이 사라집니다.

### **코디네이터가 검색 서브에이전트들의 보고를 자기 말로 요약한 뒤 종합 서브에이전트에 넘겼다. 최종 보고서는 내용은 그럴듯하지만 어느 주장이 어느 문서에서 왔는지 알 수 없다. 가장 알맞은 개선은?**

| 보기 | 설명 |

| 2. 종합 서브에이전트를 더 큰 모델로 바꾼다 | |
| **3. 앞 단계 결과를 요약하지 말고, 본문과 출처(URL·문서명·쪽)를 분리한 구조화 데이터로 위임 프롬프트에 넣는다** | |

**해설:**

## 문제 18
### **Agent SDK 세션에서 대규모 코드베이스 분석을 마쳤다. 이 분석을 바탕으로 '점진적 리팩터링'과 '모듈 재작성' 두 방안을 각각 끝까지 검토해 비교하고 싶다. 가장 알맞은 방법은?**

| 보기 | 설명 |
|------|------|
| **1. 원래 session ID로 `resume`하면서 `fork_session=True`로 갈래를 만들어 한쪽은 포크에서, 다른 쪽은 원래 세션에서 진행한다** | |
| 2. 새 세션 두 개를 열어 각각 분석부터 다시 시킨다 | |
| 3. 한 세션에서 두 방안을 번갈아 진행한다 | |
| 4. 분석 결과 요약만 일반 서브에이전트 두 개에 넘긴다 | |

**정답: 1.**

**해설:**

> 📘 레슨 1.3 · 서브에이전트 생성 — 포크

> **핵심:** 포크는 원래 이력의 복사본으로 새 세션을 만들고 원본은 그대로 둡니다. 같은 분석 기준점에서 두 방향을 독립적으로 이어 갈 수 있습니다.

1. **정답** - Agent SDK에서는 `resume` 에 원래 session ID를 주고 `fork_session=True`(TypeScript는 `forkSession: true`)를 설정하면 원래 이력을 복사한 새 세션이 새 session ID로 만들어집니다. 원래 세션의 ID와 이력은 바뀌지 않으므로, 한 방안은 포크에서, 다른 방안은 원래 세션을 `resume` 해 진행하면 됩니다. 단, 포크는 대화 이력만 나누고 파일 시스템은 나누지 않으므로, 같은 디렉터리에서 파일을 수정한다면 그 변경은 양쪽 모두에 보입니다.
2. **오답** - 새 세션 두 개는 빈 이력으로 시작하므로 대규모 분석을 두 번 반복해야 합니다. 비용과 시간이 들고, 두 분석 결과가 서로 달라 같은 기준점에서 비교하기도 어렵습니다.
3. **오답** - 한 세션에서 두 방안을 번갈아 진행하면 두 방안의 맥락과 결정이 서로 섞입니다. 앞 방안의 시도가 뒤 방안의 출발점에 영향을 줘 독립적인 비교가 되지 않습니다.
4. **오답** - 일반 서브에이전트는 새 컨텍스트로 시작하고 위임 프롬프트에 쓴 것만 압니다. 분석 결과를 요약해 넘기면 그 과정에서 세부가 빠지므로, 전체 분석이 필요한 작업에는 맞지 않습니다.

| **4. 지급 도구에 PreToolUse 게이트를 걸어, 확인된 가입자 ID가 없으면 호출을 거부한다** | |

**정답: 4.**

**해설:**

> 📘 레슨 1.4 · 선행 게이트·핸드오프 — 강제 방식

> **핵심:** 결정적 준수가 필요한 순서(본인 확인 후 지급)는 프롬프트가 아니라 프로그램으로 강제합니다. 도구 실행 전에 호출을 거부하는 PreToolUse 게이트가 그 장치입니다.

4. **정답** - PreToolUse 훅은 도구가 실행되기 전에 코드로 돌며 `permissionDecision: "deny"` 로 호출을 거부할 수 있습니다. 확인된 가입자 ID 기록이 없으면 지급 도구가 실행되지 않으므로, 모델의 판단과 무관하게 순서가 보장됩니다. 프롬프트 지침은 모델이 올바른 순서를 계획하도록 함께 남겨 둡니다.

3. **정답** - PreToolUse 콜백이 `tool_input` 의 금액을 읽어 한도를 넘으면 `permissionDecision: "deny"` 를 돌려주면, 그 호출은 실행되지 않습니다. `permissionDecisionReason` 은 Claude에게 전달되므로 "30만 원 초과는 상급자 승인이 필요하니 에스컬레이션 도구를 호출하라"처럼 대체 경로를 적어 두면 같은 호출을 재시도하지 않고 그 절차로 넘어갑니다.
4. **오답** - few-shot 예시도 모델의 선택을 유도하는 확률적 장치입니다. 실패율을 낮출 수는 있어도 0으로 만들지 못합니다.

## 문제 28
### **같은 도구 호출에 PreToolUse 훅 두 개가 걸려 있다. 하나는 읽기 전용 작업을 빠르게 하려고 `allow`를, 다른 하나는 한도 초과라서 `deny`를 돌려줬다. 결과는?**

| 보기 | 설명 |
|------|------|
| 1. 먼저 등록된 훅의 결정이 적용된다 | |
| **2. `deny`가 우선해 호출이 거부된다** | |
| 3. `allow`가 우선해 실행된다 | |
| 4. 사용자에게 승인 프롬프트가 뜬다 | |

**정답: 2.**

**해설:**

> 📘 레슨 1.5 · Agent SDK 훅 — 결정 우선순위

> **핵심:** 여러 PreToolUse 훅의 결정이 엇갈리면 우선순위는 `deny` > `defer` > `ask` > `allow` 입니다. 등록 순서와 무관합니다.

1. **오답** - 같은 이벤트에 매칭된 훅은 병렬로 실행되고 완료 순서는 비결정적입니다. 결정은 등록 순서가 아니라 정해진 우선순위로 합쳐집니다.
2. **정답** - 권한 결정은 가장 제한적인 결과가 적용되므로, 한 훅의 `deny` 가 호출을 막습니다. 읽기 전용 작업을 빠르게 하려는 자동 승인 훅이 있어도 정책 훅의 거부가 이깁니다. 그래서 자동 승인 훅과 정책 훅을 함께 두어도 안전합니다.
3. **오답** - `allow` 는 우선순위가 가장 낮습니다. `allow` 가 이긴다면 자동 승인 훅 하나가 모든 정책 훅을 무력화할 수 있게 됩니다.
4. **오답** - 승인 프롬프트는 `ask` 가 최종 결정일 때 나타납니다. 여기서는 `deny` 가 `ask` 보다도 우선하므로 프롬프트 없이 거부됩니다.

> "When multiple PreToolUse hooks return different decisions, precedence is `deny` > `defer` > `ask` > `allow`."

**해설:**

> 📘 레슨 1.6 · 작업 분해 전략 — 대형 리뷰

> **핵심:** 모듈별 패스로 주의를 집중하고, 모듈별 발견과 인터페이스 요약을 모은 통합 패스로 모듈 사이의 불일치를 잡습니다.

1. **정답** - 모듈마다 별도 패스를 돌리면 각 모듈에 주의가 집중돼 지적이 구체적이 됩니다. 이어서 모듈별 발견과 공개 인터페이스 요약을 함께 보는 통합 패스가 '발급은 초 단위, 검증은 밀리초 단위' 같은, 한 모듈 안에서는 드러나지 않는 교차 결함을 잡습니다. Anthropic도 여러 고려 사항을 각각 별도 LLM 호출로 다룰 때 성능이 좋다고 설명합니다.
2. **오답** - 컨텍스트는 수확 체감이 있는 유한한 자원이고, 토큰이 늘수록 회상 정밀도가 떨어지는 현상(context rot)은 모든 모델에서 나타납니다. 창이 커져도 25개 모듈에 주의가 얇게 퍼지는 문제는 그대로입니다.
3. **오답** - 같은 희석된 컨텍스트에서 지시만 늘린 것입니다. "꼼꼼하게"라는 문구는 모델이 각 모듈에 기울이는 주의를 늘려 주지 않습니다.
4. **오답** - 모듈별 검토만 하면 각 패스가 다른 모듈을 보지 못하므로, 만료 시간 단위 불일치처럼 두 모듈 사이에서만 드러나는 결함을 놓칩니다. 결과를 이어 붙이는 것은 통합 검토가 아닙니다.

### **검색 색인이 몇 시간씩 밀리는 원인을 사흘째 조사하고 있다. 중간중간 같은 저장소에서 다른 작은 작업용 세션도 계속 열고 닫는다. 조사 대화로는 언제든 정확히 돌아가야 한다. 가장 확실한 방법은?**

| 보기 | 설명 |
|------|------|
| 1. 조사를 이어 갈 때마다 `claude --continue`를 실행한다 | |
| **2. 조사 세션에 `/rename index-lag`로 이름을 붙여 두고, 돌아갈 때 `claude --resume index-lag`를 실행한다** | |
| 3. 기본 표시 이름(예: `my-app-3f`)을 `claude --resume`에 넘긴다 | |

2. **정답** - `/rename index-lag` 로 세션 중에 이름을 붙이면(시작할 때는 `claude -n index-lag`), `claude --resume index-lag` 가 정확히 일치하는 그 세션을 선택기 없이 바로 재개합니다. 같은 이름이 여러 세션과 일치할 때만 이름을 검색어로 채운 선택기가 열립니다.

> 📘 레슨 1.7 · 세션 재개·포크 — SDK 재개

> **핵심:** 여러 세션 가운데 특정 세션으로 돌아가려면 ID를 추적해 `resume` 에 넘깁니다. session ID는 모든 결과 메시지에 들어 있습니다.

1. **오답** - `continue_conversation=True` 는 디렉터리의 가장 최근 세션을 엽니다. 서비스를 하나씩 분석했으므로 가장 최근 세션은 마지막으로 분석한 서비스이고, 알림 서비스가 그것이라는 보장이 없습니다.
2. **오답** - SDK의 `resume` 은 session ID를 받습니다. 서비스 이름은 세션 식별자가 아니므로, 서비스 이름과 session ID의 대응은 애플리케이션이 직접 저장해야 합니다.
3. **오답** - 최종 답변 텍스트만 붙이면 그 분석이 읽은 파일, 도구 결과, 중간 추론을 잃습니다. 재개는 이 모든 맥락을 복원해 파일을 다시 읽지 않고 후속 질문에 답하게 해 줍니다.
4. **정답** - `session_id` 는 성공·오류와 상관없이 모든 결과 메시지(`ResultMessage`)에 들어 있습니다. 분석마다 서비스별로 저장해 두었다가 알림 서비스의 ID를 `ClaudeAgentOptions(resume=...)` 에 넘기면 그 분석의 전체 맥락에서 후속 질문을 이어 갑니다. 문서도 여러 세션이 있거나 가장 최근이 아닌 세션으로 돌아갈 때 resume이 필요하다고 설명합니다.

📚 근거: [Agent SDK: Work with sessions](https://code.claude.com/docs/en/agent-sdk/sessions) · [Agent SDK Python reference](https://code.claude.com/docs/en/agent-sdk/python)

> "Resume takes a specific session ID. You track the ID."

### **코드베이스 분석 세션을 마친 뒤, 그 분석을 출발점으로 "모듈 분리" 안과 "점진적 교체" 안을 각각 시도해 비교하려 한다. 두 안 모두 실제로 파일을 고친다. 가장 알맞은 방법은?**

| 보기 | 설명 |
|------|------|
| **1. 기준 세션을 두 번 포크하고, 갈래마다 별도 git worktree에서 작업하게 한다** | |
| 2. 기준 세션 하나를 두 터미널에서 동시에 `--resume`한다 | |
| 3. 포크하면 파일도 갈래별로 분리되므로 같은 디렉터리에서 두 포크를 돌린다 | |
| 4. 두 안을 같은 세션에서 차례로 시도한 뒤 마지막에 비교한다 | |

**해설:**

> 📘 레슨 1.7 · 세션 재개·포크 — 포크와 격리

2. **오답** - 포크 없이 같은 세션을 두 터미널에서 재개하면 두 쪽의 메시지가 하나의 트랜스크립트에 뒤섞입니다. 두 안의 맥락과 파일 변경이 모두 섞여 비교가 불가능합니다.
3. **오답** - 포크는 대화만 분리하고 파일 시스템은 분리하지 않습니다. 문서도 포크된 에이전트가 파일을 고치면 그 변경은 실제이며 같은 디렉터리에서 작업하는 모든 세션에 보인다고 경고합니다.
4. **오답** - 같은 세션에서 차례로 시도하면 첫 안의 시도와 결론이 두 번째 안의 컨텍스트를 오염시키고, 파일 변경도 누적돼 같은 기준점에서 비교할 수 없습니다.

## 문제 40
### **지난주 분석 세션 이후 main에 대규모 리팩터링이 병합되어, 그 세션이 읽었던 파일 대부분의 구조가 바뀌었다. 가장 신뢰할 수 있는 진행 방법은?**

| 보기 | 설명 |
|------|------|
| 1. 세션을 재개하고 "계속해"라고만 지시한다 | |
| 2. 세션을 포크해서 진행한다 | |
| **3. 확정된 사실·배제한 가설·남은 질문을 정리한 구조화 요약으로 새 세션을 시작한다** | |
| 4. 세션을 재개하고 `--add-dir`을 다시 넘긴다 | |

**정답: 3.**

**해설:**

> 📘 레슨 1.7 · 세션 재개·포크 — 낡은 결과

> **핵심:** 재개는 기록된 도구 결과를 그대로 다시 불러옵니다. 결과 대부분이 낡았다면 여전히 유효한 결론만 구조화 요약으로 넘겨 새 세션을 시작하는 편이 낫습니다.

2. **오답** - 포크도 원래 기록을 그대로 복사하므로 같은 낡은 도구 결과를 가지고 시작합니다. 포크는 갈래를 나누는 장치이지 기록을 최신화하는 장치가 아닙니다.
3. **정답** - 확정된 사실, 배제한 가설, 남은 질문처럼 코드 변경과 무관하게 유효한 결론만 구조화 요약으로 정리해 새 세션의 첫 프롬프트에 넣으면, 새 에이전트는 정확한 결론에서 출발해 현재 코드를 새로 읽습니다. Agent SDK 문서도 필요한 결과(분석 출력, 결정, 파일 diff)를 애플리케이션 상태로 저장해 새 세션 프롬프트에 넣는 방식이 트랜스크립트 파일을 옮기는 것보다 견고한 경우가 많다고 설명합니다.
4. **오답** - `--add-dir` 은 Claude가 읽고 편집할 추가 작업 디렉터리를 지정하는 실행 플래그입니다. 재개 시 다시 넘겨야 하는 플래그이긴 하지만, 기록된 결과가 낡았다는 문제와는 무관합니다.

## 문제 41
### **어제 세션 이후 동료가 두 파일만 고쳤고, 어떤 변경인지도 안다. 나머지 분석은 여전히 유효하다. 가장 효율적인 방법은?**

| 보기 | 설명 |
|------|------|
| 1. 새 세션에서 처음부터 전체 탐색을 다시 시킨다 | |
| **2. 세션을 재개하고, 바뀐 두 파일과 변경 내용을 알려 그 부분만 다시 분석하게 한다** | |
| 3. 세션을 재개하고 아무것도 알리지 않는다 — 재개할 때 바뀐 파일이 자동으로 다시 읽힌다 | |
| 4. `--fork-session`으로 포크하면 최신 파일 기준으로 기록이 다시 만들어진다 | |

**정답: 2.**

**해설:**

> 📘 레슨 1.7 · 세션 재개·포크 — 표적 재분석

> **핵심:** 기록 대부분이 유효하면 재개해서 살리고, 바뀐 부분만 짚어 다시 읽게 합니다.

1. **오답** - 처음부터 다시 탐색하면 여전히 유효한 분석까지 버리고 같은 비용을 다시 씁니다. 재개의 이유 자체를 없애는 선택입니다.
2. **정답** - "어제 이후 `a.py`·`b.py` 두 파일이 이렇게 바뀌었으니 그 둘을 다시 읽고 결론을 갱신하라"처럼 구체적으로 알리면, 에이전트는 지정한 파일만 다시 확인하고 나머지 분석은 그대로 유지합니다. 변경 내용을 알려 주지 않거나 "뭔가 바뀌었다"고만 하면 낡은 기록을 믿거나 전체를 다시 탐색하게 됩니다.
3. **오답** - 재개는 파일을 자동으로 다시 읽지 않습니다. 재개된 세션은 대화 이력(메시지, 도구 호출, 결과)을 기록된 그대로 복원하므로, 알려 주지 않으면 바뀌기 전의 파일 내용을 근거로 추론합니다.
4. **오답** - `--fork-session` 은 재개할 때 원래 ID 대신 새 session ID를 만드는 옵션입니다. 기존 기록을 그대로 복사할 뿐 최신 파일 기준으로 다시 만들지 않습니다.

## 문제 42
### **세션 포크에 대한 설명으로 옳은 것은?**

| 보기 | 설명 |
|------|------|
| 1. 원본 세션 ID를 그대로 쓰며 원본 기록 뒤에 이어 쓴다 | |
| 2. 작업 디렉터리의 파일까지 스냅숏으로 복사한다 | |
| 3. SDK `fork_session()`으로 만든 포크는 포크 이전의 파일 체크포인트로 되감을 수 있다 | |
| **4. 원본 기록을 복사한 새 세션 ID가 생기고, 원본은 바뀌지 않는다** | |

**정답: 4.**

**해설:**

> 📘 레슨 1.7 · 세션 재개·포크 — 포크의 의미

> **핵심:** 포크는 원본 기록을 복사한 새 session ID의 독립 세션을 만들고, 원본은 바뀌지 않습니다.

1. **오답** - 원본 세션 ID를 그대로 쓰며 기록 뒤에 이어 쓰는 것은 일반 재개(`resume`)의 동작입니다. 포크는 반대로 새 ID를 만들어 원본을 건드리지 않습니다.
2. **오답** - 포크는 대화 기록만 복사하고 작업 디렉터리의 파일은 복사하지 않습니다. 파일 변경을 스냅숏으로 남기고 되돌리려면 별도의 파일 체크포인트 기능을 씁니다.
3. **오답** - Python SDK 문서는 `fork_session()` 으로 만든 포크에 원본 세션의 파일 체크포인트가 포함되지 않으므로, 포크 이전에 잡힌 체크포인트로는 되감을 수 없다고 명시합니다.
4. **정답** - Agent SDK 문서에 따르면 포크는 원본 기록의 사본으로 시작하는 새 세션을 만들고 자기만의 session ID를 가지며, 원본의 ID와 기록은 그대로 유지됩니다. 그래서 두 세션을 각각 따로 재개할 수 있습니다. 방법은 `resume` 과 `fork_session=True`(TypeScript는 `forkSession: true`), CLI의 `--fork-session`, Python의 독립 함수 `fork_session()` 이 있습니다.

> "The fork gets its own session ID; the original's ID and history stay unchanged."
