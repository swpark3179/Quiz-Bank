**무엇을 어떻게 만들어야 하는지 정해 둔 문서**입니다. 제품의 기능·조건을 적은 사양서도, MCP 같은 프로토콜의 공식 규격도 모두 *specification* 이라 하고, 흔히 줄여서 *spec* 이라고 합니다.

## 문제 속 쓰임
> Every night a job takes each new product **spec** and runs the same steps in the same order.
> 매일 밤 작업 하나가 새 제품 **사양서**를 하나씩 받아 같은 단계를 같은 순서로 실행합니다.

> The error contract includes fields that are not part of the MCP **specification**.
> 오류 계약에 MCP **명세**에 없는 필드가 들어 있다.

## 함께 쓰는 표현
- **product spec** : 제품 사양서
- **MCP specification** : MCP 공식 명세
- **to spec** : 규격대로, 명세대로

## 시험 포인트
"사양서 내용이 어떤 단계를 실행할지 바꾸지 않는다"면 단계가 고정된 작업이므로, 코드로 순서를 정한 **프롬프트 체인**(작성 → 프로그램 검사 → 번역)이 정답입니다. 오케스트레이터나 적응형 분해는 매번 같은 계획을 세우는 비용만 늘립니다.
